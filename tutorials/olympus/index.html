Olympus: Xtrace on Hopper, read with the paperOlympus：对照论文读 Hopper 上的 Xtrace

Olympus rebuilds Xtrace's binary-level tracer for Hopper. It splices probes into a kernel's compiled SASS, uses only registers that are dead at each point, and lets a search choose the probes' control bits, so every original instruction keeps the bytes ptxas gave it. This page is the map: what tracing is for, what Xtrace changes, how Olympus is built and what it measured. The five chapters then follow the paper section by section.

Olympus 在 Hopper 上重建了 Xtrace 的二进制级追踪器：把探针拼接进 kernel 已编译的 SASS，每一处只使用当时的死寄存器，探针的控制位交给搜索来定，于是每条原始指令都保持 ptxas 生成时的字节。本页是一张全局地图：追踪有什么用，Xtrace 改变了什么，Olympus 怎样搭起来，又测出了什么。随后五章逐节对照论文展开。

§1What tracing is, and why fidelity is the problem追踪是什么，为什么保真度是难题

A counter-based profiler reports totals over a whole launch: how busy the tensor cores were, how many bytes moved. It cannot say which stage of a fused kernel waited on which. Intra-kernel tracing answers that. It adds probes at chosen instructions. Each probe records a timestamp, and sometimes a register value, as a warp passes, and the records form one timeline per warp: when a warp reached a barrier, when a TMA load landed, how long an epilogue took paper §2.1 README.md:17–20.

基于硬件计数器的 profiler 报告的是整次 launch 的总量：tensor core 有多忙，搬了多少字节。它说不清融合 kernel 里哪个阶段在等哪个阶段。kernel 内追踪（intra-kernel tracing）回答的正是这个问题。它在选定的指令处加入探针，warp 经过时，探针记下一个时间戳，有时再加一个寄存器值；这些记录拼成每个 warp 的时间线：warp 何时到达 barrier，TMA 加载何时落地，epilogue 用了多久 论文 §2.1 README.md:17–20。

A timeline like that is a measurement, and it is only worth something if the measured kernel is the kernel you ship. The paper calls this tracing fidelity: the probes must keep the kernel's original instructions and show its true execution time paper §1. It then shows that existing tools lose fidelity in two separate ways paper §2.2:

这样的时间线是一次测量，只有被测的 kernel 就是你要交付的那个 kernel 时，它才有价值。论文把这称为追踪保真度（tracing fidelity）：探针必须保住 kernel 原有的指令，并反映它真实的执行时间 论文 §1。论文接着指出，现有工具以两种互不相同的方式丢掉了保真度 论文 §2.2：

  • The compiler sees the probe. Neutrino inserts probes into PTX, and IKET reserves placeholder resources at the source level, so ptxas schedules the probe together with the kernel. On FlashAttention-3 the probed kernels lose three optimizations: the two unrolled SoftMax iterations are no longer interleaved, P-convert no longer overlaps SoftMax, and the release of the V tile is no longer moved early. The traces then report a V-tile wait of 1,024–1,216 ns that the real kernel doesn't have. Across FA-3, FlashMLA and FA-4, Neutrino keeps only 8–20% of the original instructions and IKET 13–48% paper §1.
  • The kernel waits on the probe. A probe's store reads registers. When a later instruction overwrites one of them, it has to wait until the store has read it (a WAR dependency), and a global memory access takes 270–380 ns on Hopper, as long as the regions being traced. Only one lane stores, but the whole warp waits for it at the reconvergence point after the probe paper §2.2.
  • 编译器看得见探针。Neutrino 在 PTX 层插入探针，IKET 在源码层预留占位资源，于是 ptxas 会把探针和 kernel 一起调度。在 FlashAttention-3 上，插了探针的 kernel 丢掉了三项优化：两次展开的 SoftMax 迭代不再交错，P-convert 不再与 SoftMax 重叠，V tile 的释放也不再提前。追踪结果于是报告了 1,024–1,216 ns 的 V tile 等待，而真实 kernel 并没有这段等待。在 FA-3、FlashMLA 和 FA-4 上，Neutrino 只保住 8–20% 的原始指令，IKET 保住 13–48% 论文 §1。
  • kernel 要等探针。探针的 store 要读寄存器。之后的指令若要改写其中某个寄存器，就得等 store 读完它（WAR 依赖）；而在 Hopper 上一次全局内存访问要 270–380 ns，和被追踪的区间一样长。虽然只有一个 lane 执行 store，整个 warp 却都在探针之后的重汇合点等它 论文 §2.2。

Binary-level tools avoid the first problem, because the compiler never sees their probes. The older ones, SASSI and NVBit, call a probe function from the kernel, and saving and restoring the register context around every call is too slow for performance tracing paper §2.3. A binary tool that puts its probe inline still has the second problem whenever the probe waits on something the kernel has in flight. G-Watch 0.0.35, the public release of Xtrace and the oracle Olympus is checked against, is an example. On Olympus's T1–T4 kernels it alters 828 original instructions, always by adding scoreboards to a wait mask, and 12% of the scoreboards it adds make the kernel wait early on its own asynchronous work EVAL.md:37–44. At DeepGEMM's tile boundary, one such wait costs 18.4% of the kernel's run time (DECISIONS 61) DECISIONS.md:215–220.

二进制级工具避开了第一个问题，因为编译器从来看不到它们的探针。较早的 SASSI 和 NVBit 从 kernel 中调用一个探针函数，每次调用前后都要保存、恢复寄存器上下文，这对性能追踪来说太慢了 论文 §2.3。把探针内联进指令流的二进制工具，只要探针去等 kernel 正在进行的某件事，就仍然有第二个问题。G-Watch 0.0.35 是 Xtrace 的公开发布版，也是 Olympus 用来对照的 oracle，它就是一个例子：在 Olympus 的 T1–T4 kernel 上，它改动了 828 条原始指令，方式无一例外是往等待掩码里加 scoreboard，而它加上的 scoreboard 中有 12% 让 kernel 提前去等自己的异步操作 EVAL.md:37–44。在 DeepGEMM 的 tile 边界，这样一次等待就让 kernel 的运行时间增加 18.4%（DECISIONS 61）DECISIONS.md:215–220。

§2Xtrace's idea: splice into the scheduled SASSXtrace 的思路：拼接进已调度的 SASS

Xtrace inserts the probe's instructions directly into the compiled instruction sequence, after ptxas has scheduled it paper §2.3. The binary leaves no room for a probe, but a probe is only a handful of instructions, and at most points some registers hold nothing the kernel will read again. The probe can borrow those registers and leave every other instruction alone. The paper takes the word splicing for this from CPU dynamic instrumentation paper §3.

Xtrace 在 ptxas 完成调度之后，把探针指令直接插进编译好的指令序列 论文 §2.3。二进制本身没给探针留位置，但一个探针只有寥寥几条指令，而在大多数位置上，总有一些寄存器装着 kernel 不会再读的值。探针可以借用这些寄存器，其余指令一概不动。论文把这种做法称为拼接（splicing），这个词借自 CPU 上的动态插桩 论文 §3。

Doing that safely means redoing the compiler's last job by hand. NVIDIA GPUs issue each warp's instructions in order and interlock neither registers nor pipes, so ptxas resolves every hazard ahead of time and writes the result into each instruction's control bits paper §4.1 paper §A.2.1:

要安全地做到这一点，就得亲手重做编译器的最后一项工作。NVIDIA GPU 按顺序发射每个 warp 的指令，既不对寄存器加互锁，也不对流水线加互锁，所以 ptxas 事先解决所有冒险，并把结果写进每条指令的控制位 论文 §4.1 论文 §A.2.1：

  • A structural hazard (two instructions on one pipe) and a static data hazard (a fixed-latency producer) are cleared by a stall count: the next instruction issues that many cycles later.
  • A dynamic data hazard (a load, a store's late read of its sources, anything with variable latency) is cleared by a scoreboard: the producer claims one of the warp's six scoreboards, and the consumer's wait mask names it.
  • 结构冒险（两条指令用同一条流水线）和静态数据冒险（生产者延迟固定）靠stall 计数解决：下一条指令晚这么多个周期再发射。
  • 动态数据冒险（load、store 对源操作数的延后读取，以及任何延迟不固定的操作）靠 scoreboard 解决：生产者占用 warp 的六个 scoreboard 之一，消费者在等待掩码里点名它。

Olympus prints these fields as [wr:rd:{wait}:stall:yield] instr.py:125–130, where 7 means "no scoreboard". In DeepGEMM's tile tail, UTMACMDFLUSH [7:0:{}:2:0] claims SB0 as a read scoreboard and stalls 2 cycles, and BSYNC PT, B0 [7:7:{2}:5:0] waits on SB2 before it issues.

Olympus 把这些字段打印成 [wr:rd:{wait}:stall:yield] instr.py:125–130，其中 7 表示“不用 scoreboard”。在 DeepGEMM 的 tile 尾部，UTMACMDFLUSH [7:0:{}:2:0] 把 SB0 占作读 scoreboard，并 stall 2 个周期；BSYNC PT, B0 [7:7:{2}:5:0] 则要等 SB2 释放后才发射。

The paper turns the three challenges of splicing into three decisions the splicer makes for every probe paper §2.3 paper §4.1:

论文把拼接面临的三个挑战，转化为拼接器对每个探针要做的三个决定 论文 §2.3 论文 §4.1：

  1. D1, registers (challenge C1): give each probe value a register that is dead at the insertion point. Which ones are dead comes from a liveness analysis of the binary itself paper §4.3.
  2. D2, order (C3): any order of the probe's instructions that respects their own data dependencies.
  3. D3, control bits (C2): stalls and scoreboards from the same hazard tables ptxas uses, minus the delay the instructions in between already provide paper §4.4.
  1. D1，寄存器（对应挑战 C1）：给探针的每个值分配一个在插入点已死的寄存器。哪些寄存器已死，来自对二进制本身的活跃性分析 论文 §4.3。
  2. D2，顺序（C3）：探针指令的任意一种满足其自身数据依赖的排列。
  3. D3，控制位（C2）：按 ptxas 所用的同一套冒险表确定 stall 和 scoreboard，并扣除中间指令已经提供的延迟 论文 §4.4。

A probe's decision space is small enough to enumerate: few dead registers, few legal orders, few control-bit settings. Algorithm 1 walks orders × register partitions × control bits and keeps the plan that delays the kernel's next instruction least, adding measured latencies for dynamic dependencies. A greedy variant, Xtrace-g, picks the order in one pass by a critical-path price paper §4.2 search.py:1–60. Whatever it picks, the kernel's own instructions keep their bytes, control bits included. Only a branch whose target moved is rewritten, which is why the paper finds no basic block changed and 94–98% of the instructions preserved paper §5.3.

一个探针的决策空间小到可以穷举：死寄存器不多，合法顺序不多，控制位的取法也不多。算法 1 遍历“顺序 × 寄存器划分 × 控制位”，保留让 kernel 下一条指令推迟最少的方案，并对动态依赖加上实测延迟。贪心版本 Xtrace-g 则按关键路径代价一遍排出顺序 论文 §4.2 search.py:1–60。无论选哪个方案，kernel 自己的指令都保持原有字节，控制位也不例外；唯一被改写的是目标地址移动了的分支。这就是论文测得没有基本块被改动、94–98% 指令得以保留的原因 论文 §5.3。

The widget plays one warp through DeepGEMM's tile tail three times, on the real instructions. The first lane has no probe. The second has G-Watch's island at the site c.tile_done, the third Olympus's, each exactly as that tool spliced it. Olympus's island waits only on the scoreboard its own store claimed. G-Watch's also waits on SB0, which the kernel's TMA stores still hold.

下面的组件用真实指令，让同一个 warp 三次走过 DeepGEMM 的 tile 尾部。第一条泳道没有探针；第二条在站点 c.tile_done 放入 G-Watch 的 island，第三条放入 Olympus 的 island，两者都与各自工具实际拼进去的完全一致。Olympus 的 island 只等它自己的 store 占用的 scoreboard；G-Watch 的 island 还要等 SB0，而 SB0 仍被 kernel 的 TMA store 占着。

Early waits and the paper's §4.4提前等待与论文 §4.4

Paper §4.4 allows one kind of early wait: when no scoreboard is free, Xtrace waits out an in-flight one to reclaim it, trading some overlap for a free scoreboard. Olympus drops that and refuses the site instead; 10 reviewed sites are refused for it (DECISIONS 63). At c.tile_done a scoreboard was free (Olympus uses SB2 there), so G-Watch's wait on SB0 at that site is not that reclamation. Why G-Watch 0.0.35 adds it can't be seen from outside its native library; this is our reading of its island, not something the paper or G-Watch states.

论文 §4.4 允许一种提前等待：没有空闲 scoreboard 时，Xtrace 提前等完一个在途的 scoreboard 来回收它，用一部分重叠换一个空闲的 scoreboard。Olympus 放弃了这种做法，改为拒绝该站点；有 10 个经过审阅的站点因此被拒（DECISIONS 63）。在 c.tile_done 处其实有空闲的 scoreboard（Olympus 在那里用的是 SB2），所以 G-Watch 在这里等 SB0 并不是那种回收。G-Watch 0.0.35 为什么要加这次等待，从它的原生库外面看不出来；这只是我们对它这个 island 的解读，论文和 G-Watch 都没有这样说。

§3Olympus: what was rebuilt and what was reusedOlympus：重写了什么，复用了什么

Olympus is an independent reimplementation of Xtrace's SASS tier for sm_90 and sm_90a, run on the H200s of one host. It rebuilds the core of the paper: decoding, the control-flow graph, liveness, the hazard model, the probe templates, the splicing search, the splicer, the record format and the analysis USAGE.md:1031–1038. Two things are reused. The sm_90 instruction database and latency tables come from nvidia-sass-document; Olympus parses the tables with its own code, which avoids two known bugs in the upstream parser tables.py:1–28. Capturing the module load and running the spliced kernel in place of the original go through G-Watch 0.0.35's Python API. That was the reviewer's decision, taken after two attempts to write interception code were stopped: "we are just reproducing the core part" (DECISIONS 29) DECISIONS.md:62–64.

Olympus 是对 Xtrace 的 SASS 层的独立重实现，面向 sm_90 与 sm_90a，运行在一台主机的 H200 上。它重写了论文的核心：解码、控制流图、活跃性分析、冒险模型、探针模板、拼接搜索、拼接器、记录格式和分析 USAGE.md:1031–1038。有两样东西是复用的。sm_90 的指令数据库和延迟表来自 nvidia-sass-document，但延迟表由 Olympus 自己的代码解析，从而避开了上游解析器已知的两个 bug tables.py:1–28。捕获模块加载、用拼接后的 kernel 替换原 kernel 运行，这两件事通过 G-Watch 0.0.35 的 Python API 完成。这是评审者在两次自写拦截代码的尝试被叫停之后做出的决定：“we are just reproducing the core part”（DECISIONS 29）DECISIONS.md:62–64。

Sites are instruction indices. The paper's splicer finds trace hints in the source through DWARF, and it also offers a low-level interface that takes a program address paper §3; Olympus has only the second. Each of the 20 corpus kernels has the three site sets of paper §5.1: trace-sche (warp entry and exit), trace-pp (pipeline-stage boundaries) and trace-mem (every memory instruction), all recorded once per warp from an elected lane paper §5.1 PLAN.md:62.

站点用指令下标指定。论文的拼接器通过 DWARF 在源码中找到追踪标记，同时也提供一个直接接受程序地址的底层接口 论文 §3；Olympus 只有后者。语料库中的 20 个 kernel 各有论文 §5.1 定义的三组站点：trace-sche（warp 的入口与出口）、trace-pp（流水线阶段边界）和 trace-mem（每条访存指令），全部按 warp 记录，由选出的一个 lane 写入 论文 §5.1 PLAN.md:62。

    Where Olympus differs from the paper与论文的不同之处

    • Hardware. One GPU model, the H200 (sm_90a). The paper evaluates H100, B300 and MI300X, and Xtrace supports 19 architectures paper §5.1.
    • No scoreboard reclamation. A site with no free scoreboard is refused, never served by an early wait on a kernel scoreboard DECISIONS.md:227–232. The paper reclaims one paper §4.4.
    • The clock's cost. Olympus records the per-SM clock and calibrates each warp to the global timer, as paper §A.2.1 does. On H200, though, a CS2R read of either clock costs 4–6 cycles, so the paper's "hundreds of nanoseconds" for the global timer does not hold for CS2R DECISIONS.md:102–107 paper §A.2.1.
    • Measured gaps. Pairs of probe instructions are held to the latency table, except pairs whose minimum safe gap was measured on H200 DECISIONS.md:142–147 and one ptxas floor right after a blocking barrier DECISIONS.md:164–168.
    • The runtime. G-Watch's runtime, not Olympus's own, swaps the module and launches the kernel gw.py:1–23.
    • The record format. Olympus's own version 1: a 32-byte header per warp slot, then a ring of 32-bit words that each hold 26 clock bits and a 6-bit site id record.py:1–27.
    • 硬件。只有一种 GPU：H200（sm_90a）。论文在 H100、B300 和 MI300X 上做评估，Xtrace 支持 19 种架构 论文 §5.1。
    • 不回收 scoreboard。没有空闲 scoreboard 的站点直接拒绝，绝不靠提前等待某个 kernel scoreboard 来腾出位置 DECISIONS.md:227–232。论文则会回收一个 论文 §4.4。
    • 读时钟的代价。Olympus 与论文 §A.2.1 一样记录每个 SM 的时钟，并把每个 warp 校准到全局计时器。不过在 H200 上，用 CS2R 读任一时钟只要 4–6 个周期，所以论文所说全局计时器要“几百纳秒”，对 CS2R 并不成立 DECISIONS.md:102–107 论文 §A.2.1。
    • 实测间隔。探针指令之间的指令对按延迟表执行，例外有二：在 H200 上实测过最小安全间隔的指令对 DECISIONS.md:142–147，以及紧跟阻塞式 barrier 的一个 ptxas 下限 DECISIONS.md:164–168。
    • 运行时。替换模块、启动 kernel 用的是 G-Watch 的运行时，而不是 Olympus 自己写的 gw.py:1–23。
    • 记录格式。Olympus 自己的第 1 版：每个 warp 槽位先是 32 字节的头部，接着是一个 32 位字组成的环形缓冲，每个字装 26 位时钟和 6 位站点编号 record.py:1–27。

    §4How the project was run项目如何推进

    PLAN.md fixed the target before any code was written: nine acceptance criteria, nine milestones, a corpus of 20 kernels in five tiers, and a validation protocol PLAN.md:60–74. A lead agent, Zeus, split the work among eleven more agents, each named after an Olympian and owning one domain PLAN.md:375–400. Each kept a journal, prefixed its commits with its name, and recorded settled points in DECISIONS.md, which held 74 entries by the end. The first rule was correctness before speed: a spliced kernel is launched only once its outputs can be checked bit-exactly against the original's.

    在写任何代码之前，PLAN.md 先定下了目标：九条验收标准、九个里程碑、分五档的 20 个 kernel 语料库，以及一套验证流程 PLAN.md:60–74。主导 agent Zeus 把工作分给另外十一个 agent，每个以一位奥林匹斯神命名，各管一个领域 PLAN.md:375–400。每个 agent 都写自己的日志，提交信息以自己的名字开头，并把已定下的事项记进 DECISIONS.md，最后共有 74 条。第一条规矩是正确先于速度：拼接后的 kernel，只有在其输出能与原 kernel 逐位比对之后才会启动。

    Reading A4 against the paper对照论文看 A4

    The paper reports 0.9–2.8% overhead on FA-3, FA-4, FlashMLA and HSTU. Olympus's T1–T4 set also has microsecond Triton kernels, where INIT and the exit calibration cost a fixed amount per launch (axpy trace-sche is +12% under both tools), and it runs trace-mem as one full set where G-Watch runs chunks of at most 63 sites. So the two sets of numbers are not directly comparable. On the kernels closest to the paper's, trace-sche is within 1% for both tools, FlashMLA's trace-pp (+2.33%) is within 3%, and DeepGEMM's and FA-3's trace-pp are not. This comparison is ours; neither EVAL.md nor the paper makes it.

    论文在 FA-3、FA-4、FlashMLA 和 HSTU 上报告的开销是 0.9–2.8%。Olympus 的 T1–T4 集合里还有微秒级的 Triton kernel，INIT 和退出校准在每次 launch 中都有一笔固定开销（axpy 的 trace-sche 在两种工具下都是 +12%）；而且 Olympus 把 trace-mem 作为一整组来跑，G-Watch 则分成每块最多 63 个站点。所以两组数字不能直接比较。在最接近论文所用的那些 kernel 上，两种工具的 trace-sche 都在 1% 以内，FlashMLA 的 trace-pp（+2.33%）在 3% 以内，DeepGEMM 与 FA-3 的 trace-pp 则没有达到。这个比较是我们自己做的，EVAL.md 和论文都没有这样比较。
