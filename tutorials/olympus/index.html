The promise承诺

Olympus records events inside a running GPU kernel: when a warp reached a barrier, when a TMA load landed, how long an epilogue took. It does this by splicing probes into the SASS the compiler already scheduled — writing a few extra instructions into the compiled binary itself, with no recompile and no edit to the source. It makes one promise about the result: the kernel's own instructions stay byte-identical and never wait for a probe. This chapter states that promise, the six invariants that make it true, and the pipeline that carries it, in one picture and then on one real site end to end. The nine chapters after it build the system from the bottom: the instruction word first, then each layer that rests on it, and nothing used before the chapter that builds it.

Olympus 记录运行中 GPU kernel 内部的事件：warp 何时到达 barrier，TMA 加载何时落地，epilogue 用了多久。它的做法是把探针拼接（splice）进编译器已经调度好的 SASS——把几条额外指令写进编译好的二进制本身，不重新编译，也不改源码。它对结果只作一个承诺：kernel 自己的指令保持逐字节一致，而且永远不会为探针等待。本章说明这个承诺、让它成立的六条不变量，以及承载它的流水线：先用一张图，再在一个真实站点上从头走到尾。之后的九章自下而上地把这个系统搭起来：先是指令字，再是依托于它的每一层，任何东西都不会在建造它的那一章之前被用到。

§1Contract契约

What Olympus promisesOlympus 的承诺

A trace of events at the instructions you chose, taken from a kernel whose own instructions are byte-identical to the one you ship and never wait for a probe.

在你选定的指令处记录事件，而被记录的 kernel 自身指令与你交付的那个逐字节一致，且永远不会为探针等待。

olympus → used by使用者 you, or an agent reading olympus show你，或读 olympus show 的 agent

Start from the problem. You have a kernel that is slower than you expected, and you want to know which part of it is waiting. Timing the launch gives you one number for the whole thing, and a kernel of a few thousand instructions can hide its stall anywhere inside that number. Adding counters to the source and recompiling gives you more numbers, but ptxas reschedules the surrounding code around your counters, so what you measure is no longer the kernel you were asking about. Olympus is the third route: leave the compiled kernel exactly as the compiler produced it, and write the measuring code into the binary afterwards.

先从问题说起。你有一个比预期慢的 kernel，想知道它究竟是哪一部分在等。给一次启动计时只会得到一个总数，而几千条指令的 kernel 可以把它的停顿藏在这个数字的任何地方。在源码里加计数器再重新编译能得到更多数字，但 ptxas 会围着你的计数器重新调度周边代码，于是你测的已经不是你要问的那个 kernel 了。Olympus 走第三条路：让编译好的 kernel 保持编译器产出的原样，事后把测量代码写进二进制。

Four words carry the contract ARCHITECTURE.md:23–26. The first is site: a site is an instruction index, a position in the kernel's instruction list counted from zero. The kernel this tutorial returns to again and again is a DeepGEMM FP8 GEMM at k = 512, and it has 1,504 instructions, so its index 1100 names the 1,101st of them sites.yaml:1–7. A probe placed at a site runs immediately before that instruction, on every path that reaches it, and whether or not that instruction's own guard predicate turns out to be true; to record something after an instruction you name the site one index later ir.py:24–33.

契约由四个词承载 ARCHITECTURE.md:23–26。第一个是 site（站点）：站点就是一个指令下标，即 kernel 指令表中从零数起的一个位置。本教程反复回到的那个 kernel 是 k = 512 的 DeepGEMM FP8 GEMM，它有 1,504 条指令，所以下标 1100 指的是其中第 1,101 条 sites.yaml:1–7。放在站点上的探针，在每条到达该指令的路径上都紧在它之前执行，而且无论该指令自己的 guard 谓词是否成立；要记录某条指令之后的事，就把站点定在下一个下标 ir.py:24–33。

What goes in at a site is a probe: the handful of SASS instructions that do the recording. As it sits in the file it is called an island — one contiguous run of inserted instructions, immediately before the instruction its site names, with no control flow of its own. At index 1100 of that kernel the island is 8 instructions long. Tracing all 41 sites of that kernel's pipeline set costs 41 islands holding 386 inserted instructions, against the kernel's own 1,504 ares.md:857–858. Chapter 04 builds the probe and chapter 06 writes the island.

放进站点里的东西是 probe（探针）：真正做记录的那几条 SASS 指令。它在文件里的形态叫 island——一段连续的插入指令，紧贴在它的站点所指的那条指令之前，自身不含任何控制流。在那个 kernel 的下标 1100 处，island 有 8 条指令。把该 kernel 流水线集合的全部 41 个站点都追踪，代价是 41 个 island、共 386 条插入指令，而 kernel 自身有 1,504 条 ares.md:857–858。第 04 章建造探针，第 06 章把 island 写进去。

What a probe leaves behind is a record, and a timestamp record is exactly 4 bytes: one 32-bit word packed as (clk << id_bits) | (site_id + 1) record.py:16–22. id_bits is 6 in the corpus configuration, which leaves room for 63 distinct sites and 26 bits of clock. The + 1 is what makes an all-zero word mean "nothing was written here", so an untouched slot can never be mistaken for a record of site 0 at time 0. A value site writes a second word holding the register's value.

探针留下的东西是 record（记录），而一条时间戳记录正好 4 字节：一个 32 位字，打包成 (clk << id_bits) | (site_id + 1) record.py:16–22。在语料库的配置里 id_bits 是 6，于是有 63 个站点 id 的空间和 26 位时钟。那个 + 1 正是让全零字表示"这里什么都没写"的原因，这样没被写过的槽位绝不会被误读成站点 0 在时刻 0 的记录。值站点还会写第二个字，装着寄存器的值。

Records are paired by a region, which is a named bracket over sites: a name, the site ids that open it and the site ids that close it ir.py:48–69. Each time one warp passes through that bracket it produces an interval — the time from a start record to the end record that closes it, within that one warp and that one visit, never averaged across warps. A set is a named list of sites and regions, pinned to one cubin's sha256 so that a set can never be applied to a binary it was not written for. The corpus carries three sets for every kernel, and for this one they are trace-sche (entry plus one site per exit: 5 sites, 1 region), trace-pp (the hand-picked pipeline phases: 41 sites, 29 regions) and trace-mem (one value site per memory instruction: 118 sites) USAGE.md:304–344.

记录由 region 来配对，它是架在站点之上的一个有名字的夹子：一个名字、打开它的那些站点 id、关上它的那些站点 id ir.py:48–69。一个 warp 每经过这个夹子一次，就产生一个 interval（区间）——从起始记录到关上它的那条结束记录之间的时间，限定在那一个 warp、那一次经过之内，绝不跨 warp 求平均。set（集合）是一份有名字的站点与 region 列表，钉在某个 cubin 的 sha256 上，这样一份集合绝不会被用在不是为它写的二进制上。语料库为每个 kernel 带三份集合，对这个 kernel 它们是 trace-sche（入口加每个出口一个站点：5 个站点、1 个 region）、trace-pp（手挑的流水线阶段：41 个站点、29 个 region）和 trace-mem（每条内存指令一个值站点：118 个站点）USAGE.md:304–344。

The promise has two halves, and both are about the kernel, not the probe. Byte-identical: the splicer copies every original instruction word straight through, and the only words that come out different are branches whose displacement had to move because an island was inserted between the branch and its target README.md:3–6. Never waits: a probe writes only registers that are provably dead where it sits, and it waits only on scoreboards — one of six per-warp counters the hardware uses to track an operation that is still in flight — that its own instructions claimed. That second rule is the one that keeps the measurement honest, because a wait on a counter the kernel is using turns latency the kernel had overlapped into a stall you then measure.

承诺有两半，都说的是 kernel 而不是探针。逐字节一致：拼接器把每条原始指令字原样复制过去，唯一会变的字是因为有 island 插在分支和它的目标之间、位移不得不改动的那些分支 README.md:3–6。永不等待：探针只写它所在位置可被证明已死的寄存器，并且只等它自己的指令占用过的 scoreboard——硬件用来追踪某个尚在途中的操作的六个 per-warp 计数器之一。第二条规则才是保住测量诚实性的那一条，因为去等一个 kernel 正在用的计数器，会把 kernel 本已重叠掉的延迟变成一次停顿，而你随后测到的正是它。

Deciding all of that for one site produces a plan: which registers the probe may use, which scoreboards it may claim, which control bits each of its instructions carries, and the order they issue in — or, where no such assignment exists, a refusal. The refusal is the price of the promise: a site at which dead registers and a free scoreboard cannot both be found simply does not get a probe, and you are told so before anything is launched rather than reading a wrong number afterwards. What the promise buys is on the other side of that trade: with all 41 pipeline sites traced, this kernel spans 31.0 µs, against 30.3 µs with no probes at all EVAL.md:101–105. Chapter 05 builds the planner that makes the decision.

为一个站点把这些全部定下来，产出的是一份 plan（计划）：探针可用哪些寄存器、可占用哪些 scoreboard、每条指令带哪些控制位、以什么顺序发射——或者，在不存在这样一种分配时，一次拒绝。拒绝就是这个承诺的代价：在既找不到死寄存器又找不到空闲 scoreboard 的站点上，根本不放探针，而且这件事在任何东西启动之前就告诉你，而不是让你事后读到一个错的数。承诺买到的东西在这笔交易的另一边：41 个流水线站点全部追踪时，这个 kernel 耗时 31.0 µs，而完全不插探针是 30.3 µs EVAL.md:101–105。作出这个决定的规划器在第 05 章。

§2The six invariants六条不变量

Invariants不变量1–6

The promise is not one rule but six, each owned by one layer and each checked by a tool that would fail if it were broken.

承诺不是一条规则而是六条，每条归一层所有，每条都有一个一旦被破坏就会失败的检查工具。

Stated in ARCHITECTURE.md:56–73; each chapter below opens with the one it protects.

出处：ARCHITECTURE.md:56–73；下面每一章都以它所保护的那一条开篇。

  1. Original instructions are never altered. Every instruction word of the original comes out of the splicer bit-for-bit; the only words that differ are branches whose displacement had to change because an island moved their target. This is proved offline on every spliced image before it is allowed near a GPU (splice/verify.py), and measured independently as 0 changed basic blocks across all 30 kernel × set combinations of the corpus (splice/similarity.py). Chapter 06.
  2. A probe uses only registers proven dead. Dead means no instruction on any path from this point reads the register before something writes it again — and the analysis also treats a register as live while an asynchronous operation still holds it, right up to its release point, because the hardware will write it from under you. The check that backs this overwrites every register the analysis called dead with garbage and requires the kernel's outputs to stay bit-identical; it passes on every corpus kernel on both architectures. Chapter 02.
  3. A probe never waits on a scoreboard only the kernel claims. Borrowing a counter the kernel is using looks harmless and is not: it turns latency the kernel had overlapped into a stall, so the number you read back is larger than the kernel you wanted to measure. A site with no free scoreboard is refused, never granted by reclaiming a busy one (DECISIONS 61, 63). Chapter 03.
  4. A wait is issued at least 2 cycles after the instruction that sets its scoreboard. At a distance of 1 the wait does not see the claim and passes straight through, so the probe reads a value that is not ready yet. This is the rule ptxas itself follows: across 976 compiled kernels it emits no distance-1 pair at all, while it waits 5,314 write claims and 1,416 read claims at distance 2 (DECISIONS 62). Chapter 03.
  5. Nothing runs before it is checked. Four gates stand between a plan and a trusted number: the offline proof that the original words came through, the hazard check re-run on the spliced cubin rather than on the plan, the parameter-layout check done three independent ways, and a bit-exact comparison of the traced kernel's own outputs against the untraced run. Chapter 07.
  6. Every result carries its provenance: the commit it was built from, the cubin's sha256, the versions of every tool in the chain, the GPU it ran on and that GPU's SM clock during the run — all written from a clean export of one commit, so a figure can always be traced back to the bytes that produced it. Chapter 09.
  1. 原始指令从不被改动。原 kernel 的每条指令字都逐位地从拼接器里出来；唯一会不同的字，是因为 island 挪动了目标、位移不得不改的那些分支。这一点在每个拼接镜像被允许靠近 GPU 之前都有离线证明（splice/verify.py），并以另一种方式独立测得：语料库全部 30 个 kernel × 集合组合上，0 个基本块被改动（splice/similarity.py）。第 06 章。
  2. 探针只使用被证明已死的寄存器。"已死"意味着从这一点出发的任何路径上，都没有指令在它被重新写入之前读它——而且只要某个异步操作还占着一个寄存器，分析就把它当作活的，一直算到释放点为止，因为硬件会在你背后写它。支撑这一条的检查，把分析判为已死的每个寄存器都用垃圾值改写，并要求 kernel 的输出保持逐位一致；它在两种架构的每个语料库 kernel 上都通过。第 02 章。
  3. 探针从不等待只有 kernel 占用的 scoreboard。借用 kernel 正在用的计数器看起来无害，其实不然：它把 kernel 本已重叠掉的延迟变成一次停顿，于是你读回的数字比你想测的那个 kernel 更大。没有空闲 scoreboard 的站点直接拒绝，绝不靠回收一个忙碌的来放行（DECISIONS 61、63）。第 03 章。
  4. 等待至少在设置其 scoreboard 的指令之后 2 个周期发出。距离为 1 时，等待看不到这次占用，直接放行，于是探针读到一个还没准备好的值。这是 ptxas 自己遵守的规则：在 976 个编译出的 kernel 中它一次距离为 1 的配对都没有发出，而它在距离 2 上等待了 5,314 次写占用和 1,416 次读占用（DECISIONS 62）。第 03 章。
  5. 没有检查过的东西不会运行。在一份计划和一个可信数字之间立着四道门：证明原指令字原样通过的离线证明；在拼接后的 cubin 上（而不是在计划上）重跑一遍的冒险检查；用三种互相独立的方法做的参数布局检查；以及把被追踪 kernel 自己的输出与未追踪运行逐位比对。第 07 章。
  6. 每个结果都带着来源：它构建自哪个提交、cubin 的 sha256、链条上每个工具的版本、它跑在哪块 GPU 上以及那次运行期间该 GPU 的 SM 时钟——全都写自同一提交的干净导出，于是任何一个数字都能一路追回产生它的那些字节。第 09 章。

Six rules rather than one, because each is broken in a different way and so has to be caught by a different check. Invariant 1 is a property of a file and is settled on the host before launch; invariant 2 is a property of an analysis and can only be falsified by running the kernel; invariants 3 and 4 are properties of timing that no static reading of the ISA manual would have predicted, and both were learned from measurements on an H200. Keeping them separate is what lets each chapter below name exactly the one it is responsible for, and lets a failure point at the layer that caused it.

之所以是六条而不是一条，是因为每条被破坏的方式不同，因而必须由不同的检查来抓住。不变量 1 是一个文件的性质，在启动之前就在主机上定下来；不变量 2 是一项分析的性质，只能靠真的运行 kernel 来反驳；不变量 3 和 4 是时序的性质，单靠静态阅读 ISA 手册是预测不出来的，两条都是在 H200 上测出来的。把它们分开，才让下面每一章都能指名道姓地说出自己负责的是哪一条，也让一次失败能指向造成它的那一层。

§3How it works: the pipeline in one picture如何工作：一张图看流水线

A cubin goes in at the top left; an analysis block comes out at the bottom right. Everything above the splicer analyses and decides on the host CPU, and in a tracing run the runtime is the only stage that touches a GPU ARCHITECTURE.md:9–21. The latency and release figures the hazard model prices waits with were measured on a GPU once, during development; by the time a run starts they are tables, and no stage above the runtime reads a device.

cubin 从左上进，分析块从右下出。拼接器以上的一切都在主机 CPU 上分析和决定，而在一次追踪运行中，运行时是唯一接触 GPU 的阶段 ARCHITECTURE.md:9–21。冒险模型给等待定价所用的延迟与释放数值，是开发期间在 GPU 上测过一次的；到一次运行开始时它们已经只是表格，运行时以上的任何阶段都不读设备。

The layers, bottom to top自下而上的各层

The binary. The bottom layer is handed a .cubin file — the ELF container the CUDA toolchain emits for one architecture — and hands on a list of decoded instructions. A SASS instruction is 128 bits on both of our architectures: an opcode with its operands, plus a control word carrying a stall count, a yield bit, a write-claim scoreboard, a read-claim scoreboard, a six-bit wait mask and the operand-reuse flags. The same layer understands the container around the code as well as the code — the section table, the relocations, NVIDIA's EIATTR records, the DWARF line tables and the Mercury capsules — because all of it has to come back out valid after an insertion. Chapter 01.

二进制。最底层接到的是一个 .cubin 文件——CUDA 工具链为某一架构产出的 ELF 容器——交出去的是一份解码后的指令表。在我们这两种架构上，一条 SASS 指令都是 128 位：一个带操作数的 opcode，加一个控制字，里面装着 stall 计数、yield 位、写占用 scoreboard、读占用 scoreboard、六位等待掩码和操作数复用标志。这一层既懂代码，也懂包着代码的容器——节表、重定位、NVIDIA 的 EIATTR 记录、DWARF 行表和 Mercury 胶囊——因为插入之后这些东西都得原样有效地出来。第 01 章。

Where it is safe. Handed the decoded instructions, this layer builds a control-flow graph — basic blocks, the edges between them, the loops — and then runs liveness backwards over it to answer one question at every index: which registers can be written here without changing what the kernel computes. It answers for four separate files (the 256 general-purpose registers R0–R255, the uniform registers UR0–UR62 on sm_90, and the predicate and uniform-predicate files) and for the six scoreboards. The hard part is not the dataflow but the holds: a register that an asynchronous copy or an MMA is still writing is live even though no instruction in sight mentions it, so the analysis follows those operations to their release points. Chapter 02.

哪里安全。这一层接到解码后的指令，先建控制流图——基本块、块之间的边、循环——再在图上反向跑活跃性分析，在每个下标上回答同一个问题：这里可以写哪些寄存器而不改变 kernel 算出的东西。它为四个独立的寄存器文件（256 个通用寄存器 R0–R255、sm_90 上的 uniform 寄存器 UR0–UR62，以及谓词和 uniform 谓词文件）以及六个 scoreboard 各自作答。难点不在数据流而在占用：一个异步拷贝或 MMA 还在写的寄存器，即使附近没有任何指令提到它，它也是活的，所以分析要一路跟到这些操作的释放点。第 02 章。

Not getting in the way. Handed the same instruction list, the hazard model answers the other half of the safety question: how many cycles must separate two instructions, and which scoreboard waits are legal where. It draws on three sources — the fixed latencies in the ISA tables, the minimum distances ptxas itself is never observed to go below, and gaps measured directly on the hardware — and it adds the two rules the measurements forced on us: never wait on a scoreboard only the kernel claims, and never issue a wait within 1 cycle of the instruction that set it. Chapter 03.

不碍事。冒险模型接到同一份指令表，回答安全问题的另一半：两条指令之间必须隔多少个周期，以及在什么位置哪些 scoreboard 等待是合法的。它有三个来源——ISA 表格里的固定延迟、ptxas 自己从未被观察到低于的最小间距，以及直接在硬件上测出的间隔——并加上测量逼出来的两条规则：绝不等待只有 kernel 占用的 scoreboard，绝不在设置它的那条指令之后 1 个周期内发出等待。第 03 章。

What a probe is. This is the first layer that writes SASS instead of reading it. It holds four templates — INIT once at kernel entry, a TS or a VALUE body at each site, and an EXIT calibration on the way out — and is handed the dead registers the layers below found, shaped to what each template asks for. INIT is where the per-warp state is set up: three uniform registers, an even pair holding this warp's slot base address and one more counting the records it has made, chosen uniform because uniform registers are shared by the whole warp and survive a USETMAXREG reallocation. A bare timestamp body is 7 instructions at the corpus settings, and the island the planner finally lays down at our example site is 8 templates.py:18–27. Chapter 04.

探针是什么。这是第一个写 SASS 而不是读 SASS 的层。它持有四个模板——kernel 入口处一次 INIT、每个站点一个 TS 或 VALUE 主体、出口处一次 EXIT 校准——并接到下面各层找到的死寄存器，按每个模板要求的形状交给它。per-warp 状态在 INIT 里建立：三个 uniform 寄存器，一对偶数寄存器装着本 warp 的槽位基址，再有一个数它已经写了多少条记录；之所以选 uniform，是因为 uniform 寄存器由整个 warp 共享，而且能活过一次 USETMAXREG 重分配。在语料库的设置下，一个纯时间戳主体是 7 条指令，而规划器最终在我们的示例站点上放下的 island 是 8 条 templates.py:18–27。第 04 章。

Choosing registers and bits. The planner is handed a template body, the dead registers at the site and the hazard model's limits, and hands on a plan: concrete register numbers, concrete scoreboards, a stall count and a wait mask for every instruction, and the order they issue in. Three planners share the same templates — a conservative one that fences every probe without consulting any latency model, an exact one that prices each fence from the tables, and a search that enumerates instruction orders against register assignments against scoreboard choices and keeps the cheapest, which is Algorithm 1 of the paper search.py:8–27. The search is anytime under a deterministic budget of 5,000 work units that never reads a clock, so the same site plans to the same island every time it is planned; the median site takes 2.99 ms and the slowest of 2,028 took 6.60 ms (DECISIONS 73). Where no legal assignment exists the plan for that site is a refusal, and a refusal is a result rather than a failure. Chapter 05.

选择寄存器与控制位。规划器接到一个模板主体、该站点上的死寄存器和冒险模型的限制，交出一份计划：具体的寄存器号、具体的 scoreboard、每条指令的 stall 计数与等待掩码，以及它们的发射顺序。三个规划器共用同一套模板——一个保守的，不查任何延迟模型就给每个探针设栅栏；一个精确的，按表格给每道栅栏定价；还有一个搜索的，枚举指令顺序 × 寄存器分配 × scoreboard 选择并保留最便宜的那个，也就是论文的算法 1 search.py:8–27。搜索在一个从不读时钟的 5,000 工作单位确定性预算下随时可停，所以同一个站点每次规划都得到同一个 island；中位站点耗时 2.99 ms，2,028 个站点中最慢的 6.60 ms（DECISIONS 73）。不存在合法分配时，该站点的计划就是一次拒绝，而拒绝是一个结果，不是一次失败。第 05 章。

Writing probes into the binary. The splicer is handed the plan and the original cubin and hands on a new cubin. Inserting instructions moves everything after them, so every encoded code offset has to be found and rewritten: branch displacements, jump tables, the return literals of CALL.REL, and the offset-bearing records that live outside the code — relocations, EIATTRs and the DWARF lines. It also appends one 8-byte parameter to the kernel's signature, the pointer to the buffer the probes store into. Then it proves its own work offline, instruction by instruction, before the image is allowed anywhere near a device; across all 30 kernel × set combinations of the corpus that proof reports 0 changed basic blocks EVAL.md:30–35. Chapter 06.

把探针写进二进制。拼接器接到计划和原 cubin，交出一个新 cubin。插入指令会把后面的一切都挪动，所以每一处编码过的代码偏移都得被找出来重写：分支位移、跳转表、CALL.REL 的返回字面量，以及活在代码之外、带着偏移的那些记录——重定位、EIATTR 和 DWARF 行。它还给 kernel 的签名追加一个 8 字节参数，即探针存数的那个缓冲区的指针。然后它逐条指令地离线证明自己的工作，证完之后镜像才被允许靠近设备；在语料库全部 30 个 kernel × 集合组合上，这个证明报告 0 个基本块被改动 EVAL.md:30–35。第 06 章。

Running a traced kernel. The runtime is handed the spliced cubin and the original launch, and hands back the bytes the probes wrote. It loads the image, allocates the record buffer with a guard band of known bytes on each side of it, launches the kernel with the appended parameter pointing at that buffer, and then refuses to report anything until two conditions hold: the guard bands are still exactly what it wrote, and the kernel's own outputs are bit-identical to the untraced run's. Afterwards it restores the original module, so a traced process is left as it was found. Chapter 07.

运行被追踪的 kernel。运行时接到拼接后的 cubin 和原来的启动，交回探针写下的那些字节。它加载镜像，分配记录缓冲区并在它两侧各放一段已知字节的保护带，用指向该缓冲区的追加参数启动 kernel，然后在两个条件成立之前拒绝报告任何东西：保护带仍然和它写进去的完全一样，而且 kernel 自己的输出与未追踪运行逐位一致。之后它恢复原来的 module，让被追踪过的进程保持原样。第 07 章。

Reading a trace. The trace layer is handed the raw buffer and hands on something a person or an agent can read. Each 4-byte word is split back into a site id and a 26-bit clock; the clock is unwrapped across its rollovers, then converted to nanoseconds using the two (global timer, SM clock) pairs the probe itself stored in the slot header at entry and at exit, so no clock frequency ever has to be assumed. Records become per-warp intervals, intervals pair into regions, and olympus show prints one analysis block in plain text. Source line numbers recovered from DWARF are offered as hints for choosing sites, never as ground truth about what the hardware did. Chapter 08.

读一份追踪。追踪层接到原始缓冲区，交出人或 agent 能读的东西。每个 4 字节字被拆回一个站点 id 和一个 26 位时钟；时钟先跨回绕展开，再用探针自己在入口和出口写进槽位头部的那两对（全局计时器，SM 时钟）换算成纳秒，于是从不需要假定任何时钟频率。记录变成 per-warp 的区间，区间配对成 region，olympus show 打印出一个纯文本的分析块。从 DWARF 恢复的源码行号只作为挑选站点的提示提供，绝不作为硬件实际行为的真相。第 08 章。

How we know. The top layer has no oracle to compare against, so it builds one out of the kernel itself, and each check it runs closes a different hole. Bit-exact outputs catch any change in what the kernel computes; the dead-register check catches a wrong liveness answer; fuzzing catches an encoder that round-trips a class of instruction incorrectly; static sweeps over the whole corpus catch a rule applied in one place and not another; record counts checked against the control flow catch a probe that ran the wrong number of times. Every figure that comes out is written with its provenance beside it. Chapter 09.

我们如何确信。最上层没有可比对的 oracle，于是它用 kernel 本身造一个，而它跑的每项检查都堵住一个不同的漏洞。逐位一致的输出抓住 kernel 计算结果的任何变化；死寄存器检查抓住一个错误的活跃性答案；模糊测试抓住某一类指令往返编码不正确的编码器；覆盖整个语料库的静态扫描抓住一条只在某处而不在别处被应用的规则；对照控制流核对的记录计数抓住运行次数不对的探针。出来的每一个数字，旁边都写着它的来源。第 09 章。

The layers are also an import order. Each package may import only packages on its own row or below, and a test scans every import, lazy ones included, to enforce it; four small modules are contracts importable from anywhere: the site and plan IR, the splicer's result, the on-device record format and the run record ARCHITECTURE.md:28–54. That is why the tutorial can be read bottom-up: start at row 0 and every chapter rests only on rows the chapters before it have already built.

这些层同时也是导入顺序。每个包只能导入自己这一行或更下面的包，一个测试扫描每一处导入（包括延迟导入）来强制执行；四个小模块是可以从任何地方导入的契约：站点与计划的 IR、拼接器的结果、设备端记录格式和运行记录 ARCHITECTURE.md:28–54。正因如此，本教程可以自下而上地读：从第 0 行起步，之后每一章都只依托于它前面各章已经搭好的那些行。

Two architectures run the same code. The ISA layer is parameterised by architecture (encoding database, control word, constant-bank layout, uniform-register file, latency tables, ptxas floors, probe templates), and everything above it is shared; the port to GB300 added tables and facts, not branches ARCHITECTURE.md:75–81.

两种架构跑同一份代码。ISA 层按架构参数化（编码数据库、控制字、常量库布局、uniform 寄存器文件、延迟表、ptxas 下限、探针模板），它之上的一切都是共用的；移植到 GB300 增加的是表格和事实，而不是分支 ARCHITECTURE.md:75–81。

§4Where it came from从何而来

Olympus is its own binary-level intra-kernel tracing system, and what it started from was a paper, not a code base. The paper is Xtrace (Huang et al.); its own tool was released, but Olympus is not a port of that tool and does not treat it as a reference implementation. What was taken is the design, and every layer in the picture above was written here, from the instruction encoder upward ARCHITECTURE.md:83–89.

Olympus 是它自己的二进制级 kernel 内部追踪系统，而它出发的地方是一篇论文，不是一份代码。论文是 Xtrace（Huang 等）；论文自己的工具是公开的，但 Olympus 不是那个工具的移植，也不把它当作参考实现。被拿来的是设计，而上图中的每一层都是在这里写的，从指令编码器往上 ARCHITECTURE.md:83–89。

Three ideas came from the paper and all three survived contact with the hardware. Splice the probe into the scheduled SASS instead of recompiling paper §2.3. Give that probe dead registers found by a liveness analysis of the binary, rather than registers reserved in advance paper §4.3. Choose its control bits by search, priced against the delay the kernel's own instructions already provide paper §4.2 paper §4.4.

有三个想法来自论文，而三个都经得住硬件的检验。把探针拼接进已调度的 SASS，而不是重新编译 论文 §2.3。给这个探针的寄存器，是由二进制活跃性分析找出来的死寄存器，而不是事先预留的寄存器 论文 §4.3。用搜索来选它的控制位，并扣除 kernel 自身指令已经提供的那部分延迟来定价 论文 §4.2 论文 §4.4。

Five things are done differently, and they are not five of the same kind. Two tighten a rule the paper allows: it may reclaim a busy scoreboard by waiting it out, and it may place a wait immediately after the instruction that sets it; Olympus does neither, because on an H200 the first changes what is measured and the second reads a value that is not there yet. One extends a rule the paper states to operands its hardware did not have, namely Blackwell's tensor-memory and tcgen05 holds. One replaces a stopping rule: where the paper's search stops on elapsed time, ours stops on a fixed count of work units, so that planning the same site twice gives the same island both times. And one adds a guarantee the paper does not make, that the spliced binary keeps its line tables, so a source view of a traced kernel is still correct. The table gives each departure one row, and its Evidence column is the measurement that forced it.

有五件事做得不一样，而这五件不是同一类。两件把论文允许的规则收紧了：论文可以靠等掉一个忙碌的 scoreboard 来回收它，也可以把等待紧放在设置它的指令之后；Olympus 两件都不做，因为在 H200 上，前者改变了被测量的东西，后者读到的值还不在那里。一件把论文陈述的规则扩展到它的硬件所没有的操作数上，即 Blackwell 的 tensor memory 与 tcgen05 占用。一件替换了停止规则：论文的搜索按已用时间停，我们的按固定的工作单位数停，这样同一个站点规划两次会得到同一个 island。还有一件加上了论文没有作出的保证：拼接后的二进制保留行表，于是被追踪 kernel 的源码视图仍然正确。表格给每处差别一行，它的"依据"列就是逼出这处差别的那次测量。

§5Try it: one warp, one island动手试试：一个 warp，一个 island

The widget plays one warp through the tail of DeepGEMM's tile loop, on the real instructions, twice: once as ptxas scheduled it, once with a real probe island spliced in before index 1100, the site c.tile_done. The island ends with a wait on SB2, the scoreboard its own store claimed. Flip the toggle and the island also waits on SB0, which the kernel's TMA stores hold while the TMA unit reads the finished tile out of shared memory: the kernel's own instructions shift by the whole hold. Flip it back and they shift by the island's 28 cycles and no more.

这个组件用真实指令让同一个 warp 两次走过 DeepGEMM tile 循环的尾部：一次按 ptxas 的调度，一次在下标 1100 之前（站点 c.tile_done）拼入一个真实的探针 island。island 以等待 SB2 结束，那是它自己的 store 占用的 scoreboard。打开开关，island 还会去等 SB0，而 SB0 被 kernel 的 TMA store 占着，直到 TMA 单元把算完的 tile 从共享内存读完：kernel 自己的指令被整段占用时间推后。关掉开关，它们只推后 island 自己的 28 个周期，一步不多。

Real: the kernel is DeepGEMM 1d2d k512, indices 1095–1109, decoded by Olympus from /ws/corpus/t3_dg_1d2d_k512/kernel.cubin (sha256 e0f1350c…); the island is the search planner's c.tile_done island as it was spliced, listed in /ws/runs/m7/final-48360e9/a6/sbwait/scan.md (guard predicates omitted). The toggle adds SB0 to the island's last wait mask, which is what a probe that borrows the kernel's scoreboard does.

真实部分：kernel 是 DeepGEMM 1d2d k512 的第 1095–1109 条指令，由 Olympus 从 /ws/corpus/t3_dg_1d2d_k512/kernel.cubin（sha256 e0f1350c…）解码得到；island 是搜索规划器在 c.tile_done 处实际拼入的那个，列于 /ws/runs/m7/final-48360e9/a6/sbwait/scan.md（省略 guard 谓词）。控制字打印为 [wr:rd:{wait}:stall:yield]，7 表示不用 scoreboard。开关把 SB0 加进 island 最后一条指令的等待掩码，这正是借用 kernel scoreboard 的探针会做的事。

Modelled: in-order issue, where each instruction waits for the previous stall and for the scoreboards in its wait mask. Release times are estimates: 14 cycles for a store's read of its sources (with it the island costs the planner's estimated 28 cycles), 37 for S2UR, and 1,450 cycles for SB0, which approximates the 0.8–0.9 µs per tile measured on the whole kernel at about 1.75 GHz (DECISIONS 61). Other warps and memory contention are not modelled.

模型部分：按顺序发射，每条指令先等上一条的 stall，再等等待掩码里的 scoreboard。释放时间是估计值：store 读取源操作数按 14 个周期（这样 island 正好是规划器估计的 28 个周期），S2UR 按 37 个周期，SB0 按 1,450 个周期，这近似于在整个 kernel 上测得的每 tile 0.8–0.9 µs（约 1.75 GHz，DECISIONS 61）。没有模拟其他 warp 和内存争用。

Measured on the whole kernel rather than modelled: a lone NOP that waits on SB0 at this site costs +18.4% at k512 and +5.3% at k2048; the same splice without the wait costs −0.3% DECISIONS.md:215–221. That measurement is why invariant 3 is a rule and not a preference.

在整个 kernel 上实测而非建模：只在这个站点插一条等待 SB0 的 NOP，k512 慢 18.4%，k2048 慢 5.3%；同样的拼接去掉这次等待，结果是 −0.3% DECISIONS.md:215–221。正是这次测量让不变量 3 成为一条规则，而不是一种偏好。

§6Read next: bottom-up through the layers接着读：自下而上穿过各层

Each chapter is one layer of the picture above, and they are ordered from the bottom up: nothing is used before the chapter that builds it. We start at the instruction word, because every promise made later is in the end a promise about bits. Then come the two analyses that decide what a probe may touch. One answers which registers are dead at a given instruction; the other answers how far apart two instructions must issue. Then what a probe actually is, how one is fitted to a particular site, and how it is written into the file. Only then do we run it, read what came back, and finish with how all of it is checked. Every chapter opens with its contract and the one invariant it protects, shows the code second and the paper third, and carries one widget driven by real data.

每一章是上图中的一层，而它们自下而上排列：任何东西都不会在建造它的那一章之前被用到。我们从指令字开始，因为之后作出的每一个承诺，归根结底都是关于比特的承诺。接着是决定探针能碰什么的两项分析。一项回答在某条指令处哪些寄存器已死；另一项回答两条指令之间必须隔多远发射。然后是探针究竟是什么、如何把一个探针装进某个具体站点、以及如何把它写进文件。只有到这时我们才运行它、读回它带回来的东西，最后以这一切如何被检查收尾。每章都以它的契约和它所保护的那一条不变量开篇，代码居第二，论文居第三，并各带一个由真实数据驱动的组件。
