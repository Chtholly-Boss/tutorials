The promise承诺

Olympus records events inside a running GPU kernel: when a warp reached a barrier, when a TMA load landed, how long an epilogue took. It does this by splicing probes into the SASS the compiler already scheduled, and it makes one promise about the result: the kernel's own instructions stay byte-identical and never wait for a probe. This chapter states that promise, the six invariants that make it true, and the pipeline that carries it, in one picture. The nine chapters after it build the system from the bottom: the instruction word first, then each layer that rests on it, and nothing used before the chapter that builds it.

Olympus 记录运行中 GPU kernel 内部的事件：warp 何时到达 barrier，TMA 加载何时落地，epilogue 用了多久。它的做法是把探针拼接进编译器已经调度好的 SASS，并对结果只作一个承诺：kernel 自己的指令保持逐字节一致，而且永远不会为探针等待。本章说明这个承诺、让它成立的六条不变量，以及承载它的流水线，一张图说清。之后的九章自下而上地把这个系统搭起来：先是指令字，再是依托于它的每一层，任何东西都不会在建造它的那一章之前被用到。

§1Contract契约

What Olympus promisesOlympus 的承诺

A trace of events at the instructions you chose, taken from a kernel whose own instructions are byte-identical to the one you ship and never wait for a probe.

在你选定的指令处记录事件，而被记录的 kernel 自身指令与你交付的那个逐字节一致，且永远不会为探针等待。

olympus → used by使用者 you, or an agent reading olympus show你，或读 olympus show 的 agent

Four words carry the contract ARCHITECTURE.md:23–26. A site is an instruction index: a probe placed there runs before that instruction on every path that reaches it ir.py:24–33. A record is what the probe writes: a timestamp, and for a value site a register's value, packed as (clock << 6) | (site_id + 1) record.py:16–22. A region is the time between a start site and an end site within one warp ir.py:48–69. A set is a named list of sites and regions, pinned to one cubin's sha256; the corpus carries three per kernel, trace-sche, trace-pp and trace-mem USAGE.md:304–344.

契约由四个词承载 ARCHITECTURE.md:23–26。站点（site）是一个指令下标：放在那里的探针，在每条到达该指令的路径上都在它之前执行 ir.py:24–33。记录（record）是探针写下的东西：一个时间戳，值站点还带一个寄存器的值，打包成 (clock << 6) | (site_id + 1) record.py:16–22。区间（region）是同一个 warp 内从起始站点到结束站点之间的时间 ir.py:48–69。集合（set）是一份有名字的站点与区间列表，钉在某个 cubin 的 sha256 上；语料库中每个 kernel 带三份：trace-sche、trace-pp 和 trace-mem USAGE.md:304–344。

The promise has two halves, and both are about the kernel, not the probe. Byte-identical: the splicer copies every original instruction word through; the only words that change are branches whose target moved with an island README.md:3–6. Never waits: a probe uses only registers that are dead where it sits and waits only on scoreboards its own instructions claimed, so the kernel's overlapped latency stays overlapped. A site where that cannot be arranged is refused before anything is launched.

承诺有两半，都说的是 kernel 而不是探针。逐字节一致：拼接器把每条原始指令字原样复制过去，唯一会变的字是目标随 island 移动了的分支 README.md:3–6。永不等待：探针只用它所在位置已死的寄存器，只等它自己的指令占用的 scoreboard，于是 kernel 原本重叠的延迟仍然重叠。无法做到这一点的站点，在任何东西启动之前就被拒绝。

§2The six invariants六条不变量

Invariants不变量1–6

The promise is not one rule but six, each owned by one layer and each checked by a tool that would fail if it were broken.

承诺不是一条规则而是六条，每条归一层所有，每条都有一个一旦被破坏就会失败的检查工具。

Stated in ARCHITECTURE.md:56–73; each chapter below opens with the one it protects.

出处：ARCHITECTURE.md:56–73；下面每一章都以它所保护的那一条开篇。

  1. Original instructions are never altered. Only branch targets that moved differ. Proved offline for every spliced image (splice/verify.py) and measured as 0 changed basic blocks on every corpus kernel (splice/similarity.py). Chapter 03.
  2. A probe uses only registers proven dead, including registers held by in-flight asynchronous operations until their release. The dead-register check overwrites every register the analysis calls dead and requires bit-identical outputs; it passes on every corpus kernel on both architectures. Chapter 07.
  3. A probe never waits on a scoreboard only the kernel claims. Such a wait turns overlapped latency into a stall and changes what is measured; a site with no free scoreboard is refused, never reclaimed (DECISIONS 61, 63). Chapter 06.
  4. A wait is issued at least 2 cycles after the instruction that sets its scoreboard, the rule ptxas follows in every kernel examined (DECISIONS 62). Chapter 06.
  5. Nothing runs before it is checked. The offline proof, the hazard check on the spliced cubin, the parameter-layout check three ways and the bit-exact output gate all run before a traced run is trusted. Chapter 02.
  6. Every result carries its provenance: commit, cubin sha256, tool versions, GPU and clock, from a clean export of one commit. Chapter 09.
  1. 原始指令从不被改动。只有目标移动了的分支会不同。对每个拼接后的镜像都有离线证明（splice/verify.py），并在每个语料库 kernel 上测得 0 个基本块被改动（splice/similarity.py）。第 03 章。
  2. 探针只使用被证明已死的寄存器，包括被在途异步操作占用、直到释放点才空出的寄存器。死寄存器检查改写分析判为已死的每个寄存器，并要求输出逐位一致；在两种架构的每个语料库 kernel 上都通过。第 07 章。
  3. 探针从不等待只有 kernel 占用的 scoreboard。这样的等待会把重叠的延迟变成停顿，改变被测量的东西；没有空闲 scoreboard 的站点直接拒绝，绝不回收（DECISIONS 61、63）。第 06 章。
  4. 等待至少在设置其 scoreboard 的指令之后 2 个周期发出，这是 ptxas 在我们检查过的每个 kernel 中都遵守的规则（DECISIONS 62）。第 06 章。
  5. 没有检查过的东西不会运行。离线证明、对拼接后 cubin 的冒险检查、三个视角的参数布局检查，以及逐位一致的输出门，都在一次追踪运行被信任之前完成。第 02 章。
  6. 每个结果都带着来源：提交、cubin 的 sha256、工具版本、GPU 与时钟，来自同一提交的干净导出。第 09 章。

§3How it works: the pipeline in one picture如何工作：一张图看流水线

A cubin goes in at the top left; an analysis block comes out at the bottom right. Everything above the splicer analyses and decides on the host CPU; the runtime is the only stage that touches a GPU ARCHITECTURE.md:9–21.

cubin 从左上进，分析块从右下出。拼接器以上的一切都在主机 CPU 上分析和决定；运行时是唯一接触 GPU 的阶段 ARCHITECTURE.md:9–21。

The layers are also an import order. Each package may import only packages on its own row or below, and a test scans every import, lazy ones included, to enforce it; four small modules are contracts importable from anywhere: the site and plan IR, the splicer's result, the on-device record format and the run record ARCHITECTURE.md:28–54. That is why the tutorial can be read bottom-up: start at row 0 and every chapter rests only on rows the chapters before it have already built.

这些层同时也是导入顺序。每个包只能导入自己这一行或更下面的包，一个测试扫描每一处导入（包括延迟导入）来强制执行；四个小模块是可以从任何地方导入的契约：站点与计划的 IR、拼接器的结果、设备端记录格式和运行记录 ARCHITECTURE.md:28–54。正因如此，本教程可以自下而上地读：从第 0 行起步，之后每一章都只依托于它前面各章已经搭好的那些行。

Two architectures run the same code. The ISA layer is parameterised by architecture (encoding database, control word, constant-bank layout, uniform-register file, latency tables, ptxas floors, probe templates), and everything above it is shared; the port to GB300 added tables and facts, not branches ARCHITECTURE.md:75–81.

两种架构跑同一份代码。ISA 层按架构参数化（编码数据库、控制字、常量库布局、uniform 寄存器文件、延迟表、ptxas 下限、探针模板），它之上的一切都是共用的；移植到 GB300 增加的是表格和事实，而不是分支 ARCHITECTURE.md:75–81。

§4Where it came from从何而来

The approach is the Xtrace paper's (Huang et al.): splice the probe into the scheduled SASS instead of recompiling paper §2.3; give it dead registers found by a liveness analysis of the binary paper §4.3; choose its control bits by search, against the delay the kernel's own instructions already provide paper §4.2 paper §4.4. Olympus is an independent system that started from that design and departs from it where its measurements said to ARCHITECTURE.md:83–89. Each departure is one line here and a section in its chapter.

方法来自 Xtrace 论文（Huang 等）：把探针拼接进已调度的 SASS，而不是重新编译 论文 §2.3；给它由二进制活跃性分析找到的死寄存器 论文 §4.3；用搜索选择它的控制位，并扣除 kernel 自身指令已经提供的延迟 论文 §4.2 论文 §4.4。Olympus 是从这个设计出发的独立系统，并在测量结果有话要说的地方离开它 ARCHITECTURE.md:83–89。每处不同在这里只占一行，在各自的章里占一节。

§5Try it: one warp, one island动手试试：一个 warp，一个 island

The widget plays one warp through the tail of DeepGEMM's tile loop, on the real instructions, twice: once as ptxas scheduled it, once with a real probe island spliced in before index 1100, the site c.tile_done. The island ends with a wait on SB2, the scoreboard its own store claimed. Flip the toggle and the island also waits on SB0, which the kernel's TMA stores hold while the TMA unit reads the finished tile out of shared memory: the kernel's own instructions shift by the whole hold. Flip it back and they shift by the island's 28 cycles and no more.

这个组件用真实指令让同一个 warp 两次走过 DeepGEMM tile 循环的尾部：一次按 ptxas 的调度，一次在下标 1100 之前（站点 c.tile_done）拼入一个真实的探针 island。island 以等待 SB2 结束，那是它自己的 store 占用的 scoreboard。打开开关，island 还会去等 SB0，而 SB0 被 kernel 的 TMA store 占着，直到 TMA 单元把算完的 tile 从共享内存读完：kernel 自己的指令被整段占用时间推后。关掉开关，它们只推后 island 自己的 28 个周期，一步不多。

真实部分：kernel 是 DeepGEMM 1d2d k512 的第 1095–1109 条指令，由 Olympus 从 /ws/corpus/t3_dg_1d2d_k512/kernel.cubin（sha256 e0f1350c…）解码得到；island 是搜索规划器在 c.tile_done 处实际拼入的那个，列于 /ws/runs/m7/final-48360e9/a6/sbwait/scan.md（省略 guard 谓词）。控制字打印为 [wr:rd:{wait}:stall:yield]，7 表示不用 scoreboard。开关把 SB0 加进 island 最后一条指令的等待掩码，这正是借用 kernel scoreboard 的探针会做的事。

Modelled: in-order issue, where each instruction waits for the previous stall and for the scoreboards in its wait mask. Release times are estimates: 14 cycles for a store's read of its sources (with it the island costs the planner's estimated 28 cycles), 37 for S2UR, and 1,450 cycles for SB0, which approximates the 0.8–0.9 µs per tile measured on the whole kernel at about 1.75 GHz (DECISIONS 61). Other warps and memory contention are not modelled.

模型部分：按顺序发射，每条指令先等上一条的 stall，再等等待掩码里的 scoreboard。释放时间是估计值：store 读取源操作数按 14 个周期（这样 island 正好是规划器估计的 28 个周期），S2UR 按 37 个周期，SB0 按 1,450 个周期，这近似于在整个 kernel 上测得的每 tile 0.8–0.9 µs（约 1.75 GHz，DECISIONS 61）。没有模拟其他 warp 和内存争用。

Measured on the whole kernel rather than modelled: a lone NOP that waits on SB0 at this site costs +18.4% at k512 and +5.3% at k2048; the same splice without the wait costs −0.3% DECISIONS.md:215–221. That measurement is why invariant 3 is a rule and not a preference.

在整个 kernel 上实测而非建模：只在这个站点插一条等待 SB0 的 NOP，k512 慢 18.4%，k2048 慢 5.3%；同样的拼接去掉这次等待，结果是 −0.3% DECISIONS.md:215–221。正是这次测量让不变量 3 成为一条规则，而不是一种偏好。

§6Read next: bottom-up through the layers接着读：自下而上穿过各层

Each chapter is one layer of the picture above, read from the bottom up: nothing is used before the chapter that builds it. We start at the instruction word, because every later promise is a promise about bits. Then the two analyses that decide what a probe may touch — which registers are dead, and how far apart instructions must issue. Then what a probe actually is, how one is fitted to a site, and how it is written into the file. Only then do we run it, read what came back, and finish with how all of it is checked. Every chapter opens with its contract and its invariant, shows the code second and the paper third, and has one widget on real data.

每一章是上图中的一层，自下而上来读：任何东西都不会在建造它的那一章之前被用到。我们从指令字开始，因为后面所有的承诺本质上都是关于比特的承诺。接着是决定探针能碰什么的两项分析：哪些寄存器已死，以及指令之间必须隔多远发射。然后是探针究竟是什么、如何把一个探针装进一个站点、以及如何把它写进文件。只有到这时我们才运行它、读回它带回来的东西，最后以这一切如何被检查收尾。每章都以它的契约和不变量开篇，代码居第二，论文居第三，并各有一个基于真实数据的组件。
