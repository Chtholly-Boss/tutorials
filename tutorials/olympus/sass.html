SASS, control bits and splicingSASS、控制位与指令拼接

A Hopper instruction carries its own schedule in 22 control bits. This chapter reads those 128-bit words the way Olympus does, shows how it re-encodes them byte for byte, how it opens room in front of an instruction for probe code and moves every code offset that shifts, and how the result compares with G-Watch 0.0.35 under the paper's binary-similarity metric.

Hopper 的每条指令都用 22 个控制位携带自己的调度。本章按 Olympus 的方式读这些 128 位指令字：它如何逐字节地重新编码，如何在指令前为探针代码腾出位置并移动随之偏移的每一个代码地址，以及在论文的二进制相似度指标下，结果与 G-Watch 0.0.35 相比如何。

§1The schedule is in the binary调度写在二进制里

A GPU tracer records timestamps or register values at chosen points inside a running kernel. The paper's §2.2 shows how the usual ways of doing that change the kernel they are meant to observe. Tools that insert probes before compilation, Neutrino at the IR level and IKET through placeholders, hand the probe to the compiler, which then schedules the whole kernel differently. Binary tools such as NVBit leave the compiled code alone but call out to a probe function, and saving and restoring registers around every call is too slow for performance tracing paper §2.3.

GPU 追踪器在运行中的 kernel 内部选定的位置记录时间戳或寄存器值。论文 §2.2 说明了常见做法如何改变它们本想观察的 kernel：在编译前插入探针的工具（IR 层的 Neutrino、借助占位符的 IKET）把探针交给编译器，编译器随之对整个 kernel 做了不同的调度；NVBit 这类二进制工具不动已编译的代码，而是跳出去调用一个探针函数，每次调用前后保存和恢复寄存器的开销太大，无法用于性能追踪 论文 §2.3。

Xtrace's answer, which Olympus reimplements for Hopper, is to put the probe's few instructions straight into the compiled instruction sequence and let them borrow registers that are dead there. The paper calls this splicing, a term it borrows from CPU dynamic instrumentation paper §3. It names three challenges: which registers may be reused (C1, chapter 02), how to resolve the new hazards while keeping the original schedule (C2, chapter 03), and how to keep the probe's own waits small (C3, chapters 03 and 04). This chapter is about the ground all three stand on: the instruction words, and how to insert between them without disturbing them.

Xtrace 的做法（Olympus 在 Hopper 上重新实现了它）是把探针的几条指令直接放进已编译的指令序列，并让它们借用在该位置已经死亡的寄存器。论文称之为拼接（splicing），这个词借自 CPU 动态插桩 论文 §3。论文列出三个挑战：哪些寄存器可以复用（C1，第 02 章）；如何在保持原调度的同时解决新产生的冒险（C2，第 03 章）；以及如何让探针自身的等待尽量少（C3，第 03、04 章）。本章讨论三者共同的基础：指令字本身，以及如何在指令之间插入代码而不扰动它们。

Splicing works on NVIDIA GPUs because the schedule is data. The hardware issues in order and, in the words of the paper's appendix, "interlocks neither the register file nor the pipes", so the compiler resolves every hazard ahead of time and writes the result into each instruction paper A.2.1. An inserted instruction can carry its own control bits, and the kernel's own words need not change. Olympus makes that a rule: original instructions are copied, never re-encoded, except for the offset field of a branch whose target moved DECISIONS 5 PLAN.md §2.1.

拼接之所以能在 NVIDIA GPU 上实现，是因为调度就是数据。硬件按序发射，用论文附录的话说，它"既不对寄存器堆、也不对流水线做互锁"，因此编译器提前解决所有冒险，并把结果写进每条指令 论文 A.2.1。插入的指令可以带上自己的控制位，kernel 原有的指令字不必改动。Olympus 把这一点定为规则：原始指令只复制、从不重新编码，唯一的例外是目标地址移动了的分支的偏移字段 DECISIONS 5 PLAN.md §2.1。

§2One instruction, 128 bits一条指令，128 位

Every sm_90 instruction is 16 bytes, so instruction i of a function starts at byte 16·i (Olympus's Instr.pc). cuobjdump prints each word as two 64-bit halves, low half first. The opcode takes bit 91 and bits [11:0]; operand fields sit wherever each encoding class puts them; and the top of the word holds a control block that sits at the same bits in every class instr.py:65–73.

每条 sm_90 指令长 16 字节，因此函数中第 i 条指令从第 16·i 字节开始（即 Olympus 的 Instr.pc）。cuobjdump 把每个指令字打印成两个 64 位半字，低半字在前。操作码占第 91 位和 [11:0] 位；操作数字段的位置由各个编码类决定；指令字顶部是控制块，它在所有编码类中都位于相同的位上 instr.py:65–73。

Two details matter later. The stall is a post-issue gap: an instruction's own stall sets how long until the next instruction of the same warp may issue, which is why a filler that never executes can still carry delay (nvidia-sass-document settles this with a poisoned-register experiment in its usched_latency.md note). And the yield bit has the opposite polarity from the usual folklore: bit 4 set (Wn) means the next instruction is independent and the warp keeps issuing; bit 4 clear (WnEG or DRAIN) ends the group. Olympus's yield_ is usched < 16, so its bracket [wr:rd:{wait}:stall:yield] prints yield 1 for WnEG and DRAIN instr.py:106–130.

有两个细节后面会用到。其一，stall 是发射之后的间隔：一条指令自己的 stall 决定本 warp 的下一条指令要等多久才能发射，所以一条永不执行的填充指令也能携带延迟（nvidia-sass-document 在 usched_latency.md 笔记中用"毒化寄存器"实验确认了这一点）。其二，yield 位的极性和常见说法相反：第 4 位置 1（Wn）表示下一条指令不相关、warp 继续发射；第 4 位为 0（WnEG 或 DRAIN）表示本组结束。Olympus 的 yield_ 定义为 usched < 16，因此它的方括号记法 [wr:rd:{wait}:stall:yield] 在 WnEG 和 DRAIN 时打印 yield 1 instr.py:106–130。

The load's latency is unknown at compile time, so both of its dependences go through scoreboards: SB5 for the result it writes, SB0 for the address it is still reading. Every fixed-latency dependence in the kernel is covered by stall counts alone, and nothing checks at run time that the counts are enough. The paper models exactly these mechanisms paper §4.1: structural hazards and static data hazards cleared by stalls, dynamic data hazards by scoreboards, six per warp. Olympus reads the fields exactly as encoded (DECISIONS 10) and adds three things the model does not need to name: the yield bit, DRAIN (§4 shows why it matters), and the reuse flags, which constrain the usched an instruction may carry.

load 的延迟在编译时未知，所以它的两个依赖都经由记分牌：它写的结果用 SB5，它仍在读的地址用 SB0。kernel 中每个固定延迟的依赖都只靠 stall 计数覆盖，运行时没有任何机制检查这些计数是否足够。论文正是这样建模的 论文 §4.1：结构冒险和静态数据冒险用 stall 消除，动态数据冒险用记分牌消除，每个 warp 六个。Olympus 按编码原样读取这些字段（DECISIONS 10），并补充了三样该模型无需命名的东西：yield 位、DRAIN（§4 说明它为什么重要），以及会限制指令可用 usched 的 reuse 标志。

§3Decoding and re-encoding exactly精确的解码与重编码

Liveness and hazard analysis need every instruction's register reads and writes with their widths, its pipe and its operation sets, so decoding must be complete. Encoding is needed only for probe instructions and for branch offsets PLAN.md M1. Olympus builds both on nvidia-sass-document's sm90.json, a machine-readable dump of the sm_90 encoding tables: 1,589 encoding classes (CLASS and ALTERNATE CLASS) with their fields, bit positions, conditions and operand-size predicates. The paper's Table 2 counts 1,588 instruction forms for sm_90 paper Table 2.

活跃性分析和冒险分析需要知道每条指令读写了哪些寄存器（含宽度）、用哪条流水线、属于哪些操作集合，所以解码必须完整；而编码只在生成探针指令和改写分支偏移时才需要 PLAN.md M1。Olympus 的解码和编码都建立在 nvidia-sass-document 的 sm90.json 之上，这是 sm_90 编码表的机器可读转储：1,589 个编码类（CLASS 与 ALTERNATE CLASS），附带字段、位位置、条件和操作数宽度谓词。论文表 2 给 sm_90 列出的指令形式是 1,588 种 论文表 2。

Each class compiles to a 128-bit (mask, value) of its fixed bits plus a generated extractor for its fields. To decode a word, Olympus takes the classes whose 13-bit opcode matches, keeps those whose fixed bits match and whose fields map back to legal values, and then evaluates every ERROR condition, which is where forms such as Ra == RZ and Ra != RZ separate. A primary class beats an alternate spelling of the same bits, and a tie goes to more fixed bits decode.py:1–11 decode.py:182–205. Encoding runs nvidia-sass-document's own assembler (parser, matcher, encoder) on the sm90 tables, with Olympus's fixes kept in its own subclasses. Every decoded instruction is re-encoded twice, through assembler text and straight from the decoded field values, and both must give back the word byte for byte encode.py:1–20.

每个编码类被编译成一个 128 位的固定位（掩码，取值）对，外加一个自动生成的字段提取器。解码一个指令字时，Olympus 先找出 13 位操作码匹配的类，保留固定位匹配、且各字段都能映射回合法取值的类，再逐条求值所有 ERROR 条件，Ra == RZ 与 Ra != RZ 这类形式就是在这一步分开的。主类优先于同一组位的别名（ALTERNATE），平局时取固定位更多的类 decode.py:1–11 decode.py:182–205。编码则在 sm90 表上运行 nvidia-sass-document 自带的汇编器（解析器、匹配器、编码器），Olympus 的修正放在它自己的子类里。每条解码出的指令都要重编码两次：一次经过汇编文本，一次直接从解码出的字段值打包，两次都必须逐字节还原指令字 encode.py:1–20。

Getting there meant working around defects in the reference tables and assembler, all inside olympus/isa with the library left untouched (DECISIONS 23): enum names containing a dot were dropped by the JSON generator, so every F2F.F64.F32 failed to match; single-register operands had wrong ILABEL sizes; the sm90 assembler port gave URZ sm_120's value 255; a c[bank][URx+off] index was silently dropped; .H0_H0 swizzles on uniform registers were lost; and 32-bit float immediates were converted to fp16 hephaestus.md:38–59.

为此要绕开参考表和汇编器里的若干缺陷，全部在 olympus/isa 内部处理，库本身不改（DECISIONS 23）：名字里带点号的枚举被 JSON 生成器丢掉了，导致所有 F2F.F64.F32 都匹配不上；单寄存器操作数的 ILABEL 宽度有误；sm90 汇编器移植版把 URZ 设成了 sm_120 的取值 255；c[bank][URx+off] 的索引被悄悄丢弃；uniform 寄存器上的 .H0_H0 分量选择丢失；32 位浮点立即数被转换成了 fp16 hephaestus.md:38–59。

A round trip that passes proves less than it seems. Two bugs passed every metric above. WARPSYNC.COLLECTIVE's PC-relative target was classified as a register anchor, so the splicer kept its old absolute target and t2_cutlass_gemm hung DECISIONS 33. And ALU c[bank][off] operands were decoded and encoded four times off in the same way, so the two directions agreed with each other and not with the hardware DECISIONS 36. The lesson recorded there is that a self-consistent encode/decode pair proves nothing about meaning, so every M1-style check now compares against an independent printer or against the hardware:

往返测试通过，证明的东西比看上去少。有两个 bug 通过了上面的全部指标。一是 WARPSYNC.COLLECTIVE 的 PC 相对目标被当成了寄存器锚点，拼接器于是保留了它旧的绝对目标，导致 t2_cutlass_gemm 挂起 DECISIONS 33。二是 ALU 指令的 c[bank][off] 操作数在解码和编码时都以同样的方式差了 4 倍，两个方向彼此一致，却与硬件不一致 DECISIONS 36。那里记下的教训是：自洽的编码/解码对并不能证明语义正确，所以现在每一项 M1 式的检查都要对照一个独立的反汇编器或硬件：

  • A field probe synthesizes one instruction per class (1,380 of the 1,589), has cuobjdump disassemble them inside a donor cubin, and compares every operand: constants 350 / 350, immediates 398 / 398 hephaestus.md:298–310.
  • Zeus 的 m1_audit 从 cuobjdump 打印的十六进制取指令字，而不是用 Olympus 自己的 ELF 读取器；用一个独立的、刻意简单的解析器解析寄存器名；并要求每个解码出的直接分支目标都等于 cuobjdump 打印的绝对目标：语料库上 725 / 725（BRA 656、BSSY 61、CALL 2、WARPSYNC 6）m1_audit.py:1–9 DECISIONS 35。

Where this departs from the paper与论文的不同之处

The paper says only that its disassembler covers the full instruction set of each of its 19 architectures. Olympus decodes one architecture from a third-party dump and treats that dump as something to audit rather than trust. The defects above are my reason for thinking the audit is not optional for a splicer: a decoder that is wrong about one field's scale still round-trips perfectly.

论文只说它的反汇编器覆盖了所支持的 19 种架构各自的完整指令集。Olympus 只针对一种架构，从第三方转储解码，并把这份转储当作需要审计而非直接信任的东西。上面那些缺陷让我认为，对拼接器来说审计不是可选项：一个把某个字段的比例弄错了的解码器，往返测试照样完美通过。

§4Islands: room in front of an instructionIsland：在指令前腾出位置

An island is a run of words inserted in front of one original instruction. The planner of chapters 02–04 decides what goes into it; the rewriter needs only the island's position and its words, which it inserts verbatim, control bits included islands.py:145–153. The meaning of a position is fixed in DECISIONS 10: a site at index i runs before instruction i on every path that reaches i, including branches to i, and it fires whether or not i's own guard passes DECISIONS 10. The paper says the same more briefly: given the insertion address, the probe is inserted ahead of it paper Figure 8.

The paper says the instructions Xtrace changes are branches whose targets must shift paper §5.3; its text does not go into return literals, jump tables, EIATTRs or debug frames. Olympus follows the principle and, as I read the record, had to extend it to every one of those, because each was found broken in some tool's output first: the return literal and the indirect-branch attribute in G-Watch's images, the WARPSYNC.COLLECTIVE target in Olympus's own.

§6Binary similarity against G-Watch对照 G-Watch 的二进制相似度

Splicing claims to leave the kernel alone, and the paper turns that into a metric paper §5.3. Align the probed and unprobed instruction sequences. A basic block is changed when any of its original instructions is altered, dropped or moved into another block; inserted instructions don't count against it. An instruction is changed when its operands, control bits or position within its block differ. Preservation is the share of original instructions left unchanged. PLAN.md adopts this as criterion A2: 0 changed blocks, at least 94% preserved, and every changed instruction a branch whose target moved, judged on T1–T4 with the T0 micro-kernels reported only PLAN.md §1.4 DECISIONS 48.

拼接号称不扰动 kernel，论文把这一点变成了一个指标 论文 §5.3：把插桩后和未插桩的指令序列对齐；只要某个基本块的原始指令有任何一条被修改、删除或移到了别的块，这个块就算改变了，插入的指令不计入；一条指令的操作数、控制位或在块内的位置有任何不同，就算改变了；保留率是未改变的原始指令所占的比例。PLAN.md 把它采纳为验收标准 A2：改变的块为 0，保留率至少 94%，并且每条改变的指令都是目标移动了的分支；在 T1–T4 上评判，T0 微型 kernel 只报告不评判 PLAN.md §1.4 DECISIONS 48。

Olympus's own FA-3 kernel, a different build of 2,696 instructions, keeps 98.32%, 97.47% and 95.98% under trace-sche, trace-pp and trace-mem, with 0 changed blocks each time.

作为对照，论文报告 Xtrace 没有改变的块、保留率 94–98%，而重新编译类工具改写了 54–92% 的指令；在论文的 FA-3 案例中，2,432 条原始指令里有 85 条改变，全部是分支。Olympus 语料中的 FA-3 kernel 是另一个构建（2,696 条指令），在 trace-sche、trace-pp、trace-mem 下分别保留 98.32%、97.47% 和 95.98%，每次都没有改变的块。

Reading the G-Watch numbers如何理解 G-Watch 的数字

The paper names G-Watch's pip package as Xtrace's public release, yet the 0.0.35 build measured here has changed blocks in every judged case × set. My reading is that its splicer adds conservative waits beside each probe that an exact hazard search would not need; that 79% of them wait on nothing fits this. Whether the paper's numbers came from a different build, this page cannot tell.

论文称 G-Watch 的 pip 包就是 Xtrace 的公开版本，但这里测量的 0.0.35 版本在每一个被评判的 case × set 上都有改变的块。我的理解是，它的拼接器在每个探针旁边都加上了保守的等待，而精确的冒险搜索并不需要这些等待；其中 79% 什么也没等到，与这一解释相符。论文的数字是否来自另一个构建，本页无法判断。
