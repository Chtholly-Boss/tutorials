Hazards and the splicing search冒险与拼接搜索

A probe spliced after ptxas must set its own control bits: every stall, every scoreboard it claims, every wait. This chapter covers the sm_90 hazard model Olympus checks them against, five scoreboard rules it learned on the GPU, and three planners in turn: a fenced template, an exact list scheduler, and Xtrace's Algorithm 1, which searches instruction orders, register partitions and scoreboard choices under a fixed work budget.

在 ptxas 之后拼接进去的探针，必须自己决定控制位：每一个 stall、它占用的每一个 scoreboard、每一次等待。本章讲 Olympus 用来检验这些控制位的 sm_90 冒险模型，讲它在 GPU 上碰壁后总结出的五条 scoreboard 规则，再依次讲三代规划器：全围栏模板、精确的列表调度器，以及 Xtrace 的 Algorithm 1——在固定工作量预算内，对指令顺序、寄存器划分和 scoreboard 选择做联合搜索。

§1The hazard model冒险模型

The paper's model starts from how a GPU core issues: in order, one warp instruction at a time, with every hazard already resolved by the compiler and baked into each instruction's control bits paper §4.1. A spliced probe inherits that contract. Nothing downstream will fix a stall that is one cycle short, so Olympus needs a model of every hazard its probe instructions can create or meet. Chapter 01 introduced the control word; here it is in use.

论文的模型从 GPU 核心如何发射指令讲起：按顺序发射，每次一条 warp 指令，所有冒险都由编译器事先解决，并写进每条指令的控制位 论文 §4.1。拼接进去的探针也要遵守这个约定。后面没有任何环节会替你补上一个少了一个周期的 stall，所以 Olympus 需要一个模型，覆盖探针指令可能制造或遇到的每一种冒险。控制字在第 01 章介绍过，这里看它怎么用。

UTMACMDFLUSH ;[7wr:0rd:{}wait:2stall:0yield]
  • stall (1–15): the cycles before the warp may issue its next instruction. The provable delay between two instructions is the sum of max(stall, 1) over the instructions between them. Stall 0 means DRAIN, which empties the warp's pipeline first (§2.4).
  • yield: 1 lets other warps issue during the stall (ptxas's WnEG); 0 keeps this warp issuing (transN). Olympus issues stalls of 1–2 as transN and longer ones as WnEG, as ptxas does.
  • wr / rd (0–5, 7 = none): the scoreboard this instruction claims. A write claim is released when a variable-latency result lands. A read claim is released when the instruction has read its source registers, which stores and memory ops do after issue.
  • wait: a mask over the warp's six scoreboards SB0–SB5. The instruction does not issue until every claim on them has been released.
  • stall（1–15）：warp 发射下一条指令之前要等的周期数。两条指令之间的可证明延迟，是二者之间每条指令 max(stall, 1) 之和。stall 为 0 表示 DRAIN，即先把 warp 的流水线排空（§2.4）。
  • yield：为 1 时，stall 期间允许其他 warp 发射（ptxas 的 WnEG）；为 0 时本 warp 继续发射（transN）。和 ptxas 一样，Olympus 把 1–2 周期的 stall 发成 transN，更长的发成 WnEG。
  • wr / rd（0–5，7 表示无）：这条指令占用的 scoreboard。写占用在可变延迟的结果写回时释放；读占用在指令读完源寄存器时释放，store 和访存指令是在发射之后才读源寄存器的。
  • wait：对 warp 六个 scoreboard（SB0–SB5）的掩码。它们上面的所有占用都释放之前，这条指令不会发射。

The upstream parser has two known bugs (MIO_SLOW_OPS parses empty; GMMA_SB swallows a table body). They cannot occur in Olympus's parser, which cuts table bodies out before any set is read tables.py:1–27.

The model had to pass one self-check before a probe could trust it: accept every ptxas-scheduled kernel. On a calibration set of 957 other kernels (521,880 instructions), it found 0 scoreboard or WGMMA violations. On the 19 corpus kernels, ptxas places 7,245 fixed-latency pairs closer than the table allows. Every one falls into 90 table cells with a known mechanism: back-to-back FMA-pipe issue against FMAI occupancy [2] (4,542 pairs), integer forwarding (1,226), late operand reads by memory and branch ops (1,118), the instruction after a blocking BAR.SYNC (183), and three smaller ones. §2Five scoreboard rules, learned on the GPU在 GPU 上学到的五条 scoreboard 规则

The paper resolves a probe's hazards with the same tables, attaches a scoreboard to each dynamic dependency from the free set, and reclaims a busy one by an early wait when none is free paper §4.4. §5.4.3 then counts the dependency waits each tool's probes add, and shows Xtrace keeping only the unavoidable RAW wait paper §5.4.3. Olympus implements the first part and holds itself to the second. Along the way it ran into five situations the paper does not discuss. Each became a rule, backed by a reproducer or a scan of ptxas output.

论文用同一套表解决探针的冒险：从空闲的 scoreboard 里为每个动态依赖分配一个；没有空闲的时候，就提前等待一个忙碌的 scoreboard，把它回收过来 论文 §4.4。§5.4.3 接着统计各工具的探针额外引入了多少依赖等待，并说明 Xtrace 只保留不可避免的 RAW 等待 论文 §5.4.3。Olympus 实现了前者，也用后者要求自己。这一路上它遇到了五种论文没有讨论的情况，每一种都成了一条规则，背后有一个复现用例，或者一次对 ptxas 输出的扫描。

TABLE_TRUE(SCOREBOARD) says ORDERED_ZERO, so the table allowed it. But a wait issued one cycle after the claim does not see the claim yet. LOP3 read a stale R7, and the S2R result landed after it, without the valid bit. ptxas never does this. Over 976 kernels (the corpus plus the M1 extra set), the provable distance from a scoreboard setter to the first instruction that waits on it is never 1, against 5,314 write claims and 1,416 read claims waited on at distance 2. The only distance-1 cases follow a DRAIN USETMAXREG, which waits for everything anyway. So SB_SET_GAP = 2. TABLE_TRUE(SCOREBOARD) 写的是 ORDERED_ZERO，所以按表是允许的。但在占用登记之后一个周期发出的等待，还看不到这个占用。于是 LOP3 读到了旧的 R7，而 S2R 的结果在它之后才写回，没有带上有效位。ptxas 从不这样做：在 976 个 kernel（语料库加上 M1 的额外集合）里，从 scoreboard 的设置者到第一条等待它的指令，可证明距离从来没有等于 1 的；而在距离 2 处被等待的写占用有 5,314 个、读占用有 1,416 个。仅有的距离为 1 的情况都跟在一条 DRAIN 的 USETMAXREG 之后，而它本来就会等待一切。所以 SB_SET_GAP = 2。调度器对 island 前紧邻的 kernel 自身设置者同样执行这条规则，verify_and_repair 和重写器则把它作为 SB-SET 检查 schedule.py:67–74 schedule.py:338–369 DECISIONS 62。M4 的围栏模板也有同样的 bug，只是轻一些：它的全等待放在第一条前导 NOP 上，恰好在一条 stall 为 1 的 kernel 占用之后一个周期 DECISIONS 65。

2 · Never wait on a scoreboard only the kernel claims2 · 不等待只被 kernel 占用的 scoreboard

On DeepGEMM k512, G-Watch's traces and Olympus's M4 traces agreed that the B-scale load plus its 256-thread barrier took about 1.2 µs per tile, against about 0.3 µs in the source-level measurements. Two independent tools agreeing looked like evidence. Ares showed it was one shared artifact ares.md:278–325. Both probes at c.tile_done wait on SB0: G-Watch's UIADD3.64 has wait {0,2}, and M4's fence waits on all six. SB0 is the TMA store group from the listing above, which the kernel waits on only one tile later. The leader warps therefore held at c.tile_done until the TMA unit had read the tile out of shared memory, then arrived last at the next tile's barrier.

在 DeepGEMM k512 上，G-Watch 的 trace 和 Olympus M4 的 trace 一致认为：B-scale 加载加上 256 线程的 barrier，每个 tile 要花约 1.2 µs，而源码级测量只有约 0.3 µs。两个独立工具的结论一致，看上去像是证据。Ares 证明这其实是同一个假象 ares.md:278–325：两者在 c.tile_done 的探针都在等待 SB0——G-Watch 的 UIADD3.64 等待掩码是 {0,2}，M4 的围栏等待全部六个。SB0 就是上面那段指令里的 TMA store group，kernel 自己要到一个 tile 之后才等待它。于是主导 warp 被卡在 c.tile_done，直到 TMA 单元把 tile 从共享内存读完，然后在下一个 tile 的 barrier 上最后一个到达。

The experiment isolates it: splice a single NOP ;[7:7:{0}:1:0] before c.tile_done into the uninstrumented kernel. k512 slows by +18.38% [+18.25, +18.61] (30.46 → 36.06 µs), and k2048 by +5.27%. The same NOP without the wait costs −0.32%. That is 0.8–0.9 µs per tile boundary, and it accounts for 18.4 of G-Watch's 27.3 points of trace-pp overhead on k512. Pick "NOP waiting SB0" in the simulator above to see the mechanism.

实验把它单独剥离了出来：在未插桩的 kernel 里，只在 c.tile_done 前拼接一条 NOP ;[7:7:{0}:1:0]。k512 慢了 +18.38% [+18.25, +18.61]（30.46 → 36.06 µs），k2048 慢了 +5.27%；同一条 NOP 去掉等待，开销是 −0.32%。折合每个 tile 边界 0.8–0.9 µs，也占了 G-Watch 在 k512 上 27.3 个百分点 trace-pp 开销中的 18.4 个。在上面的模拟器里选 “等待 SB0 的 NOP”，就能看到这个机制。

The rule (DECISIONS 61): a probe waits only on scoreboards its own instructions claimed, and on a kernel scoreboard only for a register it reads or writes that the kernel has pending there. Stall 0 is not a short stall. It is DRAIN, which empties the warp's pipeline before the next issue, about 34 cycles in nvidia-sass-document's measurements. 5 · The EXIT rules5 · EXIT 规则

Every probe claim is released inside its island, so no probe state outlives it. That fails at one kind of site: t2_cutlass_gemm's consumer @P0 EXIT, where all six scoreboards are claimed (unwaited loads, TMA store groups, STSM sources). There the EXIT calibration could not be placed at all, so the whole plan failed. ptxas shows what is safe. Over the same 976 kernels it leaves 306 read claims unwaited at an EXIT, and 1,864 of the 2,460 stores before an EXIT set no read scoreboard at all. Three rules follow apollo-m6.md:39–69 DECISIONS 67:

探针的每个占用都要在自己的 island 里释放，这样探针的状态就不会活过 island。但有一种插入点做不到：t2_cutlass_gemm 消费者的 @P0 EXIT，那里六个 scoreboard 全被占用（没等的加载、TMA store group、STSM 的源寄存器）。EXIT 校准在那里根本放不下，整个计划因此失败。ptxas 告诉了我们什么是安全的：在同样的 976 个 kernel 里，它有 306 个读占用在 EXIT 处都没有等待；EXIT 之前的 2,460 条 store 中，有 1,864 条根本不设置读 scoreboard。由此得出三条规则 apollo-m6.md:39–69 DECISIONS 67：

  1. Tail island. Right before an unconditional EXIT with no free scoreboard, a store's read claim may ride a kernel-busy scoreboard and is never waited on. Nothing of the kernel runs after it.
  2. Predicated EXIT. Before @P EXIT, the island's stores are guarded by the EXIT's predicate too. PLOP3.LUT Pk, PT, Pk, P0, PT, 0x80, 0x0 folds it into the elect predicate. Only lanes about to exit store, and registers are per lane, so nothing any lane runs later overwrites the storing lane's sources schedule.py:301–326.
  3. Only the last island at an EXIT index may leave a claim to the EXIT. An earlier island there is followed by probe code that may reuse the same dead temporaries.
  1. 尾部 island。紧挨在无条件 EXIT 之前、又没有空闲 scoreboard 时，store 的读占用可以搭在一个 kernel 正在使用的 scoreboard 上，并且永远不去等它：之后不再有 kernel 代码运行。
  2. 带谓词的 EXIT。在 @P EXIT 之前，island 里的 store 同样由 EXIT 的谓词保护，用 PLOP3.LUT Pk, PT, Pk, P0, PT, 0x80, 0x0 把它并入 elect 谓词。只有即将退出的 lane 才执行 store，而寄存器是每个 lane 私有的，所以之后任何 lane 执行的代码都不会覆盖正在 store 的那个 lane 的源寄存器 schedule.py:301–326。
  3. 只有同一 EXIT 位置上的最后一个 island，才可以把占用留给 EXIT。之前的 island 后面还跟着探针代码，可能会重用同样的死临时寄存器。

有三处值得看。在 c.tile_done，全部 150 个顺序的开销在 28 到 39 之间；根节点下界是 28，M5 已经在那里，所以最优阶段一个 DFS 节点都还没展开，最优性就已得到证明。在 SYNCS.EXCH.64，起决定作用的是 D1：模板共享 R0，它的 1,612 个顺序没有一个能低于 46；而最细的分配有 14,260 个顺序，其中 60 个达到 29。在 softmax 的 LDGSTS，贪心挑出的顺序开销是 42，而最优是 31。这个探针借用了 kernel 仍在使用的谓词 P1 来做 elect（psave 形式），所以 ELECT P1 写的是一个固定寄存器而不是一个值，式 4 看不到它通向 store 的值依赖边，给它定价 0，是整个探针体里最低的。贪心把它排得很晚，于是 13 个周期的 ELECT → @P STG 落在了关键路径上。

The cost model overprices the 32-lane store开销模型高估了 32 lane 的 store

The model prices a noelect island at about 515 cycles against about 30 for its psave twin, because it charges the 32-lane store's 499-cycle p50 release in full. On the GPU the difference was a fraction of a point, and overhead tracked the number of inserted instructions instead (DECISIONS 71). My reading, not measured: the model treats the warp's wait as the kernel's loss, but in memory-bound loops other resident warps issue during that wait, so little of it reaches the kernel's duration. A calibrated correction would need the release weighted by how much of it overlaps other warps' work.

模型给 noelect island 定价约 515 个周期，而对应的 psave 版本只有约 30，因为它把 32 lane store 的 499 周期 p50 释放延迟全额计入。在 GPU 上，二者的差别只有零点几个百分点，开销反而随插入指令的数量变化（DECISIONS 71）。下面是我的理解，没有实测：模型把 warp 的等待当成了 kernel 的损失，但在访存受限的循环里，这段等待期间其他驻留的 warp 仍在发射，真正反映到 kernel 时长上的很少。要校准这个修正，需要按释放期间有多少能被其他 warp 的工作重叠来给它加权。

The coverage gap from rule 3 remains open future work: 10 reviewed sites, and about 1% of fuzz-generated ones, where the kernel holds every scoreboard. Covering them without an early wait on the kernel's operations would take a different mechanism, not a better search.

规则 3 带来的覆盖缺口仍是留待以后的工作：10 个审核过的插入点，以及约 1% 的模糊测试生成的插入点，在那里 kernel 占着全部 scoreboard。要在不提前等待 kernel 操作的前提下覆盖它们，需要的是另一种机制，而不是更好的搜索。
