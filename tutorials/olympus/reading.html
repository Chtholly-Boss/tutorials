Reading a trace读一份追踪

A traced run leaves one file of records. This layer turns it into the thing you read: records become per-warp intervals, intervals become paired regions, and the result is one analysis block, trace.json, that olympus show prints as a header, per-region stats, the bubbles between regions and a timeline. When the cubin carries DWARF line tables, every site also names its source line. The block is complete on its own: nothing you read is re-derived from raw records.

一次追踪运行留下一个记录文件。这一层把它变成你要读的东西：记录变成每个 warp 的区间，区间配对成 region，结果是一个分析块 trace.json，olympus show 把它打印成头部、每个 region 的统计、region 之间的气泡和一条时间线。当 cubin 带有 DWARF 行表时，每个站点还会给出它的源码行。这个块自身是完整的：你读到的任何数字都不是从原始记录重新推导的。

§1Contract契约

What this layer promises这一层的承诺

One analysis block per trace, with each site's source location when the cubin has line tables, printed so that an agent can read where a kernel waits from the text alone.

每份追踪一个分析块，cubin 带行表时附上每个站点的源码位置，并打印成 agent 只凭文本就能读出 kernel 在哪里等待的样子。

olympus/trace · olympus/report → used by使用者 you, or an agent你，或一个 agent · reads读取 olympus/runtime's .olyt 写出的 .olyt

This is the layer the rest of the system exists for. Chapter 07 ended with a run that had earned trust: its outputs were bit-identical to the untraced kernel's, its buffer's guard bands were intact, and it wrote that buffer out as one .olyt file. That file is this layer's input. It is a 64-byte host header — the magic OLYTRACE, a format version, and JSON metadata — followed by the device buffer exactly as it came back, one fixed-size slot per warp record.py:173–183.

系统其余部分都是为这一层存在的。第 07 章以一次已经赢得信任的运行收尾：它的输出与未追踪的 kernel 逐位一致，缓冲区的保护带完好，它把这个缓冲区写成了一个 .olyt 文件。这个文件就是本层的输入。它是一个 64 字节的宿主头部——魔数 OLYTRACE、格式版本和 JSON 元数据——后面紧跟原封不动带回来的设备缓冲区，每个 warp 一个定长槽位 record.py:173–183。

A buffer of 32-bit words is not something a person can act on. The work of this layer is four changes of shape: words become timestamped records, records of one warp become intervals, intervals become named regions with duration distributions, and the whole lot becomes one document. That document is trace.json, schema olympus-trace/1, with two numpy sidecars holding the per-interval and per-row tables analysis.py:1–13.

一缓冲区的 32 位字不是人能据以行动的东西。这一层的工作是四次形变：字变成带时间戳的记录，一个 warp 的记录变成区间，区间变成带时长分布的命名 region，这一切再变成一份文档。这份文档就是 trace.json，schema olympus-trace/1，外加两个保存逐区间表与逐行表的 numpy 附件 analysis.py:1–13。

Deriving everything once is the point, not an optimization. Every number a reader sees — a p50, a pair rate, a bubble's share of the total — is computed in that one place, under one set of definitions, and afterwards only read. A second tool that recomputed percentiles its own way would quietly disagree with the document, and nobody would know which was right.

只推导一次是设计要点，不是优化。读者看到的每个数字——一个 p50、一个配对率、一个气泡占总量的比例——都在那一处、按同一套定义算出，此后只被读取。另一个工具若自己重算百分位，会悄悄地与这份文档不一致，而没人知道哪个是对的。

§2Invariant不变量

Invariant不变量6

Every result carries its provenance. A trace names the binary it came from, the sites file and its sha256, the run record, and the cubin whose line table gave each source location; and every number in a view is the analysis block's, computed under one set of definitions.

每个结果都带着来源。一份追踪写明它来自哪个二进制、哪份站点文件及其 sha256、运行记录，以及给出每个源码位置的那个 cubin 的行表；视图中的每个数字都来自分析块，按同一套定义计算。

Checked by analysis.validate on every block it writes analysis.py:677–683, show.self_check, which recomputes the whole run through the filter path and lists any number that differs show.py:906–958, and olympus provenance --require on evidence runs.

检查方式：analysis.validate 检查它写出的每个块 analysis.py:677–683；show.self_check 把整次运行从过滤路径重算一遍，列出任何不一致的数字 show.py:906–958；证据运行还要过 olympus provenance --require。

The reading layer protects no byte of the kernel. Chapters 02, 03 and 06 did that; this layer's invariant is about trusting what it prints. Trust here has two halves. The first is that a trace says where it came from: the source block of trace.json names the tool, the corpus case, the site set, the sites file and its sha256, and — when the sites file's pinned cubin carries a DWARF line table — that cubin and its sha256 too, with a status word saying whether the line table was usable analysis.py:14–22. A number without that provenance cannot be re-checked, and a number that cannot be re-checked is not evidence.

阅读层不保护 kernel 的任何一个字节。那是第 02、03、06 章的事；这一层的不变量关乎对它所打印内容的信任。这里的信任有两半。第一半是一份追踪要写明它来自哪里：trace.json 的 source 块写出工具、语料库案例、站点集合、站点文件及其 sha256，并且当站点文件所钉住的 cubin 带有 DWARF 行表时，还写出那个 cubin 及其 sha256，再加一个状态词说明行表是否可用 analysis.py:14–22。没有这份来源的数字无法复核，而无法复核的数字不是证据。

The second half is that every view agrees with the document. A filtered view — --block 0-3, --stime 5us, --select — is not a different analysis; it is recomputed from the same two sidecars using the analysis block's own definitions: stats from the intervals of the selected rows that overlap the window, bubbles computed on each row's full timeline and only then clipped to the window. Counts that cannot be recovered from the sidecars, because they need raw records — the pair rate, the unclosed starts — are shown only unfiltered, and come back as null in a filtered --json rather than as a plausible wrong number show.py:35–41.

第二半是每个视图都与这份文档一致。过滤后的视图——--block 0-3、--stime 5us、--select——不是另一次分析；它从同样的两个附件出发，按分析块自己的定义重算：统计取选中行里与窗口重叠的区间，气泡在每行完整的时间线上算好、之后才裁到窗口。那些无法从附件恢复、因为需要原始记录的计数——配对率、未闭合的起点——只在未过滤时显示，在过滤后的 --json 中返回 null，而不是一个看上去合理的错数 show.py:35–41。

§3How it works如何工作

Stage 1: from a slot of words to a table of records第一阶段：从一槽字到一张记录表

The buffer that comes back is not a list of events. It is a fixed-size slot per warp, written without any coordination between warps: no warp knows how many records another wrote, and a warp whose block never launched wrote nothing at all. So the decoder's first job is to find out, slot by slot, what is actually there.

带回来的缓冲区不是一串事件。它是每个 warp 一个定长槽位，各 warp 之间毫无协调地写入：没有 warp 知道别的 warp 写了多少条记录，而 block 从未启动的 warp 什么也没写。所以解码器的第一件事，是逐槽查明里面究竟有什么。

Chapter 04 gave the slot its layout, and the sizes are worth restating because every step below is arithmetic on them. A slot is a 32-byte header followed by a ring of ring_depth records, padded up to a multiple of 32 bytes. With the default layout — warp granularity, six id bits, no value words — a record is one 32-bit word, so the trace-pp set of the DeepGEMM kernel in §5, traced with a ring of 256, gives each warp a slot of 32 + 256 × 4 = 1,056 bytes record.py:1–26.

第 04 章给出了槽位的布局，这里值得把尺寸重述一遍，因为下面每一步都是在这些尺寸上做算术。一个槽位是 32 字节头部加一个深度为 ring_depth 的环，整体补齐到 32 字节的倍数。在默认布局下——warp 粒度、6 个 id 位、没有值字——一条记录就是一个 32 位字，所以 §5 里那个 DeepGEMM kernel 的 trace-pp 集合用深度 256 的环追踪时，每个 warp 的槽位是 32 + 256 × 4 = 1,056 字节 record.py:1–26。

Two header fields answer "what is there". Bit 31 of the smid word at offset +12 is set by the INIT probe and by nothing else, so a slot whose bit 31 is clear is a warp that never ran, and the decoder skips it rather than reading 256 words of zeros as records. The n_records counter at +28 holds every record the warp tried to write, and it only ever increases, so it is also the test for overflow.

头部有两个字段回答“里面有什么”。偏移 +12 的 smid 字的第 31 位只由 INIT 探针置位，别无其他，所以第 31 位为 0 的槽位就是一个从未运行的 warp，解码器跳过它，而不是把 256 个零字当成记录来读。偏移 +28 的 n_records 计数器保存这个 warp 试图写下的全部记录数，并且只增不减，所以它同时也是溢出的判据。

Overflow is where the ring matters. Only kept = min(n_records, ring_depth) records survive; if n_records is larger than the depth, the warp wrapped and overwrote its own oldest records. The decoder then reads forward from first = n_records % ring_depth, the position of the oldest record still alive, wrapping modulo the depth. A wrapped slot therefore keeps the end of the warp's history, not a random sample of it — which is the useful half when a kernel ran out of budget — and the trace model adds an issue naming the slots that wrapped, so the reader is never left to infer it record.py:127–162.

环的意义正在溢出之处。只有 kept = min(n_records, ring_depth) 条记录存活；若 n_records 大于环深，这个 warp 绕回并覆盖了自己最早的记录。此时解码器从 first = n_records % ring_depth（仍存活的最早一条记录的位置）开始向前读，按环深取模绕回。所以绕回的槽位保留的是这个 warp 历史的末段，而不是随机的一段——当 kernel 的预算用尽时，末段正是有用的那一半——而且追踪模型会加上一条 issue，点名哪些槽位绕回了，读者永远不必自己猜 record.py:127–162。

Within a slot, the records are already in the order the warp wrote them. One warp issues in program order and the ring is a plain cursor, so record k of a slot happened before record k+1 of the same slot, and the decoder never sorts inside a slot. That is the only ordering the hardware gives for free; between slots there is none, which is the reason the next stage stays inside one warp.

在一个槽位内部，记录已经按这个 warp 写下的顺序排好。一个 warp 按程序顺序发射，环只是一个游标，所以同一槽位的第 k 条记录发生在第 k+1 条之前，解码器在槽位内部从不排序。这是硬件唯一免费给出的顺序；槽位之间没有任何顺序，这正是下一阶段必须留在一个 warp 之内的原因。

What each word does not give is a usable time. The word is (clk << id_bits) | (site_id + 1), so with six id bits only 26 bits of the SM clock survive, and 226 cycles is 33.9 ms at H200's 1.98 GHz — long enough for any one kernel, short enough that the counter can roll over inside a slow one. Unwrapping walks the slot backwards from clk_end, the clock the exit probe read next to its globaltimer: each step adds the modular difference to the record after it, which over a whole slot is one reversed cumulative sum of 26-bit deltas. When the exit calibration is missing — gt_end is zero because the warp never reached its exit site — the walk runs forwards from clk_start instead decode.py:65–83.

每个字没有给出的，是一个可用的时间。这个字是 (clk << id_bits) | (site_id + 1)，所以在 6 个 id 位下只有 26 位 SM 时钟存活，而 226 个周期在 H200 的 1.98 GHz 下是 33.9 ms——对任一个 kernel 都够长，但又短到计数器可能在一个慢 kernel 内部翻转。展开的办法是从 clk_end（退出探针紧挨着它的 globaltimer 读到的那个时钟）向后走遍整个槽位：每一步把与后一条记录的模差加上去，整槽合起来就是一次对 26 位差值的反向累加和。当退出校准缺失时——gt_end 为零，因为这个 warp 从未到达它的退出站点——这趟行走改为从 clk_start 向前 decode.py:65–83。

Cycles become nanoseconds from the slot's own two clock anchors: (gt_start, clk_start) written by INIT and (gt_end, clk_end) written at the exit. Their ratio is that warp's rate, so no clock frequency is assumed anywhere and an SM clocked differently from its neighbour is still read correctly. The arithmetic is kept in integers, because a float cannot hold a globaltimer value of order 1018 ns to better than 256 ns:

周期靠槽位自己的两个 clock anchor 换成纳秒：INIT 写下的 (gt_start, clk_start) 和退出处写下的 (gt_end, clk_end)。两者之比就是这个 warp 的速率，所以任何地方都不假设时钟频率，一个与邻居频率不同的 SM 仍被正确读出。运算全程用整数，因为浮点数无法把量级为 1018 ns 的 globaltimer 值表示到优于 256 ns：

span_clk = clk_end - clk_start          # this warp's cycles
span_ns  = gt_end  - gt_start           # the same stretch in ns
ns       = gt_start + ((clk - clk_start) * span_ns + span_clk // 2) // span_clk

A slot with no usable pair of anchors cannot be calibrated at all. Rather than drop it, the model places it at the median nanoseconds-per-cycle rate of the calibrated slots of the same file, and appends an issue saying how many records that was model.py:217–223. The same guard catches nonsense: a record more than 10 s away from its launch's median timestamp is dropped as garbage, counted in an issue, and each launch's remaining records fix its origin — the earliest timestamp — so every time printed afterwards is relative to its own launch model.py:141–170.

完全没有可用锚点对的槽位无法校准。模型不丢弃它，而是按同一文件中校准成功的那些槽位的中位“每周期纳秒数”速率安置它，并附上一条 issue 说明这样的记录有多少 model.py:217–223。同一道防线也拦住明显的胡话：距离所属 launch 的中位时间戳超过 10 s 的记录被当作垃圾丢掉并计入 issue；每个 launch 剩下的记录确定它的 origin（最早的时间戳），此后打印的每个时间都相对于它自己的 launch model.py:141–170。

The shape at the end of this stage is a columnar table: eight arrays of equal length, one entry each per record, holding its launch, its row, its block, its warp, its SM, its site id, its timestamp in nanoseconds, and its value where the site recorded one. A "row" is a warp for a warp-granularity trace and a thread for a per-thread one, and it is the unit every later stage groups by model.py:1–18.

这一阶段结束时的形状是一张列式表：八个等长数组，每条记录各占一项，保存它的 launch、行、block、warp、SM、站点 id、以纳秒计的时间戳，以及站点记录了值时的那个值。“行”在 warp 粒度的追踪里是一个 warp，在逐线程的追踪里是一个线程，它是之后每一阶段的分组单位 model.py:1–18。

Stage 2: from records to regions, one warp at a time第二阶段：从记录到 region，一次一个 warp

A timestamp on its own says nothing. "The kernel waited 2 µs" is only a claim once two named points bracket the wait. That bracket is a region: a name, a set of start site ids and a set of end site ids. Any record of a start site opens an interval and any record of an end site closes one; the interval's duration is the difference of the two timestamps. The sets are sets rather than single sites because a warp can leave through any of several EXIT instructions, and a stage can be reached from more than one place.

一个时间戳本身什么也没说。“kernel 等了 2 µs”只有在两个有名字的点把这次等待夹起来之后才成为一个论断。这个夹子就是 region：一个名字、一组起始站点 id 和一组结束站点 id。任一起始站点的记录打开一个区间，任一结束站点的记录关上一个；区间的时长是两个时间戳之差。之所以是两组而不是两个站点，是因为一个 warp 可以从若干条 EXIT 指令中的任一条离开，一个阶段也可能从不止一处到达。

The words "within one warp" in that definition are not a simplification; pairing across warps would be wrong three times over. The buffer is per-warp, so records of two warps sit in different slots and nothing orders them against each other. The clock in a record is its SM's clock, and two SMs' clocks are two different counters with no fixed offset. And calibration is per slot, so each warp's nanoseconds come from its own pair of anchors. Subtracting a start on one warp from an end on another would subtract two numbers that were never on the same scale. Every interval Olympus reports lives inside one row, and a question about two warps is answered by comparing their intervals, never by pairing across them.

定义里“在一个 warp 之内”这几个字不是简化；跨 warp 配对会在三个层面上出错。缓冲区是按 warp 分的，两个 warp 的记录在不同槽位里，彼此之间没有任何顺序。记录里的时钟是它所在 SM 的时钟，两个 SM 的时钟是两个不同的计数器，之间没有固定偏移。而校准是按槽位做的，每个 warp 的纳秒来自它自己的那对锚点。把一个 warp 上的起点和另一个 warp 上的终点相减，等于相减两个从来不在同一标尺上的数。Olympus 报告的每个区间都活在一行之内；关于两个 warp 的问题靠比较它们各自的区间来回答，绝不靠跨 warp 配对。

close says which end record closes an open interval. close: first, the default, closes at the first one, which is what a wait or a stage wants. close: last keeps moving the pending close to each later end record, committing it only at the region's next start or at the end of the row. That exists for a real shape in the SASS: a site placed before a predicated EXIT fires for every warp that passes that instruction, whether or not it is the warp that leaves there, so a warp's lifetime ends at its last exit record, not its first ir.py:47–66.

close 决定哪条结束记录关闭一个打开的区间。默认的 close: first 在第一条处关闭，这是等待或阶段所需要的。close: last 把待定的关闭点一路挪到后面每一条结束记录上，只在该 region 的下一次开始处、或一行结束时才提交。它的存在对应 SASS 里一个真实的形状：放在带谓词的 EXIT 之前的站点，会在每个经过那条指令的 warp 上触发，无论它是否就是从那里离开的那个 warp，所以一个 warp 的生命期结束于它最后一条退出记录，而非第一条 ir.py:47–66。

open says what a start record does when the region is already open. open: last, the default, opens a new interval every time, so a run of starts is closed by its latest one. open: first absorbs such a start instead: it is counted in absorbed_starts and opens nothing, so the interval begins at the first start of the run. That is what a polling loop needs. If the start site is the head of a spin loop, open: last would time the last iteration — a few nanoseconds — while the question asked was how long the spin lasted (DECISIONS 40).

open 决定当 region 已经打开时，一条起始记录该做什么。默认的 open: last 每次都打开一个新区间，于是一串起点由其中最晚的那个关闭。open: first 则吸收这样的起点：它被计入 absorbed_starts，不打开任何区间，于是区间从这一串的第一个起点开始。轮询循环需要的正是这个。如果起始站点是自旋循环的头部，open: last 会量到最后一次迭代——几纳秒——而人们问的是这次自旋持续了多久（DECISIONS 40）。

Pairing can fail, and the reason nothing nonsensical appears is that a failure produces no interval at all. A start that is never closed is counted in unclosed and contributes nothing: a kernel that exits in the middle of a region loses that region's last run and keeps every earlier one, so a trace of an aborted or budget-limited launch is short, not wrong. An end with nothing open is counted in orphan_ends and changes nothing. Every one of these counts is published beside the durations, together with a pair_rate that divides intervals by the starts that actually opened, so a reader can see that a region paired 100.0% of the time rather than assume it pairing.py:50–79.

配对可能失败，而之所以不会出现荒谬的结果，是因为一次失败根本不产生区间。永远没有被关闭的起点计入 unclosed，什么也不贡献：在某个 region 中途退出的 kernel 丢掉这个 region 的最后一轮，保留之前的每一轮，所以一次中止或受预算限制的 launch 的追踪是短，而不是错。没有任何打开区间可关的终点计入 orphan_ends，什么也不改变。这些计数全都与时长一同发布，还带一个 pair_rate——用区间数除以真正打开过的起点数——于是读者能看到某个 region 的配对率是 100.0%，而不是去假定它 pairing.py:50–79。

Two implementations compute the same thing. pair_reference is the original per-row Python loop, kept verbatim as the executable spec, so the rules above have exactly one authority. pair_arrays computes identical intervals and counts with numpy, for millions of records at a time: with close: first the problem is bracket matching, solved by a prefix sum of ±1 clamped at zero, which lets each start be sorted directly in front of the end that closes it. A test runs both on random sequences and requires them to agree pairing.py:1–20.

两套实现算出同一件事。pair_reference 是最初那个逐行的 Python 循环，原样保留为可执行的规范，于是上面这些规则只有一个权威。pair_arrays 用 numpy 算出完全相同的区间和计数，一次可处理数百万条记录：在 close: first 下问题就是括号匹配，解法是一个在零处截断的 ±1 前缀和，它让每个起点可以直接排到关闭它的那个终点前面。一个测试在随机序列上跑两者并要求一致 pairing.py:1–20。

The shape now is one row per interval: launch, row, block, warp, SM, region, start time, end time, start site, end site. One more column is computed over it, and it is what makes the rest of the chapter possible. A leaf is an interval that contains no other positive-length interval of the same row. Regions nest on purpose — a warp region spanning a whole lifetime, a tile region spanning one iteration, a wait inside it — and only the innermost ones are leaves, found by sweeping each row's intervals by decreasing start time and asking whether anything seen earlier in the sweep ends no later analysis.py:123–147.

现在的形状是每个区间一行：launch、行、block、warp、SM、region、起始时间、结束时间、起始站点、结束站点。在它之上还算出一列，正是它让本章其余部分成为可能。叶子是不包含同一行中任何其他正长度区间的区间。region 是故意嵌套的——一个 warp region 跨越整个生命期，一个 tile region 跨越一次迭代，里面还有一次等待——只有最内层的才是叶子；找法是把每行的区间按起始时间递减扫一遍，问扫描中更早见到的区间里有没有哪个结束得不更晚 analysis.py:123–147。

Three quantities follow from the leaves, and they are the ones every later view is built on. A row's lifetime is the hull of all its intervals, from its earliest start to its latest end. Its active time is the union of its leaf intervals — a union, so overlapping leaves are not double-counted. A bubble is a stretch of the lifetime that is not active: a gap between two consecutive blocks of leaf intervals, during which the warp was inside no innermost region at all. Doing this with leaves rather than all intervals is what stops an envelope region from hiding the gaps inside it; a warp region covers the whole lifetime, so if it counted as active there would be no bubbles anywhere analysis.py:148–175.

叶子推出三个量，后面每个视图都建立在它们之上。一行的生命期是它所有区间的凸包，从最早的起点到最晚的终点。它的活跃时间是其叶子区间的并集——是并集，所以重叠的叶子不被重复计数。气泡是生命期中不活跃的一段：两段连续叶子区间块之间的空隙，在这段时间里这个 warp 根本不在任何最内层 region 之内。用叶子而不是用全部区间来做这件事，正是包络 region 藏不住内部空隙的原因；warp region 覆盖整个生命期，若它算作活跃，任何地方都不会有气泡 analysis.py:148–175。

Stage 3: trace.json, and why the .olyt names its sites file第三阶段：trace.json，以及 .olyt 为什么写明自己的站点文件

The two files divide the work cleanly. The .olyt is the raw side, and nothing in it is derived: the magic OLYTRACE, a format version word, a metadata length word, UTF-8 JSON metadata, zero padding out to 64 bytes, then the device buffer byte for byte. The metadata is what makes those bytes readable at all — the record layout (granularity, ring depth, value words, id bits), the kernel, the launch geometry, the clock's name, the run record — because without the layout a decoder cannot even find the second slot record.py:173–183.

两个文件把工作分得很干净。.olyt 是原始的那一侧，里面没有任何推导出来的东西：魔数 OLYTRACE、一个格式版本字、一个元数据长度字、UTF-8 JSON 元数据、补零至 64 字节，然后是逐字节的设备缓冲区。元数据才是让这些字节可读的东西——记录布局（粒度、环深、值字数、id 位数）、kernel、launch 几何、时钟的名字、运行记录——因为没有布局，解码器连第二个槽位都找不到 record.py:173–183。

The metadata also names the sites file, and that detail is load-bearing. A site id in a record is an index into one list of instruction indices, and instruction indices belong to one build of one kernel. Each architecture builds the kernel differently, so a corpus case keeps one reviewed sites file per arch: sites.yaml for sm_90 and sites.sm103.yaml for the sm_103a builds on GB300 sites/__init__.py:36–45.

元数据还写明了站点文件，这个细节是承重的。记录里的站点 id 是一份指令下标列表中的下标，而指令下标只属于一个 kernel 的一次构建。每种架构构建这个 kernel 的方式不同，所以语料库中的一个案例为每种架构保留一份经过审阅的站点文件：sm_90 用 sites.yaml，GB300 上的 sm_103a 构建用 sites.sm103.yaml sites/__init__.py:36–45。

So the tracer writes the name of the file it used into the .olyt as sites_name, and the analyzer loads that file rather than the one the machine it is running on would pick by default (DECISIONS 82). Without the name, a trace made on GB300 and analyzed on an H200 would be read against sm_90 indices: every site would still decode, every region would still pair, and every label would be attached to the wrong instruction — the worst kind of failure, because nothing in the output would look broken model.py:204–213.

所以追踪器把它实际使用的文件名作为 sites_name 写进 .olyt，分析器加载那个文件，而不是它所运行的机器默认会挑的那个（DECISIONS 82）。没有这个名字，在 GB300 上做的追踪在 H200 上分析时就会按 sm_90 的下标来读：每个站点照样解码，每个 region 照样配对，而每个标签都贴到了错误的指令上——这是最糟的一种失败，因为输出里没有任何地方看起来是坏的 model.py:204–213。

trace.json is the derived side: one JSON document, schema olympus-trace/1, holding source (the provenance of §2), launch and launches, counts, span, then sites with each site's records and source location, regions with each region's duration distribution and pairing counts, roles, activity, bubbles, concurrency, outliers, issues, timing and files. Every distribution in it is the same twelve fields — n, min, p05, p25, p50, p75, p95, p99, max, mean, std, total — and every percentile is nearest-rank: an element of the sorted list, picked by its position, never an interpolation between two neighbours analysis.py:1–13.

trace.json 是推导出来的那一侧：一份 JSON 文档，schema olympus-trace/1，包含 source（§2 里的来源信息）、launch 与 launches、counts、span，然后是带每个站点记录数与源码位置的 sites、带每个 region 时长分布与配对计数的 regions，以及 roles、activity、bubbles、concurrency、outliers、issues、timing 和 files。其中每个分布都是同样的十二个字段——n、min、p05、p25、p50、p75、p95、p99、max、mean、std、total——而每个百分位都用最近秩：按位置从排好序的列表中取出的一个元素，绝不是两个邻居之间的插值 analysis.py:1–13。

What the document does not hold is the intervals and rows themselves; a few million intervals do not belong in JSON. 这份文档不保存的，是区间和行本身；几百万个区间不该放进 JSON。它们进入写在旁边的两个 numpy 附件：intervals.npz，每个区间一项，带它的 launch、行、block、warp、SM、region、起止时间、起止站点和叶子标记；rows.npz，每行一项，带它的角色、记录数、首末记录、凸包和活跃时间 analysis.py:81–84。附件先写，每个的 sha256 记入文档的 files 键，之后才写 trace.json——于是过滤后的视图永远是从文档所描述的那些字节重算的 analysis.py:632–646。

Stage 5: source lines, and why they are hints第五阶段：源码行，以及为什么它们只是提示

A site is an instruction index, and nobody wants to read instruction indices. When the cubin that the sites file pins carries a DWARF line table, the analysis therefore gives each site a source: the file, the line, the column, the inlining chain as nvdisasm -g -gi prints it, and the text of that line. The document also records how that went, with a status of ok, no line info (a DeepGEMM or nvjet JIT cubin has none), no cubin, sha256 mismatch or no sites file — so a missing source line is a reported fact rather than a blank dwarf_line.py:1–11.

站点是一个指令下标，而没人想读指令下标。所以当站点文件所钉住的 cubin 带有 DWARF 行表时，分析会给每个站点一个 source：文件、行号、列号、按 nvdisasm -g -gi 打印方式给出的内联链，以及该行的文本。文档还记下这件事进行得如何，状态可以是 ok、no line info（DeepGEMM 或 nvjet 的 JIT cubin 没有行表）、no cubin、sha256 mismatch 或 no sites file——于是缺失的源码行是一个被报告的事实，而不是一片空白 dwarf_line.py:1–11。

The same line table runs the other way too, and this is how probes actually get placed. A hint names a source location and a pick rule, and resolves to an ordinary index site before anything is launched. start picks the position before the line's first instruction; end the position before the first instruction after its last; op=LDG the first candidate whose opcode is LDG or begins LDG., with nth to take a later match and offset to move the site one instruction past the pick. A hint can also be written as an @olympus comment in source you own. Either way the result is an index site pinned to the cubin's sha256 like any other, and nothing downstream knows a hint was involved hints.py:46–76.

同一张行表也能反向使用，而这正是探针实际被放置的方式。一条提示写明一个源码位置和一条挑选规则，并在任何东西启动之前解析成一个普通的下标站点。start 挑该行第一条指令之前的位置；end 挑其最后一条指令之后第一条指令之前的位置；op=LDG 挑第一个操作码为 LDG 或以 LDG. 开头的候选，nth 用来取后面的匹配，offset 用来把站点移到挑中位置之后一条指令。提示也可以写成你自己源码里的 @olympus 注释。两种写法的结果都是一个与其他站点一样钉在 cubin sha256 上的下标站点，下游没有任何东西知道这里用过提示 hints.py:46–76。

This is the normal workflow, not a shortcut. Nobody counts instruction indices by hand in a 1,504-instruction kernel. You put a hint on the line in the TMA producer warp that acquires the pipeline, another on the line that commits the copy, name the region between them, and read the resolver's report before trusting it.

这是常规流程，不是捷径。没人会在一个 1,504 条指令的 kernel 里用手数指令下标。你在 TMA producer warp 里获取 pipeline 的那一行放一条提示，在提交拷贝的那一行再放一条，给两者之间的 region 起个名字，然后在信任它之前读一读解析器的报告。

And it must be read, because one source line does not become one instruction. ptxas schedules, unrolls and inlines, so a line's instructions scatter across the program. Every resolution therefore prints its candidate set and how scattered it is — the candidate count, the runs of consecutive indices, the span, how many foreign instructions sit inside that span, the basic blocks touched, and the inlined instances. A three-line kernel already shows it USAGE.md:431–442:

而它必须被读，因为一个源码行不会变成一条指令。ptxas 会调度、展开和内联，于是一行的指令散布在整个程序里。所以每次解析都打印它的候选集合和散布程度——候选数、连续下标的段数、跨度、跨度内有多少条不属于这一行的指令、触及的基本块，以及内联的副本。一个三行的 kernel 就已经显出来了 USAGE.md:431–442：

That warning is the honest part. One statement, const float4 u = x[i];, became three instructions in two runs with four unrelated instructions between them. start and end are therefore positions in program order, not points every path through the line must cross, and the resolver says so whenever the line spans more than one run, basic block or inlined instance. Two further refusals follow from the same honesty: end rejects a line whose last instruction does not fall through, because the next index is then not the way out of the line, and a pick at index 0 moves to 1 with a warning, because INIT occupies that position.

那条警告是诚实的那一部分。一条语句 const float4 u = x[i]; 变成了分在两段里的三条指令，中间夹了四条无关指令。所以 start 和 end 是程序顺序上的位置，而不是穿过这一行的每条路径都必经的点；只要这一行跨越多于一段、多于一个基本块或多于一个内联副本，解析器就会这么说。同样的诚实还带来两条拒绝：end 拒绝最后一条指令不顺序落下的行，因为那时下一个下标并不是离开这一行的出路；下标 0 处的挑选会带警告地挪到 1，因为那个位置被 INIT 占着。

Inlining is the second source of scatter, and the default is deliberate: a hint matches any frame of the inlining chain, so a hint on a call site in your own code finds the callee's instructions even though their innermost frame is in a library header. The price is that a hint on a line of an inlined helper finds every inlined copy of it. Candidates are grouped into instances by the call chain outside the matched frame, the instances are reported, and instance: k takes one; match: innermost narrows to the innermost frame only, as nvdisasm -g without -gi would.

内联是散布的第二个来源，而默认行为是有意为之：提示匹配内联链的任一帧，所以放在你自己代码的调用点上的提示能找到被调函数的指令，尽管它们的最内层帧在某个库头文件里。代价是：放在某个被内联辅助函数某一行上的提示，会找到它全部的内联副本。候选按被匹配帧之外的调用链归为若干副本，这些副本会被报告出来，instance: k 取其中一个；match: innermost 把范围收窄到只有最内层帧，如同不带 -gi 的 nvdisasm -g。

  1. The layout. Warp granularity, id_bits = 6, no value words, ring_depth = 256. So a record is 4 bytes, a site id fits in 6 bits (63 sites at most), a clock field keeps 26 bits, and a slot is 32 + 256 × 4 = 1,056 bytes.
  2. The slot. The kernel launches 384 threads per block, so a block is 12 warps. Warp 10 of block 0 is the TMA producer. Its slot index is its linear warp id, 0 × 12 + 10 = 10, so its 1,056 bytes begin at byte 10,560 of the buffer.
  3. The header. Bit 31 of the word at +12 is set, so the warp ran; the low 16 bits read 128, so it ran on SM 128. n_records at +28 is 100, which is below the ring's 256, so nothing wrapped: the 100 records sit at ring positions 0 to 99 in write order.
  4. Three words. Three consecutive records of that ring read 0x00019618, 0x0001be99 and 0x0001ffda. The site-id half of each word is what the device wrote; the clock half is reconstructed here from the published nanoseconds, as the note below explains.
  5. The site ids. Take the low 6 bits: 0x18, 0x19, 0x1a — 24, 25, 26. Subtract the 1 the probe added so that an all-zero word could mean "never written", and the sites are 23, 24 and 25. The reviewed sites file calls them p.kb0.wait at instruction 1158, p.kb0.ready at 1173 and p.kb0.issued at 1245.
  6. The clocks. Shift each word right by 6: 1,624, 1,786 and 2,047 cycles. These are the low 26 bits of the SM clock, and here they need no unwrapping — the whole warp spans about 61,000 cycles, far inside one 226-cycle epoch.
  7. The nanoseconds. Applying the slot's own rate to those cycles puts the three records at 820 ns, 902 ns and 1,034 ns after the launch's origin.
  8. The pairing. The region p.kb0.wait is start [23] end [24] with close: first. The record at 820 ns opens it, the record at 902 ns closes it: one interval, 82 ns. The middle record does double duty — it also opens p.kb0.issue (start [24] end [25]), which the record at 1,034 ns closes: 132 ns. And the first record closed something too: p.sched, which had opened at 584 ns, giving 236 ns.
  9. What it says. 82 ns is the producer finding the first K block's buffer already free; 132 ns is it issuing that block's TMA copies. The eighth interval of this warp, p.kb3.wait, is 2,124 ns — longer than the first seven put together, which come to 696 ns. That is the producer blocked on a three-deep ring of K buffers, waiting for the math warps to release the fourth one, and it is the shape of the whole kernel in a single number.

The three hex words are half measured and half reconstructed. §4Where it came from从何而来

Why a trace at all is the Xtrace paper's opening argument, and it is an argument about what a counter can and cannot answer. A counter-based profiler reports totals over a launch: so many cycles, so many stalls, so many bytes. In a fused kernel those totals are the sum over stages that overlap, so they cannot say which stage waited on which. Timestamps taken at chosen instructions can, because each one is attributable to a point in the program paper §2.1.

为什么需要追踪，是 Xtrace 论文开篇的论点，而这个论点关乎计数器能回答什么、不能回答什么。基于计数器的 profiler 报告整次 launch 的总量：多少周期、多少 stall、多少字节。在一个融合 kernel 里，这些总量是若干相互重叠的阶段之和，所以它们说不清哪个阶段在等哪个阶段。而取自选定指令处的时间戳可以，因为每个时间戳都能归属到程序中的一个点 论文 §2.1。

The paper's own interface is the one stage 5 above describes: trace hints written in the source, located in the binary through DWARF. It also keeps a low-level interface that names a program address directly, and it gives the reason — DWARF does not always preserve the source-to-binary mapping paper §3. Olympus agrees with that diagnosis and inverts the emphasis, which is what the first note below records.

论文自己的接口正是上面第五阶段所讲的那一种：追踪标记写在源码里，通过 DWARF 在二进制中定位。它同时保留一个直接写明程序地址的底层接口，并给出了理由——DWARF 并不总能保住源码到二进制的映射 论文 §3。Olympus 同意这个诊断，但把主次调换了过来，这正是下面第一条注记所记下的事。

The mechanics of getting the records home are the paper's too: the trace driver appends the buffer address to the launch's parameters, and walks the per-slot records after the kernel finishes paper §4.5. Stage 1 above is that walk, with the slot layout of chapter 04 in place of the paper's. What the paper does not specify, and what this layer had to settle, is everything downstream of the walk: what a region means when a warp exits in the middle of one, which percentile definition every view shares, and what a trace must say about its own provenance before a number in it counts as evidence.

把记录带回主机的机制也是论文的：追踪驱动把缓冲区地址追加到 launch 的参数上，并在 kernel 结束后遍历每个槽位的记录 论文 §4.5。上面的第一阶段就是这趟遍历，只是用第 04 章的槽位布局替换了论文的布局。论文没有规定、而这一层必须定下来的，是这趟遍历之后的一切：当一个 warp 在某个 region 中途退出时，region 意味着什么；每个视图共享哪一种百分位定义；以及在其中某个数字算得上证据之前，一份追踪必须说出关于自己来源的哪些话。

The paper keeps an address interface as a fallback. Olympus makes the index the authority and the source hint the convenience, after the FlashAttention-3 line table put K waits on the V line. Hints resolve to indices with warnings; the reviewed index file is what every tool reads DECISIONS.md:441–449.

论文把地址接口留作后备。Olympus 在 FlashAttention-3 的行表把 K 等待记到 V 行之后，把下标定为权威，把源码提示定为便利。提示解析成下标并附带警告；每个工具读的都是经过审阅的下标文件 DECISIONS.md:441–449。
