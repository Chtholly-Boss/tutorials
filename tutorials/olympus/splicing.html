Writing probes into the binary把探针写进二进制

The splicer takes a compiled kernel and a plan of probe islands and returns a new image in which every original instruction word is the compiler's, byte for byte. It opens room in front of an instruction, and then makes every code offset in the file follow: branch fields, return literals, jump tables, EIATTRs, symbols, the debug frame and the line tables. It appends one parameter, the trace buffer's address. And before anything runs, it proves offline that this is all it did.

拼接器接收一个编译好的 kernel 和一份探针 island 计划，返回一个新镜像，其中每条原始指令字都逐字节是编译器写下的。它在某条指令前腾出位置，然后让文件里的每个代码偏移都跟着移动：分支字段、返回字面量、跳转表、EIATTR、符号、调试帧和行表。它追加一个参数：追踪缓冲区的地址。在任何东西运行之前，它离线证明自己只做了这些。

§1Contract契约

What this layer promises这一层的承诺

The original instructions are copied through unchanged; only branch targets that moved differ. splice/verify.py proves it offline for every image.

原始指令原样复制；只有目标移动了的分支会不同。splice/verify.py 对每个镜像离线证明这一点。

olympus/splice → hands a交付 SpliceResult to给 olympus/runtime · takes a接收 SplicePlan from来自 olympus/planner · built on建立在 olympus/cubin, olympus/isa

Two of the system’s four contract modules live in this layer, which is unusual for a layer this deep, and the reason is that the planner above it and the runtime below it both have to name the same things without importing anything of the splicer’s own ARCHITECTURE.md:30–34. ir.py is the input side. A SplicePlan is a list of Islands, and an Island says four things: the original instruction index it is inserted in front of, what it is for (an init island runs once at kernel entry, a site island is a probe, a calib island is a clock calibration at a block exit), the probe instructions themselves, and the resources it uses — which registers it writes, each of which the planner has already shown to be dead at that index, and which scoreboards it claims. The plan also carries the byte offset at which the trace buffer’s pointer will be appended to the parameter block ir.py:84–106.

系统的四个契约模块中有两个就在这一层里。对一个这么底层的层来说这很罕见，理由是：它之上的规划器和它之下的运行时都必须能叫出同样的东西，而又不能导入拼接器自己的任何东西 ARCHITECTURE.md:30–34。ir.py 是输入侧。一份 SplicePlan 是一串 Island，而一个 Island 说四件事：它被插在哪条原始指令下标之前、它是做什么的（init island 在 kernel 入口执行一次，site island 是一个探针，calib island 是基本块出口处的时铟校准）、探针指令本身，以及它用到的资源——它写哪些寄存器（每一个都已经被规划器证明在那个下标处已死）、它占用哪些 scoreboard。计划还带着追踪缓冲区指针将被追加到参数块中的字节偏移 ir.py:84–106。

result.py is the output side. A SpliceResult is the new image plus, for every kernel whose launches now need the extra argument, a KernelEdit: the parameter block’s size before and after, the offset and size of the appended parameter, and index_map, which sends each original instruction index to its new one result.py:18–36. That map has to leave the layer, because everything upstream recorded its work by instruction index: a site is an index, and a report that says “this stall is at instruction 19” means index 19 of the kernel as the compiler wrote it. Without the map, nothing above could find that instruction in the file that actually ran.

result.py 是输出侧。一份 SpliceResult 是新镜像，再加上每个启动时现在需要额外参数的 kernel 各一个 KernelEdit：参数块前后的大小、追加参数的偏移和大小，以及 index_map，它把每个原始指令下标送到它的新下标 result.py:18–36。这张映射必须离开这一层，因为上游的一切都是按指令下标记录自己的工作的：一个站点就是一个下标，而一份说“这次停顿在指令 19”的报告，指的是编译器写下的那个 kernel 的下标 19。没有这张映射，上面的任何一层都在真正运行的那个文件里找不到那条指令。

What this layer does not decide is what an island contains. The planner of chapter 05, just behind us, picks the dead registers and the free scoreboards and searches for control bits; this layer decides where every byte of the file ends up. Original instructions never appear in a plan at all, so a plan has no way to ask for one to be changed — which is the strongest form Invariant 1 can take: the layer has no vocabulary for violating it.

这一层不决定的是一个 island 里有什么。第 05 章的规划器就在我们身后，它挑出已死的寄存器和空闲的 scoreboard、搜索控制位；这一层决定文件里的每个字节最终落在哪里。原始指令根本不会出现在计划里，所以一份计划没有任何办法要求改动它们——这是不变量 1 能采取的最强形式：这一层连违反它的词汇都没有。

Two kinds of reader depend on what comes out. The runtime of chapter 07, just ahead, uses the KernelEdit to check the parameter layout from three sides before it launches anything, and needs the image to load as an ordinary module. The analyses behind us depend on the contract rather than on the data: a liveness result (chapter 02) and a hazard model (chapter 03) are both computed on the compiler’s schedule, and they are only true of the kernel that actually runs if that schedule survives the splice.

有两类读者依赖输出结果。第 07 章的运行时就在前面，它用 KernelEdit 在启动任何东西之前从三个视角检查参数布局，并要求镜像能当作普通模块加载。我们身后的各项分析依赖的是契约而不是数据：活跃性结果（第 02 章）和冒险模型（第 03 章）都是在编译器的调度上算出来的，只有当这份调度在拼接后依然成立时，它们才对真正运行的那个 kernel 为真。

§2Invariant不变量

Invariant不变量1

Original instructions are never altered. The splicer copies every original word through; the only changed words are branches whose target moved with an island.

原始指令从不被改动。拼接器把每条原始字原样复制过去；唯一会变的字是目标随 island 移动了的分支。

Checked by check_kernel, the offline proof that re-decodes both images and compares every original instruction at its new index verify.py:43–108, and measured by splice/similarity.py: 0 changed basic blocks on every one of the 30 T1–T4 case × sets and on all 30 T0 ones, every changed instruction a relocation (EVAL.md, A2).

检查方式：check_kernel，重新解码两个镜像并在新下标处逐条比较每条原始指令的离线证明 verify.py:43–108；再由 splice/similarity.py 测量：30 个 T1–T4 用例 × 集合和 30 个 T0 上全部 0 个基本块改变，每条有变化的指令都是重定位（EVAL.md，A2）。

A weaker rule would be "the spliced kernel still computes the same outputs". That is necessary, and the runtime's gate checks it on every run, but it is not what a trace needs. A tool can add wait bits to original instructions and still pass bit-exactness: on T1–T4, G-Watch 0.0.35 alters 828 original instructions, every one an added scoreboard in a wait mask, and 12% of those additions make the kernel wait early on its own asynchronous work (EVAL.md, side by side). The timing such a trace reports is then partly the tracer's. Invariant 1 keeps the measured schedule the compiler's, which is the only reason the overhead chapters can treat a probe's cost as a separate quantity.

更弱的规则会是"拼接后的 kernel 仍算出同样的输出"。这是必要的，运行时的门每次运行都检查它，但追踪需要的不止这个。一个工具可以给原始指令加等待位而仍然通过逐位一致：在 T1–T4 上，G-Watch 0.0.35 改动了 828 条原始指令，每一条都是在等待掩码里加了一个 scoreboard，其中 12% 让 kernel 提前等待自己的异步工作（EVAL.md，side by side）。这样的追踪报出的时间里就有一部分是追踪器自己的。不变量 1 让被测量的调度仍是编译器的，这也是开销章节能把探针成本当作一个独立量来讨论的唯一理由。

What “altered” means has to be exact, because the proof decides it mechanically. Two words are the same instruction when all 128 bits agree. There are exactly two licensed exceptions, and both are forced by the fact that code moved: a branch whose target moved differs in its offset field, and the 32-bit immediate that holds a CALL.REL.NOINC’s return address differs in that immediate. Nothing else may differ. Not a register number, not a predicate, and above all not a control bit — a changed control word is the one failure the proof reports by name, as an “A2 violation”.

“被改动”的含义必须精确，因为证明要机械地判定它。两个字当全部 128 位一致时才是同一条指令。恰好有两个被许可的例外，且两者都是代码移动所逼：目标移动了的分支在它的偏移字段上不同，以及装着 CALL.REL.NOINC 返回地址的那个 32 位立即数在该立即数上不同。其余一律不得不同。不是寄存器编号，不是谓词，最重要的是不得是控制位——变了的控制字是证明会点名报出的唯一一种失败，叫做“A2 violation”。

Invariant 1 is about the words, not about the clock. An island’s own words issue and take cycles, so a kernel with probes in it is slower than the same kernel without them. What the invariant buys is that the slowdown is attributable: the compiler’s schedule for the original instructions is still in the file, bit for bit, so the difference between the two runs is the probes and nothing else. Keeping that difference small is a different problem, and it is the one chapter 03 solves.

不变量 1 管的是字，不是时铟。island 自己的字要发射、要占周期，所以装了探针的 kernel 比没装的慢。不变量换来的是：这份减速是可归因的——编译器对原始指令的调度逐位还在文件里，于是两次运行的差别就是探针，再无其他。把这个差别压小是另一个问题，那是第 03 章解决的。

§3How it works如何工作

An island before an instruction index指令下标前的 island

Everything about the relocation follows from one sentence about what a site means. A site is an instruction index i, and its probe must run before instruction i on every path that reaches i — including a branch that jumps straight to i, and whether or not i’s own predicate guard turns out to pass (DECISIONS 10) ir.py:24–33. The alternative reading, “before i in program order”, would be cheaper: a branch into i could keep landing on i and skip the probe. But then a loop body probed at its top would miss every iteration after the first, and the trace would be quietly incomplete rather than visibly wrong.

重定位的一切都从一句关于“站点”含义的话推出。一个 站点 是一个指令下标 i，而它的探针必须在每一条到达 i 的路径上都在指令 i 之前执行——包括直接跳到 i 的分支，也不论 i 自己的谓词 guard 最终是否通过（DECISIONS 10）ir.py:24–33。另一种读法——“按程序顺序在 i 之前”——会便宜得多：跳进 i 的分支可以继续落在 i 上并跳过探针。但那样的话，一个在循环体顶部被探测的循环就会错过第一次以后的每次迭代，而追踪会是静悄悄地不完整，而不是显眼地出错。

So an island is a run of words inserted in front of one original instruction islands.py:1–24, and the consequence is that one old byte offset now needs two answers, not one. An IndexMap gives both. target_off returns the first word of the island in front of that instruction, counting only the island words inserted strictly before it; that is where a branch to it must now land, so that the branch runs the probe. instr_off returns where the instruction itself now sits, counting the island in front of it as well; that is what any record naming the instruction must say islands.py:62–93. When there is no island in front of an instruction the two answers are equal, which is why the distinction is easy to miss and expensive to get wrong.

于是一个 island 就是插在一条原始指令前面的一串字 islands.py:1–24，而结果是：一个旧的字节偏移现在需要两个答案，而不是一个。IndexMap 两个都给。target_off 返回该指令前面 island 的第一个字，只数严格插在它之前的 island 字；跳到它的分支现在必须落在这里，这样这条分支才会执行探针。instr_off 返回指令本身现在的位置，把它前面的 island 也数进来；任何命名这条指令的记录必须这样说 islands.py:62–93。当一条指令前面没有 island 时，两个答案相等——这正是这个区别容易被忽略、而弄错了代价很大的原因。

Both maps are the same arithmetic, because an island is whole words and an instruction is 16 bytes: an old offset becomes 16 × (its index + the number of island words ahead of it), and the two maps differ only in whether “ahead of it” includes its own island. Take t0_call under the trace-pp plan this page’s widget plays, which places 8 islands totalling 107 words. Its CALL.REL.NOINC is instruction 13, at byte 208 in the original. instr_off counts 51 island words at or before index 13 and puts the call at byte 1,024. target_off of the same offset counts only the 43 words of the entry island and would answer byte 896 — the first word of the island in front of instruction 13. Each answer is right for exactly one question.

两张映射是同样的算术，因为 island 是整个的字、指令是 16 字节：一个旧偏移变成 16 ×（它的下标 + 它前面 island 字的个数），而两张映射的唯一区别在于“它前面”是否包含它自己的 island。以本页组件播放的 trace-pp 计划下的 t0_call 为例，它放了 8 个 island、共 107 个字。它的 CALL.REL.NOINC 是指令 13，在原镜像的第 208 字节。instr_off 数出下标 13 及之前共 51 个 island 字，把这条调用放在第 1,024 字节。同一个偏移的 target_off 只数入口 island 的 43 个字，给出的是第 896 字节——也就是指令 13 前面那个 island 的第一个字。两个答案各自只对一个问题是对的。

The filler word, and why it never drains填充字，以及它为什么从不排空

Not every island word is a probe. A plan may ask for an island of n words that does nothing — that is how a null splice is built, to separate the cost of inserting code from the cost of the code itself — and the text is padded at the end to a multiple of 128 bytes. Both need a word that is as close to free as the machine allows, and “free” turns out to be a property of the control bits rather than of the operation.

并不是每个 island 字都是探针。一份计划可以要求一个由 n 个什么也不做的字组成的 island——空拼接就是这么做出来的，用以把“插入代码”的代价与“代码本身”的代价分开——而代码段末尾要被填充到 128 字节的整数倍。两者都需要一个尽量接近“免费”的字，而“免费”结果是控制位的属性，而不是操作的属性。

The null splice and the 128-byte tail padding use one filler word, ptxas’s own stall extender, printed below with its control bits. The first filler was ptxas's padding NOP, whose usched 0 means DRAIN: drain the warp's pipeline before the next issue. Placed before every block leader it cost +59.6% on matmul, +29% on FlashMLA and +26% on DeepGEMM k512; the same islands with a stall-1 word cost +0.1%, +1.1% and +0.9%. The rule that followed is that an island word never uses usched 0, and the scheduler rejects stall 0 (DECISIONS 54). The cost of a splice was in the control bits, not in where the islands sat.

空拼接和 128 字节的尾部填充用同一个填充字：ptxas 自己的 stall 延长器，连同控制位印在下面。最初的填充字是 ptxas 的填充 NOP，它的 usched 为 0，意思是 DRAIN：下一次发射前排空该 warp 的流水线。把它放在每个基本块首指令前，matmul 慢了 59.6%，FlashMLA 慢了 29%，DeepGEMM k512 慢了 26%；同样的 island 换成 stall 1 的字，只慢 0.1%、1.1% 和 0.9%。由此定下的规则是：island 字永不使用 usched 0，调度器拒绝 stall 0（DECISIONS 54）。拼接的代价在控制位里，不在 island 放在哪。

lo = 0x0000003F3F3FF290   hi = 0x000FE2000FFFE03F

The word Olympus settled on is ptxas’s own stall extender. It is predicated off on UPT, a uniform predicate the hardware treats as always true, so @!UPT never fires; its destination is the uniform zero register, so it writes nothing even if it did; and its stall count is 1, the smallest the scheduler accepts islands.py:40–49. It still costs an issue slot, which is the floor on what inserting a word can cost. What it does not cost is a pipeline drain, and the measured gap between those two prices — a factor of nearly 600 on t1_matmul_bf16, from +59.6% to +0.1% — is why “island words never use usched 0” is a rule and not a preference.

Olympus 最终选定的字是 ptxas 自己的 stall 延长器。它用 UPT 做谓词——硬件把这个 uniform 谓词当作恒真——所以 @!UPT 永不生效；它的目的寄存器是 uniform 零寄存器，所以即使生效也什么都不写；而它的 stall 计数是 1，是调度器接受的最小值 islands.py:40–49。它仍然要花一个发射槽，这就是“插入一个字”代价的下限。它不花的是一次流水线排空，而这两个价钱之间测到的差距——在 t1_matmul_bf16 上将近 600 倍，从 +59.6% 到 +0.1%——就是“island 字永不使用 usched 0”是一条规则、而不是一种偏好的原因。

Every code offset follows每个代码偏移都跟着走

A code offset is any number in the file that means “byte n of this kernel’s text”, and inserting words invalidates every one of them at once. They fall into two groups. Some live in the instruction words themselves, as a branch’s offset field or an immediate; in t0_call exactly 8 of the 48 words carry one, which is the most the splicer can ever have to touch; the other 40 are copied without a decision. The rest live outside the text altogether — in the constant bank, in the .nv.info attributes, in the symbol table, in DWARF — and those are the ones a splicer forgets, because the kernel it just edited still disassembles and still runs.

代码偏移是文件里任何表示“本 kernel 代码段的第 n 字节”的数，而插入字会一下子使它们全部失效。它们分为两类。有些就在指令字里，作为分支的偏移字段或一个立即数；在 t0_call 里 48 个字中恰好 8 个带着它，这就是拼接器最多需要动的数量；其余 40 个是不用做任何判断的复制。剩下的根本不在代码段里——在常量 bank、在 .nv.info 属性、在符号表、在 DWARF 里——而被拼接器遗忘的正是这些，因为刚被它改过的 kernel 仍然能反汇编、仍然能跑。

The text is rebuilt in one pass: before instruction i its island, if any, then the original word, copied through unless it carries a code offset islands.py:191–219. Each kind of offset has one rule, and each rule is a field write that copies every other bit encode.py:283–305.

代码段一趟重建：在指令 i 之前先放它的 island（如果有），再放原始字，除非它带着代码偏移，否则原样复制 islands.py:191–219。每种偏移各有一条规则，每条规则都是只改一个字段、其余位全部复制的写入 encode.py:283–305。

Six refusals make edit_kernel return None, which leaves that kernel entirely untouched islands.py:168–176. A relocation against the text means some offset in it will be patched after Olympus has written the file, by a value Olympus cannot see. A relocated jump table is the same problem one section over: the entries in c[0x2] are not yet the numbers that will run. An unknown offset-bearing EIATTR might hold a position or a target, and guessing is a coin flip whose wrong side is silent. A CALL.REL.NOINC with no locatable return literal means the search went back 32 words without finding the MOV that materializes the return address, so the call would come back to a byte offset that no longer means what it did. A register-absolute target is a branch to a full address computed at run time, with nothing in the file to rewrite, and a register-relative branch with no offset field targets next_pc plus a register, which the move changes and no field can compensate islands.py:205–215. In each case the choice is between no trace and a wrong trace, and the layer is built so that the cheap failure is the automatic one.

有六种拒绝让 edit_kernel 返回 None，于是该 kernel 完全保持不动 islands.py:168–176。针对代码段的重定位意味着其中某个偏移会在 Olympus 写完文件之后被修补，而补上的值 Olympus 看不到。带重定位的跳转表是隔了一个节的同一个问题：c[0x2] 里的表项还不是将来真正运行的数。未知的带偏移 EIATTR 可能装的是位置、也可能是目标，而猜是抛硬币，猜错的那一面是沉默的。找不到返回字面量的 CALL.REL.NOINC 意味着往回找了 32 个字也没找到物化返回地址的那条 MOV，于是这条调用会返回到一个含义已经变了的字节偏移。寄存器绝对目标是跳向一个运行时算出的完整地址，文件里没有东西可改；而没有偏移字段的寄存器相对分支目标是 next_pc 加一个寄存器，移动会改变它而没有字段能补回来 islands.py:205–215。每一种情况下要选的都是“没有追踪”还是“错的追踪”，而这一层的构造让代价低的那种失败成为自动发生的那种。

One call, and everything that moves with it一条调用，以及跟着它动的一切

The table says what the rules are; one real kernel says what they cost. t0_call calls a __noinline__ helper twice, so it uses the relative-return convention, and under the trace-pp plan the helper’s entry is itself a probe site. Walking its second-to-last code offset end to end shows all four kinds in one kernel.

表格说的是规则是什么；一个真实的 kernel 说的是这些规则的代价。t0_call 两次调用一个 __noinline__ 辅助函数，所以用的是相对返回约定；而在 trace-pp 计划下，辅助函数的入口本身就是一个探针站点。把它的调用从头走到尾，四类偏移在一个 kernel 里全部出现了。

  1. The plan. trace-pp places 8 islands: 43 words before instruction 1 (a 35-word init island and an 8-word entry probe), 16 before instruction 23 (a probe and a clock calibration), and 8 before each of 13, 14, 19, 20, 24 and 36. That is 107 inserted words, so the text goes from 48 words to 155, padded to 160, and .text.t0_call grows from 768 bytes to 2,560.
  2. The instruction. Instruction 13, at byte 208, is CALL.REL.NOINC 0x180: low half 0000000000287944, high half 020fea0003c00000, control bits [7:7:{5}:5:0]. Its target lives in one field, Sa, which is bits [81:34] followed by bits [23:16], scaled by 4 and signed.
  3. What the field holds is not the target. A relative call stores target − (pc + 16), the distance from the following instruction, divided by 4: (384 − 224) / 4 = 40. Both halves of that subtraction move when code is inserted, which is why relocating a branch needs its new pc as well as its new target.
  4. The new pc. instr_off counts the island words at or before index 13 — 43 before instruction 1 and the call’s own 8 — and puts the call at 16 × (13 + 51) = byte 1,024.
  5. The new target. Byte 384 is instruction 24, the helper’s entry, and trace-pp has a site there named helper.entry. target_off counts the 91 island words strictly before index 24 and answers 16 × (24 + 91) = byte 1,840 — the island’s first word. The helper’s own first instruction is at 1,968.
  6. Why that distinction is the whole point. Use instr_off here and the call lands on 1,968, skipping the probe. The only other way into instruction 24 is fallthrough from instruction 23 — and instruction 23 is EXIT. So the helper.entry probe would fire on neither of the two calls, and the trace would show a helper that was never entered.
  7. The one field that changes. (1,840 − (1,024 + 16)) / 4 = 200. Both 40 and 200 fit in the field’s low 8 bits, which sit at [23:16], so exactly one byte of the sixteen changes: the low half becomes 0000000000c87944 and the high half is untouched. The predicate, the opcode and the control word are the integers ptxas wrote.
  8. The return address, which is not a branch. MOV R2, 0xe0 at instruction 12 puts 224 into R2 — to the ISA a plain 32-bit immediate, to the program the address the helper will return to. 224 is instruction 14, so it maps by target: 16 × (14 + 51) = byte 1,040, the word right after the relocated call. Leave it alone and both calls return to byte 224 of the new text, which is inside the entry island. The reference implementation leaves it alone, which is why its t0_call image is not a usable baseline (DECISIONS 20).
  9. The relocation anchor on the way back. A relocation anchor is an instruction whose immediate is a byte offset measured from its own next pc, so moving the instruction changes what that immediate has to say. RET.REL.NODEC R2 0x0 at instruction 36 computes next_pc + R2 + immediate, and its immediate is −592, because 592 is its own next pc and the sum has to come out at the function’s base. The instruction moves to 16 × (36 + 107) = byte 2,288, so moved_anchor writes −592 + 576 − 2,288 = −2,304 and the sum is 0 again. This value needs the field’s upper bits as well, so two bytes of the word change rather than one.
  10. The record that names an instruction, not a target. t0_call has eight EIATTRs and one of them carries a code offset: EXIT_INSTR_OFFSETS [368], its single EXIT at instruction 23. That is a position, so it maps by instr_off to 1,824, not by target to 1,568, which is where the 16-word island in front of the EXIT begins. Get it backwards and every tool that reads the attribute is told the kernel exits inside a probe. The symbols take the other map: the helper’s symbol value is a target, 384 → 1,840, and its size becomes 2,560 − 1,840 = 720, while the kernel symbol keeps value 0 and takes the new text size, 2,560.
  11. The jump table, borrowed from the other kernel. t0_call has no c[0x2] table; t0_switch has a seven-entry one. Under its own trace-pp plan (146 inserted words) the table [496, 624, 800, 896, 976, 1152, 336] becomes [1424, 1680, 1984, 2208, 2416, 2720, 1136], every entry by target, and INDIRECT_BRANCH_TARGETS carries those same seven plus the BRX’s own byte offset, 320, which maps by position to 1,120. Forget the table and the dispatch branches into the middle of an island, in one of seven cases picked at run time; forget the attribute and cuobjdump’s listing disagrees with the code that runs.
  12. What ends up different. Of t0_call’s 48 original words, 43 are byte-identical copies and 5 differ: the two call targets, the two return literals and the one anchor. The three BRAs do not change at all — the same number of island words lies between each of them and its target, so target − (pc + 16) comes out the same integer. That is the shape Invariant 1 predicts, and the offline proof is what turns the prediction into a check.
  1. 计划。trace-pp 放了 8 个 island：指令 1 前 43 个字（一个 35 字的 init island 加一个 8 字的入口探针），指令 23 前 16 个字（一个探针加一次时铟校准），以及 13、14、19、20、24、36 各 8 个字。共插入 107 个字，于是代码从 48 个字变成 155 个、填充到 160 个，.text.t0_call 从 768 字节涨到 2,560 字节。
  2. 这条指令。指令 13 在第 208 字节，是 CALL.REL.NOINC 0x180：低半 0000000000287944，高半 020fea0003c00000，控制位 [7:7:{5}:5:0]。它的目标存在一个字段 Sa 里，该字段是 [81:34] 位接上 [23:16] 位，比例 4，有符号。
  3. 字段里装的不是目标。相对调用存的是 target − (pc + 16)，即到下一条指令的距离除以 4：(384 − 224) / 4 = 40。插入代码时这个减法的两边都会动，所以重定位一条分支除了新目标还需要它的新 pc。
  4. 新 pc。instr_off 数下标 13 及之前的 island 字——指令 1 前的 43 个加这条调用自己的 8 个——把调用放在 16 × (13 + 51) = 第 1,024 字节。
  5. 新目标。第 384 字节是指令 24，也就是辅助函数的入口，而 trace-pp 在那里有一个叫 helper.entry 的站点。target_off 数严格在下标 24 之前的 91 个 island 字，给出 16 × (24 + 91) = 第 1,840 字节——island 的第一个字。辅助函数自己的第一条指令在 1,968。
  6. 这个区别就是全部要点。在这里用 instr_off，调用就落在 1,968，跳过了探针。而进入指令 24 的唯一其他路径是从指令 23 落下来——而指令 23 是 EXIT。于是 helper.entry 探针在两次调用中都不会触发，追踪会显示一个从未被进入的辅助函数。
  7. 只有一个字段变。(1,840 − (1,024 + 16)) / 4 = 200。40 和 200 都能装进字段的低 8 位，而那 8 位就在 [23:16]，所以十六个字节里恰好变一个：低半变成 0000000000c87944，高半没动。谓词、操作码和控制字都是 ptxas 写下的那些整数。
  8. 返回地址，它不是分支。指令 12 的 MOV R2, 0xe0 把 224 放进 R2——对 ISA 来说就是一个普通的 32 位立即数，对程序来说是辅助函数将返回的地址。224 是指令 14，所以按目标映射：16 × (14 + 51) = 第 1,040 字节，正是重定位后那条调用后面的一个字。不理它，两次调用就都返回到新代码的第 224 字节，而那在入口 island 里面。参考实现就没理它，这就是它的 t0_call 镜像不能当基线用的原因（DECISIONS 20）。
  9. 回程上的重定位锚点（relocation anchor）。重定位锚点指的是这样一条指令：它的立即数是一个以它自己的 next_pc 为基准量出的字节偏移，所以指令一挪位置，这个立即数该写什么也就变了。指令 36 的 RET.REL.NODEC R2 0x0 算的是 next_pc + R2 + 立即数，而它的立即数是 −592，因为 592 是它自己的 next_pc，而和必须落在函数的基址。这条指令移到 16 × (36 + 107) = 第 2,288 字节，于是 moved_anchor 写入 −592 + 576 − 2,288 = −2,304，和又回到 0。这个值还用到了字段的高位，所以字里变的是两个字节而不是一个。
  10. 命名指令、而不是命名目标的记录。t0_call 有八条 EIATTR，其中一条带代码偏移：EXIT_INSTR_OFFSETS [368]，指的是指令 23 那条唯一的 EXIT。这是一个位置，所以按 instr_off 映射到 1,824，而不是按目标映射到 1,568——后者是 EXIT 前面那个 16 字 island 的起点。弄反了，所有读这条属性的工具都会被告知 kernel 在一个探针内部退出。符号走的是另一张映射：辅助函数的符号值是目标，384 → 1,840，它的大小变成 2,560 − 1,840 = 720；kernel 符号的值仍为 0，大小取新的代码段大小 2,560。
  11. 跳转表，从另一个 kernel 借来。t0_call 没有 c[0x2] 表；t0_switch 有一张七项的。在它自己的 trace-pp 计划（插入 146 个字）下，表 [496, 624, 800, 896, 976, 1152, 336] 变成 [1424, 1680, 1984, 2208, 2416, 2720, 1136]，每一项都按目标映射；而 INDIRECT_BRANCH_TARGETS 带着同样这七个，再加上 BRX 自身的字节偏移 320，它按位置映射到 1,120。忘了表，分派就会跳进某个 island 的中间，而是七种情况中运行时挑中的那一种；忘了属性，cuobjdump 的列表就与真正运行的代码不一致。
  12. 最终不同的部分。t0_call 的 48 个原始字里，43 个是逐字节相同的复制，5 个不同：两个调用目标、两个返回字面量和一个锚点。三条 BRA 完全没变——它们各自与自己目标之间的 island 字数量相同，所以 target − (pc + 16) 算出来是同一个整数。这正是不变量 1 预测的形状，而离线证明把这个预测变成了一项检查。

The offline proof离线证明

Everything above is a set of rules, and a rule can be implemented wrongly. The obvious way to find out — launch the kernel and compare its outputs — catches only the mistakes that change the answer. A call that returns into the middle of an island may fault, or may land on the filler word and run on as if nothing happened; a stale EXIT_INSTR_OFFSETS changes no output at all and misleads every tool that reads it afterwards. So the spliced image is checked against the original as a pair of files, before anything is loaded.

上面的一切都是规则，而规则是可以被实现错的。最显而易见的查法——启动 kernel 并比对输出——只能抓住那些会改变答案的错误。一条返回到 island 中间的调用可能出错，也可能正好落在填充字上、像什么事也没发生一样继续跑；一条过期的 EXIT_INSTR_OFFSETS 根本不改变任何输出，却会误导此后每一个读它的工具。所以拼接后的镜像在被加载之前，先作为一对文件与原镜像对照检查。

check_kernel needs no GPU. It decodes the original and the spliced image with the original's arch and walks every original instruction to its new index: same class and mnemonic; the same control word, or the error says "A2 violation"; the same register sets; a direct branch's target equal to target_off of its old target; an anchor's base next_pc + imm preserved; and otherwise the raw word equal, with the one exception of a relocated return literal. Island words must be the words requested, and a filler island may wait on or claim no scoreboard verify.py:43–108. When the original has line info, every original instruction must keep its source location and PTX line, and every island word must carry the location of the instruction it precedes verify.py:111–140. This is the first stage of Invariant 5, nothing runs before it is checked; the second stage is the runtime’s output gate, in chapter 07.

check_kernel 不需要 GPU。它用原镜像的架构解码原镜像和拼接后的镜像，把每条原始指令走到它的新下标：同样的编码类和助记符；同样的控制字，否则报"A2 violation"；同样的寄存器集合；直接分支的目标等于旧目标的 target_off；锚点的基址 next_pc + imm 不变；其余情况下原始字必须相等，唯一例外是重定位过的返回字面量。island 字必须是请求的那些字，填充 island 不得等待或占用任何 scoreboard verify.py:43–108。原镜像有行信息时，每条原始指令必须保留它的源码位置和 PTX 行，每个 island 字必须带着其前方指令的位置 verify.py:111–140。这是不变量 5（没有检查过的东西不会运行）的第一个阶段；第二个阶段是运行时的输出门，在第 07 章。

What the proof does not say is that the probe is a good probe. It establishes one thing: this image is the original kernel plus the islands the plan asked for, with every code offset following. Whether the island’s own words compute the right thing is chapter 04’s question, whether they are cheap is chapter 03’s, and whether the whole pipeline agrees with an independent profiler is chapter 09’s. Each of those answers is only worth having because this one is already settled.

证明没说的是这个探针是不是一个好探针。它只立了一件事：这个镜像就是原 kernel 加上计划所要求的那些 island，且每个代码偏移都跟着走了。island 自己的字算得对不对，是第 04 章的问题；它们够不够便宜，是第 03 章的；整条流水线与一个独立剖析器是否一致，是第 09 章的。那几个答案值得要，只因为这一个已经定下来了。

Measuring what changed测量改变了什么

The proof says the splice is right; similarity.py says how much it touched. It aligns the two images by the KernelEdit's index map, gives every original instruction one status (unchanged, branch, anchor, literal, altered, moved, dropped), builds the CFG on both sides, and calls a block changed if any instruction in it is altered, moved or dropped, or its successors differ similarity.py:1–55. The verdict is 0 changed blocks, every changed instruction a relocation whose target resolves, and at least 94% of the code instructions unchanged similarity.py:141–150. On the 30 judged T1–T4 case × sets the shipped planner has 0 changed blocks everywhere and passes 29; t2_cutlass_gemm trace-mem is at 92.86%, because 150 inline islands in a 1,900-instruction branch-dense kernel relocate almost every branch that spans one, and a relocated branch counts as changed by definition (EVAL.md, A2 and D2).

证明说拼接是对的；similarity.py 说它碰了多少。它用 KernelEdit 的下标映射对齐两个镜像，给每条原始指令一个状态（unchanged、branch、anchor、literal、altered、moved、dropped），在两侧各建 CFG，只要某个块里有指令被改动、移动或丢失，或它的后继不同，就算这个块改变了 similarity.py:1–55。判定标准是：0 个块改变，每条有变化的指令都是目标可解析的重定位，且至少 94% 的代码指令未变 similarity.py:141–150。在 30 个受评的 T1–T4 用例 × 集合上，交付的规划器处处 0 个块改变，通过 29 个；t2_cutlass_gemm trace-mem 为 92.86%，因为在一个 1,900 条指令、分支密集的 kernel 里放 150 个内联 island，几乎每条跨越 island 的分支都要重定位，而按定义重定位过的分支算作改变（EVAL.md，A2 与 D2）。

§4Where it came from从何而来

The paper's splicer locates the trace hints in the binary, inserts probe code ahead of each insertion address, and rewrites the branches whose targets must shift paper §3. It can do this because, in the words of its appendix, the hardware issues in order and interlocks neither the register file nor the pipes: the schedule is data in the instruction, so an inserted word carries its own and the kernel's words need not change paper §A.2.1. Its evaluation of a splice is binary similarity: the instructions Xtrace changes are the branches whose targets moved paper §5.3. Olympus makes that the contract and the first invariant, and makes it a rule from the first day: original instructions are copied, never re-encoded, except for the offset field of a branch whose target moved (DECISIONS 5).

论文的拼接器在二进制里定位追踪提示，在每个插入地址之前插入探针代码，并改写目标必须移动的分支 论文 §3。它能这样做，是因为用它附录的话说，硬件按序发射，既不对寄存器堆也不对流水线做互锁：调度是指令里的数据，于是插入的字带着自己的调度，kernel 的字不必改变 论文 §A.2.1。它对拼接的评估是二进制相似度：Xtrace 改动的指令是目标移动了的分支 论文 §5.3。Olympus 把这一点定为契约和第一条不变量，并从第一天起定为规则：原始指令只复制、从不重新编码，唯一的例外是目标移动了的分支的偏移字段（DECISIONS 5）。

Where Olympus departs: every code offset, not only branchesOlympus 的不同之处：每个代码偏移，而不只是分支DECISIONS 20

The paper's text names branches. Olympus relocates the return literal a CALL.REL.NOINC materializes, the anchor of RET.REL and BRX, the jump table, every offset-bearing EIATTR, the symbols, the debug frame and the line tables, and empties what it cannot follow. Each of these was found broken in some tool's output before it became a rule: the reference implementation's t0_call image keeps the CALL.REL offset, the MOV R2 literals and the RET.REL offset while the words move, so the traced kernel jumps into probe code and the case is not a valid baseline DECISIONS.md:52; its t0_switch image moves the BRX and the table but copies EIATTR_INDIRECT_BRANCH_TARGETS unchanged (EVAL.md, T0).

论文的文字说的是分支。Olympus 还重定位 CALL.REL.NOINC 物化的返回字面量、RET.REL 和 BRX 的锚点、跳转表、每个带偏移的 EIATTR、符号、调试帧和行表，并清空它无法跟随的东西。这些每一项在成为规则之前，都先在某个工具的输出里被发现出了错：参考实现的 t0_call 镜像在字移动的同时保留了 CALL.REL 的偏移、MOV R2 字面量和 RET.REL 的偏移，被追踪的 kernel 于是跳进探针代码，该用例不能作为有效基线 DECISIONS.md:52；它的 t0_switch 镜像移动了 BRX 和跳转表，却原样复制了 EIATTR_INDIRECT_BRANCH_TARGETS（EVAL.md，T0）。

Where Olympus departs: line tables survive the spliceOlympus 的不同之处：行表在拼接后仍然有效DECISIONS 79

The paper reads DWARF to find insertion points and says nothing about what the spliced binary's debug sections contain. Olympus's first splicer stripped the line tables, because stale code offsets there mislead ncu's source view and cuda-gdb (DECISIONS 30). Now it relocates them: every row moves with its instruction and an island takes the line of the instruction it precedes, which adds no rows, keeps NVIDIA's inlining references valid, and charges a probe's cost to the traced source line. On 43 spliced images every original instruction keeps its line and nvdisasm agrees; the image is otherwise byte-identical to the stripped splice DECISIONS.md:450–463. Stripping stays as the fallback when a table cannot be relocated exactly.

论文读 DWARF 来找插入点，对拼接后二进制的调试节里有什么只字未提。Olympus 的第一个拼接器把行表剥掉，因为那里过期的代码偏移会误导 ncu 的源码视图和 cuda-gdb（DECISIONS 30）。现在它重定位行表：每一行随它的指令移动，island 取其前方指令的行号，这样不新增行、NVIDIA 的内联引用保持有效、探针的成本被记到被追踪的源码行上。在 43 个拼接镜像上，每条原始指令都保留了它的行号，nvdisasm 同意；镜像的其余部分与剥掉行表的拼接逐字节相同 DECISIONS.md:450–463。当某张表无法精确重定位时，剥除仍是后备方案。

Beyond the paper: the proof and the filler论文之外：证明与填充字DECISIONS 54

The offline proof, the fail-closed rule and the filler word are Olympus's. The paper measures a splice afterwards by similarity; Olympus proves each image before any launch and measures it as well. And the filler is chosen for its control bits: ptxas's padding NOP drains the pipeline, which turned a null splice into a 60% slowdown, so an island word never carries usched 0.

离线证明、失败即停的规则和填充字都是 Olympus 自己的。论文事后用相似度来衡量一次拼接；Olympus 在任何启动之前证明每个镜像，同时也测量它。填充字是按控制位挑选的：ptxas 的填充 NOP 会排空流水线，把一次空拼接变成 60% 的减速，所以 island 字永不携带 usched 0。

The fail-closed rule is the quietest of the three and the one that shapes the output most. A splicer that does its best on a kernel it only partly understands produces images that are right on the paths it tested; Olympus instead reports the kernel as untraced and relocates nothing, so a trace that exists is a trace whose image was proven, and the coverage of the tool is a number you can read off the report rather than a property of the run.

失败即停的规则是这三样里最不起眼的一样，却最决定输出的形状。一个对自己只部分理解的 kernel 也“尽力而为”的拼接器，做出来的镜像只在它测过的路径上是对的；Olympus 的做法是把这个 kernel 报为未追踪、一个偏移也不改，于是存在的追踪就是镜像被证明过的追踪，而工具的覆盖率是报告里可以读到的一个数，而不是某次运行的属性。
