Not getting in the way不碍事

A GPU core interlocks nothing. Two dependent instructions issue the right distance apart because the compiler encoded that distance into their control bits, and a variable-latency result is waited for because the compiler named a scoreboard. Once a probe is spliced in, those are the planner's responsibilities, and the hazard model is what it knows. This chapter is the model, where its numbers come from, how it proves itself on ptxas's own code, and the three rules it learned on the GPU.

GPU 核心不做任何互锁。两条相互依赖的指令之所以隔着正确的距离发射，是因为编译器把这段距离编进了它们的控制位；一个可变延迟的结果之所以被等到，是因为编译器指定了一个 scoreboard。探针一旦拼进去，这些就成了规划器的责任，而冒险模型就是它所知道的一切。本章讲这个模型、它的数字从哪来、它如何在 ptxas 自己的代码上证明自己，以及它在 GPU 上学到的三条规则。

§1Contract契约

What this layer promises这一层的承诺

The minimum issue distance and the scoreboard rules that keep a probe from stalling the kernel.

让探针不会使 kernel 停顿的最小发射间距和 scoreboard 规则。

olympus/hazards → used by使用者 olympus/planner (the exact and search schedulers) and（exact 与 search 调度器）和 olympus/verify · reads读取 olympus/isa (decode, the control word) and（解码、控制字）和 olympus/cfg (paths)（路径）

Olympus measures a kernel's internal timing by inserting a few extra instructions — a probe — at chosen points inside the kernel's own machine code. Chapter 04 builds those instructions; chapter 05 decides which registers and which control bits each one carries. Every inserted instruction raises the same question twice. How many cycles must separate it from the instruction before it, and from the instruction after it? And if some result it depends on does not arrive at a fixed time, which of the warp's six scoreboards must be waited on before that result is read? Answering those two questions, for any pair of instructions where at least one is a probe instruction, is this layer's whole job.

Olympus 通过在 kernel 自己的机器码中选定的位置插入少量额外指令——一个探针——来测量 kernel 的内部时序。第 04 章构造这些指令，第 05 章决定每条指令带哪些寄存器和哪些控制位。每一条插入的指令都会两次引出同一个问题：它与前一条指令之间、以及它与后一条指令之间，必须隔多少个周期？如果它依赖的某个结果到达时间不固定，那么在读这个结果之前必须等待 warp 六个 scoreboard 中的哪一个？对任何至少有一方是探针指令的指令对回答这两个问题，就是这一层的全部工作。

The promise is two-sided, and both sides can be got wrong. Too small a distance and the probe reads a register whose producer has not landed yet, or overwrites a register the kernel is still going to read: either the trace is wrong or the kernel is. Too large a distance, or a wait on the wrong scoreboard, and the probe holds the warp up. The kernel then runs slower than it would have without instrumentation, and the number the probe wrote down describes the instrumented kernel rather than the real one. A tracer that changes what it measures has failed even when every bit it writes out is correct.

这个承诺是双向的，两边都可能出错。间距太小，探针会读到生产者还没写完的寄存器，或者覆盖掉 kernel 之后还要读的寄存器：要么追踪结果是错的，要么 kernel 是错的。间距太大，或者等错了 scoreboard，探针就会把 warp 挡住。kernel 于是跑得比没有插桩时更慢，探针记下的数字描述的是被插桩的 kernel，而不是真实的那个。一个会改变被测对象的追踪器，即使写出的每一位都正确，也已经失败了。

So the model is consulted three times on the way to the GPU. The planner asks it for each distance and each scoreboard while it schedules. The planner then hands the whole spliced program back for check, which re-derives every pair from scratch. And the rewriter checks the real spliced cubin, decoded again from its own bytes, before the runtime of chapter 07 is allowed to load it. Run over unmodified kernels instead, the same model is also what proves the model (§3).

所以在送上 GPU 之前，这个模型会被用到三次。规划器在调度时向它逐一询问每个间距和每个 scoreboard。然后规划器把整个拼接后的程序交回来做 check，从头重新推导每一对。重写器再对真实拼接后的 cubin（从它自己的字节重新解码）检查一遍，第 07 章的运行时才被允许加载它。而把同一个模型用在未经修改的 kernel 上，它也正是证明这个模型本身的手段（§3）。

§2Invariant不变量

Invariants不变量3 · 4

A probe never waits on a scoreboard only the kernel claims; such a wait would turn the kernel's overlapped latency into a stall and change what is being measured. A wait is issued at least 2 cycles after the instruction that sets its scoreboard, the rule ptxas itself follows in every kernel we have examined.

探针从不等待只有 kernel 占用的 scoreboard；这样的等待会把 kernel 本可重叠的延迟变成停顿，改变被测量的东西。等待至少在设置其 scoreboard 的指令之后 2 个周期发出，这是 ptxas 在我们检查过的每个 kernel 中都遵守的规则。

Checked by the hazard model's check over the spliced program and again over the real spliced cubin, which reports every probe store without a read scoreboard and every probe variable-latency write without a write scoreboard model.py:488–491; by the planner's static check of every probe wait bit (chapter 05); by SB-SET, which flags any wait fewer than SB_SET_GAP = 2 cycles after its setter exact.py:79–86; and by the self-check's sbgap survey, which is the rule's evidence: over 976 ptxas kernels, 0 waits at distance 1 against 5,314 write and 1,416 read claims waited on at distance 2 (DECISIONS 62).

检查方式：冒险模型的 check 先过拼接后的程序，再过真实拼接后的 cubin，报告每一个没有读 scoreboard 的探针 store 和每一个没有写 scoreboard 的探针可变延迟写入 model.py:488–491；规划器对每个探针等待位的静态检查（第 05 章）；SB-SET，标出任何距离设置者不足 SB_SET_GAP = 2 个周期的等待 exact.py:79–86；以及自检的 sbgap 普查，它是这条规则的依据：976 个 ptxas kernel 中，距离为 1 的等待 0 个，而在距离 2 处被等待的写占用有 5,314 个、读占用 1,416 个（DECISIONS 62）。

A scoreboard is claimed when some instruction has set it and nothing has waited on it yet; the claim is outstanding, and the hardware will clear it when that operation completes. A scoreboard "only the kernel claims" is one the kernel set for an operation of its own, which no probe register depends on. Waiting on it buys the probe nothing and costs it the whole remaining lifetime of the kernel's operation.

当某条指令设置了一个 scoreboard 而还没有谁等待它时，这个 scoreboard 处于被占用状态；占用悬而未决，待那次操作完成后由硬件清除。"只有 kernel 占用的" scoreboard，指 kernel 为自己的某次操作设置、而没有任何探针寄存器依赖它的那一个。等它对探针毫无益处，代价却是 kernel 那次操作剩下的全部寿命。

Both rules replaced something weaker that the documentation allowed. The latency file's TABLE_TRUE(SCOREBOARD) says ORDERED_ZERO: a wait may follow its setter immediately. The first hazard-exact scheduler believed it, waited one cycle after an S2R that claimed SB0, read a stale register, and 0 of 57 trace-buffer checks passed on the GPU. And a weaker form of invariant 3, "wait on a kernel scoreboard when it is cheap", needs a latency the model does not have: how long an asynchronous TMA store or bulk copy will hold its scoreboard is a property of the copy, not of the instruction that started it. At k512's c.tile_done the answer was about 1,450 cycles; the widget below shows what that does to one warp.

两条规则各自取代了一个文档允许、却更弱的说法。延迟文件的 TABLE_TRUE(SCOREBOARD) 写的是 ORDERED_ZERO：等待可以紧跟在设置者之后。第一版按冒险精确调度的调度器相信了它，在占用 SB0 的 S2R 之后一个周期就等待，读到了过期的寄存器，GPU 上 57 次追踪缓冲区检查 0 次通过。而不变量 3 的弱化版"便宜的时候就等 kernel 的 scoreboard"，需要一个模型没有的延迟：一次异步的 TMA store 或 bulk copy 会把它的 scoreboard 占多久，是那次拷贝的性质，而不是发起它的那条指令的性质。在 k512 的 c.tile_done，答案是约 1,450 个周期；下面的组件展示这对一个 warp 意味着什么。

§3How it works如何工作

What "issue" means, and what a stall count buys什么叫"发射"，stall 计数又买到了什么

Start with what goes wrong. A streaming multiprocessor holds several warps at once and, each cycle, issues one instruction from one of them: it hands that instruction to a pipeline and moves on. Within one warp the instructions are issued in program order, one at a time. What the hardware does not do is check whether the operands of the instruction it is issuing are ready. There is no interlock on a register and none on a pipe. If a consumer issues before its producer's result has reached the register file, the consumer reads whatever was in the register before — silently, with no fault and no retry.

先说会出什么错。一个流多处理器同时驻留若干 warp，每个周期从其中一个 warp 发射一条指令：把这条指令交给某条流水线，然后继续。在单个 warp 内部，指令按程序顺序逐条发射。硬件不会做的事情是：检查它正在发射的这条指令的操作数是否就绪。寄存器上没有互锁，流水线上也没有。如果消费者在生产者的结果写回寄存器文件之前就发射了，消费者读到的就是寄存器里原来的内容——悄无声息，不报错，也不重试。

Correct machine code is therefore code whose instructions were placed far enough apart, and the distance is carried by the instructions themselves. Every sm_90 instruction is 128 bits wide, and part of it is a scheduling control word which these chapters write in the assembler's own bracket form. Its stall count lives in the 5-bit usched field at bit 105 and is the number of cycles this warp must let pass before issuing its next instruction instr.py:65–70:

因此，正确的机器码就是指令被摆得足够开的代码，而这段距离由指令自己携带。每条 sm_90 指令宽 128 位，其中一部分是调度控制字，本系列章节用汇编器自己的方括号写法来表示它。它的 stall 计数位于第 105 位起的 5 位 usched 字段，表示这个 warp 在发射下一条指令之前必须放过多少个周期 instr.py:65–70：

[wr_sb : rd_sb : {wait mask} : stall : yield]

  wr_sb        the scoreboard this instruction's destination releases; 7 = none
  rd_sb        the scoreboard this instruction's sources release;      7 = none
  {wait mask}  wait here until every listed scoreboard is clear; {} = wait on nothing
  stall        cycles before this warp's next instruction may issue (0..15)
  yield        1 = other warps may issue in those cycles, 0 = keep issuing this warp

  ;[2:7:{}:1:0]    claims SB2 for its result, waits on nothing, stalls 1 cycle
  ;[7:0:{}:2:0]    claims SB0 for its sources, waits on nothing, stalls 2 cycles
  ;[7:7:{2}:1:0]   claims nothing, waits until SB2 is clear, stalls 1 cycle

A stall count buys exactly one thing: provable cycles between two issues, at most 15 at a time. That is why the model's arithmetic is a sum. Instruction i+1 issues at least gap(i) cycles after i, where gap(i) is the stall count and at least 1 — a stall of 0 still costs the one cycle of issue, and it also means DRAIN, which is worse than nothing (third rule below). The provable delay between a producer P and a consumer C is the sum of gap over the instructions from P to C−1, taken along every path through the control-flow graph that reaches C model.py:1–30.

stall 计数买到的东西只有一样：两次发射之间可证明的周期数，一次最多 15 个。这也是为什么模型的算术是求和。指令 i+1 在 i 之后至少 gap(i) 个周期才发射，其中 gap(i) 是 stall 计数且至少为 1——stall 为 0 仍然要花掉发射本身的那一个周期，而且它还意味着 DRAIN，那比什么都不做更糟（见下面第三条规则）。生产者 P 与消费者 C 之间可证明的延迟，是从 P 到 C−1 这些指令上 gap 的和，并且要沿控制流图中到达 C 的每一条路径分别取 model.py:1–30。

Now the reason this chapter exists. Those distances were made exactly tight by the compiler: ptxas gave each instruction the smallest stall that was safe, because every extra cycle is a cycle the warp does not issue. Insert instructions between two of the kernel's own and you have lengthened a distance that was already sufficient, which is harmless. But the same insertion makes the kernel's instruction at the insertion point issue later than the compiler intended — and that lateness, counted in cycles, is the entire cost of instrumenting that point. Everything below is about keeping that number small while keeping the code correct.

这就是本章存在的理由。那些距离是编译器刚刚卡紧的：ptxas 给每条指令配的是安全前提下最小的 stall，因为每多一个周期都是 warp 不发射的一个周期。在 kernel 自己的两条指令之间插入指令，会把一段本来就够长的距离拉得更长，这无害。但同一次插入也让插入点处 kernel 的那条指令比编译器预期的更晚发射——而这段以周期计的"晚"，就是在该点插桩的全部代价。下面讲的一切，都是如何在保持代码正确的同时把这个数字压小。

Fixed latency, variable latency固定延迟，可变延迟

Not every result arrives at a time you can count. An IADD3 writes its destination a fixed number of cycles after it issues, every time it runs, because the integer datapath has a fixed depth. A LDG writes its destination when the memory system comes back, which depends on which cache hit, on what other warps are doing, and on the DRAM. A distance in cycles can protect the first kind of result and cannot protect the second, so the architecture gives the two kinds different machinery and the model makes two separate passes.

并非每个结果都在一个数得出来的时刻到达。IADD3 每次执行都在发射后固定若干周期写回目的寄存器，因为整数数据通路深度固定。LDG 则是在存储系统返回时才写回目的寄存器，这取决于命中了哪一级缓存、其他 warp 在做什么，以及 DRAM。以周期计的距离能保护第一类结果，却保护不了第二类，所以架构为这两类提供了不同的机制，模型也分两遍处理。

For a fixed-latency pair the model looks the required distance up in one of three tables and compares it with the provable delay. TABLE_TRUE covers a read after a write (RAW: the consumer needs the value). TABLE_OUTPUT covers a write after a write (WAW: the two writes must land in order). TABLE_ANTI covers a write after a read (WAR: the later write must not clobber the register before the earlier instruction has read it). Each table is given per register file — general-purpose, uniform, predicate — and each entry is indexed by the roles the shared register plays in the two instructions, so an IMAD whose result a store later uses as an address is a different cell from one a later IADD3 adds. Above the three tables sits an occupancy table: two instructions needing the same pipe cannot issue in the same cycle even when no register connects them.

对固定延迟的指令对，模型在三张表之一里查出所需距离，再与可证明的延迟比较。TABLE_TRUE 管写后读（RAW：消费者需要这个值）。TABLE_OUTPUT 管写后写（WAW：两次写必须按顺序落地）。TABLE_ANTI 管读后写（WAR：后面的写不能在前面那条指令读到之前就把寄存器覆盖掉）。每张表按寄存器文件分别给出——通用、uniform、谓词——每个表项还按共享的那个寄存器在两条指令中扮演的角色索引，所以"IMAD 的结果被后面的 store 当地址用"和"被后面的 IADD3 当加数用"是两个不同的单元格。三张表之上还有一张占用表：两条需要同一条流水线的指令，即使没有寄存器把它们联系起来，也不能在同一周期发射。

A variable-latency result has no table value at all. It is pending from the moment its instruction issues until some later instruction waits on the scoreboard that instruction claimed, and no amount of stall makes it safe: there is no number of cycles after an LDG at which its register is certainly written. So the model requires something different here. Every later access to a pending register — a read of a pending write, a write over a pending write, a write over a pending late read — must be preceded, on every path that can reach it, by a wait on the claiming scoreboard. Which instruction classes are variable-latency is read off the ISA: the DECOUPLED and MIO classes always, the COUPLED_EMULATABLE ones such as HMMA only for the instances that actually set a scoreboard model.py:1–30. A third pass handles the asynchronous WGMMA groups, whose register reads and writes are committed in batches by a gsb0 operation rather than tracked one at a time.

可变延迟的结果根本没有表值。从它的指令发射那一刻起，它就处于未决状态，直到后面某条指令等待该指令占用的 scoreboard；再多的 stall 也不能让它变安全：在 LDG 之后并不存在某个周期数，能保证它的寄存器一定已经写好。所以模型在这里要求的是另一种东西。之后对一个未决寄存器的每一次访问——读一个未决的写、覆盖一个未决的写、覆盖一次未决的延后读——都必须在能到达它的每一条路径上，先有一次对占用它的那个 scoreboard 的等待。哪些指令类属于可变延迟是从 ISA 里读出来的：DECOUPLED 与 MIO 类总是如此，而 HMMA 这类 COUPLED_EMULATABLE 只在真正设置了 scoreboard 的那些实例上才算 model.py:1–30。第三遍处理异步的 WGMMA group，它们的寄存器读写由一条 gsb0 操作成批提交，而不是逐条跟踪。

Six scoreboards, set and waited on六个 scoreboard：登记与等待

A scoreboard is one of six per-warp counters the hardware uses to track an operation that is still in flight. Each instruction can set one write scoreboard (wr_sb: my destination register is not written yet) and one read scoreboard (rd_sb: I will read my source registers later, so do not overwrite them yet), and can wait on any subset of the six through its 6-bit wait mask or through a DEPBAR.LE instruction. A scoreboard with no outstanding claim is free, and which ones are free is a property of a point in the program, not of the kernel as a whole model.py:1093–1098.

scoreboard 是硬件用来跟踪尚在执行中的操作的六个 per-warp 计数器之一。每条指令可以设置一个写 scoreboard（wr_sb：我的目的寄存器还没写好）和一个读 scoreboard（rd_sb：我稍后才读我的源寄存器，先别覆盖它们），并通过 6 位等待掩码或一条 DEPBAR.LE 指令等待这六个中的任意子集。没有未决占用的 scoreboard 是空闲的；哪些空闲是程序中某一点的性质，而不是整个 kernel 的性质 model.py:1093–1098。

The read scoreboard is the less obvious of the two, and a probe cannot do without it. A store does not read its data and address registers when it issues; the load-store unit collects them later, when the memory operation is dispatched. The measurements found no safe fixed gap at all for store sources — a store's registers can still be read up to 32 cycles after it issued — so only its read scoreboard can tell a later instruction that they are free. Probes are therefore held to a stricter standard than the kernel. A probe store must set a read scoreboard and a probe variable-latency write must set a write scoreboard; the checker reports SB-NORD and SB-NOWR otherwise model.py:488–491. The kernel may skip a claim because ptxas knows the operation will retire in order behind a later one in the same queue; a probe never leans on that economy measured.py:20–24.

读 scoreboard 是两者中不那么直观的一个，而探针离不开它。store 并不在发射时读它的数据和地址寄存器；加载存储单元要等存储操作真正派发时才去收集它们。实测结果是：store 的源操作数根本没有任何安全的固定间隔——一条 store 的寄存器在它发射之后最多 32 个周期还可能被读取——所以只有它的读 scoreboard 能告诉后面的指令这些寄存器已经空出来了。因此探针被要求得比 kernel 更严：探针的 store 必须设置读 scoreboard，探针的可变延迟写入必须设置写 scoreboard；否则检查器报告 SB-NORD 和 SB-NOWR model.py:488–491。kernel 可以省掉一次占用，因为 ptxas 知道这次操作会在同一队列里排在后面某次操作之后按序退休；探针从不依赖这种省法 measured.py:20–24。

Six is a small number, and it is the hard limit on this whole approach. A probe needs at least one free scoreboard at its insertion point, because its own store has to claim one. At a point where the kernel already holds all six there is nothing left to claim and nothing safe to borrow, so that point cannot be instrumented at all; the planners refuse it rather than guess.

六是个小数字，也是整套做法的硬上限。探针在它的插入点上至少需要一个空闲 scoreboard，因为它自己的 store 必须占一个。在 kernel 已经占满六个的位置上，既没有可占的，也没有可安全借用的，所以这个位置根本无法插桩；规划器会拒绝它，而不是去猜。

Where the numbers come from数字从哪里来

Three sources give numbers for the same pair of instructions, they disagree, and the rule is that the strictest applicable one wins. The first source is the tables themselves: nvidia-sass-document's sm_90_latencies.txt (and sm_103_latencies.txt for GB300), parsed completely by Olympus's own parser — operation sets with their set algebra, connector roles, the TRUE / OUTPUT / ANTI tables per register file, the occupancy table. The two known bugs of the upstream parser cannot occur here, because table bodies are cut out before any set is read and statements run to their terminating semicolon tables.py:1–36. Each variable-latency class's execution queue comes from the instruction dump, scanned line by line because that file is far too large to hold in memory isaprops.py:1–11.

同一对指令有三个来源给出数字，它们互不一致，而规则是：适用者中最严的那个胜出。第一个来源是表本身：nvidia-sass-document 的 sm_90_latencies.txt（GB300 上是 sm_103_latencies.txt），由 Olympus 自己的解析器完整解析——带集合代数的操作集合、连接器角色、按寄存器文件的 TRUE / OUTPUT / ANTI 表、占用表。上游解析器的两个已知 bug 在这里不可能发生，因为表体在读任何集合之前就被切出，而语句一直读到结尾的分号 tables.py:1–36。每个可变延迟指令类的执行队列来自指令转储，逐行扫描，因为那个文件大到无法整体读入内存 isaprops.py:1–11。

The second source is ptxas. Real compiler output schedules some pairs closer than the table allows, and that code runs correctly, so a model that rejected it would be wrong about the hardware. For the kernel's own pairs the model therefore accepts a gap at or above ptxas's floor for that exact table cell: the smallest gap ptxas was observed to use for the cell over 957 ptxas-compiled kernels that are not in the corpus. Each floor also carries a mechanism that explains it — integer and uniform forwarding, a memory or branch consumer that reads its operands after issue, back-to-back FMA-pipe issue, a blocking barrier that holds the warp anyway — so a floor is a documented hardware fact, not a fitted constant relaxations.py:1–8. 7,245 original corpus pairs are closer than the table, and every one of them is inside a floor (DECISIONS 43).

第二个来源是 ptxas。真实的编译器输出里，有些指令对排得比表允许的更紧，而那些代码运行正确，所以一个会拒绝它们的模型对硬件的判断是错的。因此，对 kernel 自己的指令对，模型接受不低于该表格单元 ptxas 下限的间隔：在语料库之外 957 个由 ptxas 编译的 kernel 上，观察到 ptxas 为该单元用过的最小间隔。每个下限还附有解释它的机制——整数与 uniform 前递、在发射之后才读操作数的内存或分支消费者、背靠背的 FMA 流水线发射、本来就会挡住 warp 的阻塞式 barrier——所以下限是一条有据可查的硬件事实，而不是拟合出来的常数 relaxations.py:1–8。语料库里有 7,245 对原始指令比表更紧，其中每一对都落在某个下限之内（DECISIONS 43）。

Probe pairs never take the floors. A floor is evidence about ptxas's code in ptxas's context, and a probe is neither. What a probe may take instead is the third source: the measured minimum safe gap, for the specific pairs the probe templates actually use. Each was measured on H200 with every thread checked fresh at every gap from the candidate up to the table value, across filler shapes, alignments, launch shapes and repetitions, up to 330 million threads per pair; a pair that does not match a measured entry exactly — same dependency kind, same register file, same roles, same opcodes — keeps the table value measured.py:1–18 (DECISIONS 46). The measurements cut some pairs well below ptxas's own floor (CS2R to STG is safe at 4 where the table says 8) and raised others above it (FXU to IMAD needs 5, not ptxas's 3), and they found one pair with no slack at all: ELECT to a store guarded by its predicate needs the table's full 13 cycles. Exactly one floor is allowed through for a probe: a probe consumer directly after a blocking kernel BAR.SYNC may take ptxas's floor of 1 for that one cell, because the barrier itself already held the warp (DECISIONS 50). On GB300 none of the measurements apply yet, so every probe pair there is held to the raw table — correct, only slower.

探针的指令对从不使用下限。下限是关于 ptxas 的代码、在 ptxas 的上下文里的证据，而探针两者都不是。探针能用的是第三个来源：针对探针模板实际用到的那些具体指令对的实测最小安全间隔。每一对都在 H200 上测过：从候选间隔到表值之间的每个间隔上，每个线程都被检查为读到新值，覆盖各种填充形状、对齐、启动形状和重复次数，每对最多 3.3 亿线程；没有精确匹配上某条实测条目的指令对——依赖种类、寄存器文件、角色、操作码都要相同——仍用表值 measured.py:1–18（DECISIONS 46）。实测把一些指令对压到了远低于 ptxas 自己下限的位置（CS2R 到 STG 在 4 就安全，而表说 8），也把另一些抬到了下限之上（FXU 到 IMAD 需要 5，而不是 ptxas 的 3），还找到一对完全没有余量的：ELECT 到受它的谓词保护的 store，需要表上完整的 13 个周期。只有一个下限被允许用于探针：紧跟在 kernel 阻塞式 BAR.SYNC 之后的探针消费者，可以用 ptxas 对该单元的下限 1，因为 barrier 本身已经把 warp 挡住了（DECISIONS 50）。在 GB300 上还没有任何实测可用，所以那里每一对探针指令都按原始表值处理——正确，只是更慢。

The self-check: ptxas's code must pass自检：ptxas 的代码必须通过

A hazard model that rejects correct code is wrong, so the model is run over every original corpus kernel along its control flow: fixed latencies and occupancy against the table with the floors applied, scoreboards and WGMMA groups exactly. The result on all 19 corpus kernels is 0 unexplained violations and 0 scoreboard or GMMA violations; the 7,245 original pairs below the table are all inside a floor, and the free scoreboards the model computes agree with the liveness analysis of chapter 02 at all 19,858 reachable instructions (DECISIONS 43). The same tool calibrates the floors on kernels that are not in the corpus, checks held-out cubin lists, and runs sbgap, the setter-to-wait distance survey behind invariant 4 selfcheck.py:1–31. The walk over a kernel's instructions and successors is shared with the planners, so they check the same graph the self-check proved walk.py:1–4.

一个会拒绝正确代码的冒险模型是错的，所以模型会沿控制流过一遍语料库里的每个原始 kernel：固定延迟和占用对照应用了下限的表，scoreboard 和 WGMMA group 精确检查。在全部 19 个语料库 kernel 上的结果是 0 个无法解释的违例、0 个 scoreboard 或 GMMA 违例；低于表值的 7,245 对原始指令全部在某个下限之内，模型算出的空闲 scoreboard 在全部 19,858 条可达指令上与第 02 章的活跃性分析一致（DECISIONS 43）。同一个工具在语料库之外的 kernel 上校准下限、检查保留的 cubin 列表，并运行 sbgap，即不变量 4 背后的设置者到等待距离普查 selfcheck.py:1–31。遍历 kernel 指令及其后继的代码与规划器共用，所以它们检查的正是自检证明过的那张图 walk.py:1–4。

Three rules learned on the GPU在 GPU 上学到的三条规则

Everything above can be derived at a desk. The three rules below could not: each one replaced a reading of the documentation that was defensible on paper and wrong on the hardware, and each is given here with the measurement that settled it and with what the earlier version cost.

上面的内容都可以在桌面上推导出来。下面三条规则不行：每一条都取代了一种在纸面上说得通、在硬件上却是错的文档读法，而每一条都连同定下它的那次测量、以及早先那版的代价一起写在这里。

  1. No probe waits on a scoreboard only the kernel claims. The mechanism is the thing to see. A wait does not test a register; it blocks the warp until the claiming operation has completed. At each tile end of DeepGEMM k512 the TMA-store leader warps commit stores that claim SB0, and the kernel does not wait on SB0 until one tile later — it deliberately overlaps the whole store with the next tile's arithmetic. A probe that waits on SB0 at that point converts latency the kernel had successfully hidden into a stall the kernel never had, which is to say it changes the very delay the probe is there to measure. Splicing nothing but a single NOP that waits on SB0 costs +18.4% end to end at k512, about 0.8–0.9 µs per tile, and +5.3% at k2048; the same island without that one wait costs −0.3%, which is inside the noise. It accounts for 18.4 of the 27.3 points of overhead charged by the oracle tool — G-Watch 0.0.35, the second tracer Olympus was measured against, which chapter 09 uses as its reference — on that kernel (DECISIONS 61). The rule is implemented three ways: probe claims are drawn only from the free set; a kernel scoreboard is waited on only for a register the probe itself touches that is pending there; and when no scoreboard is free the site is refused rather than reclaimed (DECISIONS 63) exact.py:25–35.
  2. A wait is issued at least 2 cycles after the instruction that sets its scoreboard. The table permits zero: TABLE_TRUE(SCOREBOARD) says ORDERED_ZERO, so in principle a wait may follow its setter immediately. This rule is instead the one ptxas itself follows in every kernel we have examined. Over 976 ptxas kernels there are 0 set-to-wait pairs at distance 1, against 5,314 write claims and 1,416 read claims waited on at distance 2; the only distance-1 cases in the whole survey follow a draining USETMAXREG, which waits for everything anyway selfcheck.py:19–21. What happens if you issue it sooner is that the wait does not see the claim at all: it passes, the warp reads the register before the late write lands, and then the late write overwrites what the consumer computed. The first hazard-exact scheduler did exactly this — an S2R claiming SB0, and a LOP3 on the same register waiting on SB0 one cycle later — and wrote stale slot headers and stale addresses into the trace buffer: 0 of 57 buffer checks passed on the GPU. SB_SET_GAP is now 2, counted in provable cycles, with kernel setters just before an island included, and checked as SB-SET both in the repair loop and in the rewriter (DECISIONS 62).
  3. No DRAIN in an island word. A stall count of 0 does not mean "no delay": usched 0 is DRAIN, which holds the warp until its pipeline has emptied before the next instruction issues. nvidia-sass-document's notes measure that at about 34 solo-warp cycles (DECISIONS 53), and ptxas uses it only where it wants exactly that. The first null splices — islands with no probe in them, spliced purely to price the splicing itself — were padded with ptxas's own padding word NOP ;[7:7:{}:0:1], which carries usched 0. Placed before every basic-block leader it cost +59.6% on matmul, +29% on FlashMLA and +26% on k512. The identical splice with a stall-1 word costs +0.1%, +1.1% and +0.9%. The island filler is now ptxas's stall extender @!UPT UIADD3 URZ, …, which is predicated off so it never executes, has no operands and no pipe occupancy, waits on nothing and claims nothing islands.py:40–45, and the schedulers reject stall 0 outright (DECISIONS 54).
  1. 探针不等待只有 kernel 占用的 scoreboard。要看清的是机制。一次等待并不是去检测某个寄存器，而是把 warp 挡住，直到占用它的那次操作完成。在 DeepGEMM k512 每个 tile 结尾，负责 TMA store 的 leader warp 提交 store 并占用 SB0，而 kernel 要到下一个 tile 才等 SB0——它是故意让整个 store 与下一个 tile 的算术重叠。在那个位置等待 SB0 的探针，会把 kernel 成功隐藏起来的延迟变成 kernel 本来没有的停顿，也就是说，它改变的正是探针要去测量的那段延迟。只拼接一条等待 SB0 的 NOP，别的什么都不加，k512 端到端就慢 +18.4%，约合每个 tile 0.8–0.9 µs，k2048 上慢 +5.3%；同一个 island 去掉这一次等待则是 −0.3%，落在噪声之内。它解释了 oracle 工具——G-Watch 0.0.35，Olympus 用来对照测量的第二个追踪器，第 09 章拿它当参考——在该 kernel 上 27.3 个百分点开销中的 18.4 个（DECISIONS 61）。这条规则用三种方式落实：探针的占用只从空闲集合中取；只在探针自己触及的寄存器挂在某个 kernel scoreboard 上时才等它；没有空闲 scoreboard 时拒绝该站点，而不是回收（DECISIONS 63）exact.py:25–35。
  2. 等待至少在设置其 scoreboard 的指令之后 2 个周期发出。表允许零：TABLE_TRUE(SCOREBOARD) 写的是 ORDERED_ZERO，所以原则上等待可以紧跟在设置者之后。这条规则其实是 ptxas 在我们检查过的每个 kernel 中都遵守的做法。在 976 个 ptxas kernel 上，距离为 1 的登记到等待对有 0 个，而距离 2 处被等待的写占用有 5,314 个、读占用 1,416 个；整个普查中唯一的距离 1 情形都在排空流水线的 USETMAXREG 之后，而它本来就等一切 selfcheck.py:19–21。更早发出会发生的事情是：这次等待根本看不见那个占用——它直接通过，warp 在延后的写落地之前就读了寄存器，随后那次延后的写又把消费者算出的结果覆盖掉。第一版按冒险精确调度的调度器正是这么做的——一条占用 SB0 的 S2R，一个周期之后一条读同一寄存器、等待 SB0 的 LOP3——结果把过期的槽位头和过期的地址写进了追踪缓冲区：GPU 上 57 次缓冲区检查 0 次通过。现在 SB_SET_GAP 为 2，按可证明的周期计，紧邻 island 之前的 kernel 设置者也算在内，并在修复循环和重写器中都以 SB-SET 检查（DECISIONS 62）。
  3. island 的字里不出现 DRAIN。stall 计数为 0 并不表示"不延迟"：usched 0 就是 DRAIN，它会在下一条指令发射之前把 warp 挡住，直到流水线排空。nvidia-sass-document 的笔记把这个代价测为单 warp 约 34 个周期（DECISIONS 53），而 ptxas 只在它正想要这个效果的地方才用它。最早的空拼接（null splice）——里面没有探针、纯粹为给拼接本身定价而拼进去的 island——用 ptxas 自己的填充字 NOP ;[7:7:{}:0:1] 来垫，而它带着 usched 0。放在每个基本块首指令之前，它让 matmul 慢 +59.6%、FlashMLA 慢 +29%、k512 慢 +26%。完全相同的拼接换成 stall 为 1 的字，只慢 +0.1%、+1.1%、+0.9%。island 的填充字现在是 ptxas 的 stall 延长器 @!UPT UIADD3 URZ, …，它的谓词永假因而永不执行，没有操作数、没有流水线占用，不等待任何东西也不占用任何东西 islands.py:40–45，而调度器直接拒绝 stall 0（DECISIONS 54）。

Worked example: one island at k512's tile end实例：k512 tile 结尾处的一个 island

One real site, decoded from the DeepGEMM k512 cubin, planned two ways. The site is labelled c.tile_done and its insertion point is instruction index 1100; the same site and the same instructions drive the widget in §5, so every value below can be read off it. The two ways are the island the search planner produced and the one-instruction experiment of DECISIONS 61.

一个真实站点，从 DeepGEMM k512 的 cubin 解码而来，按两种方式规划。这个站点标签为 c.tile_done，插入点是指令索引 1100；§5 的组件用的就是同一个站点和同一批指令，所以下面的每个数值都能在上面读出来。两种方式分别是 search 规划器给出的 island，和 DECISIONS 61 的单指令实验。

  1. The kernel instruction at the insertion point. Index 1100 is S2UR UR16, SR_CTAID.X ;[2:7:{}:1:0]: it reads a special register into a uniform register, claims write scoreboard SB2 for that result because the read is variable-latency, waits on nothing, and stalls 1 cycle. An island inserted "before index 1100" runs on every path that reaches 1100, and the cost of this site is how many cycles later this S2UR issues.
  2. What the kernel is holding there. Two instructions earlier, index 1098 is UTMACMDFLUSH ;[7:0:{}:2:0], which claims read scoreboard SB0 on behalf of the two TMA stores at 1096 and 1097 — their source registers are read late, by the TMA engine. The kernel's wait on SB0 is a DEPBAR.LE SB0 one tile later, at code offset 0x3ad0. SB1 is held too, by 22 STSM read claims and a BAR. So at index 1100 the busy scoreboards are {0, 1} and the free ones are {2, 3, 4, 5}.
  3. What the probe needs. The search planner's island here is 8 instructions. Its payload is a 32-bit store, @P0 STG.E [RZ+UR0+0x20], R4, writing one record into the trace buffer; R4 holds a clock reading taken by CS2R.32 R4, SR_CLOCKLO, and P0 is the predicate an ELECT set so that only one lane of the warp stores. By the rule above the store must claim a read scoreboard, and it takes SB2 — free at this point, and claimed by the kernel's own S2UR only after the island has ended.
  4. The one distance with no slack. ELECT to a store guarded by its predicate needs 13 cycles, the full table value, and it is the one probe pair the measurements could not reduce (DECISIONS 46). Had the scheduler trusted ptxas's floor here, the guarded store could have issued before P0 was written and the wrong lanes would have stored. The island pays those 13 cycles with work rather than with stalls: the ULOP3 that computes the slot mask, the CS2R clock read, the UIADD3 that bumps the slot counter and the UIMAD.WIDE.U32 that turns it into a byte offset all sit between ELECT and the store, and only the LEA.LO just before it carries a long stall, 7.
  5. Closing the island. The last instruction is a bare NOP ;[7:7:{2}:1:0]: it waits on SB2 and nothing else, so the probe's claim is released before the kernel's instruction at 1100 issues and no probe state outlives the island. The store before it carries stall 2, which is exactly SB_SET_GAP. At stall 1 the NOP might not have seen the claim at all, passed straight through, and left the store's registers to be reused while the load-store unit was still reading them — the failure of rule 2, with a corrupt trace record as the symptom.
  6. The verdict. The island's wait mask mentions SB2 and nothing else. SB0 and SB1, the two the kernel holds, are never touched. The island adds its own provable length before index 1100 and nothing more, and end to end at k512 that measures −0.3%: no distinguishable change in the kernel's running time.
  7. The same site, done wrong. Now splice a single instruction, NOP ;[7:7:{0}:1:0], which does nothing except wait on SB0. There is no register to protect and no value to read; the wait exists only because SB0 was busy and waiting on a busy scoreboard looked free. The warp now blocks at index 1100 until the tile's TMA stores have completed — about 1,450 cycles, the latency the kernel had spread across the whole next tile. End to end: +18.4% [18.25, 18.61] at k512 and +5.3% at k2048. One instruction, and the probe costs more than the phase it was timing. The oracle tool's probe at this same site makes the same mistake plus one of its own: its closing UIADD3.64 waits on {0, 2}, SB0 being the kernel's and SB2 its own.
  1. 插入点处 kernel 的那条指令。索引 1100 是 S2UR UR16, SR_CTAID.X ;[2:7:{}:1:0]：它把一个特殊寄存器读入 uniform 寄存器，因为这次读取是可变延迟的，所以为该结果占用写 scoreboard SB2；它不等待任何东西，stall 为 1。插在"索引 1100 之前"的 island 会在所有到达 1100 的路径上执行，而这个站点的代价，就是这条 S2UR 推迟了多少个周期发射。
  2. kernel 在那里占着什么。往前两条，索引 1098 是 UTMACMDFLUSH ;[7:0:{}:2:0]，它代表 1096 和 1097 处那两条 TMA store 占用了读 scoreboard SB0——它们的源寄存器要由 TMA 引擎延后读取。kernel 对 SB0 的等待是下一个 tile 里、代码偏移 0x3ad0 处的一条 DEPBAR.LE SB0。SB1 也被占着，由 22 条 STSM 的读占用和一条 BAR 持有。所以在索引 1100 处，繁忙的 scoreboard 是 {0, 1}，空闲的是 {2, 3, 4, 5}。
  3. 探针需要什么。search 规划器在这里的 island 有 8 条指令。它的主体是一条 32 位 store，@P0 STG.E [RZ+UR0+0x20], R4，把一条记录写进追踪缓冲区；R4 里是 CS2R.32 R4, SR_CLOCKLO 读到的时钟值，而 P0 是一条 ELECT 设置的谓词，使得 warp 中只有一条 lane 去存储。按上面的规则，这条 store 必须占用一个读 scoreboard，它取了 SB2——在这个位置它是空闲的，而 kernel 自己的 S2UR 要到 island 结束之后才来占用它。
  4. 唯一没有余量的那段距离。ELECT 到受它的谓词保护的 store 需要 13 个周期，即完整的表值，这也是实测唯一压不下来的探针指令对（DECISIONS 46）。如果调度器在这里相信了 ptxas 的下限，受保护的 store 就可能在 P0 写好之前发射，于是存储的会是错误的 lane。这个 island 用工作而不是用 stall 来支付这 13 个周期：算槽位掩码的 ULOP3、读时钟的 CS2R、给槽位计数器加一的 UIADD3、把它换算成字节偏移的 UIMAD.WIDE.U32，全都排在 ELECT 与 store 之间，只有紧挨 store 之前的 LEA.LO 带了一个较长的 stall，7。
  5. 收尾这个 island。最后一条是一条光秃秃的 NOP ;[7:7:{2}:1:0]：它只等 SB2，别的都不等，于是探针的占用在 1100 处 kernel 那条指令发射之前就被释放，没有任何探针状态活过这个 island。它前面那条 store 带的 stall 是 2，正好等于 SB_SET_GAP。若 stall 为 1，这条 NOP 可能根本看不见那个占用、直接通过，于是 store 的寄存器会在加载存储单元还在读它们的时候就被重用——这正是第 2 条规则失效的样子，症状是一条被破坏的追踪记录。
  6. 结论。这个 island 的等待掩码里只提到 SB2，别无其他。kernel 占着的 SB0 和 SB1 从未被碰过。它在索引 1100 之前只加上自己那段可证明的长度，不多一分，而端到端在 k512 上实测为 −0.3%：kernel 的运行时间没有可分辨的变化。
  7. 同一个站点，做错的版本。现在只拼进一条指令，NOP ;[7:7:{0}:1:0]，它除了等待 SB0 什么都不做。这里没有要保护的寄存器，也没有要读的值；这次等待之所以存在，只是因为 SB0 忙着，而等一个忙碌的 scoreboard 看起来不花钱。于是 warp 在索引 1100 处一直阻塞，直到本 tile 的那些 TMA store 完成——约 1,450 个周期，也就是 kernel 原本摊到整个下一个 tile 上的延迟。端到端：k512 上 +18.4% [18.25, 18.61]，k2048 上 +5.3%。一条指令，探针就比它所计时的那个阶段还贵。oracle 工具在同一站点的探针犯了同样的错误，还外加一个它自己的：它收尾的 UIADD3.64 等待 {0, 2}，SB0 是 kernel 的，SB2 是它自己的。

That figure is derived, not measured: DECISIONS 61's 0.8–0.9 µs per tile at the kernel's calibrated clock of about 1.75 GHz (EVAL.md, A6 — A1 to A9 are the nine acceptance criteria the plan set before any code was written, and chapter 09 judges every one of them). The sign and the order of magnitude are what the experiment established; the exact release cycle is not.

下面的组件让 SB0 在 UTMACMDFLUSH 之后保持占用 1,450 个周期。这个数字是推算的，不是实测的：按 DECISIONS 61 的每 tile 0.8–0.9 µs 和该 kernel 约 1.75 GHz 的校准时钟（EVAL.md，A6——A1 到 A9 是计划在写任何代码之前就定下的九条验收标准，第 09 章逐条审它们）折算。实验确立的是方向和数量级，不是精确的释放周期。

§4Where it came from从何而来

The paper's model starts from how a GPU core issues: in order, one warp instruction at a time, with no hardware interlock. Every hazard is therefore the compiler's to resolve, and its decision is encoded in the control bits of the instruction itself — fixed-latency dependencies by issue distance, variable-latency ones by scoreboards paper §4.1. A spliced probe is ordinary machine code in the same warp, so it inherits that contract exactly, and the splicer resolves the probe's hazards with the same tables, attaches a scoreboard to each dynamic dependency from the free set, and, when none is free, reclaims a busy one by waiting on it early paper §4.4. The evaluation counts the dependency waits each tool's probes add and shows the paper's tool keeping only the unavoidable RAW wait paper §5.4.3. Olympus keeps the model and holds itself to that count; the three departures below are where the GPU disagreed with the documentation the model is built on.

论文的模型从 GPU 核心如何发射讲起：按序，每次一条 warp 指令，没有硬件互锁。于是所有冒险都要由编译器解决，而它的决定被编进指令自身的控制位——固定延迟的依赖靠发射间距，可变延迟的依赖靠 scoreboard 论文 §4.1。拼进去的探针是同一个 warp 里普通的机器码，因此完全继承这份约定，所以拼接器用同一套表解决探针的冒险，从空闲集合里给每个动态依赖分配一个 scoreboard，没有空闲的就提前等待一个忙碌的、把它回收过来 论文 §4.4。评估部分统计各工具的探针额外引入的依赖等待，并展示论文的工具只保留不可避免的 RAW 等待 论文 §5.4.3。Olympus 保留了这个模型，并以同样的计数要求自己；下面三处不同，都是 GPU 与模型所依据的文档意见相左的地方。

Where Olympus departs: no early waits on the kernel's scoreboardsOlympus 的不同之处：不提前等待 kernel 的 scoreboardDECISIONS 61

The paper's §4.4 reclaims a busy scoreboard by an early wait, and its tool does so at k512's c.tile_done. Olympus measured that wait alone: +18.4% [18.25, 18.61] at k512, +5.3% at k2048, against −0.3% for the same island without it; it explained 18.4 of the oracle's 27.3 overhead points on that kernel, and the "barrier wait" both tools had reported was this artifact DECISIONS.md:215–221. The rule became invariant 3.

论文 §4.4 用提前等待来回收忙碌的 scoreboard，它的工具在 k512 的 c.tile_done 就是这么做的。Olympus 单独测了这一次等待：k512 上 +18.4% [18.25, 18.61]，k2048 上 +5.3%，而同一个 island 不带它是 −0.3%；它解释了 oracle 在该 kernel 上 27.3 个百分点开销中的 18.4 个，两个工具都报告过的"barrier 等待"就是这个伪影 DECISIONS.md:215–221。这条规则成了不变量 3。

Where Olympus departs: 2 cycles between a setter and its waitOlympus 的不同之处：设置者与等待之间隔 2 个周期DECISIONS 62

The latency file allows a wait at distance zero and the paper does not say otherwise. ptxas, surveyed over 976 kernels, never waits at distance 1, and the scheduler that did wrote stale slot headers on the GPU. Olympus requires 2 provable cycles between a setter and any wait on its scoreboard, kernel setters just before an island included DECISIONS.md:222–226. The rule became invariant 4.

延迟文件允许在距离零处等待，论文也没有另作说明。在 976 个 kernel 上普查，ptxas 从不在距离 1 处等待，而那个这么做的调度器在 GPU 上写出了过期的槽位头。Olympus 要求设置者与任何对其 scoreboard 的等待之间有 2 个可证明的周期，紧邻 island 之前的 kernel 设置者也算在内 DECISIONS.md:222–226。这条规则成了不变量 4。

Where Olympus departs: refuse, do not reclaimOlympus 的不同之处：拒绝，而不回收DECISIONS 63

With no free scoreboard the paper's splicer reclaims; Olympus refuses the site and reports it as a coverage gap. The first hazard-exact scheduler had reclaimed in 117 islands, 66 of them in FlashMLA's memory set, and reproduced the artifact above; the exception for registers the probe itself touches is the only wait on a kernel scoreboard that remains DECISIONS.md:227–232.

没有空闲 scoreboard 时论文的拼接器回收；Olympus 拒绝该站点，并把它报告为覆盖缺口。第一版按冒险精确调度的调度器曾在 117 个 island 里回收，其中 66 个在 FlashMLA 的内存集合里，并复现了上面的伪影；唯一保留的对 kernel scoreboard 的等待，是探针自己触及的寄存器这一例外 DECISIONS.md:227–232。

    Knowing where it's safe知道哪里安全

    Everything this chapter reasons about arrives from there: which registers are dead at a point, which asynchronous operations are still in flight, and so which of the six scoreboards are free. The two analyses are independent and agree at all 19,858 reachable instructions of the corpus.

    本章推理所用的一切都来自那里：某一点上哪些寄存器是死的、哪些异步操作还在执行中，以及由此得出六个 scoreboard 中哪些是空闲的。两个分析彼此独立，在语料库全部 19,858 条可达指令上结论一致。
