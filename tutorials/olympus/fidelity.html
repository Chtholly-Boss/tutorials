Fidelity against G-Watch对照 G-Watch 的保真度

How Olympus's overhead, region timings and tile phases were measured on a shared H200, and what they show: an overhead target that both tools miss, record counts that agree exactly, a 1.2 µs barrier hold that turned out to be the tracer's own doing, and an FA-3 producer that waits on K, not V.

在一台共享的 H200 上，Olympus 的开销、区域时长和 tile 各阶段时间是怎样测出来的，又说明了什么：一个两个工具都没达到的开销目标，一份完全一致的记录数，一段原来是追踪器自己造成的 1.2 µs 屏障等待，以及一个等 K 而不等 V 的 FA-3 producer。

§1How we measure怎样测量

The paper measures overhead in two ways: the kernel's end-to-end duration, and the share of the kernel's dependency waits that land on probe instructions, taken from PC sampling paper §5.4.1. Olympus's criterion A4 uses the first: overhead is (Tspliced − Torig) / Torig on the median kernel duration PLAN.md:81. The second appears on this page only as a way to find causes (§4), not as a criterion.

论文用两种方式衡量开销：kernel 的端到端时长，以及 kernel 的依赖等待中落在探针指令上的比例（由 PC 采样得到）论文 §5.4.1。Olympus 的验收标准 A4 采用前者：开销等于 (Tspliced − Torig) / Torig，T 取 kernel 时长的中位数 PLAN.md:81。后者在本页只作为找原因的手段出现（§4），不作为标准。

A 1% target is small, and h200-30 is a shared host. Olympus may not lock clocks or change global GPU state there. cuBLAS nvjet is power-capped under this load: its SM clock moved between 1,635 and 1,980 MHz, and its median moved 8.75% from one process to the next ares.md:92–95. The L2 holds whatever ran last. And the same FlashMLA kernel ran 1.75% slower in the timing process than in a plain one: an offset of that whole process, not of any probe ares.md:141–151. Each of these effects is larger than the differences being measured, so the protocol is built so that each one cancels or shows up.

1% 是个很小的目标，而 h200-30 是一台共享主机：Olympus 不能在上面锁定时钟，也不能改变 GPU 的全局状态。在这种负载下 cuBLAS nvjet 会触发功耗上限：它的 SM 时钟在 1,635 到 1,980 MHz 之间变化，中位数在不同进程之间相差 8.75% ares.md:92–95。L2 里留着上一次运行的数据。同一个 FlashMLA kernel 在计时进程里比在普通进程里慢 1.75%：这是整个进程的偏移，不是某个探针造成的 ares.md:141–151。这些效应每一个都比要测的差异更大，所以测量协议的设计目标是让它们要么相互抵消，要么暴露出来。

  • Paired rounds. Each round calls the original, then the variant, back to back (A B A B …) protocol.py:1–15.
  • One prelude for every call. Every variant's trace buffer is zeroed, then a 256 MiB memset flushes the L2. The flush comes last, so no call finds its own buffer, or the previous call's data, in cache.
  • The kernel's own time. The duration is the target kernel's CUPTI activity record, read without subscribing to CUPTI. G-Watch's runtime, which swaps the spliced kernel in, is the process's one CUPTI subscriber and keeps working. The host, the prelude and the case's other kernels never enter the number DECISIONS.md:169–187.
  • Blocks and processes. 10 warm-up and 50 timed rounds make a block. A verdict pools at least 3 blocks, and each variant runs in its own process, because A and B are only comparable inside one process. Where a cell's CI straddled the target, 7–11 processes were run and the CI resamples whole processes stats.py:112–136.
  • Bootstrap intervals. Overhead is the median of every B call over the median of every A call, minus 1. Its 95% CI comes from a paired bootstrap stratified by block stats.py:79–110. A cell passes when the point estimate is within target; "(CI)" marks an interval that straddles it a4.py:132–138.
  • The A/A control. identity loads the same bytes as a second module and swaps them in through the same runtime path rewriters.py:24–27. Its overhead should be zero. In the first protocol runs its CI contained zero in 106 of 114 blocks, so about 0.5% is the resolution floor ares.md:99–112.
  • Pinned images. An Olympus variant is timed only if its spliced image is byte-identical (sha256) to the one that passed the trace sweep, and G-Watch's only if it is byte-identical to its oracle's jobs.py:228–250.
  • The bit-exact gate. Outputs are poisoned, the variant runs once, and every output hash must equal the reference, before timing and after it jobs.py:50–55. G-Watch's wrong t1_attention outputs are caught here and reported as not timed.
  • Idle, dedicated GPUs. Timing ran on GPUs 3 and 4 only. Before each process the parent, which never touches CUDA itself, requires no process, 0% utilization and under 1 GiB used gpu.py:69–94.
  • Clean exports and provenance. Every final-pass run came from a git archive export of F = 48360e9. olympus provenance --require checks that every run record is complete, clean, and names that one commit provenance.py:1–36. Before this rule, other agents' syncs had twice replaced code under a running sweep DECISIONS.md:286–304.
  • 成对的轮次。每一轮先调用原 kernel，紧接着调用变体（A B A B …）protocol.py:1–15。
  • 每次调用前都做同样的准备。先把所有变体的 trace buffer 清零，再用 256 MiB 的 memset 刷掉 L2。刷 L2 放在最后，这样任何一次调用都不会在缓存里碰到自己的 buffer，也不会碰到上一次调用留下的数据。
  • 只计 kernel 自己的时间。时长取目标 kernel 的 CUPTI activity 记录，读取时不订阅 CUPTI。负责把拼接后的 kernel 换进来的 G-Watch 运行时是进程中唯一的 CUPTI 订阅者，照常工作。主机端开销、准备步骤以及用例里的其他 kernel 都不会算进来 DECISIONS.md:169–187。
  • 块与进程。10 轮预热加 50 轮计时构成一块。一个结论至少合并 3 块；每个变体在自己的进程里运行，因为 A 与 B 只有在同一进程内才可比。CI 跨过目标线的格子会跑 7–11 个进程，此时 CI 以整个进程为单位重采样 stats.py:112–136。
  • bootstrap 置信区间。开销等于所有 B 调用的中位数除以所有 A 调用的中位数再减 1，95% CI 来自按块分层的成对 bootstrap stats.py:79–110。点估计在目标以内即判为通过；区间跨过目标线时标注 “(CI)” a4.py:132–138。
  • A/A 对照。identity 把同样的字节作为第二个 module 加载，并通过同一条运行时路径换进来 rewriters.py:24–27，它的开销应当为零。在最早的几次协议运行中，114 块里有 106 块的 CI 包含零，所以约 0.5% 就是分辨率的下限 ares.md:99–112。
  • 固定镜像。Olympus 的变体只有在拼接后的镜像与通过 trace 扫描的那份逐字节相同（sha256）时才计时；G-Watch 的变体则须与其 oracle 的镜像逐字节相同 jobs.py:228–250。
  • 逐位一致的门控。先毒化输出，再运行一次变体，所有输出的哈希必须等于参考值，计时前后各检查一次 jobs.py:50–55。G-Watch 在 t1_attention 上的错误输出就是在这里被拦下，记为未计时。
  • 空闲的专用 GPU。计时只在 GPU 3 和 4 上进行。每个进程开始前，父进程（它自己从不初始化 CUDA）要求 GPU 上没有进程、利用率为 0%、显存占用低于 1 GiB gpu.py:69–94。
  • 干净导出与来源记录。最终一轮的每次运行都来自 F = 48360e9 的 git archive 导出。olympus provenance --require 检查每份运行记录是否完整、干净，并且都指向这同一个提交 provenance.py:1–36。在有这条规则之前，其他 agent 的同步曾两次在扫描运行中途替换了代码 DECISIONS.md:286–304。

One thing the protocol cannot remove is a per-process offset like FlashMLA's 1.75%. It sidesteps it instead: A and B are only ever compared inside one process, and the A/A there shows no bias (FlashMLA identity −0.16% in the final pass).

协议无法消除的是 FlashMLA 那种 1.75% 的进程级偏移，它的做法是绕开：A 与 B 只在同一进程内比较，而同一进程里的 A/A 没有显示偏差（最终一轮中 FlashMLA 的 identity 为 −0.16%）。

§2Overhead (A4)开销（A4）

The paper reports Xtrace at no more than 0.8% for trace-sche, 0.9–2.7% for trace-pp and 0.7–5.4% for trace-mem, including 0.7% on FlashMLA's trace-mem, whose accesses sit in the innermost loops paper §5.4.2. PLAN A4 took its targets from that range: 1 / 3 / 6%, on every T1–T4 kernel PLAN.md:69. The explorer shows the final pass: Olympus's M6 search planner against G-Watch 0.0.35 on the same sites, for each case and probe set.

论文报告的 Xtrace 开销是：trace-sche 不超过 0.8%，trace-pp 为 0.9–2.7%，trace-mem 为 0.7–5.4%，其中 FlashMLA 的 trace-mem 只有 0.7%，而它的访存都在最内层循环里 论文 §5.4.2。PLAN 的 A4 据此定下目标：1 / 3 / 6%，要求每个 T1–T4 kernel 都达到 PLAN.md:69。下面的浏览器展示最终一轮的结果：在相同的插桩点上，Olympus 的 M6 搜索规划器对比 G-Watch 0.0.35，按用例与探针集逐一列出。

The verdict: A4 is not met. M6 is within target on 13 of 30 cells: 8 of 10 for trace-sche, 3 of 10 for trace-pp, 2 of 10 for trace-mem. G-Watch is within target on 7 of 10 trace-sche cells, 0 of 9 trace-pp cells and 15 of 25 trace-mem chunks (9 of 29 if a set counts only when every chunk passes). On trace-pp, M6 is below G-Watch on all 9 kernels G-Watch can time, e.g. DeepGEMM k512 at +8.86% against +27.46%.

结论：A4 未达标。M6 在 30 个格子中有 13 个达到目标：trace-sche 10 个中 8 个，trace-pp 10 个中 3 个，trace-mem 10 个中 2 个。G-Watch 在 trace-sche 上 10 个中 7 个达标，trace-pp 9 个中 0 个，trace-mem 25 个分块中 15 个（如果要求一个集合的所有分块都达标才算，则是 29 个中 9 个）。在 trace-pp 上，G-Watch 能计时的 9 个 kernel，M6 的开销全部低于 G-Watch，例如 DeepGEMM k512 是 +8.86% 对 +27.46%。

Why it misses为什么没达标

The M6 islands are already close to their dependency-chain minimum, so what remains is structural. Three causes, found by Apollo and Poseidon DECISIONS.md:261–286 DECISIONS.md:328–346:

M6 的插入岛已经接近各自依赖链的下限，剩下的开销来自结构本身。Apollo 和 Poseidon 找到了三个原因 DECISIONS.md:261–286 DECISIONS.md:328–346：

  1. Per-record work in hot loops. A record is clock → pack → store. The ring-address chain ends in an 8-cycle UIMAD → STG gap, and the store holds a read claim on its source register until it has read it: about 14 cycles, or about 500 when no predicate is dead and the store has to run on all 32 lanes. In a K loop, that is paid every iteration.
  2. A fixed cost per launch. INIT at kernel entry and the clock calibration at EXIT cost about the same whatever the kernel does. On axpy, a 49 µs Triton kernel, trace-sche is +12.45% under M6 and +12.15% under G-Watch.
  3. Whole sets against chunks. G-Watch splices at most 63 warp-level sites per run, so its trace-mem numbers are per chunk. Olympus traces the whole set in one run DECISIONS.md:185.
  1. 热循环中每条记录的固定工作。一条记录要经过读时钟 → 打包 → 存储。环形缓冲地址的计算链最后有一段 8 周期的 UIMAD → STG 间隔；存储指令在读到源寄存器之前一直占着这个寄存器的读 scoreboard，这大约要 14 个周期；如果没有死的谓词寄存器、存储只能在全部 32 个 lane 上执行，则要约 500 个周期。在 K 循环里，每一次迭代都要付这笔代价。
  2. 每次启动的固定开销。kernel 入口处的 INIT 和 EXIT 处的时钟校准，不论 kernel 做什么，开销都差不多。axpy 是一个 49 µs 的 Triton kernel，它的 trace-sche 在 M6 下是 +12.45%，在 G-Watch 下是 +12.15%。
  3. 整个集合对比分块。G-Watch 一次运行最多拼接 63 个 warp 级插桩点，所以它的 trace-mem 数字是按分块给的；Olympus 则在一次运行中追踪整个集合 DECISIONS.md:185。

Two template changes were tried in a time-boxed attempt. psave, which elects the recording lane with a borrowed live predicate instead of a 32-lane store, was adopted in a narrow form: −1.26 [−1.40, −1.09] points on matmul trace-mem. A persistent write pointer was dropped: on the islands both plans keep it changed nothing (0.0%), because the ring arithmetic runs beside the clock → store chain, not on it.

在一次限时尝试中改过两处模板。psave 借用一个仍然活跃的谓词来选出负责记录的 lane，代替 32 lane 的存储，以收窄后的形式被采纳：matmul 的 trace-mem 降低 1.26 [1.09, 1.40] 个百分点。持久化写指针被放弃：在两种方案都保留的插入岛上它没有任何改善（0.0%），因为环形缓冲的地址运算与“时钟 → 存储”这条链并行，不在链上。

Against the paper's ranges与论文数字的对照

This is my reading. Our numbers do not reproduce the paper's ranges, and they are not directly comparable to them: the paper measures its own kernels on H100 and B300, and ours are the ten T1–T4 kernels on H200. What the data do say: G-Watch 0.0.35, the released implementation, misses the same targets on this corpus (0 of 9 on trace-pp). The two µs-scale Triton kernels (axpy 49 µs, softmax 20 µs) miss every set in both tools. On the long T2–T4 kernels, trace-sche is within the paper's range (at most +0.63%). trace-pp is inside 3% only on matmul, FlashMLA and nvjet. Neither the paper nor our runs isolate why the gap is larger here.

以下是我的理解。我们的数字没有复现论文的范围，也不能与之直接比较：论文测的是它自己在 H100 与 B300 上的 kernel，我们测的是 H200 上的十个 T1–T4 kernel。数据能说明的是：已发布的实现 G-Watch 0.0.35 在这套语料上同样没达到这些目标（trace-pp 9 个中 0 个）。两个 µs 级的 Triton kernel（axpy 49 µs、softmax 20 µs）在两个工具下的每个集合都不达标。在耗时长的 T2–T4 kernel 上，trace-sche 落在论文的范围内（最多 +0.63%）。trace-pp 则只有 matmul、FlashMLA 和 nvjet 在 3% 以内。为什么这里的差距更大，论文和我们的运行都没有单独隔离出原因。

§3Consistency with G-Watch (A5)与 G-Watch 的一致性（A5）

A5 has no counterpart in the paper; it is Olympus's check that it reimplements the same tracer. Given the same sites and inputs, both tools must give the same record counts, and each region's p50 and p95 must be within max(5%, 50 ns) of G-Watch's PLAN.md:70. G-Watch misses that tolerance against itself in 13 of 22 sets, so DECISIONS 60 added a second rule: a region also passes if the difference is within twice the larger tool's run-to-run range DECISIONS.md:210–214. The evidence is 5 runs of each tool on GPU 5 (3 for FlashMLA trace-mem), across 9 case × sets.

A5 在论文里没有对应的内容，它是 Olympus 用来确认自己重实现的是同一个追踪器的检查：在相同的插桩点和输入下，两个工具的记录数必须相同，每个区域的 p50 与 p95 必须与 G-Watch 相差不超过 max(5%, 50 ns) PLAN.md:70。G-Watch 自己和自己比，22 个集合里就有 13 个超出这个容差，因此 DECISIONS 60 加了第二条规则：差值不超过两个工具中较大的那个运行间波动范围的两倍，也算通过 DECISIONS.md:210–214。证据是每个工具在 GPU 5 上各跑 5 次（FlashMLA 的 trace-mem 为 3 次），覆盖 9 个用例 × 集合。

Record counts: met. All 568 ordinary sites have equal counts in every run of both tools, and the pair rates are equal on all 72 regions. At mbarrier polling sites and under lane-group divergence the counts depend on timing in both tools, so those sites are compared per warp instead EVAL.md:90–103.

记录数：达标。全部 568 个普通插桩点在两个工具的每次运行中记录数都相同，72 个区域的配对率也全部相同。在 mbarrier 轮询点和 lane 组分叉处，两个工具的记录数都取决于时序，这些点改为按 warp 比较分布 EVAL.md:90–103。

Timing: not met. 51 of 72 regions are within A5 as written, 5 more under the spread rule (56 in all), and 16 exceed: Olympus is longer on 6 and shorter on 10. 8 regions are not compared, because the planner refuses 5 sites that have no free scoreboard DECISIONS.md:227–232. Pick a case below; each row puts G-Watch's median at zero and measures Olympus's difference in units of the A5 tolerance, so every row shares one axis.

时长：未达标。72 个区域中 51 个按原定的 A5 通过，按波动规则再多 5 个（共 56 个），16 个超出：其中 Olympus 更长的 6 个，更短的 10 个。有 8 个区域没有比较，因为规划器拒绝了 5 个没有空闲 scoreboard 的插桩点 DECISIONS.md:227–232。在下面选一个用例：每一行都以 G-Watch 的中位数为零点，以 A5 容差为单位量出 Olympus 的差值，所以所有行共用一根坐标轴。

A hold that two tools agreed on两个工具都“看到”的等待

Both G-Watch and Olympus's first planner, M4, showed about 1.1–1.3 µs per tile at the B-scale barrier, against §2.4's 306 ns. At first we read the agreement of two tools as evidence that §2.4 was wrong DECISIONS.md:210–214. It was the probes. The two store-leader warps (0 and 4) end every tile with four UTMASTG and a UTMACMDFLUSH, and the flush claims scoreboard SB0 until the TMA unit has read the tile out of shared memory. The kernel itself waits on SB0 only one tile later, at DEPBAR.LE SB0 in the next epilogue. The probe at c.tile_done, just after the flush, waited on SB0 anyway: every G-Watch probe there does, and M4's fences wait on every scoreboard. So the leaders stalled at the tile boundary, reached the next tile's B-scale barrier last, and held all eight math warps there DECISIONS.md:215–221.

G-Watch 和 Olympus 的第一个规划器 M4 都显示，每个 tile 在 B-scale 屏障处大约有 1.1–1.3 µs，而 §2.4 只有 306 ns。起初我们把两个工具的一致当作 §2.4 有误的证据 DECISIONS.md:210–214。其实是探针造成的。两个负责存储的 leader warp（0 和 4）在每个 tile 结束时发出四条 UTMASTG 和一条 UTMACMDFLUSH，这条 flush 会一直占用 scoreboard SB0，直到 TMA 单元把 tile 从共享内存里读走。kernel 自己要到下一个 tile 的 epilogue，在 DEPBAR.LE SB0 处才等 SB0。而紧跟在 flush 之后、位于 c.tile_done 的探针却照样等了 SB0：G-Watch 在这里的每个探针都会等，M4 的栅栏则等所有 scoreboard。于是两个 leader 卡在 tile 边界上，最后才到达下一个 tile 的 B-scale 屏障，把全部 8 个计算 warp 都拖在那里 DECISIONS.md:215–221。

One experiment settles it. Splicing a single NOP that waits on SB0 at that site into the uninstrumented kernel costs +18.38% [+18.25, +18.61] at k512, about 0.8–0.9 µs per tile. The same NOP without the wait costs −0.32% ares.md:300–308. That one wait also accounts for 18.4 of the 27.3 points G-Watch then added to k512's trace-pp. It is the paper's §5.4.3 point in a single instruction: splicing should remove a probe's wait on a store scoreboard it doesn't need paper §5.4.3. Since DECISIONS 61, M5 and M6 probes wait only on scoreboards their own instructions claim, and on registers they touch.

一个实验就能定论。在不插桩的 kernel 的这个位置只拼接一条等待 SB0 的 NOP，k512 就慢了 +18.38% [+18.25, +18.61]，相当于每个 tile 约 0.8–0.9 µs；同样的 NOP 去掉等待则是 −0.32% ares.md:300–308。G-Watch 当时给 k512 的 trace-pp 增加的 27.3 个百分点中，有 18.4 个就来自这一次等待。这正是论文 §5.4.3 的观点，只不过浓缩在一条指令里：拼接应当去掉探针对存储 scoreboard 的不必要等待 论文 §5.4.3。自 DECISIONS 61 起，M5 与 M6 的探针只等自己指令占用的 scoreboard，以及与自己读写的寄存器有关的冒险。
