Knowing where it's safe知道哪里安全

A probe spliced into a compiled kernel brings instructions but no registers; the compiler's allocation is gone, and nothing in the binary says which registers are free. The liveness layer answers that question once per instruction, from the binary alone: which registers may an island placed before instruction i overwrite? The answer counts not only the registers the kernel will read next but the ones an operation still in flight owns, and it is proven, not assumed: a check overwrites every register the analysis calls dead and requires the kernel's outputs to stay bit-identical.

拼接进已编译 kernel 的探针只带来指令，不带寄存器；编译器的分配信息已经不在，二进制里没有任何地方说明哪些寄存器是空闲的。活跃性层只凭二进制、对每条指令回答一次这个问题：放在指令 i 之前的 island 可以改写哪些寄存器？答案不仅算上 kernel 接下来会读的寄存器，也算上仍在途的操作所占有的那些；而且它是被证明的，不是被假设的：一项检查改写分析判为已死的每个寄存器，并要求 kernel 的输出逐位不变。

§1Contract契约

What this layer promises这一层的承诺

A register the analysis calls dead at a point can be overwritten there without changing the kernel's outputs.

分析在某个位置判为已死的寄存器，可以在那里被改写，而不改变 kernel 的输出。

olympus/cfg → olympus/liveness → used by使用者 olympus/hazards · olympus/planner · olympus/verify

The promise is the one line of ARCHITECTURE.md's table for this layer ARCHITECTURE.md:46, and it rests on the layer below it, the control-flow graph: the blocks, edges, dominators and loops that the analyses and the splicer both use ARCHITECTURE.md:43. Every register a probe writes comes from this answer. The planner (chapter 04) asks dead_before(i) for each site and partitions the result among the probe's registers; the hazard model (chapter 06) asks free_scoreboards(i) for the scoreboards no in-flight operation holds; the dead-register check asks the same question and then tries to falsify the answer api.py:53–67.

这个承诺就是 ARCHITECTURE.md 表格里这一层的那一行 ARCHITECTURE.md:46，它建立在下面一层、控制流图之上：分析与拼接器共用的基本块、边、支配关系和循环 ARCHITECTURE.md:43。探针写的每一个寄存器都来自这个答案。规划器（第 04 章）对每个站点询问 dead_before(i)，再把结果分配给探针的各个寄存器；冒险模型（第 06 章）询问 free_scoreboards(i)，得到没有被在途操作占用的 scoreboard；死寄存器检查问同一个问题，然后设法证伪这个答案 api.py:53–67。

Without it there is no probe at all. A register that is written while the kernel still needs its value does not fault; the kernel computes something else and says nothing. That is why the contract is phrased about outputs rather than about registers, and why the layer above never reasons about liveness itself: a site where too few registers are dead is refused by the planner, or handed to an explicit fallback (the per-warp downgrade, or an opt-in register raise), never patched over by a guess.

没有它就根本没有探针。一个在 kernel 仍需要其值时被改写的寄存器不会出错；kernel 只是算出别的东西，什么也不说。寄存器太少的站点由规划器拒绝，或交给一条明确的回退路径（降级为按 warp 记录，或经选择启用的寄存器抬升），绝不靠猜测糊弄过去。

§2Invariant不变量

Invariant不变量2

A probe uses only registers proven dead, including registers held by in-flight asynchronous operations until their release point.

探针只使用被证明已死的寄存器，包括被在途异步操作占用、直到释放点才空出的寄存器。

Checked by the dead-register check, verify/deadcheck.py, which overwrites every register the analysis calls dead at every reachable instruction and requires bit-identical outputs ARCHITECTURE.md:61–63: 20 / 20 corpus kernels on H200, 10 / 10 T0 kernels and both DeepGEMM sm100 kernels on GB300, with controls that overwrite a live register and must change the outputs (EVAL.md).

检查方式：死寄存器检查 verify/deadcheck.py，在每条可达指令处改写分析判为已死的每个寄存器，并要求输出逐位一致 ARCHITECTURE.md:61–63：H200 上 20 / 20 个语料库 kernel，GB300 上 10 / 10 个 T0 kernel 和两个 DeepGEMM sm100 kernel，另有改写活跃寄存器、必须改变输出的对照（EVAL.md）。

The weaker invariant would be "a probe uses only registers that are not live", the textbook notion. It is not enough on this hardware. Hopper interlocks neither the register file nor the pipes: a load's destination is written cycles after it issues, a wgmma reads its register operands and writes its accumulators while the warp runs on, and the compiler resolves every such hazard in the control bits of the instructions it scheduled. A register that one of those operations still owns looks dead to backward liveness, and a probe that writes it races the hardware. The failure is timing-dependent: when the analysis still missed the wgmma fence window, 3 of 3 runs matched before the fence and 8 of 9 differed after it (DECISIONS 55). So the invariant says proven dead, with the holds inside the definition, and the check runs the kernel rather than inspecting the analysis.

更弱的不变量会是"探针只使用不活跃的寄存器"，也就是教科书上的概念。在这种硬件上它不够。Hopper 既不对寄存器文件也不对流水线做互锁：load 的目的寄存器在发射后若干周期才被写入，wgmma 在 warp 继续前进的同时读取寄存器操作数、写入累加器，而编译器把每一个这样的冒险都解决在它所调度指令的控制位里。被这类操作仍然占有的寄存器，在反向活跃性看来就是死的，而写它的探针是在与硬件赛跑。这种失败与时序有关：当分析还没有算上 wgmma 的 fence 窗口时，fence 之前 3 次运行 3 次一致，fence 之后 9 次里 8 次不同（DECISIONS 55）。所以不变量说的是被证明已死，把占用写进定义本身，而检查是真的运行 kernel，不是审视分析。

§3How it works如何工作

The question, and the first answer问题，与第一个答案

"Dead before i" has the site semantics of chapter 00: the island runs on every path that reaches instruction i, branches into i included, so a register is dead there only if, on every such path, no later read can observe a write made there api.py:1–25. The paths come from the control-flow graph: blocks and edges for every branch form, indirect jumps resolved from the cubin's EIATTR_INDIRECT_BRANCH_TARGETS, calls whose returns go to every return site, and a kernel the graph cannot represent soundly is refused rather than guessed at graph.py:1–28; dominators give the back edges and natural loops the holds will need dominators.py:1–10. On that graph the first pass is the classical backward equation, live_in(i) = use(i) ∪ (live_out(i) ∖ kill(i)), iterated to a fixed point, with two SASS details: a guarded write may not happen, so it does not kill, and @!PT instructions never execute analysis.py:289–325. The four register files a probe can use, GPRs, uniform registers, predicates and uniform predicates, share one bitset, and the six scoreboards are tracked beside them effects.py:1–16.

"在 i 之前已死"沿用第 00 章的站点语义：island 在每条到达指令 i 的路径上执行，跳转到 i 的分支也算在内，所以只有当每条这样的路径上都没有后续读取能看到在这里写下的值时，寄存器才算死 api.py:1–25。路径来自控制流图：每种分支形式的基本块与边，从 cubin 的 EIATTR_INDIRECT_BRANCH_TARGETS 解析出的间接跳转，返回边连到每个返回点的调用；图无法可靠表示的 kernel 直接拒绝，而不是猜 graph.py:1–28；支配关系给出回边和自然循环，占用分析会用到 dominators.py:1–10。在这张图上，第一遍就是经典的反向方程 live_in(i) = use(i) ∪ (live_out(i) ∖ kill(i))，迭代到不动点，外加两处 SASS 细节：带 guard 的写不一定发生，所以不杀死旧值；@!PT 指令永不执行 analysis.py:289–325。探针能用的四种寄存器文件，GPR、uniform 寄存器、谓词和 uniform 谓词，共用一个位集，六个 scoreboard 在旁边一起跟踪 effects.py:1–16。

Registers that look dead and are not看似已死、其实不然的寄存器

The second pass runs forward and computes the holds: the operands an issued instruction still owns when control reaches i, joined over paths and followed across back edges analysis.py:327–365. A variable-latency destination is held until its write scoreboard is waited on; a late source, until its read scoreboard is; an operand with no scoreboard, until the kernel itself next accesses the register, which it may also do under the issuer's own guard with the predicate unchanged (DECISIONS 89). Every GPR an HGMMA reads or writes, accumulators and a register-sourced A operand, is held from issue until the WARPGROUP.DEPBAR that retires its group, even when that wait is in the next iteration (DECISIONS 25) effects.py:18–49. A third, backward pass adds the fence windows: between a WARPGROUP.ARRIVE, which is wgmma.fence, and the GMMA it fences, no register that GMMA accesses is dead, accumulators the GMMA only writes included, because PTX leaves any access in between undefined analysis.py:453–492. On Blackwell the same late-operand rule covers the tcgen05 and tensor-memory instructions whose register effects are established; a kernel with any other such class is refused with UnsupportedKernel, so no register of it is ever claimed dead effects.py:86–95. Each hold is also reported by issuer and release point, which is what the heatmap's hover text reads holds.py:1–24.

第二遍正向进行，计算占用（holds）：当控制流到达 i 时，已发射的指令仍然占有的操作数，沿路径取并集，并跨过回边继续跟踪 analysis.py:327–365。可变延迟的目的寄存器被占用到它的写 scoreboard 被等待；延迟读取的源操作数，到它的读 scoreboard 被等待；没有 scoreboard 的操作数，到 kernel 自己下一次访问这个寄存器，而这次访问也可以带着发射者自己的 guard、只要谓词没有变过（DECISIONS 89）。HGMMA 读或写的每一个 GPR，累加器和从寄存器读取的 A 操作数，从发射起一直被占用到让它所在组退休的 WARPGROUP.DEPBAR，哪怕那次等待在下一轮迭代里（DECISIONS 25）effects.py:18–49。第三遍反向进行，加上 fence 窗口：在 WARPGROUP.ARRIVE（即 wgmma.fence）和它所隔离的 GMMA 之间，该 GMMA 访问的任何寄存器都不是死的，包括 GMMA 只写不读的累加器，因为 PTX 规定两者之间的任何访问都是未定义行为 analysis.py:453–492。在 Blackwell 上，同一条延迟操作数规则覆盖那些寄存器效应已经确立的 tcgen05 和 tensor memory 指令；含有任何其他此类指令的 kernel 以 UnsupportedKernel 拒绝，于是它的任何寄存器都不会被判为已死 effects.py:86–95。每个占用还按发射者和释放点逐一报告，热力图的悬停文字读的就是它 holds.py:1–24。

Registers the warp does not have这个 warp 并不拥有的寄存器

Two more terms are about the allocation itself. A warp's register cap is REGCOUNT at the entry, but USETMAXREG.DEALLOC n lowers it to n for a producer role and TRY_ALLOC n raises it only on the success edge of its retry loop, so the cap in force is a forward must-analysis, the minimum over paths analysis.py:367–408. And both architectures reserve the top two GPRs of whatever allocation is in force: no corpus kernel names them, and an island that writes either faults with an illegal instruction (DECISIONS 44) analysis.py:66–72. The last term is about uniform registers: a UR or UP is one value per warp, so while the warp may be split into lane groups, an island one group runs must also spare the uniform registers live or held wherever another group may be at that moment; the divergence analysis finds those regions, and the branches that cannot split a group divergence.py:1–27.

还有两项关乎分配本身。warp 的寄存器上限在入口处是 REGCOUNT，但 USETMAXREG.DEALLOC n 把 producer 角色的上限降到 n，TRY_ALLOC n 只在其重试循环的成功边上把它抬高，所以生效的上限是一个正向的 must 分析，取各路径上的最小值 analysis.py:367–408。而且两种架构都保留当前生效分配顶端的两个 GPR：没有一个语料库 kernel 用到它们，写其中任何一个的 island 都会以非法指令出错（DECISIONS 44）analysis.py:66–72。最后一项关乎 uniform 寄存器：一个 UR 或 UP 对整个 warp 只有一个值，所以在 warp 可能分裂成多组 lane 的时候，一组 lane 执行的 island 还必须让出另一组此刻可能所在位置上活跃或被占用的 uniform 寄存器；分叉分析找出这些区域，以及那些不可能分裂一组 lane 的分支 divergence.py:1–27。

The answer is one mask. A register is dead before i when it is inside the allocation in force at i, less the two reserved GPRs, and in none of the four sets; why_live names which term excludes a register, which is what the heatmap shows on hover analysis.py:498–510 analysis.py:529–551:

答案是一个掩码。寄存器在 i 之前是死的，当且仅当它位于 i 处生效的分配范围之内、去掉两个保留 GPR，并且不属于那四个集合中的任何一个；why_live 说出是哪一项排除了某个寄存器，热力图悬停时显示的就是它 analysis.py:498–510 analysis.py:529–551：

# olympus/liveness/analysis.py, the Liveness protocol
def live_mask(self, i):          # registers not dead before i, ignoring the allocation cap
    return self.live_in[i] | self.held[i] | self.fence_in[i] | self.div_extra[i]

def dead_mask(self, i):          # registers dead before i: GPRs below the cap in force at i
    alloc = (_cap_mask(self.cap_in[i]) & GPR_MASK) | _ureg_mask(max_ureg) | PRED | UPRED
    return alloc & ~self.live_mask(i)

How the contract is checked契约如何被检查

The dead-register check does not inspect the analysis; it tries to break the kernel with it. At every reachable instruction of a corpus kernel it splices an island that sets every register dead_before(i) reports, in all four files, to a test value, then runs the kernel on its usual inputs and compares every output byte with the stored reference. Two phases write complementary values, 0x5a5a5a5a with true predicates and 0xa5a5a5a5 with false ones, so every bit of every overwritten register takes both values; the islands use immediates only and touch no scoreboard; a batch whose outputs differ, or that faults or hangs, is bisected to one point and then to a minimal register set deadcheck.py:1–40. A check that cannot fail proves nothing, so every case also runs controls that overwrite a register the analysis calls live: a store's data GPRs, its guard predicate, its address UR. These must change the outputs, and they do.

死寄存器检查不审视分析；它用分析的结论去尝试破坏 kernel。在语料库 kernel 的每条可达指令处，它拼入一个 island，把 dead_before(i) 报告的四种文件里的每个寄存器都设为测试值，然后用平常的输入运行 kernel，把每个输出字节与保存的参考比较。两个阶段写入互补的值，0x5a5a5a5a 配真谓词，0xa5a5a5a5 配假谓词，于是每个被改写寄存器的每一位都取过两种值；island 只用立即数，不碰任何 scoreboard；输出不一致、出错或挂起的批次被二分到单个位置，再二分到最小的寄存器集合 deadcheck.py:1–40。不可能失败的检查什么也证明不了，所以每个用例还运行对照：改写一个分析判为活跃的寄存器，store 的数据 GPR、它的 guard 谓词、它的地址 UR。这些必须改变输出，而它们确实改变了。

A pass is evidence, not proof: the fence bug showed in 8 runs of 9, so a timing-dependent hazard could hide in a single run. That is why the three rules the check found on its way, the fence window, the reserved GPRs and the BSYNC that releases waiting lanes early, each rest on a PTX contract or a measurement of their own rather than on the check.

通过只是证据，不是证明：fence 的问题 9 次运行里出现了 8 次，所以一个与时序有关的冒险完全可能藏在单次运行里。这正是为什么检查一路发现的三条规则，fence 窗口、保留的 GPR，以及会提前放行等待 lane 的 BSYNC，各自以 PTX 的约定或一次专门的测量为依据，而不以这项检查为依据。

§4Where it came from从何而来

The paper names this the first challenge of splicing: the probe may overwrite a register that still holds a live value, and the binary does not say which are safe paper §2.3. Its answer is the one Olympus keeps: a backward liveness analysis over the kernel's control flow gives each register its live periods, a probe borrows registers in the gaps, and the registers of asynchronous operations such as wgmma are marked live until the operation completes paper §4.3. The paper then asks whether dead-period registers are enough for the probes: on its three NVIDIA kernels they fed every splice without a fallback and without adding a register, with 6 to 9 registers still free at the tightest insertion points paper §5.5. Olympus's corpus has tighter points than that, which is why its planner has a per-warp fallback, raises REGCOUNT only when asked to, and otherwise refuses the site.

论文把这列为拼接的第一个挑战：探针可能改写一个仍装着活跃值的寄存器，而二进制没有说明哪些是安全的 论文 §2.3。它的答案就是 Olympus 保留的那个：对 kernel 的控制流做反向活跃性分析，得到每个寄存器的活跃区间，探针在区间之间的空档里借用寄存器，而 wgmma 这类异步操作的寄存器被标为活跃，直到操作完成 论文 §4.3。论文随后考察死区间寄存器是否够探针使用：在它的三个 NVIDIA kernel 上，每一次拼接都只靠它们完成，既没有回退，也没有增加寄存器，最紧的插入点上仍有 6 到 9 个寄存器空闲 论文 §5.5。所以它的规划器有按 warp 的回退，只在被要求时才抬高 REGCOUNT，否则就拒绝该站点。

Where Olympus departs: the fence windowOlympus 的不同之处：fence 窗口DECISIONS 55

The paper holds a wgmma's registers from issue to completion. Olympus also holds them before issue, from the WARPGROUP.ARRIVE fence to the GMMA, accumulators the GMMA only writes included, because PTX makes any access in between undefined and the sm_90 latency tables check the GMMA's register dependency at the fence. Found by the dead-register check at t1_attention 294–297: 8 of 9 runs differed after the fence, 3 of 3 matched before it DECISIONS.md:198.

论文把 wgmma 的寄存器从发射占用到完成。Olympus 还在发射之前就占用它们，从 WARPGROUP.ARRIVE 这道 fence 一直到 GMMA，包括 GMMA 只写不读的累加器，因为 PTX 规定两者之间的任何访问都是未定义行为，而 sm_90 的延迟表在 fence 处检查 GMMA 的寄存器依赖。由死寄存器检查在 t1_attention 的 294–297 处发现：fence 之后 9 次运行 8 次不同，fence 之前 3 次 3 次一致 DECISIONS.md:198。

Where Olympus departs: tcgen05 and tensor-memory holdsOlympus 的不同之处：tcgen05 与 tensor memory 的占用DECISIONS 87

The paper's hardware is Hopper. On Blackwell the same hold rule is applied to the 14 tcgen05 / TMEM SASS classes ptxas emits, each backed by the PTX contract or a GB300 probe: LDTM destinations are held until tcgen05.wait::ld, the asynchronous MMAs' descriptor registers until their read scoreboard is released. The probe: 252 plans × 2 phases × 2 runs over 7 kernels; 0 of 496 runs after a release point changed anything, while inside the hold LDTM destinations differed in 112 of 112 and MMA descriptor URs faulted in 36 of 48. Classes the probe did not cover stay refused DECISIONS.md:549–561.

论文的硬件是 Hopper。在 Blackwell 上，同一条占用规则施加于 ptxas 会生成的 14 个 tcgen05 / TMEM SASS 类，每一条都以 PTX 的约定或一次 GB300 探测为依据：LDTM 的目的寄存器被占用到 tcgen05.wait::ld，异步 MMA 的描述符寄存器到它们的读 scoreboard 释放为止。探测：7 个 kernel 上 252 份计划 × 2 个阶段 × 2 次运行；释放点之后的 496 次运行无一改变任何东西，而占用期内 LDTM 的目的寄存器 112 次里 112 次不同，MMA 描述符 UR 48 次里 36 次出错。探测没有覆盖的类继续被拒绝 DECISIONS.md:549–561。

Where Olympus departs: the two reserved GPRsOlympus 的不同之处：两个保留的 GPRDECISIONS 44

The paper treats every register below the allocation as a candidate. sm_90 reserves the top two GPRs of every allocation, under REGCOUNT and under USETMAXREG caps alike: REGCOUNT 16 → R14 and R15 fault while R13 is fine; REGCOUNT 255 → R253 faults; DeepGEMM's caps 40 and 232 → R38 and R230 fault. GB300 reserves the same two. The analysis never offers them DECISIONS.md:126–130.

论文把分配范围内的每个寄存器都当作候选。sm_90 保留每个分配顶端的两个 GPR，在 REGCOUNT 下和 USETMAXREG 上限下都一样：REGCOUNT 16 → R14、R15 出错而 R13 没事；REGCOUNT 255 → R253 出错；DeepGEMM 的上限 40 和 232 → R38 和 R230 出错。GB300 保留同样的两个。分析从不把它们交出去 DECISIONS.md:126–130。
