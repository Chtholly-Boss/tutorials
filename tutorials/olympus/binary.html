The binary二进制

Everything above this layer reasons about instructions; this layer is the only one that reads bits. It turns a 128-bit word into an instruction with its registers, pipe and control word, turns probe text back into a word, rewrites one offset field with every other bit copied, and reads and writes the ELF container around the code. Two architectures share one code path through a table of facts. And because a decoder that round-trips perfectly can still be wrong about what a field means, every claim here is audited against NVIDIA's own tools.

这一层之上的一切都在推理指令；只有这一层读取比特。它把一个 128 位的字变成一条带寄存器、流水线和控制字的指令，把探针文本变回一个字，只改写一个偏移字段而复制其余所有位，并读写代码周围的 ELF 容器。两种架构通过一张事实表共用一条代码路径。而因为一个能完美往返的解码器仍可能弄错某个字段的含义，这里的每一项声明都要对照 NVIDIA 自己的工具审计。

§1Contract契约

What these two layers promise这两层的承诺

isa: a byte-identical re-encode of every instruction class the splicer emits or retargets. cubin: read any cubin; write one back with changed section sizes and every offset-bearing record fixed.

isa：拼接器会生成或重定位的每个指令类都能逐字节重新编码。cubin：读任何 cubin；写回时节的大小可以改变，而每条带偏移的记录都被修正。

olympus/isa, olympus/cubin → used by使用者 olympus/cfg, liveness, hazards, probes, splice · built on建立在 nvidia-sass-document (read-only)（只读）

A cubin is the file nvcc leaves behind for the GPU: an ELF64 object holding one block of machine code per kernel, plus the tables the driver and the profilers read. The machine code is SASS, NVIDIA's real instruction set, and it is not documented. Every layer above this one wants to reason about those instructions — which registers they touch, where the branches go, how much a probe would cost — and none of them should ever see a bit. So this layer does two jobs. isa turns one 128-bit word into an Instr: a record with the mnemonic, the encoding class, the pipe, the registers read and written with their widths, the branch target if it has one, and the control word, read as Ctrl instr.py:1–9. cubin reads and writes the file around that code.

cubin 就是 nvcc 为 GPU 留下的那个文件：一个 ELF64 目标文件，每个 kernel 一块机器码，再加上驱动和性能分析器要读的各种表。那些机器码是 SASS，NVIDIA 真正的指令集，而它没有文档。这一层之上的每一层都想推理这些指令——它们碰哪些寄存器、分支去哪里、一个探针要花多少代价——而它们都不该看见任何一个比特。所以这一层做两件事。isa 把一个 128 位的字变成一个 Instr：一条记录，含助记符、编码类、流水线、带宽度的读写寄存器、分支目标（如果有），以及按 Ctrl 读出的控制字 instr.py:1–9。cubin 读写这段代码周围的文件。

Each layer above takes a different part of that record. The control-flow graph needs the branch targets and the flags that say which instructions end a block. The liveness analysis needs every register read and written, with its width, because a 64-bit load writes a pair. The hazard model needs the pipe, the operation sets and the control word. The probes need the opposite direction: a line of assembly text has to become a word. The splicer needs the narrowest thing of all — to rewrite one field of an existing word and be able to prove that nothing else about it moved.

上面的每一层各取这条记录的一部分。控制流图需要分支目标和"哪些指令结束一个基本块"的标志。活跃性分析需要每个被读写的寄存器及其宽度，因为一条 64 位的 load 会写一对寄存器。冒险模型需要流水线、操作集合和控制字。探针需要的是反方向：一行汇编文本要变成一个字。拼接器需要的是最窄的那件事——改写一个已有字的某一个字段，并且能证明它别的地方都没动。

That is why the isa promise above is narrower than "encode anything". Emitting means building a word from scratch, which only probe code does; the list of mnemonics a probe may use has 31 entries, from MOV and IMAD through STG and DEPBAR. Retargeting means taking a word the compiler wrote and changing only the field that holds a code offset, which only the splicer does when an instruction or its target has moved; that list has 14 entries, every branching mnemonic sm_90 has, from BRA to BSYNC encode.py:37–48. Those 45 mnemonics are the ones a byte-identical re-encode is promised for, and the coverage report checks every instance of them in the corpus. An instruction outside both lists still has to decode, because the analyses read all of it; it never has to be rebuilt.

这就是上面 isa 的承诺比"什么都能编码"窄的原因。生成（emit）指从零造出一个字，只有探针代码这么做；探针可以使用的助记符一共 31 个，从 MOV、IMAD 到 STG、DEPBAR。重定位（retarget）指拿编译器写下的一个字，只改其中存放代码偏移的那个字段，只有拼接器在某条指令或它的目标移动了时这么做；这个名单有 14 个，是 sm_90 全部的分支类助记符，从 BRA 到 BSYNC encode.py:37–48。这 45 个助记符才是"逐字节重新编码"所承诺的范围，覆盖报告会检查语料库里它们的每一个实例。不在这两张名单上的指令仍然必须能解码，因为各项分析要读它的全部；它只是永远不必被重建。

The cubin side is the container the splicer edits, and the promise there is about records, not bytes. A cubin holds the code in a section per kernel, and it holds several other things that point into that code by byte offset: the symbol table, the .nv.info EIATTRs, the relocations, a jump table in a constant bank, the DWARF frame and line tables, and on sm_100+ the Mercury capsules elf.py:1–12. Growing a section moves code, so every one of those records is a thing that can go stale. The writer's job is to make growing a section the only change: section order, count, names and links stay exactly as ptxas wrote them, so every index any record holds stays valid, and only file offsets, sizes and contents move writer.py:1–12.

cubin 这一侧是拼接器编辑的容器，而这里的承诺关于记录，不是字节。一个 cubin 每个 kernel 用一个节存代码，同时还存着另外几样按字节偏移指向这段代码的东西：符号表、.nv.info 里的 EIATTR、重定位、常量库里的跳转表、DWARF 帧表和行表，以及 sm_100 以上的 Mercury 胶囊 elf.py:1–12。让一个节变大就会移动代码，所以上面每一样记录都可能因此过期。写入器的职责是让"节变大"成为唯一的变化：节的顺序、数目、名字和链接与 ptxas 留下的完全一致，于是任何记录持有的下标都仍然有效，只有文件偏移、大小和内容会动 writer.py:1–12。

§2Invariant不变量

Serves服务于1

This layer protects no invariant directly; it serves Invariant 1. "Original instructions are never altered" is only checkable if decoding is complete and re-encoding is exact, and a relocated branch is only "the same word with one field changed" if the field write copies every other bit.

这一层不直接保护任何不变量；它服务于不变量 1。"原始指令从不被改动"只有在解码完整、重编码精确时才可检查；一条重定位过的分支只有在字段写入复制了其余所有位时，才是"同一个字只改了一个字段"。

Checked by four audits that share no code with the decoder's own path: the coverage report, 100% on all nine metrics over the ten sm_103a T0 cubins — T0 is the corpus's bottom tier, ten small kernels carrying one hazard or control-flow feature each, written so the right answer is known before Olympus runs; T1 to T4 above it are real kernels, Triton, CUTLASS, DeepGEMM and FlashMLA, and closed-source cuBLAS — and an identical decoded IR on 317 sm_90 cubins (15.7 M instructions) after the port; the independent audit from cuobjdump's printed hex, 725 / 725 direct-branch targets equal to the printed ones (DECISIONS 35); the field probe, 350 / 350 constants and 398 / 398 immediates against cuobjdump on 1,380 synthesized variants (DECISIONS 40); and nvdisasm's life ranges, 0 disagreements on sm_103 (DECISIONS 80).

检查方式：四项与解码器自身路径不共享代码的审计：覆盖报告，在十个 sm_103a T0 cubin 上九项指标全部 100%——T0 是语料库最底层的一档，十个小 kernel，每个只带一种冒险或控制流特征，写成这样是为了在 Olympus 跑之前就知道正确答案；之上的 T1 到 T4 是真实 kernel：Triton、CUTLASS、DeepGEMM 与 FlashMLA，以及闭源的 cuBLAS——移植后 317 个 sm_90 cubin（1,570 万条指令）的解码 IR 完全相同；从 cuobjdump 打印的十六进制出发的独立审计，725 / 725 个直接分支目标与打印值相等（DECISIONS 35）；字段探测，在 1,380 个合成变体上对照 cuobjdump 常量 350 / 350、立即数 398 / 398（DECISIONS 40）；以及 nvdisasm 的生命期范围，在 sm_103 上 0 处分歧（DECISIONS 80）。

Olympus has six numbered invariants, listed in chapter 00. The first one belongs to the splicer, four chapters ahead: original instructions are never altered, meaning that the words the compiler wrote appear in the traced binary byte for byte, and the only words that differ are branches whose target moved. This layer cannot break that rule, because it never decides to change anything. It can make the rule uncheckable, in two ways. If a word does not decode, nobody can say what it was, so "unchanged" has no witness. And if a field write touches a bit it was not asked to touch, a relocated branch is a different instruction wearing the same mnemonic.

Olympus 有六条编号的不变量，列在第 00 章。第一条属于四章之后的拼接器：原始指令从不被改动，意思是编译器写下的字在被追踪的二进制里逐字节出现，唯一不同的字是目标移动了的分支。这一层无法违反那条规则，因为它从不决定改动任何东西。但它能让那条规则变得无法检查，有两种方式。如果某个字解码不出来，就没人能说它原来是什么，"没有改动"也就没有见证。而如果一次字段写入碰到了没让它碰的位，一条重定位过的分支就是一条顶着同样助记符的不同指令。

A round trip is the obvious way to test both: decode a word, encode it again, compare the 16 bytes. Olympus does it two ways for every instruction of every corpus cubin — once through the rendered assembly text and once straight from the decoded field values — and it is not enough. Two defects passed every round-trip metric. WARPSYNC.COLLECTIVE's PC-relative target was classified as a register anchor, so the splicer kept its old absolute target and a kernel hung. And the ALU c[bank][off] operand was decoded and encoded four times off in the same way, so the two directions agreed with each other and not with the hardware. The rule that came out of it is the reason the audits above exist: a self-consistent encode/decode pair proves nothing about meaning, so every check of this layer compares against an independent printer or the GPU (DECISIONS 36).

往返（round trip）是检验这两点最显然的办法：解码一个字，再编码回去，比较那 16 个字节。Olympus 对语料库里每个 cubin 的每条指令都做两遍——一遍经渲染出的汇编文本，一遍直接从解码出的字段值——但这还不够。有两个缺陷通过了每一项往返指标。WARPSYNC.COLLECTIVE 的 PC 相对目标被归为寄存器锚点，拼接器于是保留了它旧的绝对目标，一个 kernel 挂起了。ALU 的 c[bank][off] 操作数在解码和编码时都以同样的方式差了 4 倍，两个方向彼此一致，却与硬件不一致。由此得出的规则就是上面那些审计存在的理由：自洽的编码/解码对并不能证明语义正确，所以这一层的每一项检查都要对照一个独立的反汇编器或 GPU（DECISIONS 36）。

§3How it works如何工作

The 128-bit word, and why it is 128128 位的字，以及它为什么是 128 位

An sm_90 instruction is one 128-bit word: 16 bytes, always. Sixty-four would be plenty for an opcode, three source registers and a destination. The other 64 are there because this machine has no hardware scheduler. An SM issues a warp's instructions strictly in program order, and it interlocks nothing: it will not hold an instruction back because a register it reads is still being written, and it will not hold it back because the pipe it needs is busy. Someone still has to decide when each instruction may issue, and on this architecture that someone is ptxas, at compile time. Its decision is written into the top bits of every word. A 64-bit instruction plus a schedule is a 128-bit instruction, and the schedule is not annotation: get it wrong and the instruction reads a register whose value has not arrived yet, with no fault and no warning.

一条 sm_90 指令就是一个 128 位的字：16 字节，永远如此。64 位足够放一个操作码、三个源寄存器和一个目的寄存器。另外 64 位之所以存在，是因为这台机器没有硬件调度器。SM 严格按程序顺序发射一个 warp 的指令，而且什么都不互锁：它不会因为某个要读的寄存器还在被写就把指令拦住，也不会因为要用的流水线正忙就拦住它。可是总得有人决定每条指令何时可以发射，在这个架构上，这个人是编译时的 ptxas。它的决定被写进每个字的高位。64 位的指令加上一份调度，就是 128 位的指令；而这份调度不是注解：弄错了，指令就会读到一个值还没到的寄存器，既不报错也不警告。

Fixed width buys the rest of the system its arithmetic. There is no instruction-length decoding, and instruction i of a function starts at byte 16·i, which Olympus stores on the instruction as Instr.pc. The corpus kernel t0_call is 48 words, so its code occupies bytes 0 through 767, and its EXIT at index 23 is at byte 368, which cuobjdump prints as 0x170. Every offset in the rest of this tutorial — a branch target, an EIATTR, a symbol value — is a byte offset of this kind, and is therefore always a multiple of 16. cuobjdump prints a word as two 64-bit halves with the low half first, and Olympus keeps exactly that shape: a word is a (lo, hi) pair of integers, never a 16-byte string.

固定宽度为整个系统的其余部分换来了简单的算术。不需要判别指令长度，函数里第 i 条指令从第 16·i 字节开始，Olympus 把它存在指令上，叫 Instr.pc。语料库里的 kernel t0_call 有 48 个字，所以它的代码占第 0 到第 767 字节，下标 23 的 EXIT 在第 368 字节，cuobjdump 打印成 0x170。本教程后面所有的偏移——分支目标、EIATTR、符号值——都是这种字节偏移，所以永远是 16 的倍数。cuobjdump 把一个字打印成两个 64 位半字，低半字在前，Olympus 保持的正是这个形状：一个字是一对整数 (lo, hi)，从不是一个 16 字节的串。

Inside the word there is no byte structure at all. A field is a list of bit ranges, and the ranges need not be adjacent: the opcode is 13 bits made of bit 91 followed by bits [11:0]. Where the operands sit depends on which encoding class the word belongs to. An encoding class is one concrete bit layout for one spelling of one instruction — MOV with an immediate source is a different class from MOV with a register source, and each class names its own fields at its own bit positions. nvidia-sass-document's sm_90 dump compiles to 1,589 of them. The only part of the word that sits at the same bits in every class is the control block at the top instr.py:65–73.

字的内部完全没有字节结构。一个字段是一串位区间，而这些区间不必相邻：操作码是 13 位，由第 91 位接上 [11:0] 位组成。操作数的位置取决于这个字属于哪个编码类（encoding class）。一个编码类就是某条指令某一种写法的一个具体位布局——带立即数源的 MOV 和带寄存器源的 MOV 是不同的类，每个类在自己的位位置上命名自己的字段。nvidia-sass-document 的 sm_90 转储编译出 1,589 个这样的类。字里唯一在所有类中都位于相同位上的部分，是顶部的控制块 instr.py:65–73。

The control word: six scoreboards and a stall count控制字：六个 scoreboard 和一个 stall 计数

Two different problems hide inside "when may this instruction issue". An integer add has a fixed latency: its result is in the register file a known number of cycles later. For that, counting is enough — the compiler writes a stall count into the producer, and a consumer placed that many issue slots later is safe. A global load has no fixed latency; the same instruction may be an L1 hit or a trip to DRAM, and the gap between those is more than an order of magnitude. Counting cannot work, because there is no number to write.

"这条指令何时可以发射"里藏着两个不同的问题。整数加法的延迟是固定的：它的结果在已知的若干周期后出现在寄存器堆里。对这种情况，数周期就够了——编译器在生产者里写一个 stall 计数，而放在那么多个发射位之后的消费者就是安全的。全局 load 没有固定延迟；同一条指令可能命中 L1，也可能要跑一趟 DRAM，两者之间差一个数量级以上。数周期行不通，因为没有一个数可以写。

For those the hardware offers scoreboards. A scoreboard is a counter inside the SM, private to one warp, and there are exactly six of them: SB0 through SB5. An instruction may name one scoreboard to increment when it issues and decrement when the operation it started is finished; a later instruction may name a set of scoreboards and will not issue until every one of them reads zero. That is the whole mechanism. The hardware does not know which register the dependence was about — the compiler chose the scoreboard, and the compiler is responsible for the match. Six per warp is the entire supply, and the compiler has usually spent several of them, which is why chapter 05, where a probe's registers and control bits are chosen, has to search for one that is free at the site.

对这种情况，硬件提供 scoreboard。一个 scoreboard 是 SM 内部的一个计数器，为单个 warp 私有，一共恰好六个：SB0 到 SB5。一条指令可以指定一个 scoreboard，在它发射时加一、在它启动的操作完成时减一；后面的指令可以指定一组 scoreboard，在它们全部读为零之前不发射。整个机制就是这样。硬件并不知道这个依赖关系说的是哪个寄存器——scoreboard 是编译器选的，配对也由编译器负责。每个 warp 六个就是全部供应，而编译器通常已经用掉了好几个，这就是第 05 章（探针的寄存器与控制位在那里被选定）必须在站点上搜索一个空闲 scoreboard 的原因。

The control block spends its 22 bits on those two ideas plus two smaller ones. Three fields are about scoreboards: a 6-bit wait mask, one bit per scoreboard, naming the set this instruction waits on; a 3-bit wr_sb, the scoreboard released when the result is written, with 7 meaning "none"; and a 3-bit rd_sb, the scoreboard released when the sources have been read, also 7 for none. A load needs both of its own: the value it writes is not ready for a long time, and the address registers it reads are not free for reuse until the memory unit has taken them. One field, usched, is the stall count and the yield bit packed into 5 bits. The last two are small: three bits of operand reuse flags, and two bits of pm_pred, which selects a performance counter.

控制块把它的 22 位花在这两个想法上，再加两个次要的。三个字段关于 scoreboard：6 位的 wait 掩码，每个 scoreboard 一位，指出本指令要等的那一组；3 位的 wr_sb，结果写回时释放的 scoreboard，7 表示"无"；3 位的 rd_sb，源操作数读完后释放的 scoreboard，同样 7 表示无。一条 load 自己就要用上两个：它要写的值很久才就绪，而它读的地址寄存器在内存单元取走之前都不能被复用。一个字段 usched 把 stall 计数和 yield 位打包进 5 位。最后两个很小：3 位操作数 reuse 标志，和 2 位 pm_pred，用于选择一个性能计数器。

Three of those need one more sentence each. usched packs two decisions into one number because they are taken together: 0 means DRAIN, wait until this warp's pipelines are empty before issuing anything else; 1 to 15 mean "stall this many cycles, then end the issue group", where ending the issue group — the yield bit — lets the warp scheduler pick a different warp on the next cycle; and 17 to 27 mean "stall value−16 cycles and keep this warp as the only candidate". So usched 7 and usched 23 are both a stall of 7, and they differ only in whether another warp may cut in. A reuse flag is a hint, not a dependence: it says an operand is bit-identical to the one the previous instruction read in the same slot, so the hardware may re-read it from the operand collector instead of the register file, saving a port. And pm_pred picks which hardware performance counter this instruction increments, which is why Olympus copies it rather than reasoning about it. Ctrl reads all six fields exactly as encoded and writes them back bit-exactly, and nothing above this layer touches the raw bits instr.py:88–130.

其中三个还各需要一句话。usched 把两个决定打包进一个数，因为它们是一起作出的：0 表示 DRAIN，在发射任何别的东西之前先等本 warp 的流水线排空；1 到 15 表示"停顿这么多周期，然后结束发射组"，而结束发射组——也就是 yield 位——允许 warp 调度器在下一周期挑另一个 warp；17 到 27 表示"停顿（取值−16）个周期，并让本 warp 继续作为唯一候选"。所以 usched 为 7 和为 23 都是停顿 7 个周期，区别只在别的 warp 能不能插进来。reuse 标志是提示，不是依赖：它说某个操作数与上一条指令在同一槽位读到的那个逐位相同，于是硬件可以从操作数收集器而不是寄存器堆再读一次，省下一个端口。而 pm_pred 选择本指令要递增哪个硬件性能计数器，这也是 Olympus 只复制它、不对它做推理的原因。Ctrl 把这六个字段按编码原样读出、再逐位精确写回，这一层之上没有任何东西碰原始比特 instr.py:88–130。

Assemblers and this tutorial write the control word as one bracket after the instruction, in the order [wr:rd:{wait}:stall:yield]. Three consecutive words of t0_call use all of it:

汇编器和本教程把控制字写成指令后面的一个方括号，顺序是 [wr:rd:{wait}:stall:yield]。t0_call 连续的三个字就把它用全了：

11  0x0b0  LDG.E.CONSTANT R0, desc[UR6][R2.64]   [5:0:{}:2:0]
12  0x0c0  MOV R2, 0xe0                          [7:7:{0}:7:1]
13  0x0d0  CALL.REL.NOINC 0x180                  [7:7:{5}:5:0]

The load claims two scoreboards and waits on none. SB5 is its write scoreboard, released when the loaded value reaches R0; SB0 is its read scoreboard, released when the memory unit has taken the address pair R2:R3. The MOV one word later overwrites R2, so it waits on SB0 — not because it needs a value, but because it would otherwise clobber an address that is still being read. The CALL waits on SB5, because the helper it calls adds R0 into its accumulator. Three instructions, three different uses of the same six counters, and not one of them checked by hardware. This is also the shape of the risk a probe runs: a probe that waits on SB0 here would block until the kernel's own load retired, and the delay it then measured would be the delay it caused. Chapter 03 is about avoiding exactly that.

这条 load 占用两个 scoreboard，自己不等任何一个。SB5 是它的写 scoreboard，在载入的值到达 R0 时释放；SB0 是它的读 scoreboard，在内存单元取走地址对 R2:R3 时释放。16 字节之后的 MOV 要覆盖 R2，所以它等 SB0——不是因为它需要某个值，而是因为否则它会践踏一个还在被读的地址。CALL 等 SB5，因为它调用的辅助函数要把 R0 加进自己的累加器。三条指令，对同样六个计数器的三种不同用法，而没有一种由硬件检查。这也正是探针要承担的风险的形状：一个在这里等 SB0 的探针会一直阻塞到 kernel 自己的 load 退休，而它随后测到的延迟就是它自己造成的延迟。第 03 章讲的正是如何避开这件事。

Nothing later in this list is meaningful without this step: the class is the field map, so a wrong class makes every field below a different number.
  2. The fixed bits. mov__RI pins 19 of the 128 bits to constants: bits [11:0] and bit 91 are the opcode, and bits [115:110] are pinned to 7 and 7.   3. The destination. Field Rd at bits [23:16] holds 2, which is R2. This is the number the liveness analysis of chapter 02 will read to decide that R2 is written here, and a probe placed one word earlier may therefore not use R2 to hold anything it still needs.

  5. The modifier. Field PixMaskU04 at bits [75:72] holds 0xf, all four lanes, which is why cuobjdump prints no mask suffix. A field whose value is the default is still a field; it is read and it is written back.

The encoding DB编码数据库

Where does a field map come from, if NVIDIA documents none of this? Olympus writes no instruction tables of its own. It reads nvidia-sass-document's machine-readable dump for the architecture — sm90.json or sm103.json, read-only — and compiles it. Each entry in that dump is a CLASS, or an ALTERNATE CLASS, which is a second spelling of the same bits; Olympus turns each one into a Variant. A Variant holds four things. The fixed bits become a single 128-bit (mask, value) pair, so "do the constants of this class match this word" is one and and one comparison. Each encoding field gets an action that maps it back to a FORMAT slot — the named operand the assembly syntax uses, such as Rd or Sb — together with that slot's scale and whether it is signed, because a branch offset is stored divided by 4 and a negative offset has to sign-extend. Each slot that is an enumeration keeps the list of values it is allowed to hold. And the CONDITIONS come along: these are the dump's own predicates over slot values, such as "this form requires Ra to be RZ" encdb.py:1–16 encdb.py:136–168.

如果这一切 NVIDIA 都没有文档，字段图从哪里来？Olympus 自己不写任何指令表。它读 nvidia-sass-document 为该架构提供的机器可读转储——sm90.json 或 sm103.json，只读——然后把它编译。那份转储里每一项是一个 CLASS，或者一个 ALTERNATE CLASS，也就是同一组位的第二种写法；Olympus 把每一项变成一个 Variant。一个 Variant 装四样东西。固定位合成一个 128 位的（掩码，取值）对，于是"这个类的常量和这个字相符吗"就是一次 and 加一次比较。每个编码字段得到一个动作，把它映射回一个 FORMAT 槽位——汇编语法里用的那个有名字的操作数，比如 Rd 或 Sb——连同该槽位的比例和有无符号，因为分支偏移是除以 4 存的，而负偏移需要符号扩展。每个属于枚举的槽位保留它允许取的值的清单。CONDITIONS 也一起带上：它们是转储自带的、关于槽位取值的谓词，比如"这种形式要求 Ra 是 RZ" encdb.py:1–16 encdb.py:136–168。

Decoding a word is then four filters in a row. The candidates are the classes whose 13-bit opcode matches. Of those, keep the ones whose fixed bits match and whose every field holds a legal slot value. Then every condition marked ERROR in the dump must hold, which is the step that separates the Ra == RZ form of an instruction from its Ra != RZ form. If more than one survives, a primary class beats an alternate spelling of the same bits, and a tie between two primaries goes to the one with more fixed bits, because the more specific layout is the one the assembler would have chosen decode.py:194–217. The result keeps the chosen variant and the slot values beside the Instr, so a field can be rewritten later without re-deriving any of this decode.py:166–174.

于是解码一个字就是依次四道筛子。候选是 13 位操作码匹配的那些类。在它们之中，保留固定位匹配、且每个字段都取合法槽位值的。然后转储里标为 ERROR 的每个条件都必须成立，正是这一步把一条指令的 Ra == RZ 形式和它的 Ra != RZ 形式分开。如果还剩下不止一个，主类优先于同一组位的别名拼法，两个主类打平时取固定位更多的那个，因为更具体的布局才是汇编器本来会选的 decode.py:194–217。结果把选中的变体和槽位值留在 Instr 旁边，这样以后改写某个字段时，这些都不必重新推导 decode.py:166–174。

Encoding goes the other way and reuses the library's own assembler — its parser, matcher and encoder — on the same database, so there is one description of the ISA and not two. Olympus keeps its fixes in its own subclasses and leaves the library untouched (DECISIONS 23). There are four of them: a dropped c[bank][URx+off] index, lost .H0_H0 half-word swizzles, f32 immediates being converted to fp16, and, in the sm90 port, URZ encoded as 255 encode.py:1–25. Every decoded instruction can be rebuilt two ways — from its rendered assembly text, and straight from its slot values — and both must give the original word back.

编码走的是反方向，并且复用该库自带的汇编器——它的解析器、匹配器和编码器——在同一份数据库上，于是对这套 ISA 只有一份描述，而不是两份。Olympus 把自己的修正放在自己的子类里，库本身不动（DECISIONS 23）。一共四处：被丢弃的 c[bank][URx+off] 索引、丢失的 .H0_H0 半字分量选择、被转成 fp16 的 f32 立即数，以及 sm90 移植版里 URZ 编码为 255 encode.py:1–25。每条解码出的指令都能以两种方式重建——从渲染出的汇编文本，或直接从槽位值——两种都必须还原出原来的字。

For an original instruction the splicer uses neither. Rebuilding a word means trusting that Olympus understood all 128 bits of it, and §2 is the argument that it should not. So retarget and moved_anchor take the decoded word, compute the new value for exactly one offset field, and write that field in place. The write is place followed by w = (w & ~mask) | bits: the mask covers only that field's bit ranges, so every bit outside it is literally the integer the file held encode.py:288–305 encode.py:321–338. That is what makes Invariant 1 checkable rather than merely intended: a relocated branch is the compiler's word with one field's worth of bits different, and chapter 06 shows a real one where the difference is a single byte.

对原始指令，拼接器两种都不用。重建一个字意味着相信 Olympus 读懂了它全部 128 位，而 §2 正是在论证它不该这么相信。所以 retarget 和 moved_anchor 拿着解码出的那个字，只为一个偏移字段算出新值，然后就地写入这个字段。这次写入是 place 再接上 w = (w & ~mask) | bits：掩码只覆盖该字段的那些位区间，所以它之外的每一位就是文件里原本那个整数的位 encode.py:288–305 encode.py:321–338。这才让不变量 1 从"意图"变成"可检查"：一条重定位过的分支就是编译器那个字，只有一个字段那么多位不同，而第 06 章会展示一个真实的例子，其中的差别只有一个字节。

The cubin around the code代码周围的 cubin

A kernel's instructions are not a file. They are the contents of one section of an ELF64 object, and if that section grows, several other parts of the same file become wrong. Knowing which parts is the whole job of the cubin layer, so it is worth naming them once, here, with a real kernel to count on.

一个 kernel 的指令并不是一个文件。它们是一个 ELF64 目标文件中某一个节的内容，而如果那个节变大，同一个文件里另外几个部分就会变错。搞清楚是哪几个部分，就是 cubin 这一层的全部工作，所以值得在这里用一个真实的 kernel 把它们点一遍。

A cubin written by ptxas for sm_90 is little-endian ELF64 with no program headers that matter, and the kernel-specific parts are a family of sections named after the function. .text.t0_call holds the 48 instruction words. .nv.constant0.t0_call is the kernel's parameter bank, the constant memory the driver fills in at launch; on sm_90 the user's parameters start at byte 0x210 of it. .nv.constant2.t0_call, when it exists, holds a jump table: an array of 4-byte code offsets that an indirect branch indexes. .nv.info.t0_call holds EIATTRs. An EIATTR is one tag-length-value record; the tag is an id from NVIDIA's own eiattrs.inc, and the layer knows these ids because the splicer has to answer "does this record contain a code offset?" for every one of them eiattr.py:150–179. Outside that family sit the symbol table, which gives each kernel and device function a value and a size in bytes, and the DWARF sections .debug_frame, .debug_line and .nv_debug_line_sass, which map code offsets to stack-unwinding rules and to source lines.

ptxas 为 sm_90 写出的 cubin 是小端 ELF64，没有需要在意的程序头，而与 kernel 相关的部分是一族以函数名命名的节。.text.t0_call 装着那 48 个指令字。.nv.constant0.t0_call 是这个 kernel 的参数库，也就是驱动在启动时填入的常量内存；在 sm_90 上，用户的参数从它的第 0x210 字节开始。.nv.constant2.t0_call 如果存在，装的是一张跳转表：一个 4 字节代码偏移的数组，由某条间接分支来索引。.nv.info.t0_call 装着 EIATTR。一条 EIATTR 是一条"标签—长度—取值"记录；标签是 NVIDIA 自己的 eiattrs.inc 里的一个 id，而这一层认识这些 id，是因为拼接器必须对其中每一条回答"这条记录里有代码偏移吗？" eiattr.py:150–179。这一族之外还有符号表，它给每个 kernel 和设备函数一个取值和一个以字节为单位的大小；以及 DWARF 的 .debug_frame、.debug_line 和 .nv_debug_line_sass 节，它们把代码偏移映射到栈回溯规则和源码行。

Four kinds of record carry a code offset, and each kind is a separate way to break a kernel. First, the instruction words themselves: a branch's offset field, and the 32-bit immediate of the MOV that materializes a return address. Second, the EIATTRs whose names end in _INSTR_OFFSETS, each of which points at a particular instruction; t0_call has eight EIATTR records in all and exactly one of them is of this kind, EXIT_INSTR_OFFSETS [0x170], naming its single EXIT. Third, INDIRECT_BRANCH_TARGETS, which lists an indirect branch's own offset followed by every offset it can jump to, and the .nv.constant2 jump table that holds the same targets a second time; t0_switch has one BRX at byte 320 and seven targets, recorded in both places. Fourth, the symbol table and the DWARF tables. A device function's symbol value is where its code starts, and the kernel symbol's size is the size of the whole text section.

有四类记录带着代码偏移，而每一类都是一种把 kernel 弄坏的独立方式。第一类是指令字本身：分支的偏移字段，以及物化返回地址的那条 MOV 的 32 位立即数。第二类是名字以 _INSTR_OFFSETS 结尾的 EIATTR，每一条指向某一条特定指令；t0_call 一共有八条 EIATTR 记录，其中恰好一条属于这一类，EXIT_INSTR_OFFSETS [0x170]，指的是它唯一的那条 EXIT。第三类是 INDIRECT_BRANCH_TARGETS，它列出一条间接分支自身的偏移，后面跟着它能跳到的每一个偏移；还有 .nv.constant2 里的跳转表，把同样的目标再存一遍；t0_switch 有一条在第 320 字节的 BRX 和七个目标，两处都记着。第四类是符号表和 DWARF 表。一个设备函数的符号值是它的代码起始位置，而 kernel 符号的大小是整个代码节的大小。

So the reader's job is to hand all of that up as records rather than bytes, and the writer's job is to put it back without disturbing anything a record refers to by index. Section order, count, names, sh_link and sh_info all stay exactly as ptxas wrote them, so every st_shndx and every EIATTR-referenced section index remains valid; only sh_offset, sh_size and the section data change. The five program headers nvcc emits are dropped, because the driver and cuobjdump accept a cubin with none and keeping them would mean fixing up offsets for no benefit. The layout is byte-for-byte deterministic, which is what lets chapter 09 compare two spliced images for equality writer.py:1–12.

于是读取器的职责是把这一切作为记录而不是字节交上去，写入器的职责是把它放回去，同时不扰动任何被记录按下标引用的东西。节的顺序、数目、名字、sh_link 和 sh_info 全部与 ptxas 写下的完全一致，于是每个 st_shndx、每个被 EIATTR 引用的节下标都仍然有效；只有 sh_offset、sh_size 和节的数据会变。nvcc 发出的五个程序头被丢弃，因为驱动和 cuobjdump 都接受没有程序头的 cubin，而保留它们意味着白做一遍偏移修正。布局是逐字节确定的，这正是第 09 章能把两个拼接镜像拿来比较是否相等的前提 writer.py:1–12。

Two architectures, one table两种架构，一张表

Olympus supports two architectures, and the only place that fact is written down is a table. Everything arch-specific that the ISA, cubin and splice layers need sits in one frozen Arch record: which DB file to compile, which instruction and latency dumps to read, the name the library's assembler wants for its config, the byte at which user parameters start in the constant bank, which registers hold the stack pointer and the memory descriptor, which number means the uniform zero register, and how many uniform registers exist arch.py:32–68. A cubin’s architecture is read out of its ELF header, so a cubin is never decoded with another architecture’s tables — the mistake that would otherwise be silent, because wrong tables still produce instructions arch.py:119–139.

What sm_103 changes is entirely inside that table. The word is still 128 bits and the control fields are still in the same places. But user parameters start at c[0x0][0x380] instead of 0x210; there are 80 uniform registers instead of 63, so URZ is 255 and not 63; LDCU replaces ULDC for uniform constant loads; ALU instructions may not take a constant operand at all; and native code arrives beside Mercury capsules. One thing had to be derived rather than read: the sm_100+ dumps carry no operand maps, so Olympus infers a slot’s role from its name, and that inference reproduces sm_90’s explicit maps on 1,587 of its 1,589 variants encdb.py:44–50. Above the ISA layer it is the same code on both machines: the port added tables and facts, not branches (DECISIONS 80) ARCHITECTURE.md:75–81.

Olympus 支持两种架构，而这个事实被写下来的地方只有一张表。ISA、cubin 和 splice 三层需要的所有架构相关事实都在一个冻结的 Arch 记录里：要编译哪个数据库文件、要读哪份指令和延迟转储、库自带的汇编器要的配置名、用户参数在常量库里从第几字节开始、哪些寄存器存栈指针和内存描述符、哪个编号是 uniform 零寄存器，以及一共有多少个 uniform 寄存器 arch.py:32–68。cubin 的架构从它的 ELF 头读出，所以一个 cubin 永远不会用另一种架构的表来解码——否则这个错误会是无声的，因为用错的表也能解出指令来 arch.py:119–139。

sm_103 改的东西全在那张表里。字还是 128 位，控制字段还在同样的位置。但用户参数从 c[0x0][0x380] 而不是 0x210 开始；uniform 寄存器有 80 个而不是 63 个，于是 URZ 是 255 而不是 63；uniform 常量载入由 LDCU 取代 ULDC；ALU 指令根本不能取常量操作数；而原生代码旁边还跟着 Mercury 胶囊。有一件事只能推导而不能读出：sm_100 以上的转储不带操作数映射，所以 Olympus 从槽位名推导它的角色，而这条推导在 sm_90 的 1,589 个变体中复现了 1,587 个的显式映射 encdb.py:44–50。ISA 层之上，两台机器上跑的是同一份代码：移植加的是表和事实，不是分支（DECISIONS 80）ARCHITECTURE.md:75–81。

The audits审计

A decoder cannot audit itself, because the thing in question is whether its tables mean what it thinks they mean. So four tools check this layer, and each of them gets its ground truth from outside Olympus. The coverage report is the broad one: it decodes every word of a set of cubins and scores nine things per kernel — that a variant satisfying every ERROR condition was found, that the register sets are fully known, that every register cuobjdump names appears in the reads or writes with a consistent width, that the rendered c[bank][idx+off] operands and the immediates and the memory references each equal cuobjdump’s exactly, that the word re-encodes from rendered text and again from slot values, and that every branch with an offset field survives a retarget round trip coverage.py:301–302 coverage.py:1–19. Five of those nine compare against cuobjdump’s text, which is NVIDIA’s own answer for the same bytes.

The other three go after what coverage structurally cannot see. The independent audit does not use Olympus’s ELF reader at all: it takes its words from the hex cuobjdump prints, parses register names with a separate, deliberately naive parser, and requires every decoded direct-branch target to equal the absolute target cuobjdump prints beside it isa_audit.py:1–9. The field probe exists because a corpus can only check the instructions it contains: it synthesizes one instruction per encoding variant with distinctive immediates and constant offsets, puts them in a donor cubin, and asks cuobjdump what they say. Real sm_90 code has no ALU constant operand, so no amount of corpus coverage could ever have found the scale defect of §2 fieldprobe.py:1–19. And the life-range check settles the one thing cuobjdump’s text cannot: direction. It reads nvdisasm --print-life-ranges, where ^ marks a write and v a last read, so the claim “this instruction writes R2” is confirmed by an NVIDIA-side oracle rather than by Olympus’s own field map lifecheck.py:1–21. The port to sm_103 ran all four, plus a listing audit that compares cuobjdump’s text of a spliced image against the original’s without involving Olympus’s decoder in the comparison at all archport.py:13–26.

解码器无法审计自己，因为被质疑的正是“它的表是否如它所想的那个含义”。所以有四个工具检查这一层，而每一个的真值都来自 Olympus 之外。覆盖报告是广度那一个：它解码一组 cubin 的每个字，为每个 kernel 评九项——找到了一个满足所有 ERROR 条件的变体、寄存器集合完全已知、cuobjdump 点名的每个寄存器都以一致的宽度出现在读或写里、渲染出的 c[bank][idx+off] 操作数与立即数与内存引用各自与 cuobjdump 完全相等、该字能从渲染文本重编码且能从槽位值再重编码一次、以及每条带偏移字段的分支都能活过一次重定位往返 coverage.py:301–302 coverage.py:1–19。这九项里有五项是和 cuobjdump 的文本比，而那是 NVIDIA 自己对同一串字节给出的答案。

其余三个冲的是覆盖报告从结构上就看不到的东西。独立审计根本不用 Olympus 的 ELF 读取器：它从 cuobjdump 打印的十六进制取字，用一个独立的、刻意写得很朴素的解析器解析寄存器名，并要求每个解码出的直接分支目标都等于 cuobjdump 在旁边打印的绝对目标 isa_audit.py:1–9。字段探测存在的理由是：语料库只能检查它里面有的指令。它为每个编码变体合成一条带有辨识度的立即数和常量偏移的指令，放进一个载体 cubin，再问 cuobjdump 它们是什么。真实的 sm_90 代码里没有 ALU 常量操作数，所以再多的语料库覆盖也找不到 §2 里那个比例缺陷 fieldprobe.py:1–19。生命期检查则解决 cuobjdump 的文本唯一解决不了的东西：方向。它读 nvdisasm --print-life-ranges，其中 ^ 标记写、v 标记最后一次读，于是“这条指令写 R2”这个说法由 NVIDIA 一侧的 oracle 确认，而不是由 Olympus 自己的字段表确认 lifecheck.py:1–21。向 sm_103 的移植跑了这四项，外加一项列表审计：把拼接镜像的 cuobjdump 文本与原镜像的相比，整个比较过程根本不涉及 Olympus 的解码器 archport.py:13–26。

§4Where it came from从何而来

The paper's instruction model has three mechanisms: structural and static data hazards are cleared by stall counts, dynamic data hazards by scoreboards, six per warp, and the compiler encodes all of it in the instruction because the hardware checks none of it at run time paper §4.1. Its appendix is where that fact is stated plainly: the machine issues in order and interlocks neither the register file nor the pipes paper §A.2.1. Olympus reads the same fields, as encoded, and adds the three the model does not need to name: the yield bit, DRAIN, and the reuse flags, which constrain the usched a word may carry.

论文的指令模型有三种机制：结构冒险和静态数据冒险用 stall 计数消除，动态数据冒险用 scoreboard 消除，每个 warp 六个，而编译器把这一切都编码进指令，因为硬件在运行时什么都不检查 论文 §4.1。附录里把这个事实说得最直白：机器按序发射，既不对寄存器堆也不对流水线做互锁 论文 §A.2.1。Olympus 按编码原样读同样的字段，并补上模型无需命名的三样东西：yield 位、DRAIN，以及会限制一个字可携带的 usched 的 reuse 标志。

Where Olympus departs: a third-party dump, audited rather than trustedOlympus 的不同之处：第三方转储，审计而非信任DECISIONS 36

The paper's disassembler covers the full instruction set of each of its 19 architectures. Olympus covers two, from nvidia-sass-document's dumps, and treats the dump as a claim to check. The constant-operand defect decided the rule: Olympus both assembled and decoded ConstBankAddress2 offsets 4× off, self-consistently, so the byte round trip could not see it and the corpus, which has none of these instructions, could not either. Every check of this layer now compares against cuobjdump, nvdisasm or the hardware, and the probe templates use only LDC / ULDC for constants, enforced by a unit test DECISIONS.md:83.

论文的反汇编器覆盖其 19 种架构各自的完整指令集。Olympus 覆盖两种，来自 nvidia-sass-document 的转储，并把转储当作需要核实的声明。常量操作数的缺陷定下了这条规则：Olympus 对 ConstBankAddress2 偏移的汇编和解码都差了 4 倍，而且自洽，所以字节往返看不出来，没有这类指令的语料库也看不出来。这一层的每一项检查现在都对照 cuobjdump、nvdisasm 或硬件，探针模板的常量只用 LDC / ULDC，由单元测试强制 DECISIONS.md:83。

Beyond the paper: the port is a table论文之外：移植是一张表DECISIONS 80

The second architecture did not fork the code. On sm_103a the decode and re-encode are 100% on all nine metrics over 1,840 instructions of the ten T0 cubins, the offline splice proof passes 30 / 30 and null and every-instruction splices run bit-exact 10 / 10 on GB300, while sm_90 is unchanged: an identical decoded IR on 317 cubins and identical spliced images on 20 / 20 corpus cubins DECISIONS.md:464–483.

第二种架构没有让代码分叉。在 sm_103a 上，十个 T0 cubin 的 1,840 条指令解码与重编码九项指标全部 100%，离线拼接证明 30 / 30 通过，空拼接和逐指令拼接在 GB300 上 10 / 10 逐位一致；而 sm_90 没有变化：317 个 cubin 的解码 IR 完全相同，20 / 20 个语料库 cubin 的拼接镜像完全相同 DECISIONS.md:464–483。

§5Try it: one word, every field动手试试：一个字，所有字段

Pick a real instruction from the corpus. The grid is its 128 bits, colored by field as the encoding class lays them out, with the control block at the top; hover a bit to see which field it belongs to, and click a control bit to flip it. Below are the control editor, the word as cuobjdump prints it with changed digits marked, every field with its value, and an issue timeline: this instruction and the next seven of its kernel, placed at the cycle each can issue given the stall counts.
