How we know我们如何确信

The nine chapters before this one each made a claim. The kernel's own instruction words come through byte-identical. Every register a probe writes is already dead. No probe waits on work the kernel started. Nothing is launched before it has been checked. This chapter is where those claims are attacked. There is no second tracer to measure against, so there is no single proof of the whole system — there are eleven separate checks instead, each aimed at one way it could be wrong, each sharing no code with the thing it checks, and most carrying a negative control that has to fail. Every number quoted here is quoted with the host it was measured on and the commit it was measured from.

本章之前的九章各自做出了一个断言。kernel 自己的指令字逐字节原样通过。探针写入的每个寄存器都已经死了。没有探针去等 kernel 发起的工作。没有经过检查的东西不会被启动。这一章就是攻击这些断言的地方。没有第二个追踪工具可以对照，所以不存在对整个系统的唯一证明——取而代之的是十一项彼此独立的检查，每一项针对它可能出错的一种方式，每一项都与被它检查的对象不共享代码，而且大多带一个必须失败的阴性对照。这里引用的每个数字，都连同它所测量的主机和所依据的提交一起写明。

§1Contract契约

What this layer promises这一层的承诺

Every claim in this tutorial has a check that can fail. Every check leaves a run record you can trace to one commit and one cubin. The tools may import anything; nothing imports them.

本教程中的每条断言都有一项可能失败的检查。每项检查都留下一份能追溯到唯一提交、唯一 cubin 的运行记录。工具可以导入任何东西；没有任何东西导入工具。

olympus/verify → checks检查 olympus/* · olympus/env → a run record under every result in给每个结果一份运行记录，位于 /ws/runs

The reader relies on it, because every chapter before this one ended in a claim. Chapter 01 claimed that an SM90 instruction word decodes and re-encodes to the same eight bytes. Chapter 02 claimed that a register its analysis calls dead at some instruction is never read again on any path from there. Chapter 03 claimed that a probe issues far enough from the kernel's own instructions and waits on no scoreboard the kernel owns. Chapters 04 and 05 claimed that a plan writes only dead registers and claims only free scoreboards. Chapter 06 claimed that the kernel's own instruction words come through the splice byte-identical. Chapter 07 claimed that a traced run is trusted only once its outputs match the original's bit for bit. Chapter 08 claimed that the bits in a record decode back to what the probe wrote. Until something tries to break them, all nine are intentions.

依赖它的是读者，因为本章之前的每一章都以一条断言结束。第 01 章断言：一条 SM90 指令字解码再编码得到同样的八个字节。第 02 章断言：分析在某条指令处判为已死的寄存器，从那里出发的任何路径上都不会再被读。第 03 章断言：探针与 kernel 自己的指令之间发射距离足够远，并且不等待任何 kernel 占用的 scoreboard。第 04 和 05 章断言：一个计划只写已死的寄存器，只占用空闲的 scoreboard。第 06 章断言：kernel 自己的指令字逐字节原样穿过拼接。第 07 章断言：一次追踪运行只有在输出与原 kernel 逐位一致之后才被信任。第 08 章断言：一条记录里的位能解码回探针写入的内容。在有东西试着推翻它们之前，这九条都只是意图。

There is no oracle for the whole system. A second tracer would only move the question, since it has its own probes and its own bugs; the evaluation's comparison with G-Watch 0.0.35 measured differences, not correctness (§4). So what this chapter offers is not one proof but a set of independent gates — eleven of them. Each is aimed at one specific way the system could be wrong, and a gate that passes says only that that one way is closed. The confidence comes from the independence: a bug that survives all eleven has to be invisible at once to a byte comparison of the spliced image, to a GPU run judged against the original's outputs, to a CPU re-decode of the real spliced cubin, and to eight hundred randomised probe sets.

整个系统没有 oracle。第二个追踪工具只会把问题挪个地方，因为它有自己的探针、自己的 bug；评估中与 G-Watch 0.0.35 的比较测的是差异，不是正确性（§4）。所以这一章给出的不是一个证明，而是一组彼此独立的门——一共十一道。每一道针对系统可能出错的一种具体方式，一道门通过，只说明那一种方式被堵住了。信心来自独立性：一个能活过全部十一道门的 bug，必须同时对拼接镜像的逐字节比较、对照原输出评判的 GPU 运行、对真实拼接 cubin 的 CPU 重新解码，以及八百组随机探针集合都不可见。

Independence is enforced by the import order, not by habit. ARCHITECTURE.md puts the tools on row 9, the top of that order: they may import anything, and nothing imports them ARCHITECTURE.md:54. A test checks it two ways: an abstract-syntax-tree scan of every import in olympus/**/*.py, lazy imports inside functions included, against that row table; and a subprocess that imports every module of rows 0 to 8 and asserts that nothing from olympus.verify or olympus.bench was loaded test_layering.py:1–26. That buys one half of independence: a bug in the core cannot reach into its own checker and silence it verify/__init__.py:1–17.

独立性由导入顺序来强制，不靠习惯。ARCHITECTURE.md 把工具放在第 9 行，也就是该顺序的顶端：它们可以导入任何东西，没有任何东西导入它们 ARCHITECTURE.md:54。一个测试从两个方向检查它：对 olympus/**/*.py 中每一条 import（包括函数内部的惰性导入）做抽象语法树扫描，与那张行表比对；以及一个子进程导入第 0 到 8 行的每个模块，并断言没有加载 olympus.verify 或 olympus.bench 里的任何东西 test_layering.py:1–26。这买到独立性的一半：核心里的 bug 没法伸进自己的检查器里把它按住 verify/__init__.py:1–17。

The other half has to come from outside Olympus altogether. A decoder that is wrong in the same way twice will agree with itself, which is the lesson DECISIONS 36 drew after a constant-bank operand was assembled and decoded four times off, self-consistently, for months: a self-consistent encode/decode pair proves nothing about meaning DECISIONS.md:83. So the gates take their second opinions from tools Olympus did not write: cuobjdump's printed text for what a spliced instruction really says, nvdisasm's line listings for the line tables, the kernel's own reference outputs for whether it still computes the same thing, and the kernel's own control flow for how many records a site should produce. Without this layer the rest of the tutorial is a design. With it, each design rule is a number with a directory behind it.

另一半必须完全来自 Olympus 之外。一个在同一处错了两次的解码器会与自己一致——这正是 DECISIONS 36 在一个常量 bank 操作数被自洽地错了四倍地汇编又解码好几个月之后得出的教训：一个自洽的编码／解码对不证明任何关于含义的事 DECISIONS.md:83。所以这些门从 Olympus 没有参与编写的工具那里取第二意见：cuobjdump 打印的文本，用来确认一条拼接后的指令究竟说了什么；nvdisasm 的行号列表，用来核对行表；kernel 自己的参考输出，用来判断它算的是否还是同一件事；kernel 自己的控制流，用来预测一个站点应该产出多少条记录。没有这一层，教程其余部分只是一份设计。有了它，每条设计规则都是一个背后有目录的数字。

§2Invariant不变量

Invariant不变量6

Every result carries its provenance. Run records name the commit, the cubin's sha256, tool versions, the GPU and its clock; evidence runs come from clean exports of one commit.

每个结果都带着自己的来历。运行记录写明提交、cubin 的 sha256、工具版本、GPU 及其时钟；证据运行来自同一个提交的干净导出。

Checked by olympus provenance --require, which walks every run.json under a path and exits 1 unless every record is complete and clean, all name one commit, and no job directory lacks its record provenance.py:1–37. On the final pass: 22 / 22 result directories pass on 48360e9, and --from EVAL.md passes 29 / 30 cited runs EVAL.md:223–225.

检查方式：olympus provenance --require 遍历路径下的每个 run.json，除非每条记录完整且干净、全部指向同一个提交、且没有任何任务目录缺少记录，否则以 1 退出 provenance.py:1–37。在最终一轮上：22 / 22 个结果目录在 48360e9 上通过，--from EVAL.md 对被引用的运行通过 29 / 30 EVAL.md:223–225。

The weaker rule would be "every result has a record". The first audit showed why that is not enough: of 12,953 records, 4,739 came from a dirty tree, and none of the 11 runs the evaluation then cited was clean; one sweep spanned seven commits, because its jobs read the shared tree's REVISION while other agents synced DECISIONS.md:287–304. So evidence runs come from a git archive export of one commit, written with its own REVISION under a temporary name and renamed only when complete export.sh:1–12. The other five invariants are each protected by a check in the next section; this one makes those checks citable.

更弱的规则会是"每个结果都有一份记录"。第一次审计说明了为什么这不够：12,953 条记录里有 4,739 条来自脏树，当时评估引用的 11 次运行没有一次是干净的；有一次扫描横跨了七个提交，因为它的任务在别的 agent 同步时读了共享树的 REVISION DECISIONS.md:287–304。所以证据运行来自对单个提交的 git archive 导出，连同它自己的 REVISION 先写到临时名字下，完整之后才改名 export.sh:1–12。另外五条不变量各由下一节的一项检查保护；这一条让那些检查可以被引用。

A run, to this tool, is any directory holding a run.json, and six things are checked inside it runrecord.py:1–10. The Olympus commit, forty hex digits read from the synced tree's REVISION file, with a flag saying whether that tree was dirty. A sha256 for every cubin among the run's inputs and outputs, required of a leaf run of a kind that launches a cubin and not of a sweep whose jobs keep their own records. The versions of Python, nvcc, G-Watch and nvidia-sass-document, with G-Watch excused on sm_103a because it does not exist there. The GPU's nvidia-smi index and its UUID. The SM clock, read before or after the run, excused only for a run that hid every GPU. And the start and end timestamps, with the end not before the start.

对这个工具来说，一次运行就是任何一个含有 run.json 的目录，里面有六样东西会被检查 runrecord.py:1–10。Olympus 提交，四十位十六进制数，从同步树的 REVISION 文件读出，并带一个标志说明那棵树当时是否是脏的。运行的输入和输出里每个 cubin 的 sha256；会启动 cubin 的那类叶子运行必须有，而任务自带记录的扫描不必。Python、nvcc、G-Watch 和 nvidia-sass-document 的版本；在 sm_103a 上 G-Watch 可免，因为它在那里并不存在。GPU 的 nvidia-smi 编号及其 UUID。SM 时钟，运行前或运行后读取，只有隐藏了全部 GPU 的运行可免。以及起止时间戳，结束不早于开始。

Each record then comes out complete, dirty (every field present, but a tree was dirty), missing (with the absent fields named) or unreadable. Results with no record are reported as well: a directory of files under no run directory is no record, or aggregate when the runs below it are recorded, and a directory inside a recorded sweep that has a job.log but no run.json is a job without record — a job process that died before writing one. Citable is the stricter word, and it is what --require demands of a path: at least one run in its tree, every run in it complete, all of them naming one commit, and nowhere below it a no record or job without record directory. That is the standard every row of the acceptance matrix in §3 had to meet before its number could be quoted.

于是每条记录的结论是 complete、dirty（字段齐全，但某棵树是脏的）、missing（并列出缺失的字段）或 unreadable。没有记录的结果也会被报告：不在任何运行目录之下的一堆文件是 no record，若其下的运行都有记录则是 aggregate；而在一个有记录的扫描内部，有 job.log 却没有 run.json 的目录是 job without record——一个在写出记录之前就死掉的任务进程。可引用是更严的那个词，也是 --require 对一个路径的要求：树里至少有一次运行，其中每次运行都完整，全部指向同一个提交，且其下任何地方都没有 no record 或 job without record 的目录。这就是 §3 验收矩阵里每一行在它的数字可以被引用之前必须达到的标准。

§3How it works如何工作

Each check, and the invariant it protects每项检查，以及它保护的不变量

A check is only worth its runtime if you can say what failure it catches that nothing else would. So each row below gives three things: the invariant it protects, what it actually does, and the result it last returned. The invariant numbers are ARCHITECTURE.md's own, where all six are stated with their checkers ARCHITECTURE.md:56–73. A filled number means the check is that invariant's gate; an outlined number means it is extra evidence for it.

一项检查值不值它花的时间，取决于你能不能说清它能抓住什么别的检查抓不到的故障。所以下面每一行给出三样东西：它保护的不变量、它实际做什么，以及它上一次返回的结果。不变量编号用的是 ARCHITECTURE.md 自己的编号，那里把全部六条连同各自的检查工具一起写明 ARCHITECTURE.md:56–73。实心编号表示这项检查是该不变量的门；空心编号表示它只是该不变量的额外证据。

The rows are in the order a traced run meets them. One is the gate that runs on the GPU at every traced launch. One is a static proof about the image, decided on the CPU with nothing launched. Two attack an analysis rather than an image: the dead-register check attacks liveness, the static sweep attacks the hazard rules and the plan. One attacks the whole pipeline with pseudo-random probe sets. One predicts from the source how many records a site should produce. The last two make everything above repeatable: plan invariance proves a refactor changed no plan, and provenance makes every number citable.

各行按一次追踪运行遇到它们的顺序排列。一项是每次追踪启动时都在 GPU 上运行的门。一项是关于镜像的静态证明，在 CPU 上判定，什么都不启动。两项攻击的是分析而不是镜像：死寄存器检查攻击活跃性，静态扫描攻击冒险规则与计划。一项用伪随机的探针集合攻击整条流水线。一项从源码预测一个站点应该产出多少条记录。最后两项让上面的一切可以重复：计划不变性证明一次重构没有改动任何计划，来历让每个数字可以被引用。

  1. The claim under attack. Chapter 02 said that a register the analysis calls dead before instruction i is never read again on any path from i. If that is wrong anywhere, a probe that borrows such a register silently corrupts the kernel, and the corruption surfaces as a wrong number in an output buffer with nothing to connect it to a register name. So the check does not wait for a probe to find out.
  2. The island is a wall of writes. At each test point Olympus splices in one MOV Rr, 0x5a5a5a5a for every dead GPR, one UMOV for every dead uniform register, one PLOP3.LUT or UPLOP3.LUT for every two dead predicates, and a NOP spacer at each end deadcheck.py:113–127. Every control word is [7:7:{}:stall:1]: scoreboard 7 for both read and write, which on SM90 means claim none, and an empty wait mask, which means wait on nothing. The stall is 2 cycles after each write and 15 at the spacers, which satisfies the island spacing rule of at least 7 cycles before the first write and 8 after the last (DECISIONS 33).
  3. Two phases, because one bit pattern can be lucky. Phase 0 writes 0x5a5a5a5a and sets each predicate TRUE; phase 1 writes 0xa5a5a5a5 and sets it FALSE deadcheck.py:86–95. A stale read can be harmless for one value and fatal for the other — a predicate read as FALSE may skip a store whose data was wrong anyway. Both phases must pass at every point.
  4. Every island word is read back three ways before anything is launched.   5. The points are batched, because 4,452 islands will not fit in one image. 2,226 points × 2 phases is 4,452 islands, and at t1_attention the average island is hundreds of instructions. The packer fills a batch until the inserted instructions reach the budget of 32,768, then starts another deadcheck.py:297–311. Beyond the paper: equality of outputs, and a check that attacks the analysis论文之外：输出相等，以及一项攻击分析本身的检查

Binary similarity says the kernel's instructions are still there; it does not say the kernel still computes the same thing. Olympus requires both: every traced run must reproduce the original's outputs bit for bit, with a canary that must fail, and the liveness analysis is tested directly by overwriting what it calls dead, with controls that overwrite what it calls live. That check has found two bugs, and neither was a mistake in the dataflow equations. The first was a hardware fact nobody had written down: sm_90 reserves the top two GPRs of every allocation, under REGCOUNT and under a USETMAXREG cap alike. The measurements were plain once looked for — at REGCOUNT 16 a write to R14 or R15 faults while R13 is fine, at 255 R253 faults, and DeepGEMM's caps of 40 and 232 fault at R38 and R230 — so the analysis now subtracts two from the top of every allocation DECISIONS.md:126–130. The second was the wgmma fence windows walked through in §3. Both were invisible to every static check in the table, which is why the dead-register check is standing and not a one-time experiment.

二进制相似度说明 kernel 的指令还在；它不说明 kernel 算的还是同一件事。Olympus 两者都要求：每次追踪运行都必须逐位复现原 kernel 的输出，并有一个必须失败的 canary；活跃性分析则被直接检验，改写它判为已死的寄存器，再用改写它判为活跃的寄存器做对照。这项检查找出过两个 bug，而两个都不是数据流方程里的错。第一个是一条没人写下来的硬件事实：sm_90 为每次分配保留最高的两个 GPR，在 REGCOUNT 下和在 USETMAXREG 上限下都一样。一旦去找，测量结果很直白——REGCOUNT 为 16 时写 R14 或 R15 会出错而 R13 没问题，为 255 时 R253 出错，DeepGEMM 的 40 和 232 两个上限分别在 R38 和 R230 出错——所以分析现在从每次分配的顶端减去两个 DECISIONS.md:126–130。第二个就是 §3 里走过的 wgmma fence 窗口。两者对表里的每一项静态检查都不可见，这正是死寄存器检查成为常设检查、而非一次性实验的原因。
