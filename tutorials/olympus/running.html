Running a traced kernel运行被追踪的 kernel

The runtime runs a spliced image in place of the original and decides whether to believe what came back. In a tracing run it is the only stage that touches a GPU — the hazard tables of chapter 03 and the checks of chapter 09 were measured on one too, but offline, before any trace — and it is built to refuse: nothing launches until the plan matches the captured kernel, the image loads, and three views of the parameter layout agree; nothing is trusted until the outputs are bit-identical to the original's, the trace buffer's guard bands are intact, and the original kernel runs again and reproduces the reference.

运行时用拼接后的镜像替代原 kernel 运行，并决定是否相信返回的结果。在一次追踪运行里，它是唯一接触 GPU 的阶段——第 03 章的冒险表和第 09 章的各项检查同样是在 GPU 上测出来的，但那是离线的、在任何追踪之前——而且它是为拒绝而造的：在计划与捕获到的 kernel 匹配、镜像成功加载、参数布局的三个视角一致之前，什么都不启动；在输出与原 kernel 逐位一致、追踪缓冲区的保护带完好、原 kernel 再次运行并复现参考结果之前，什么都不信任。

§1Contract契约

What this layer promises这一层的承诺

A traced run is trusted only after its outputs are bit-identical to the original's and its buffer's guard bands are intact.

一次追踪运行只有在输出与原 kernel 逐位一致、缓冲区保护带完好之后才被信任。

olympus/runtime → hands交付 .olyt to给 olympus/trace · takes a接收 SpliceResult from来自 olympus/splice

This layer's input is the file chapter 06 produced, wrapped in a SpliceResult: the spliced cubin, and for each kernel the splicer edited, a KernelEdit recording what it did to that kernel's parameters — old_param_size bytes of original block, then param_size bytes appended at param_offset, which hold the trace buffer's address result.py:1–36.

这一层的输入是第 06 章产出的文件，装在一个 SpliceResult 里：拼接后的 cubin，以及拼接器改动过的每个 kernel 的一个 KernelEdit，记录它对该 kernel 参数做了什么——old_param_size 字节的原参数块，然后在 param_offset 处追加 param_size 字节，里面放追踪缓冲区的地址 result.py:1–36。

Its output is one .olyt file per traced site set: the trace buffer's bytes with a metadata header. Beside it goes a result.json naming the last stage the run reached, the verdict, and the result of every check. A run whose outputs did not match is recorded with the verdict fail and the failure that caused it; the file may exist, but the verdict beside it is what says not to read it as data.

它的输出是每个被追踪的站点集合一个 .olyt 文件：追踪缓冲区的字节加一个元数据头。旁边是一份 result.json，记录运行到达的最后一个阶段、判定结果，以及每项检查的结果。输出不匹配的运行会被记成判定 fail，并附上导致失败的原因；文件可能存在，但旁边的判定就是在说：别把它当数据读。

Two layers consume that. The layer that turns an .olyt into per-warp intervals, paired regions and one analysis block — a trace, which is what this whole tutorial is for — comes next, in chapter 08. The tools that run the whole corpus and report on it (chapter 09) call this layer directly, once per case, which is how a claim like "800 of 800 random site sets ran clean" is produced.

有两层消费它。把 .olyt 变成每 warp 的区间、配对的 region 和一个分析块的那一层——也就是一份追踪，本教程的目的所在——紧接在后面，第 08 章。跑完整个语料库并给出报告的工具（第 09 章）直接调用这一层，每个用例一次，"20 个 kernel 上 800 组随机站点全部干净通过"这类结论就是这样得出的。

§2Invariant不变量

Invariant不变量5

Nothing runs before it is checked. The offline proof, the hazard check on the spliced cubin, the parameter-layout check three ways and the bit-exact output gate all run before a traced run is trusted; a problem is reported before launch.

没有检查过的东西不会运行。离线证明、对拼接后 cubin 的冒险检查、三个视角的参数布局检查、逐位一致的输出门，都在一次追踪运行被信任之前完成；问题在启动之前报告。

Checked by the fail-closed stages of trace_launch, each raising RuntimeFailure with its stage name before any launch base.py:27–34; by the canary rewriter, a negative control whose outputs must differ; and by fuzzing: 800 of 800 random site sets across 20 kernels, 0 faults, 0 refused (EVAL.md, A7).

检查方式：trace_launch 的各个失败即停的阶段，每个都在任何启动之前抛出带阶段名的 RuntimeFailure base.py:27–34；canary 重写器，一个输出必须不同的阴性对照；以及模糊测试：20 个 kernel 上 800 组随机站点，800 次全部通过，0 次故障，0 次拒绝（EVAL.md，A7）。

A weaker gate would be "the outputs look right". Three things make that weak. A kernel that never ran at all leaves the output buffer holding whatever was in it before, which may well be the right answer from an earlier run. A kernel that exited early writes part of the buffer and leaves the rest. And a comparison with a tolerance hides a probe that changed one rounding.

更弱的门会是"输出看起来没错"。有三点让它站不住。一个根本没运行的 kernel，输出缓冲区里留着之前的内容，而那很可能正是上一次运行算对的结果。一个提前退出的 kernel 写了缓冲区的一部分，剩下的没动。而带容差的比较会掩盖一个改变了某次舍入的探针。

So the gate poisons first and compares exactly. Before the traced run, every byte of every output tensor is overwritten with 0xA5, and the poison is read back to prove it stuck — a case whose outputs() hands back copies instead of the live buffers fails right there corpus/__init__.py:182–191. The traced run must then write every one of those bytes itself. The comparison is the sha256 of each output tensor's bytes against the hash in ref/ref.json: not a tolerance, not a norm.

所以这道门先投毒，再精确比较。追踪运行之前，每个输出张量的每个字节都被覆写为 0xA5，并读回确认毒值生效——如果某个用例的 outputs() 返回的是副本而不是真正的缓冲区，当场就失败 corpus/__init__.py:182–191。于是追踪运行必须自己把这些字节全部写一遍。比较的方式是每个输出张量字节的 sha256 与 ref/ref.json 中的哈希对照：不是容差，也不是范数。

After the run the spliced kernel is unregistered, the outputs are poisoned a third time, and the case runs again with the original kernel, which must reproduce the reference. That last run is what proves the swap left nothing behind in the process.

运行之后，拼接后的 kernel 被注销，输出第三次被投毒，用例再用原 kernel 跑一遍，必须复现参考结果。最后这次运行用来证明：这次替换没有在进程里留下任何残留。

The canary makes the gate prove itself. It overwrites instruction 1 of every kernel with that kernel's own unguarded EXIT word, so the kernel writes nothing and the outputs must keep the poison. A match there would mean the swap did not run our image at all, and the run is failed for matching rewriters.py:10–14.

canary 让这道门证明自己。它把每个 kernel 的第 1 条指令改写成该 kernel 自己的无 guard EXIT 字，于是 kernel 什么都不写，输出必须保留毒值。此时若匹配，就说明替换根本没有运行我们的镜像，这次运行会因为"匹配"而被判失败 rewriters.py:10–14。

§3How it works如何工作

What chapter 06 handed over第 06 章交来的东西

You arrive at this chapter holding one file. Chapter 06's splicer returned a SpliceResult, and the cubin inside it is the original cubin with two kinds of word changed and nothing else: the words inside the probe islands, and the branch field of each branch whose target moved because an island opened in front of it. Every other instruction word is the compiler's own, byte for byte, and splice/verify.py proved that offline before this chapter begins.

进入本章时，你手上只有一个文件。第 06 章的拼接器返回了一个 SpliceResult，里面的 cubin 就是原 cubin，只有两类字不同，别无其他：探针 island 内部的字，以及因为前面插入了 island 而目标偏移发生变化的那些分支的分支字段。其余每一条指令字都是编译器自己的，逐字节相同，而 splice/verify.py 在本章开始之前就已离线证明了这一点。

The file also declares one change no instruction word shows: the kernel now takes one more parameter than the original. It is 8 bytes wide and it holds an address. The probes of chapter 04 read the trace buffer's base out of it, and until this layer puts a real address there, there is nothing to read.

这个文件还声明了一处任何指令字都看不出的改动：kernel 现在比原来多一个参数。它宽 8 字节，里面放一个地址。第 04 章的探针从它里面读出追踪缓冲区的基址；而在这一层往里放进一个真实地址之前，那里没有东西可读。

Nothing in that file has run. This chapter is everything that stands between a file that ought to work and a trace we are willing to read.

这个文件里的东西一行都还没跑过。本章就是"一个应该能用的文件"和"一份我们愿意去读的追踪"之间的全部距离。

The problem: the application loads its own cubin问题：应用加载的是它自己的 cubin

A kernel reaches the GPU through a module load. The application hands the driver the bytes of a cubin — cuModuleLoadData from memory, cuModuleLoad or cuLibraryLoadFromFile from a file — and gets back a module handle. It then calls cuModuleGetFunction with the kernel's mangled name and gets a CUfunction, the handle a launch names. Each launch passes the packed arguments for that function's parameters.

kernel 是通过一次模块加载到达 GPU 的。应用把一个 cubin 的字节交给驱动——cuModuleLoadData 从内存，cuModuleLoad 或 cuLibraryLoadFromFile 从文件——拿回一个模块句柄。然后它用 kernel 的 mangled 名字调用 cuModuleGetFunction，拿到一个 CUfunction，这就是启动时指名的那个句柄。每次启动都为这个函数的参数传入打包好的实参。

Nowhere in that chain does the application read a file Olympus wrote. It loads its own cubin, built by its own compiler, from its own path, and launches its own CUfunction with its own arguments. So this layer has a substitution to arrange: the launch that was going to name the original function must name the spliced one, and must carry one argument more than the application packed.

这条链上没有任何一步会去读 Olympus 写出的文件。应用加载的是它自己的 cubin，由它自己的编译器构建、放在它自己的路径下，启动的是它自己的 CUfunction，传的是它自己的实参。所以这一层要安排一次替换：原本要指名原函数的那次启动必须指名拼接后的函数，并且要比应用打包的实参多带一个。

Olympus does not patch the application and writes no interception layer of its own. It has two backends instead, and both exist because neither one covers both machines.

Olympus 既不改动应用，也不自己写拦截层。它改用两个后端，而两个都存在的原因是：没有任何一个能覆盖两台机器。

Backend gwatch: a module swap below the application后端 gwatch：在应用之下换模块

On an H200 the kernels worth tracing are launched by code we do not own: Triton's launcher, the CUDA runtime, cuBLAS, DeepGEMM's JIT. There is no Python object to reach into. The substitution has to happen below all of them, at the driver.

在 H200 上，值得追踪的 kernel 都由不属于我们的代码启动：Triton 的 launcher、CUDA runtime、cuBLAS、DeepGEMM 的 JIT。没有哪个 Python 对象可以伸手进去。替换必须发生在这一切之下，在驱动那一层。

G-Watch 0.0.35 already does exactly that, and Olympus uses it through its public Python API, the way G-Watch's own tracing command does. A ProfileContext subscribes to CUPTI and sees every module the driver loads and every kernel it launches. Olympus builds that context before the case loads anything, because a context started later misses the module load and then has no original image to give us.

G-Watch 0.0.35 正是这么做的，而 Olympus 通过它公开的 Python API 使用它，用法与 G-Watch 自己的追踪命令相同。一个 ProfileContext 订阅 CUPTI，看到驱动加载的每个模块和启动的每个 kernel。Olympus 在用例加载任何东西之前就建好这个 context，因为启动得晚的 context 会漏掉模块加载，之后就没有原镜像可以交给我们了。

The capture is one run of the case between start_tracing_kernel_launch() and stop_tracing_kernel_launch(), which return every launch with its geometry. The original cubin comes from get_list_binary_cubin(): the images the driver actually loaded, not a file on disk. The spliced image goes in as a second module, and register_trace_kernel_sass — given the original kernel, the spliced one and the buffer pointer as its one appended parameter value — makes every launch of the original function go to the spliced one with that pointer appended. A single unregister_trace_kernel_sass in a finally undoes it gwatch.py:176–201.

捕获就是在 start_tracing_kernel_launch() 和 stop_tracing_kernel_launch() 之间把用例运行一次，后者返回每次启动及其几何。原 cubin 来自 get_list_binary_cubin()：驱动真正加载过的那些镜像，而不是磁盘上的文件。拼接后的镜像作为第二个模块加入，然后 register_trace_kernel_sass——传入原 kernel、拼接后的 kernel，以及作为唯一追加参数值的缓冲区指针——让原函数的每次启动都转到拼接后的函数，并追加那个指针。一个放在 finally 里的 unregister_trace_kernel_sass 把它撤销 gwatch.py:176–201。

What this backend can do is serve every launch path in the corpus, because it hooks the driver and not the case. What it cannot do is exist anywhere but H200: G-Watch 0.0.35 has no aarch64 build, so backend.resolve refuses --runtime gwatch on any arch but sm_90 before a byte is loaded backend.py:25–47. It also wants the process to itself: its own CUDA 12.8 runtime and CUPTI from gwatch_env.sh, one runtime object per process, and the process's single CUPTI subscriber, which rules out ncu or a torch profiler in the same run. On sm_90 it is the default (DECISIONS 81).

这个后端能做到的是：服务语料库里的每一条启动路径，因为它挂的是驱动，不是用例。它做不到的是：存在于 H200 之外的任何地方。G-Watch 0.0.35 没有 aarch64 构建，所以在除 sm_90 以外的任何架构上，backend.resolve 在加载任何字节之前就拒绝 --runtime gwatch backend.py:25–47。它还要求独占进程：用 gwatch_env.sh 提供的自带 CUDA 12.8 runtime 和 CUPTI，每进程一个运行时对象，以及进程里唯一的那个 CUPTI 订阅者——这就排除了在同一次运行里再用 ncu 或 torch profiler。在 sm_90 上它是默认后端（DECISIONS 81）。

Backend direct: Olympus's own loader后端 direct：Olympus 自己的加载器

GB300 has no G-Watch build, so on sm_103a something else has to do the swap. direct does it with documented driver calls and nothing else.

GB300 上没有 G-Watch 的构建，所以在 sm_103a 上得由别的东西来做替换。direct 只用有文档的驱动调用来做，别无其他。

Loading is the easy half: cuModuleLoadData on the spliced bytes through ctypes over libcuda.so.1, then cuModuleGetFunction for the mangled name, which returns a second CUfunction for the same kernel. The hard half is making the application's launch use it. The T0 corpus cases launch through the Kernel class in corpus/_common/cudrv.py, which offers two opt-in attributes for exactly this: on_launch, a callback that sees each launch, and redirect, a (function, extra arguments) pair a launch uses in place of its own. run sets redirect for the duration of one run and clears it in a finally, so the next run of the same case is the original again — which is what the restore check needs — and then checks that every launch went to the spliced function with the expected argument sizes direct.py:251–270.

加载是容易的那一半：通过 ctypes 调 libcuda.so.1 的 cuModuleLoadData 加载拼接后的字节，再用 mangled 名字调 cuModuleGetFunction，为同一个 kernel 拿到第二个 CUfunction。难的那一半是让应用的启动用上它。T0 语料库用例通过 corpus/_common/cudrv.py 里的 Kernel 类启动，这个类正好为此提供两个可选属性：on_launch，一个能看到每次启动的回调；以及 redirect，一个（函数，额外实参）对，启动时用它替代自己的。run 在一次运行期间设置 redirect，并在 finally 里清掉，于是同一用例的下一次运行又回到原 kernel——这正是恢复检查所需要的——随后它检查每次启动都确实去了拼接后的函数，且实参大小符合预期 direct.py:251–270。

What direct cannot do is see a launch it does not own. A Triton launch, a cuBLAS launch, a CUDA-runtime launch: it has no handle on any of them, and it says so at bind, by name, before anything is captured direct.py:96–122. It is the default on every arch but sm_90, and can be asked for on sm_90, which is how the two backends were compared.

direct 做不到的是：看见不属于它的启动。Triton 的启动、cuBLAS 的启动、CUDA runtime 的启动——它对哪一个都没有句柄，并且会在 bind 阶段按名字明确拒绝，发生在任何捕获之前 direct.py:96–122。它是除 sm_90 以外所有架构上的默认后端，在 sm_90 上也可以显式指定——两个后端就是这样对比的。

The relaunch path: observing a launch instead of intercepting it重启动路径：观察一次启动，而不是拦截它

One class of kernel defeats both halves of that. DeepGEMM's sm100 kernels are compiled by DeepGEMM's own C++ JIT, loaded with cuLibraryLoadFromFile and launched with cuLaunchKernelEx through entry points it resolves with dlsym. There is no cudrv.Kernel to redirect, and on GB300 no G-Watch to hook the driver. This is the path the DeepGEMM cases are traced on, so it is not a corner case.

有一类 kernel 把上面两半都破掉了。DeepGEMM 的 sm100 kernel 由 DeepGEMM 自己的 C++ JIT 编译，用 cuLibraryLoadFromFile 加载，通过 dlsym 解析出的入口以 cuLaunchKernelEx 启动。没有 cudrv.Kernel 可以重定向，在 GB300 上也没有 G-Watch 去挂驱动。DeepGEMM 的用例正是走这条路被追踪的，所以它不是边角情况。

The answer is to watch rather than interfere. A read-only CUPTI observer records every image the driver loads and every launch it sees: for a cuLaunchKernelEx, the whole CUlaunchConfig — grid, block, dynamic shared memory, stream, and each launch attribute's raw 64-byte value — together with the CUfunction, its name, and every parameter's offset, size and bytes cupti.py:1–25. Olympus then loads the spliced image the way DeepGEMM loaded the original, mirrors the one function attribute DeepGEMM sets (MAX_DYNAMIC_SHARED_SIZE_BYTES), and replaces the case's one call into DeepGEMM with a single cuLaunchKernelEx of its own, rebuilt from the capture with the buffer pointer appended relaunch.py:1–37.

办法是观察，而不是干预。一个只读的 CUPTI 观察者记录驱动加载的每个镜像和它看到的每次启动：对 cuLaunchKernelEx，记录整个 CUlaunchConfig——grid、block、动态共享内存、stream，以及每个启动属性的原始 64 字节值——连同 CUfunction、它的名字，以及每个参数的偏移、大小和字节 cupti.py:1–25。随后 Olympus 按 DeepGEMM 加载原镜像的方式加载拼接后的镜像，镜像化 DeepGEMM 设置的那一个函数属性（MAX_DYNAMIC_SHARED_SIZE_BYTES），并把用例对 DeepGEMM 的那一次调用替换成自己的一次 cuLaunchKernelEx，由捕获结果重建、追加缓冲区指针 relaunch.py:1–37。

Read-only is not caution for its own sake. CUPTI declares the callback's functionParams as const and documents no way to change a call, so a swap inside the callback would rest on undocumented driver behaviour. Rebuilding the launch instead means proving the rebuild faithful, which costs three checks. The replaced call must make exactly one launch and no other device work the observer can see — no memcpy, no memset, no stream value write, no graph launch. The identity relaunch, the same bytes with no splice, must be bit-exact. And after the restore, DeepGEMM's own next launch must carry byte-identical parameters, which is what shows that the bytes Olympus launched with were DeepGEMM's bytes for this call (DECISIONS 86).

只读不是为谨慎而谨慎。CUPTI 把回调的 functionParams 声明为 const，也没有记载任何改变一次调用的方法，所以在回调内部做替换只能依赖未公开的驱动行为。改为重建启动，就得证明重建是忠实的，这需要三项检查。被替换的那次调用必须恰好发起一次启动，且观察者看不到任何其他设备工作——没有 memcpy、没有 memset、没有 stream 值写入、没有 graph 启动。恒等重启动，也就是同样的字节、不做拼接，必须逐位一致。恢复之后，DeepGEMM 自己的下一次启动必须携带逐字节相同的参数，这证明 Olympus 启动时用的字节就是 DeepGEMM 为这次调用准备的字节（DECISIONS 86）。

Whichever path ran, every check below sees the same two objects: a Capture (the kernel's mangled name, each launch with its geometry, and the original image with its sha256) and a Swap (the spliced image, the KernelEdit, both function handles, and the layout check) base.py:37–74. The gate is written once. On H200, where both backends can run, they were compared: identical spliced images, identical output hashes, identical ring escalations, identical records per site, and the same site order in every warp (DECISIONS 81).

不论走的是哪条路，下面每一项检查看到的都是同样两个对象：一个 Capture（kernel 的 mangled 名字、每次启动及其几何、原镜像及其 sha256）和一个 Swap（拼接后的镜像、KernelEdit、两个函数句柄，以及布局检查）base.py:37–74。这道门只写一次。在两个后端都能跑的 H200 上，它们被对比过：拼接镜像完全相同、输出哈希完全相同、环升级完全相同、每站点记录数完全相同，每个 warp 内的站点顺序也相同（DECISIONS 81）。

The parameter layout, three ways参数布局的三个视角

Appending a parameter changes the kernel's ABI, and the caller is not ours to change. That is the one place in Olympus where a mistake would be both invisible and destructive, so it gets three independent checks.

追加一个参数改变了 kernel 的 ABI，而调用方不是我们能改的。这是 Olympus 中唯一一处"出错既看不见又有破坏性"的地方，所以它有三项独立检查。

A kernel's parameters live in a block in constant bank 0 — based at c[0x0][0x210] on sm_90a and c[0x0][0x380] on sm_103a, the base chapter 04's INIT probe reads from — and each parameter is an (offset, size) slot in it. The driver fills that block from the launch's packed arguments, using the layout it read out of the image when it loaded the module. The probes read the buffer's address from one 8-byte slot, at param_offset.

kernel 的参数放在 constant bank 0 的一个块里——在 sm_90a 上基址为 c[0x0][0x210]，在 sm_103a 上为 c[0x0][0x380]，也就是第 04 章 INIT 探针读取的那个基址——每个参数在其中是一个（偏移，大小）槽。驱动用加载模块时从镜像里读出的布局，把启动时打包好的实参填进这个块。探针从 param_offset 处的一个 8 字节槽里读出缓冲区地址。

If those two numbers disagree, nothing faults. The probe reads whatever the application's own arguments left at that offset and writes every trace record to that address. That is a silent write into memory the kernel owns, in a run we are about to certify as bit-exact. So the offset is checked from three sources that cannot be wrong in the same way.

如果这两个数不一致，不会有任何故障发生。探针会读到应用自己的实参在那个偏移上留下的任意值，并把每条追踪记录写到那个地址去。那是对 kernel 自己拥有的内存的一次无声写入，而这次运行马上就要被认定为逐位一致。所以这个偏移要从三个不可能以同一种方式出错的来源分别检查。

The first view is the splicer's promise, the KernelEdit. The second is the images' own EIATTR_KPARAM_INFO records — the ELF notes chapter 06 rewrote — read back out of both the original image and the spliced one by Olympus's ELF reader. The third is the driver's: cuFuncGetParamInfo on each loaded function, one query per parameter until the driver says there are no more drv.py:42–56.

第一个视角是拼接器的承诺，即 KernelEdit。第二个是镜像自带的 EIATTR_KPARAM_INFO 记录——第 06 章重写过的那些 ELF 注记——由 Olympus 的 ELF 读取器从原镜像和拼接后镜像里分别读回。第三个是驱动的视角：对两个已加载函数各调 cuFuncGetParamInfo，每个参数查一次，直到驱动说没有更多 drv.py:42–56。

Each view answers a different question. The KernelEdit says what Olympus meant to do. KPARAM_INFO says what Olympus actually wrote into the file. cuFuncGetParamInfo says what the driver will do with that file at the next launch, which is the only one of the three that decides where the pointer lands. A slip in the splicer's arithmetic shows up as view 1 against view 2; a note written wrongly, or read differently by the driver than by us, shows up as view 2 against view 3.

三个视角回答的是不同的问题。KernelEdit 说的是 Olympus 打算做什么。KPARAM_INFO 说的是 Olympus 实际写进了文件什么。cuFuncGetParamInfo 说的是驱动在下一次启动时会怎么处理这个文件——三者之中只有它决定指针最终落在哪里。拼接器算错会表现为视角 1 与视角 2 不符；注记写错、或驱动读法与我们不同，会表现为视角 2 与视角 3 不符。

The check itself is then a list of equalities layout.py:56–100. param_size must be 8. param_offset must be old_param_size rounded up to a multiple of 8. new_param_size must be param_offset + param_size. old_param_size must equal the end of the driver's original block. Exactly one parameter value must have been handed in. And in both the image's view and the driver's, the spliced layout must be the original layout plus exactly one appended entry at (param_offset, 8) — not two entries, not one at another offset. A rewriter that appends nothing, like identity or the canary, must instead produce a spliced layout equal to the original's, with no parameter value given.

检查本身就是一串等式 layout.py:56–100。param_size 必须是 8。param_offset 必须是 old_param_size 向上对齐到 8 的倍数。new_param_size 必须等于 param_offset + param_size。old_param_size 必须等于驱动视角下原参数块的末端。必须恰好传入一个参数值。并且在镜像视角和驱动视角下，拼接后的布局都必须是原布局加上恰好一个位于 (param_offset, 8) 的追加项——不是两个，也不是位于别的偏移的一个。像 identity 或 canary 这样不追加参数的重写器，则必须给出与原布局完全相同的拼接后布局，且不传任何参数值。

The direct backend adds a fourth comparison, because it watched the application's own launch argument by argument: the size of every argument the application passed must equal the driver's original parameter sizes, exactly and in order direct.py:222–234. If the application passed eight arguments where the kernel declares nine, the appended 8 bytes would land one slot early. None of these numbers is ever assumed: the same source compiles to param_offset 112 on sm_90a and 128 on sm_103a, so the offset always comes from the captured layout (DECISIONS 86). Any failure raises LayoutFailure at stage layout, and nothing launches.

direct 后端还加了第四项比较，因为它逐个实参地看到了应用自己的那次启动：应用传入的每个实参的大小，必须与驱动视角下的原参数大小完全一致、顺序也一致 direct.py:222–234。如果 kernel 声明了九个参数而应用只传了八个，追加的 8 字节就会落到前一个槽里。这些数字从来不靠假设：同一份源码编译出的 param_offset 在 sm_90a 上是 112，在 sm_103a 上是 128，所以偏移永远来自捕获到的布局（DECISIONS 86）。任何一项不成立都会在 layout 阶段抛出 LayoutFailure，什么都不会启动。

The guarded trace buffer带保护带的追踪缓冲区

The probes write to the address they are handed, and they do not check it. Chapter 04 fixed what they write: one slot per warp, each a 32-byte header followed by a ring of records, indexed by the warp's linear id computed from the launch geometry. Nothing in the kernel validates that index. If the buffer is one warp too small for the grid the application actually launched, a probe writes past the end of the allocation into whatever the allocator put there next — and the kernel's own outputs can still be perfect.

探针往交给它的地址写，而且它不检查这个地址。第 04 章定下了它写什么：每个 warp 一个槽位，每个槽位是 32 字节头部后跟一个记录环，索引是由启动几何算出的 warp 线性编号。kernel 里没有任何东西会校验这个索引。如果缓冲区比应用实际启动的 grid 少了一个 warp 的量，探针就会写到分配区末尾之外、写进分配器接着放在那里的任何东西里——而 kernel 自己的输出仍然可能完全正确。

So the buffer is sized from the capture, never from the plan's expectation. n_slots is blocks × warps per block, taken from the captured launch's grid and block; the body is n_slots × slot_bytes. If the plan computes a size of its own, the two must agree to the byte or the run stops at stage plan tracer.py:108–132.

所以缓冲区的大小来自捕获，而不是来自计划的预期。n_slots 是 block 数 × 每个 block 的 warp 数，取自捕获到的那次启动的 grid 和 block；主体是 n_slots × slot_bytes。如果计划自己也算了一个大小，两者必须逐字节相等，否则运行在 plan 阶段停下 tracer.py:108–132。

The allocation is one torch tensor holding [guard][body][guard]. A guard band is 4,096 bytes filled with 0xA5, a byte no probe ever writes. The body's address is what the appended parameter carries, and it must be 32-byte aligned or the buffer refuses to be built. The body is zeroed before the launch, which is what gives a zero exit timestamp its meaning: a slot whose EXIT calibration never ran tracebuf.py:65–111.

这次分配是一个 torch 张量，内容为 [保护带][主体][保护带]。一条保护带是 4,096 字节的 0xA5，这是任何探针都不会写出的字节。主体的地址就是追加参数携带的值，它必须 32 字节对齐，否则缓冲区拒绝被构造。主体在启动前被清零，这正是"退出时间戳为零"这件事有意义的原因：那是一个 EXIT 校准从未运行过的槽位 tracebuf.py:65–111。

After the launch the whole allocation is copied to the host, and the guard report counts the bytes on each side that are no longer 0xA5 and names the first one, as an offset relative to the body. A broken guard band means one specific thing: a probe wrote outside the region allocated for it. The likely cause is a slot index out of range — a launch bigger than the capture, or warp-id arithmetic wrong for this block shape — and in that case some records went somewhere else too. The run fails.

启动之后，整块分配被拷到主机，保护带报告统计两侧不再是 0xA5 的字节数，并给出第一个这样的字节相对主体的偏移。保护带被破坏只意味着一件具体的事：有探针写到了分配给它的区域之外。最可能的原因是槽位索引越界——启动比捕获时更大，或者 warp 编号算法在这种 block 形状下是错的——而那种情况下也有一些记录写到了别处。这次运行失败。

The body is then checked by numpy on the host, with no GPU involved, and most of that check is a list of places the probes must never have written tracebuf.py:145–154. Every slot must have the valid bit that only INIT sets, and a nonzero exit timestamp that only the EXIT calibration writes. No slot may name an SM id at or above the device's SM count, and the reserved bits of that word must be clear. No ring entry below n_records may have a zero first word, because every record's first word carries site_id + 1. No site id may fall outside [0, n_sites). The entries past n_records in a slot that did not wrap, the padding at the end of a slot, and bytes +4..+7 of a 16-byte record must all still be zero. And no exit timestamp may precede its own start. When the planner offers a buffer check of its own, it runs on the same bytes independently and the two must agree.

随后主体在主机上由 numpy 检查，完全不涉及 GPU，而这项检查的大部分内容是"探针绝不该写到的地方"的清单 tracebuf.py:145–154。每个槽位都必须有只由 INIT 置上的有效位，以及只由 EXIT 校准写入的非零退出时间戳。没有槽位可以给出大于或等于设备 SM 数量的 SM 编号，该字的保留位必须为零。n_records 以内的环表项不得有首字为零的，因为每条记录的首字都带着 site_id + 1。站点编号不得落在 [0, n_sites) 之外。未回绕槽位中超过 n_records 的表项、槽位末尾的填充、以及 16 字节记录的 +4..+7 字节，都必须仍为零。退出时间戳不得早于它自己的起始时间戳。当规划器提供自己的缓冲区检查时，它在同样的字节上独立跑一遍，两者必须一致。

One failure mode is not a bug but a size. A slot's ring holds ring_depth records, and a warp that reaches its sites more often than that overwrites its own oldest ones. The header makes it detectable: n_records counts every record the warp made, not the number that fit, so the largest n_records over all slots compared against ring_depth detects a wrap exactly, and wrapped_slots counts how many slots lost something. On a wrap the run fails — the data is incomplete, not wrong — and olympus trace re-runs the whole set at the next power of two above that largest count, keeping each attempt in its own d<depth>/ directory, up to --max-ring, 16,384 by default cli.py:304–315. It is the one automatic retry in this layer, and it relaxes nothing: the re-run is the same plan with a deeper ring.

有一种失败不是 bug，而是尺寸问题。一个槽位的环只放 ring_depth 条记录，命中站点次数超过这个数的 warp 会覆盖掉自己最老的记录。头部让这件事可检测：n_records 统计的是该 warp 产生的全部记录数，而不是放得下的条数，所以把所有槽位中最大的 n_records 与 ring_depth 比较就能精确判定是否回绕，而 wrapped_slots 统计有多少槽位丢了东西。一旦回绕，这次运行失败——数据是不完整，不是错——并且 olympus trace 会以"大于那个最大值的下一个 2 的幂"把整个集合重跑一遍，每次尝试保留在各自的 d<depth>/ 目录里，上限是 --max-ring，默认 16,384 cli.py:304–315。这是本层唯一的自动重试，而且它不放松任何东西：重跑的是同一份计划，只是环更深。

The gate, in order这道门，按顺序

Here is the whole order of operations, with what each step catches. Every step before the launch raises RuntimeFailure with its own stage name and stops there base.py:27–34; every step after it records a failure and the run's verdict becomes fail tracer.py:183–226.

下面是完整的操作顺序，以及每一步能抓住什么。启动之前的每一步都会抛出带自己阶段名的 RuntimeFailure 并就此停下 base.py:27–34；启动之后的每一步则记下一个失败，并把这次运行的判定变成 fail tracer.py:183–226。

  1. Reference. Long before any tracing, olympus corpus ref ran the case three times — twice in one process with the outputs poisoned in between, then once more after a fresh setup(seed) — and wrote every output tensor's sha256 to ref/ref.json. That file is what "correct" means for everything below USAGE.md:281–287.
  2. Bind. The backend is built before the case loads anything; then case.setup(0) builds the inputs and the backend binds what it will substitute. The direct backend refuses here, by name, any case whose launches it cannot see.
  3. Capture. One run with launch tracing on. The sites file's kernel must be found by its pattern. It must have launched exactly once, because one buffer serves one launch. Its image's sha256 must equal the built corpus cubin. And this run's own outputs must already match the reference — the easiest check to leave out and the most important, because if the untouched kernel does not reproduce the reference on this machine, no comparison below means anything.
  4. Plan. The planner builds the probe plan, which must name the captured kernel and the captured image's sha256. A plan error ends the run here, with nothing spliced and nothing loaded.
  5. Splice. The rewriter returns a SpliceResult whose original_sha256 must equal the captured image's hash and whose spliced_sha256 must equal the hash of the bytes it carries, so a result built from some other image cannot be loaded by mistake.
  6. Load. The backend loads the spliced image as its own module. The kernel must be in it; the new CUfunction must be non-null and different from the original's; and the instruction count the loader parses must equal the count Olympus's own ELF reader finds in the same bytes.
  7. Layout. The parameter block, three ways, as above.
  8. Buffer. Allocate [guard][body][guard], fill the guards, zero the body, check the body's alignment, and take its address as the appended argument.
  9. Poison. Every byte of every output tensor is overwritten with 0xA5 and read back to confirm it stuck.
  10. Launch. The spliced function is registered, or the redirect set; the case runs once; the launches are counted. Exactly one launch of this kernel, or the run fails.
  11. Compare. The sha256 of every output tensor against the reference, bit for bit.
  12. Guards, contents, ring. The guard bands intact; the body checked by numpy, and independently by the planner where it offers a check; the largest n_records within the ring depth.
  13. Write and read back. <set>.olyt is written and immediately loaded with the trace layer's own reader. It must decode exactly the number of records the buffer kept, and see as many sites as the plan has.
  14. Restore. The spliced kernel is unregistered or the redirect cleared, the outputs are poisoned a third time, and the case runs with the original kernel, which must reproduce the reference. On the relaunch path the application's own next launch must also carry the captured parameter bytes. A failure here says the swap left the process changed.
  1. 参考。在任何追踪之前很久，olympus corpus ref 已把用例跑了三次——同一进程内两次、中间对输出投毒，然后在新的 setup(seed) 之后再跑一次——并把每个输出张量的 sha256 写进 ref/ref.json。下面所有步骤里的"正确"都以这个文件为准 USAGE.md:281–287。
  2. 绑定。后端在用例加载任何东西之前建好；然后 case.setup(0) 构造输入，后端绑定它将要替换的对象。direct 后端在这里按名字拒绝任何它看不到启动的用例。
  3. 捕获。开启启动追踪运行一次。站点文件所指的 kernel 必须按其 pattern 被找到。它必须恰好启动一次，因为一个缓冲区只服务一次启动。它的镜像 sha256 必须等于构建出的语料库 cubin。而且这次运行自己的输出必须已经与参考匹配——这是最容易被省掉、也最重要的一项检查，因为如果未经改动的 kernel 在这台机器上都复现不出参考，下面任何比较都没有意义。
  4. 规划。规划器构建探针计划，它必须指名捕获到的 kernel 和捕获镜像的 sha256。计划出错就在此结束，没有拼接，也没有加载。
  5. 拼接。重写器返回一个 SpliceResult，其 original_sha256 必须等于捕获镜像的哈希，其 spliced_sha256 必须等于它所携带字节的哈希，这样由别的镜像构建出的结果就不会被误加载。
  6. 加载。后端把拼接后的镜像作为自己的模块加载。该 kernel 必须在里面；新的 CUfunction 必须非空且与原来的不同；加载器解析出的指令数必须等于 Olympus 自己的 ELF 读取器在同样字节里数出的条数。
  7. 布局。参数块，三个视角，如上。
  8. 缓冲区。分配 [保护带][主体][保护带]，填好保护带，清零主体，检查主体对齐，取它的地址作为追加的实参。
  9. 投毒。每个输出张量的每个字节被覆写为 0xA5，并读回确认生效。
  10. 启动。注册拼接后的函数，或设置重定向；用例运行一次；统计启动次数。该 kernel 必须恰好启动一次，否则运行失败。
  11. 比较。每个输出张量的 sha256 对照参考，逐位比较。
  12. 保护带、内容、环。保护带完好；主体由 numpy 检查，并在规划器提供检查时再独立检查一遍；最大的 n_records 在环深度之内。
  13. 写出并读回。写出 <set>.olyt，并立刻用追踪层自己的读取器加载。它必须恰好解码出缓冲区保留的记录条数，并看到与计划一样多的站点。
  14. 恢复。注销拼接后的 kernel 或清除重定向，第三次对输出投毒，用原 kernel 运行用例，它必须复现参考结果。在重启动路径上，应用自己的下一次启动还必须携带捕获到的参数字节。这一步失败说明替换让进程发生了改变。

A failed run is reported, not salvaged. There is no second attempt with a looser comparison, no best-effort trace, no stage skipped because it was inconvenient. Before the launch, a failure is an exception named for its stage — one of bind, capture, image, rewrite, parse, load, layout, run — and no GPU work happens at all. After the launch, the remaining checks still run, so the record says everything that was wrong rather than only the first thing, and then the verdict is fail with the stage named. The .olyt is written in that case too, deliberately: it is evidence about the failure, and the verdict beside it is what keeps it from being read as a trace.

失败的运行只被报告，不被挽救。没有"换个更松的比较再试一次"，没有尽力而为的追踪，也没有哪个阶段因为不方便而被跳过。启动之前，失败就是一个以阶段命名的异常——bind、capture、image、rewrite、parse、load、layout、run 之一——完全不会有 GPU 工作发生。启动之后，剩下的检查仍然会跑完，所以记录里写的是所有出错的地方，而不只是第一个，然后判定为 fail 并注明阶段。那种情况下 .olyt 也会写出，这是刻意的：它是关于这次失败的证据，而旁边的判定正是阻止它被当成一份追踪来读的东西。

The final trace sweep traced DeepGEMM's k512 1D-2D kernel with the trace-pp site set. It was one command, and the escalation in the middle of it is real: the default ring of 64 was too shallow for this kernel, so the set ran twice.

最终的追踪扫描用 trace-pp 站点集合追踪了 DeepGEMM 的 k512 1D-2D kernel。只有一条命令，而中间那次升级是真实发生的：默认的 64 深环对这个 kernel 太浅，所以这个集合跑了两次。

The attempt that passed, step by step, with the values its result.json records:

通过的那次尝试，逐步走一遍，数值取自它的 result.json：

  1. Capture. One launch of the kernel: grid 132×1×1, block 384×1×1, 216,336 bytes of dynamic shared memory. Its image hashed e0f1350cd90ca693…, equal to the case's built kernel.cubin. The capture run's own outputs already matched ref.json.
  2. Plan. The search planner placed 46 islands — 1 INIT, 41 RECORD, 4 EXIT calibrations, 386 probe instructions in all — holding the slot base in UR60 and UR61 and the record count in UR62. Layout: warp granularity, 4-byte records, id_bits 6, ring 256, so a slot is 1,056 bytes. 2.23 s.
  3. Splice. 1,504 instruction words became 1,896: the 386 probe instructions plus 6 never-executed filler words that pad the text section to a 128-byte boundary, with every original word copied through. The parameter block went from 624 to 632 bytes, the buffer pointer at offset 624. REGCOUNT 168 before and after. The spliced image is 40,072 bytes, sha256 d7d11d6df03ff582…. The hazard check on those exact bytes found 1,603 probe instruction pairs and 0 violations touching a probe.
  4. Load. The driver loaded the image and found the kernel. The spliced CUfunction came back as 0x8fd7b100, the original's was 0x71abf6f0: non-null and distinct. Olympus's ELF reader counted 1,896 instructions, which is what the loader parsed. NUM_REGS 168 for both kernels, in both the image's view and the driver's.
  5. Layout, three ways. Nine original parameters, the last of them at (496, 128). The same gate on a run that fails同一道门，面对一次失败的运行

A gate you have only seen pass is not evidence. The canary rewriter is the negative control: it overwrites instruction 1 of every kernel with that kernel's own unguarded EXIT word, taken from the end of its text, so the kernel exits before computing anything, and EXPECT_MATCH records that this rewriter must not match. Here is the same gate on it, on the straight-line micro-kernel t0_straight:

一道只见它通过过的门不构成证据。canary 重写器就是那个阴性对照：它把每个 kernel 的第 1 条指令改写成该 kernel 自己的无 guard EXIT 字（取自其代码段末尾），于是 kernel 在计算任何东西之前就退出，而 EXPECT_MATCH 记录着这个重写器必须不匹配。下面是同一道门在它身上的表现，用的是直线型微 kernel t0_straight：

$ olympus splice-check t0_straight --rewriter canary --out .../m2check-canary
t0_straight            pass      load=ok layout=True match=False (14.9 s)   # the negative control: it passes because the outputs differ
  1. Capture. As in any run: the kernel found, launched exactly once, its image equal to the corpus cubin by sha256, and this run's outputs already matching the reference.
  2. Rewrite. The canary writes one instruction word and appends no parameter, so the SpliceResult carries an empty kernels map and there is no KernelEdit.
  3. Load and layout. The image parses, loads, and defines the kernel. With no edit, the layout check applies its other rule: the spliced parameter layout must equal the original's exactly, and no parameter value may be handed in. It did, and none was.
  4. Launch. Outputs poisoned with 0xA5. There is no trace buffer: splice-check allocates a zeroed 4 KiB scratch buffer and hands its address over as the appended parameter when the rewriter appended one, then checks afterwards that the kernel left it untouched. The canary appends nothing, so no value was passed and the buffer stayed zero. One launch of the kernel.
  5. The gate. The outputs did not match the reference: they still held the poison, because the kernel exited at instruction 1 without writing anything. For every other rewriter that is a failure. For the canary it is the pass condition — expect_match is false — and a match here would have meant the swap never ran our image at all. The scratch buffer was untouched.
  6. Restore. The redirect cleared, the outputs poisoned once more, the original kernel run again: it reproduced the reference. Verdict pass, as a negative control, with match=False in the record.
  1. 捕获。与任何一次运行一样：找到 kernel，恰好启动一次，镜像 sha256 等于语料库 cubin，这次运行的输出已与参考匹配。
  2. 重写。canary 只写一条指令字，不追加参数，所以 SpliceResult 带的 kernels 映射为空，也就没有 KernelEdit。
  3. 加载与布局。镜像解析、加载，并定义了该 kernel。没有编辑时，布局检查走的是它的另一条规则：拼接后的参数布局必须与原布局完全相同，且不得传入任何参数值。事实如此，也确实没传。
  4. 启动。输出投毒为 0xA5。没有追踪缓冲区：splice-check 分配一个清零的 4 KiB 暂存缓冲区，在重写器追加了参数时把它的地址作为追加参数传入，事后检查 kernel 没有碰过它。canary 什么都不追加，所以没有传入任何值，缓冲区保持为零。该 kernel 启动一次。
  5. 这道门。输出与参考不匹配：它们仍是毒值，因为 kernel 在第 1 条指令就退出，什么都没写。对其他任何重写器，这是失败。对 canary，这正是通过条件——expect_match 为 false——而此处若匹配，就说明替换根本没有运行我们的镜像。暂存缓冲区未被触碰。
  6. 恢复。清除重定向，再次对输出投毒，重新运行原 kernel：它复现了参考结果。判定 pass，作为阴性对照，记录中带着 match=False。

§4Where it came from从何而来

The paper's system has three parts: a probe library, a splicer, and a runtime driver paper §3. The driver is this chapter's ancestor, and it does three things. It intercepts the kernel's launch. It swaps in the spliced binary. And it appends the trace buffer's address to the launch parameters — the same appended parameter this layer fills in, read by the same kind of INIT probe, which takes the warp's slot from the launch geometry while the RECORD probes write into it. Afterwards the driver collects the slots paper §4.5.

论文的系统有三部分：探针库、拼接器，以及一个运行时驱动 论文 §3。那个驱动就是本章的前身，它做三件事。它拦截 kernel 的启动。它换入拼接后的二进制。它把追踪缓冲区的地址追加到启动参数上——正是这一层填入的那个追加参数，由同一类 INIT 探针读取，该探针从启动几何得到本 warp 的槽位，而 RECORD 探针往里写。事后，驱动收集各槽位 论文 §4.5。

Olympus keeps that shape exactly: an appended 8-byte parameter, per-warp slots, something that swaps and collects. What it changes is all in the two words "intercepts" and "afterwards". The paper's driver is one interception layer; Olympus has two backends and writes no interception code at all, because no single mechanism exists on both of its machines. And where the paper's driver collects the slots and is done, Olympus's does not hand the data over until the run has passed a gate the paper does not have. The three asides below are those differences, each with the decision that settled it.

Olympus 完整保留了这个形状：追加一个 8 字节参数、每 warp 一个槽位、一个负责替换和收集的东西。它改动的全在"拦截"和"事后"这两处。论文的驱动是一层拦截；Olympus 有两个后端，而且完全不写拦截代码，因为没有任何单一机制能同时在它的两台机器上存在。而论文的驱动收集完槽位就结束了，Olympus 的则要等这次运行通过一道论文没有的门，才会把数据交出去。下面三条旁注就是这些差异，每条都附上拍定它的那个决定。

Where Olympus departs: two backends instead of one interception layerOlympus 的不同之处：两个后端，而不是一层拦截DECISIONS 81

Olympus writes no interception code. On sm_90 the swap is G-Watch 0.0.35's module-swap runtime, used through its public Python API; on sm_103, where that runtime has no build, Olympus's own driver-API loader does the swap. Both run every check of this chapter, and on H200 they agree image for image and record for record DECISIONS.md:484–492. Retiring the first backend needs an Olympus-owned module-load interception; that is a follow-up, not a design choice (DECISIONS 92).

Olympus 不写拦截代码。在 sm_90 上，替换由 G-Watch 0.0.35 的模块替换运行时完成，通过它的公开 Python API 使用；在没有该运行时构建的 sm_103 上，由 Olympus 自己的驱动 API 加载器完成替换。两者都跑本章的全部检查，在 H200 上逐镜像、逐记录一致 DECISIONS.md:484–492。退役第一个后端需要一个 Olympus 自己的模块加载拦截；那是后续工作，不是设计选择（DECISIONS 92）。

Where Olympus departs: a relaunch, not an in-callback swapOlympus 的不同之处：重启动，而不是在回调内替换DECISIONS 86

The paper's driver changes the application's launch as it happens. For kernels launched from native code, Olympus instead observes the launch read-only and rebuilds it with documented driver calls, because CUPTI declares the callback's parameters const and documents no way to change a call. Checked on every run: the application makes exactly one launch and no other device work, the identity relaunch is bit-exact, and the application's next launch after the restore carries the same bytes DECISIONS.md:538–548.

论文的驱动在应用启动发生时改变它。对于从原生代码启动的 kernel，Olympus 改为只读地观察启动，再用有文档的驱动调用重建它，因为 CUPTI 把回调参数声明为 const，且没有记载任何改变调用的方法。每次运行都检查：应用恰好发起一次启动、没有其他设备工作，恒等重启动逐位一致，恢复之后应用的下一次启动携带同样的字节 DECISIONS.md:538–548。

Beyond the paper: the gate论文之外：这道门

Poisoned outputs, the reference hashes, the guard bands, the restore run and the canary are Olympus's. The paper evaluates correctness by binary similarity and overhead paper §5.3; Olympus also requires, on every run, that the traced kernel compute exactly what the original computes.

投毒的输出、参考哈希、保护带、恢复运行和 canary 都是 Olympus 自己的。论文用二进制相似度和开销来评估正确性 论文 §5.3；Olympus 还要求每一次运行中，被追踪的 kernel 算出的结果与原 kernel 完全相同。
