Running a traced kernel运行被追踪的 kernel

The runtime runs a spliced image in place of the original and decides whether to believe what came back. It is the only layer that touches a GPU, and it is built to refuse: nothing launches until the plan matches the captured kernel, the image loads, and three views of the parameter layout agree; nothing is trusted until the outputs are bit-identical to the original's, the trace buffer's guard bands are intact, and the original kernel runs again and reproduces the reference.

运行时用拼接后的镜像替代原 kernel 运行，并决定是否相信返回的结果。它是唯一接触 GPU 的层，而且是为拒绝而造的：在计划与捕获到的 kernel 匹配、镜像成功加载、参数布局的三个视角一致之前，什么都不启动；在输出与原 kernel 逐位一致、追踪缓冲区的保护带完好、原 kernel 再次运行并复现参考结果之前，什么都不信任。

§1Contract契约

What this layer promises这一层的承诺

A traced run is trusted only after its outputs are bit-identical to the original's and its buffer's guard bands are intact.

一次追踪运行只有在输出与原 kernel 逐位一致、缓冲区保护带完好之后才被信任。

olympus/runtime → hands交付 .olyt to给 olympus/trace · takes a接收 SpliceResult from来自 olympus/splice

The reading layer (chapter 01) never sees a run that failed this gate. The runtime's input is a SpliceResult: the new image, and for each kernel a KernelEdit saying that param_size bytes were appended at param_offset, the trace buffer's address result.py:1–36. Its output is the .olyt file, written only after every check below has passed, plus a result.json that records each stage reached.

阅读层（第 01 章）永远看不到一次没过这道门的运行。运行时的输入是一个 SpliceResult：新镜像，以及每个 kernel 的一个 KernelEdit，说明在 param_offset 处追加了 param_size 字节，即追踪缓冲区的地址 result.py:1–36。它的输出是 .olyt 文件，只在下面每项检查都通过后才写出，外加一份记录到达了哪个阶段的 result.json。

§2Invariant不变量

Invariant不变量5

Nothing runs before it is checked. The offline proof, the hazard check on the spliced cubin, the parameter-layout check three ways and the bit-exact output gate all run before a traced run is trusted; a problem is reported before launch.

没有检查过的东西不会运行。离线证明、对拼接后 cubin 的冒险检查、三个视角的参数布局检查、逐位一致的输出门，都在一次追踪运行被信任之前完成；问题在启动之前报告。

Checked by the fail-closed stages of trace_launch, each raising RuntimeFailure with its stage name before any launch base.py:27–34; by the canary rewriter, a negative control whose outputs must differ; and by fuzzing: 800 of 800 random site sets across 20 kernels, 0 faults, 0 refused (EVAL.md, A7).

检查方式：trace_launch 的各个失败即停的阶段，每个都在任何启动之前抛出带阶段名的 RuntimeFailure base.py:27–34；canary 重写器，一个输出必须不同的阴性对照；以及模糊测试：20 个 kernel 上 800 组随机站点，800 次全部通过，0 次故障，0 次拒绝（EVAL.md，A7）。

A weaker gate would be "the outputs look right". The gate here poisons every output byte with 0xA5 before the traced run, so a kernel that never ran, or exited early, cannot match by accident; and after the traced run it unregisters the spliced kernel, poisons again and runs the original, which must reproduce the reference. The canary makes the gate prove itself: it overwrites instruction 1 of every kernel with an unguarded EXIT, so the kernel writes nothing and the outputs must keep the poison; a match would mean the swap did not run our image rewriters.py:10–14.

更弱的门会是"输出看起来没错"。这里的门在追踪运行之前把每个输出字节投毒为 0xA5，于是从未运行或提前退出的 kernel 不可能碰巧匹配；追踪运行之后，它注销拼接后的 kernel，再次投毒并运行原 kernel，后者必须复现参考结果。canary 让这道门证明自己：它把每个 kernel 的第 1 条指令改写成无 guard 的 EXIT，kernel 什么都不写，输出必须保留毒值；若匹配，就说明替换并没有运行我们的镜像 rewriters.py:10–14。

§3How it works如何工作

One traced launch一次追踪启动

trace_launch takes a captured kernel and a probe plan and runs the case once with the spliced kernel and a fresh trace buffer tracer.py:1–22:

trace_launch 接收一个捕获到的 kernel 和一份探针计划，用拼接后的 kernel 和一个新的追踪缓冲区把用例运行一次 tracer.py:1–22：

  1. Capture. One run of the case with launch tracing on. The kernel named by the sites file must be found, launched exactly once, and its image must equal the corpus cubin by sha256; the plan must be for that kernel and that image.
  2. Splice and load. The plan's rewriter splices the image; the backend loads it and checks the parameter layout three ways. Nothing launches if any of this fails.
  3. Buffer. One allocation of n_slots × slot_bytes, zeroed, between two 4 KiB guard bands of 0xA5; its address becomes the appended parameter.
  4. Launch. Outputs poisoned, then the case runs with the spliced kernel in place of the original; exactly one launch of the kernel must have happened.
  5. Check. Outputs against the reference, the buffer copied back, guards and contents checked, and the ring depth checked against the largest n_records.
  6. Write and restore. <set>.olyt is written and read back, and must decode every record the buffer holds; then the original kernel runs again and must reproduce the reference.
  1. 捕获。开启启动追踪把用例运行一次。站点文件所指的 kernel 必须被找到、恰好启动一次，其镜像的 sha256 必须等于语料库中的 cubin；计划必须是针对这个 kernel 和这个镜像的。
  2. 拼接并加载。计划的重写器拼接镜像；后端加载它，并从三个视角检查参数布局。任一环节失败，什么都不启动。
  3. 缓冲区。一次分配 n_slots × slot_bytes，清零，夹在两段 4 KiB 的 0xA5 保护带之间；它的地址就是追加的参数。
  4. 启动。先对输出投毒，再用拼接后的 kernel 替代原 kernel 运行用例；该 kernel 必须恰好启动一次。
  5. 检查。输出对照参考，缓冲区拷回，检查保护带和内容，并对照最大的 n_records 检查环深度。
  6. 写出并恢复。写出 <set>.olyt 并读回，必须解码出缓冲区中的每条记录；然后原 kernel 再次运行，必须复现参考结果。

The parameter layout, three ways参数布局的三个视角

The spliced kernel takes one more parameter than the original: the buffer pointer. Three views of the parameter block must agree before a launch: the splicer's promise in the KernelEdit, the images' own EIATTR_KPARAM_INFO records read by Olympus's ELF reader, and the driver's cuFuncGetParamInfo on both loaded functions. With an edit, the spliced layout must be the original's plus exactly one appended entry (param_offset, 8); without one, it must equal the original's layout.py:1–17. The offset is never assumed: the same source puts it at 112 on sm_90a and 128 on sm_103a, so it always comes from the captured layout (DECISIONS 86).

拼接后的 kernel 比原 kernel 多一个参数：缓冲区指针。启动之前，参数块的三个视角必须一致：拼接器在 KernelEdit 中的承诺、由 Olympus 的 ELF 读取器读出的镜像自带 EIATTR_KPARAM_INFO 记录，以及驱动对两个已加载函数的 cuFuncGetParamInfo。有编辑时，拼接后的布局必须等于原布局加上恰好一个追加项 (param_offset, 8)；没有编辑时，必须与原布局相同 layout.py:1–17。偏移从不假设：同一份源码在 sm_90a 上是 112，在 sm_103a 上是 128，所以它永远来自捕获到的布局（DECISIONS 86）。

Guarded buffers and the ring带保护带的缓冲区与环

The buffer has one slot per warp: a 32-byte header, then a ring of records. After the launch a numpy check, no GPU, verifies what the probes wrote: every slot has a valid header and an exit calibration; every ring entry the kernel did not fill, every byte of slot padding and the reserved bits of the SM-id word are still zero; no exit timestamp precedes its INIT one; and the guard bands are untouched tracebuf.py:1–18. n_records is monotonic, so a value above the ring depth means the ring wrapped and records were lost: the run fails its check and the set is re-run at the next power of two, up to --max-ring, every attempt kept as d<depth>/ USAGE.md:659–706.

缓冲区每个 warp 一个槽位：32 字节头部，之后是一个记录环。启动之后，一个不用 GPU 的 numpy 检查核对探针写下的内容：每个槽位都有有效的头部和退出校准；kernel 没有填写的每个环表项、槽位填充的每个字节、SM 编号字的保留位仍为零；没有退出时间戳早于它的 INIT 时间戳；保护带未被触碰 tracebuf.py:1–18。n_records 单调递增，所以超过环深度的值意味着环回绕、记录丢失：这次运行的检查失败，该集合以下一个 2 的幂重跑，直到 --max-ring，每次尝试都保留为 d<depth>/ USAGE.md:659–706。

Two backends, one set of checks两个后端，一套检查

Both backends give the same Capture and Swap objects to the checks above base.py:1–15. gwatch is a thin layer over the module-swap runtime of G-Watch 0.0.35, through its Python API: it sees the module loads and launches, loads the spliced image as a separate module and registers it in place of the original for one run. It exists on sm_90 only and is the default there, because it serves every corpus launch path, Triton and cuBLAS included gwatch.py:1–24. direct is Olympus's own: a ctypes driver-API loader that cuModuleLoadDatas the spliced image and redirects the case's launch to the spliced function with the buffer pointer appended, with no G-Watch and no interception; it serves the kernels that launch through Olympus's loader and is the default on GB300 direct.py:1–42. On H200 the two produce identical spliced images, outputs, ring escalations and records per site (DECISIONS 81) backend.py:1–13.

两个后端把同样的 Capture 与 Swap 对象交给上面的检查 base.py:1–15。gwatch 是 G-Watch 0.0.35 模块替换运行时之上的一层薄封装，通过它的 Python API：它看到模块加载和启动，把拼接后的镜像作为独立模块加载，并在一次运行中注册替换原 kernel。它只存在于 sm_90 上，也是那里的默认，因为它能服务语料库的每一条启动路径，包括 Triton 和 cuBLAS gwatch.py:1–24。direct 是 Olympus 自己的：一个 ctypes 驱动 API 加载器，用 cuModuleLoadData 加载拼接后的镜像，并把用例的启动重定向到拼接后的函数、追加缓冲区指针，不用 G-Watch，也不做拦截；它服务通过 Olympus 加载器启动的 kernel，是 GB300 上的默认 direct.py:1–42。在 H200 上两者给出完全相同的拼接镜像、输出、环升级和每站点记录数（DECISIONS 81）backend.py:1–13。

A kernel launched from native code the loader cannot redirect, such as DeepGEMM's JIT on GB300, goes through the direct backend's relaunch path: a read-only CUPTI observer records the application's own cuLaunchKernelEx, its configuration and parameter bytes; the spliced run loads the spliced image the same way the application did and makes one launch of its own with the captured parameters plus the buffer pointer; after the restore, the application's next launch must carry byte-identical parameters relaunch.py:1–37.

由加载器无法重定向的原生代码启动的 kernel，比如 GB300 上 DeepGEMM 的 JIT，走 direct 后端的重启动路径：一个只读的 CUPTI 观察者记录应用自己的 cuLaunchKernelEx、它的配置和参数字节；拼接运行按应用加载原镜像的方式加载拼接后的镜像，并用捕获到的参数加缓冲区指针自己发起一次启动；恢复之后，应用的下一次启动必须携带逐字节相同的参数 relaunch.py:1–37。

Two commands两个命令

olympus splice-check runs every case through the runtime with a rewriter and compares outputs with the reference: null (a NOP island before every basic-block leader plus the appended parameter), identity (the swap path itself), canary (must not match), or any function returning a SpliceResult splicecheck.py:1–32. olympus trace does the same with a planner's probes, one fresh process per case × set, and prints one line per set: the verdict, the last stage reached, whether the outputs were bit-exact (out), whether the guard bands and slot headers were valid (buf), and the record count USAGE.md:659–706.

olympus splice-check 用一个重写器让每个用例走一遍运行时，并把输出与参考比较：null（每个基本块首指令前一个 NOP island 加追加参数）、identity（替换路径本身）、canary（必须不匹配），或任何返回 SpliceResult 的函数 splicecheck.py:1–32。olympus trace 用规划器的探针做同样的事，每个用例 × 集合一个新进程，每个集合打印一行：判定、到达的最后阶段、输出是否逐位一致（out）、保护带和槽位头是否有效（buf），以及记录数 USAGE.md:659–706。

§4Where it came from从何而来

The paper's system has three parts: a probe library, a splicer and a runtime driver that intercepts the kernel's launch, swaps in the spliced binary and appends the trace buffer's address to the launch parameters paper §3. Its INIT probe takes the slot from the launch geometry and the RECORD probes write into it; the driver collects the slots afterwards paper §4.5. Olympus keeps that shape: an appended 8-byte parameter, per-warp slots, a driver that swaps and collects.

论文的系统有三部分：探针库、拼接器，以及一个拦截 kernel 启动、换入拼接后二进制、把追踪缓冲区地址追加到启动参数的运行时驱动 论文 §3。它的 INIT 探针从启动几何得到槽位，RECORD 探针往里写；驱动事后收集各槽位 论文 §4.5。Olympus 保留了这个形状：追加一个 8 字节参数，每 warp 一个槽位，一个负责替换和收集的驱动。

Where Olympus departs: two backends instead of one interception layerOlympus 的不同之处：两个后端，而不是一层拦截DECISIONS 81

Olympus writes no interception code. On sm_90 the swap is G-Watch 0.0.35's module-swap runtime, used through its public Python API; on sm_103, where that runtime has no build, Olympus's own driver-API loader does the swap. Both run every check of this chapter, and on H200 they agree image for image and record for record DECISIONS.md:484–492. Retiring the first backend needs an Olympus-owned module-load interception; that is a follow-up, not a design choice (DECISIONS 92).

Olympus 不写拦截代码。在 sm_90 上，替换由 G-Watch 0.0.35 的模块替换运行时完成，通过它的公开 Python API 使用；在没有该运行时构建的 sm_103 上，由 Olympus 自己的驱动 API 加载器完成替换。两者都跑本章的全部检查，在 H200 上逐镜像、逐记录一致 DECISIONS.md:484–492。退役第一个后端需要一个 Olympus 自己的模块加载拦截；那是后续工作，不是设计选择（DECISIONS 92）。

Where Olympus departs: a relaunch, not an in-callback swapOlympus 的不同之处：重启动，而不是在回调内替换DECISIONS 86

The paper's driver changes the application's launch as it happens. For kernels launched from native code, Olympus instead observes the launch read-only and rebuilds it with documented driver calls, because CUPTI declares the callback's parameters const and documents no way to change a call. Checked on every run: the application makes exactly one launch and no other device work, the identity relaunch is bit-exact, and the application's next launch after the restore carries the same bytes DECISIONS.md:538–548.

论文的驱动在应用启动发生时改变它。对于从原生代码启动的 kernel，Olympus 改为只读地观察启动，再用有文档的驱动调用重建它，因为 CUPTI 把回调参数声明为 const，且没有记载任何改变调用的方法。每次运行都检查：应用恰好发起一次启动、没有其他设备工作，恒等重启动逐位一致，恢复之后应用的下一次启动携带同样的字节 DECISIONS.md:538–548。

Beyond the paper: the gate论文之外：这道门

Poisoned outputs, the reference hashes, the guard bands, the restore run and the canary are Olympus's. The paper evaluates correctness by binary similarity and overhead paper §5.3; Olympus also requires, on every run, that the traced kernel compute exactly what the original computes.

投毒的输出、参考哈希、保护带、恢复运行和 canary 都是 Olympus 自己的。论文用二进制相似度和开销来评估正确性 论文 §5.3；Olympus 还要求每一次运行中，被追踪的 kernel 算出的结果与原 kernel 完全相同。

§5Try it: the gate, on three real runs动手试试：三次真实运行过门

Step through capture → splice → load → launch → check → restore on three runs that happened. The first is DeepGEMM k512's trace-pp set at ring depth 256: every check holds. The second is the same set's first attempt at depth 64: the outputs and guard bands are fine, but a slot wrote 130 records into a 64-deep ring, so the check fails and the set is re-run deeper. The third is the canary on a micro-kernel: the outputs differ from the reference, which is exactly what the gate must see. The last stage shows the shape of each run's result.json.

在三次真实发生过的运行上逐步走过 捕获 → 拼接 → 加载 → 启动 → 检查 → 恢复。第一次是 DeepGEMM k512 的 trace-pp 集合、环深度 256：每项检查都成立。第二次是同一集合在深度 64 上的首次尝试：输出和保护带都没问题，但有一个槽位往 64 深的环里写了 130 条记录，于是检查失败，集合以更深的环重跑。第三次是在一个微 kernel 上的 canary：输出与参考不同，而这正是这道门必须看到的。最后一个阶段展示每次运行的 result.json 的形状。
