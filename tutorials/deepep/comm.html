Communication Layer and PTX通信层与 PTX

The layer under every DeepEP kernel: one device handle that turns a rank index into an NVLink pointer or a NIC request, the queue pairs behind it, barriers built from counters, the symmetric memory those counters live in, and the PTX instructions that move the bytes.

位于每个 DeepEP kernel 之下的那一层：一个把 rank 编号换成 NVLink 指针或 NIC 请求的设备端 handle、它背后的 queue pair、由计数器构成的 barrier、这些计数器所在的对称内存，以及真正搬运字节的 PTX 指令。

§1One handle, three teams一个 handle，三个 team

Every kernel builds a comm::NCCLGin from the NCCL device communicator and the buffer's window. It holds a Gin handle bound to one QP and three team descriptors from NCCL: World (every rank), LSA (the ranks this GPU can load from and store to over NVLink) and Rail (one rank per node, the GPUs with the same local index) handle.cuh:26–35. A destination index means something different in each team: a world rank, a position inside the NVLink domain, or a node index.

每个 kernel 都用 NCCL device communicator 和 buffer 的 window 构造一个 comm::NCCLGin。它持有一个绑定到某个 QP 的 Gin 句柄，以及 NCCL 的三个 team 描述：World（所有 rank）、LSA（本 GPU 能经 NVLink 直接 load/store 的 rank）和 Rail（每个节点一个 rank，即本地编号相同的 GPU）handle.cuh:26–35。目标编号在不同 team 中含义不同：world rank、NVLink 域内的位置，或者节点编号。

get_sym_ptr is where the transport gets decided handle.cuh:63–92. For World and LSA it checks whether the destination sits in this GPU's NVLink domain. If it does, it returns the peer's address for the same window offset from ncclGetLsaPointer, or the local pointer itself when the destination is this rank. For Rail it only returns a pointer when the destination is this rank's own node. A null result means the peer is reachable only through the NIC. The operations built on it pick their instruction from that result:

传输方式在 get_sym_ptr 里决定 handle.cuh:63–92。对 World 和 LSA，它检查目标是否在本 GPU 的 NVLink 域内；若在，就用 ncclGetLsaPointer 返回 peer 上同一 window 偏移的地址，目标是本 rank 时直接返回本地指针。对 Rail，只有目标就是本 rank 所在节点时才返回指针。返回空指针意味着只能经 NIC 到达该 peer。建立在它之上的操作按这个结果选择指令：

  • put_value: st.relaxed.sys through the pointer, otherwise gin.putValue handle.cuh:227–247.
  • red_add_rel: red.release.gpu for this rank or the Rail team, red.release.sys for an NVLink peer, otherwise a Gin signal-add, which only takes 64-bit values handle.cuh:94–120.
  • put: always a Gin put through the NIC, even when the destination is local or on NVLink, and only for World and Rail handle.cuh:200–225. Kernels that want NVLink bulk copies call get_sym_ptr and issue TMA stores themselves, as chapter 01 shows.
  • put_value：有指针就用 st.relaxed.sys 写，否则用 gin.putValue handle.cuh:227–247。
  • red_add_rel：本 rank 或 Rail team 用 red.release.gpu，NVLink peer 用 red.release.sys，否则用 Gin signal-add，后者只接受 64 位数值 handle.cuh:94–120。
  • put：总是经 NIC 发一次 Gin put，即使目标是本地或在 NVLink 上；只支持 World 和 Rail handle.cuh:200–225。需要 NVLink 批量拷贝的 kernel 会调用 get_sym_ptr 后自己发 TMA store，见第 01 章。

§2Queue pairsQueue pair

When a buffer builds its Context, it asks NCCL for a device communicator with GDAKI-type Gin: num_allocated_qps exclusive Gin contexts, a queue depth of 1024 by default, and num_ranks + 4 signals for the custom barrier context.cpp:121–146. DeepEP calls these contexts QPs, and ncclGin(dev_comm, qp_idx, mode) binds a kernel's handle to one of them handle.cuh:26–32. Kernels choose the index with get_qp_mode:

buffer 构造 Context 时，向 NCCL 申请一个 GDAKI 类型 Gin 的 device communicator：num_allocated_qps 个独占的 Gin context，默认队列深度 1024，另有 num_ranks + 4 个 signal 供自定义 barrier 使用 context.cpp:121–146。DeepEP 把这些 context 叫作 QP，ncclGin(dev_comm, qp_idx, mode) 把 kernel 的句柄绑定到其中一个 handle.cuh:26–32。kernel 用 get_qp_mode 选择编号：

Notify warps always take QP 0 with CTA-level sharing. When there are at least as many data QPs as SMs, each SM owns a disjoint strided set and its channels cycle through it, so a QP is only ever used inside one block (NCCL_GIN_RESOURCE_SHARING_CTA). With fewer QPs than SMs, channels map round-robin over all QPs and the sharing becomes GPU-wide. The EP defaults from chapter 01 fall in the first case when hybrid mode is allowed (129 QPs) and in the second in direct mode, where a call uses min(num_sms, 9) ep.py:553–560.

notify warp 总是用 QP 0，共享级别为 CTA。数据 QP 不少于 SM 数时，每个 SM 独占一组跨步分布的 QP，它的 channel 在这组里轮转，所以一个 QP 只在一个 block 内使用（NCCL_GIN_RESOURCE_SHARING_CTA）。QP 少于 SM 时，channel 在全部 QP 上轮转，共享范围扩大到整个 GPU。第 01 章的 EP 默认值在允许 hybrid 模式时（129 个 QP）属于第一种情况；direct 模式每次调用只用 min(num_sms, 9) 个 QP，属于第二种 ep.py:553–560。

Solid gold cells keep their QP inside one SM (CTA sharing); dashed cells share it across SMs (GPU sharing). Column N is the notify warp.

实心金色格子的 QP 只在一个 SM 内使用（CTA 共享）；虚线格子跨 SM 共享（GPU 共享）。N 列是 notify warp。

Why keep a QP inside one block为什么让 QP 留在一个 block 内

A QP shared only by one block lets NCCL coordinate posting with block-scope synchronization; GPU-wide sharing needs coordination across SMs. That is my reading of the two sharing modes, not something DeepEP states.

只被一个 block 使用的 QP，NCCL 提交请求时只需 block 级别的同步；GPU 级共享则需要跨 SM 协调。这是我对两种共享模式的理解，DeepEP 并未明说。

§3Barriers made of counters由计数器构成的 barrier

gpu_barrier is the barrier every kernel calls at its start and end barrier.cuh:196–252. It optionally drains outstanding TMA stores, syncs the cooperative grid, and runs the scale-up and scale-out barriers. When both exist they run in parallel: SM 0 takes scale-up and the remaining SMs take scale-out. A final grid sync ends it. The two halves use different mechanisms.

gpu_barrier 是每个 kernel 开头和结尾都会调用的 barrier barrier.cuh:196–252。它可选地先排空未完成的 TMA store，同步整个 cooperative grid，再执行 scale-up 与 scale-out 两个 barrier。两者都存在时并行进行：SM 0 负责 scale-up，其余 SM 负责 scale-out。最后再做一次 grid 同步。两部分的机制各不相同。

NVLink: two slots and a sign bitNVLink：两个槽和一个符号位

The NVLink barrier never resets anything. Each rank keeps a 64-bit counter and two int slots in its signal workspace layout/common/barrier.cuh:11–22. On entry it reads the counter's low two bits: bit 0 picks the slot (the phase) and bit 1 picks the direction (the sign). It adds +1 or −1 to that slot on every rank with red.release.sys, bumps its own counter, and polls with ld.acquire.sys until its own slot reaches kNumRanks for +1 or 0 for −1 barrier.cuh:88–131.

NVLink barrier 从不重置任何东西。每个 rank 在自己的信号区里有一个 64 位计数器和两个 int 槽 layout/common/barrier.cuh:11–22。进入时读取计数器的低两位：bit 0 选槽（phase），bit 1 选方向（sign）。它用 red.release.sys 给每个 rank 的这个槽加 +1 或 −1，把自己的计数器加一，再用 ld.acquire.sys 轮询自己的槽，直到 +1 时变成 kNumRanks、−1 时变成 0 barrier.cuh:88–131。

Four barriers in a row take slot 0 up to N, slot 1 up to N, slot 0 back to 0 and slot 1 back to 0, so both slots are clean again without anyone writing a zero. The second slot is what lets a fast rank enter the next barrier while slow ranks are still watching the current one. Try it: release the resting barrier with rank 3, then let one rank run ahead.

连续四次 barrier 依次让 slot 0 升到 N、slot 1 升到 N、slot 0 降回 0、slot 1 降回 0，两个槽又都干净了，全程没有人写过 0。第二个槽让快的 rank 可以进入下一次 barrier，而慢的 rank 仍在观察当前这一次。可以试试：先用 rank 3 放行当前的 barrier，再让某个 rank 先跑一步。

Animation动画NVLink barrier across 4 ranks4 个 rank 的 NVLink barrier

Each card shows one rank's counter and its own two slots. Arriving ranks send a colored ±1 to the same slot on every rank; a rank leaves once its own slot hits the target. Only SM 0 of a kernel runs this barrier.

每张卡片显示一个 rank 的计数器和它自己的两个槽。到达的 rank 向每个 rank 的同一个槽发送带颜色的 ±1；自己的槽达到目标值时该 rank 离开。kernel 中只有 SM 0 执行这个 barrier。

Gin: flush, fence, signalGin：flush、fence、signal

The RDMA barrier first flushes every QP that may carry earlier puts, with each warp taking a slice of them, so all prior writes have completed. For the World team, which can mix NVLink stores with Gin signals, it adds a system-scope fence. Then it syncs the grid barrier.cuh:133–169. SM 0 uses QP 0 to increment signal rank_idx on every peer and waits on each peer's signal. Gin signals are rolling counters: the waiter keeps a shadow copy, increments it, and waits for the signal to reach the new value, so they never need a reset handle.cuh:178–198.

RDMA barrier 先 flush 所有可能承载过先前 put 的 QP（每个 warp 负责其中一部分），确保之前的写入都已完成。World team 可能混用 NVLink store 与 Gin signal，因此还要加一次系统级 fence。然后同步 grid barrier.cuh:133–169。SM 0 用 QP 0 给每个 peer 的第 rank_idx 个 signal 加一，再等待每个 peer 的 signal。Gin signal 是滚动计数器：等待方保留一份影子副本，先加一，再等 signal 达到这个新值，所以永远不需要重置 handle.cuh:178–198。

Every wait in the library goes through timeout_while barrier.cuh:30–54. It compares clock64() against the cycle budget compiled into the kernel, lets the waiter print diagnostics on the last check, spins about one more second (2·10⁹ cycles) so every thread gets to print, and then executes trap. A hang becomes a crash with a message naming the rank and the counter. Python's buffer.barrier() launches a standalone barrier_impl kernel with 512 threads on one SM, or two when the halves run in parallel, and flushes every allocated QP kernels/comm/barrier.hpp:17–54 impls/comm/barrier.cuh:11–41.

库中的每一次等待都经过 timeout_while barrier.cuh:30–54。它拿 clock64() 与编译进 kernel 的周期预算比较，最后一次检查时让等待方打印诊断信息，再空转约一秒（2·10⁹ 个周期）让每个线程都有机会打印，然后执行 trap。于是一次挂起会变成一次带有 rank 和计数器信息的崩溃。Python 的 buffer.barrier() 会单独启动一个 512 线程的 barrier_impl kernel，占 1 个 SM（两部分并行时占 2 个），并 flush 所有已分配的 QP kernels/comm/barrier.hpp:17–54 impls/comm/barrier.cuh:11–41。

§4Symmetric memory对称内存

The Context gets its memory from one of three allocators symmetric.hpp:302–330. The choice depends on whether the buffer needs extra RDMA storage, which only Engram does, and on whether hybrid mode is on.

Context 从三种分配器之一取得内存 symmetric.hpp:302–330。选哪一种取决于 buffer 是否需要额外的 RDMA 存储（只有 Engram 需要），以及是否开启 hybrid 模式。

  • GPUSymmetricMemory wraps ncclMemAlloc for the workspace plus the buffer symmetric.hpp:119–135.
  • ElasticSymmetricMemory reserves one virtual range, maps a device allocation for the symmetric part, then maps storage created on the GPU or on the host NUMA node closest to it. With host storage, the GPU gets read/write access to those pages through the same pointer symmetric.hpp:137–190.
  • HybridElasticSymmetricMemory starts with each local rank creating its storage segment and exporting it as a POSIX file descriptor. The ranks swap (pid, fd) pairs through torch.distributed engram.py:73–77. Each rank then pulls the others' descriptors with pidfd_open and pidfd_getfd, imports them, and maps every shard after its own GPU segment symmetric.hpp:192–299.
  • GPUSymmetricMemory 用 ncclMemAlloc 分配 workspace 加 buffer symmetric.hpp:119–135。
  • ElasticSymmetricMemory 预留一段虚拟地址，把一块设备内存映射为对称部分，再映射在 GPU 上或其最近的 host NUMA 节点上创建的存储。存储在 host 上时，GPU 通过同一个指针获得对这些页的读写权限 symmetric.hpp:137–190。
  • HybridElasticSymmetricMemory 先让每个本地 rank 创建自己的存储段，并导出为 POSIX 文件描述符。各 rank 通过 torch.distributed 交换 (pid, fd) engram.py:73–77。随后每个 rank 用 pidfd_open 和 pidfd_getfd 取得其他进程的描述符，导入后把所有分片映射到自己 GPU 段之后 symmetric.hpp:192–299。

On CUDA 13 the allocation properties request fabric handles when the device supports them. If cuMemCreate refuses, they fall back to file descriptors. Device segments must support GPUDirect RDMA with VMM, which the constructor asserts symmetric.hpp:32–93. With host storage the allocator also sets NCCL_ELASTIC_BUFFER_REGISTER=1 symmetric.hpp:325–328. The Context registers the symmetric part as one window with NCCL_WIN_STRICT_ORDERING, and each storage shard as its own NCCL_WIN_GIN_ONLY window context.cpp:195–223. Chapter 04 shows how Engram reads from those shards.

在 CUDA 13 上，设备支持时分配属性会申请 fabric handle；若 cuMemCreate 拒绝，就退回到文件描述符。设备段必须支持基于 VMM 的 GPUDirect RDMA，构造函数会对此断言 symmetric.hpp:32–93。存储放在 host 上时，分配器还会设置 NCCL_ELASTIC_BUFFER_REGISTER=1 symmetric.hpp:325–328。Context 把对称部分注册为一个 NCCL_WIN_STRICT_ORDERING window，把每个存储分片各自注册为 NCCL_WIN_GIN_ONLY window context.cpp:195–223。第 04 章讲 Engram 如何从这些分片读取数据。

How many shards分片数量

The hybrid allocator maps gin_min_stride shards, the NCCL ginMinStride property, and the context registers the same number of storage windows context.cpp:185–193. I read that stride as the group of consecutive ranks on one node; the figure draws four.

hybrid 分配器映射 gin_min_stride 个分片，即 NCCL 的 ginMinStride 属性，context 也注册同样数量的存储 window context.cpp:185–193。我把这个 stride 理解为同一节点上连续的一组 rank；图中画了四个。

§5TMA and the mbarrier, step by step逐步看 TMA 与 mbarrier

Most data movement in DeepEP is one warp, one shared-memory slot and two TMA operations: a 1D bulk load into shared memory and a 1D bulk store out of it. The load reports completion to an mbarrier. The store joins a bulk group, and the warp waits on that group before it reuses the slot ptx.cuh:49–160. Step through one token of direct dispatch, and switch the proxy fence off to see what it protects.

DeepEP 的大部分数据搬运都是一个 warp、一个共享内存槽和两次 TMA 操作：一次 1D bulk load 读入共享内存，一次 1D bulk store 从中写出。load 向 mbarrier 报告完成；store 加入一个 bulk group，warp 在复用这个槽之前等待该 group ptx.cuh:49–160。下面逐步走完 direct dispatch 中的一个 token，也可以关掉 proxy fence，看看它保护的是什么。

Step-through逐步执行One token, one slot一个 token，一个槽

    Three details are easy to miss. The mbarrier starts with an arrival count of 1 and a fence.mbarrier_init ptx.cuh:49–53. The TMA load is issued before arrive.expect_tx, so bytes may land before the expectation is raised. The wait loop spins on try_wait.parity with a suspend-time hint of 0x989680, and the caller keeps the parity bit in a register and flips it after each wait ptx.cuh:70–83.

    有三个细节容易忽略。mbarrier 以到达数 1 初始化，并跟一条 fence.mbarrier_init ptx.cuh:49–53。TMA load 在 arrive.expect_tx 之前发出，因此字节可能在期望值提高之前就已落地。等待循环在 try_wait.parity 上自旋，挂起时间提示为 0x989680；调用方把奇偶位保存在寄存器里，每次等待后翻转 ptx.cuh:70–83。

    FP8 scale factors can't use a 1D TMA because their source is strided. Instead each lane issues a 4-byte cp.async, and cp.async.mbarrier.arrive hooks those copies into the same mbarrier. That arrive has to come before the expect_tx arrive dispatch.cuh:294–311 350–356.

    FP8 缩放因子的源地址是跨步的，不能用 1D TMA。取而代之，每个 lane 发一次 4 字节的 cp.async，再由 cp.async.mbarrier.arrive 把这些拷贝挂到同一个 mbarrier 上。这个 arrive 必须在 expect_tx 那次 arrive 之前 dispatch.cuh:294–311 350–356。

    From the PTX ISA, not from DeepEP来自 PTX ISA，而非 DeepEP

    Two facts in this section come from the PTX specification rather than the source. The mbarrier's transaction count is signed, which is why bytes may complete before expect_tx raises the expectation. And shared-memory writes made by ordinary stores need a proxy fence before an async-proxy operation such as a TMA store reads them. The "stale metadata" outcome in the widget is that rule applied; I haven't reproduced it on hardware.

    本节有两点来自 PTX 规范而非源码。mbarrier 的事务计数是有符号的，所以字节可以在 expect_tx 提高期望值之前完成。普通 store 对共享内存的写入，在被 TMA store 这类 async proxy 操作读取之前，需要一次 proxy fence。组件中“元数据可能过期”的结果就是这条规则的推论，我没有在硬件上复现过。

    §7Host plumbingHost 侧的管道

    • One communication stream. Every buffer shares a single high-priority stream taken from PyTorch's pool stream.hpp:9–12.
    • Events that hold tensors. EventHandle records on a stream and can keep tensors alive in place of record_stream event.hpp:13–30.
    • Barrier from Python. buffer.barrier() can synchronize the device or chain the communication stream before and after the barrier kernel comm/barrier.hpp:9–42.
    • Copy engines. copy_engine_push issues a cudaMemcpyBatchAsync that prefers overlapping with compute.
