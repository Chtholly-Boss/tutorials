Load Balancing, Engram and PP负载均衡、Engram 与 PP

Three smaller features built from the same parts as EP: copying redundant experts' weights and gradients across NVLink, fetching table rows from remote GPU or CPU memory with RDMA reads, and passing activations between pipeline stages through a fixed number of slots.

三个用 EP 同一套部件搭出的较小功能：经 NVLink 拷贝冗余专家的权重与梯度，用 RDMA 读从远端 GPU 或 CPU 内存取表行，以及通过固定数量的槽位在流水线 stage 之间传递激活。

§1Redundant experts: pushing weights, pulling gradients冗余专家：推送权重，拉回梯度

A hot expert slows down every step. Dynamic replication spreads its tokens over extra copies on other GPUs, which means two transfers per step: the copies need the expert's weights before the expert GEMM, and the original needs the copies' gradients after backward. DeepEP provides those two transfers as EPBuffer.lb_prefetch_weights and EPBuffer.lb_reduce_grads. The caller still plans the replicas, reroutes the tokens and runs the GEMMs README:326–376.

一个过热的专家会拖慢每一步。动态复制把它的 token 分摊到其他 GPU 上的额外副本，这意味着每步有两次传输：副本在专家 GEMM 之前需要专家权重，原专家在反向之后需要副本的梯度。DeepEP 把这两次传输提供为 EPBuffer.lb_prefetch_weights 和 EPBuffer.lb_reduce_grads；副本规划、token 重路由和 GEMM 仍由调用者负责 README:326–376。

Where the replicas live副本放在哪里

The constructor argument lb_allocation_plan_or_num_bytes reserves an LB region directly after the EP data buffer, inside the same symmetric window, and exposes it as lb_storage ep.hpp:82–86. When you pass a BufferAllocator plan, its placeholder tensors become views into that region ep.py:348–350. Redundant tensors have to live there, because peers write and read them through NVLink pointers. The original expert weights and gradients can be ordinary CUDA tensors, since only their owner touches them.

构造参数 lb_allocation_plan_or_num_bytes 在 EP 数据区之后、同一个对称窗口内预留一块 LB 区域，并以 lb_storage 暴露出来 ep.hpp:82–86。传入 BufferAllocator 计划时，其中的占位张量会变成指向这块区域的视图 ep.py:348–350。冗余张量必须放在这里，因为 peer 要通过 NVLink 指针读写它们；原始的专家权重和梯度可以是普通 CUDA 张量，因为只有持有者自己访问。

The plan is a redundancy_mapping of shape [num_nvlink_ranks, num_redundant_experts], identical on every rank of the NVLink domain. Entry [r, c] names the expert that goes into slot c on rank r, as owner × num_local_experts + local_idx, or −1 for an empty slot. A rank's own experts may not appear in its slots README:337–339, and the test's mapping generator asserts exactly that test_prefetch_weights.py:62–96. Both calls are collective over the domain: every rank calls them, even one with nothing to send.

规划用 redundancy_mapping 表示，形状为 [num_nvlink_ranks, num_redundant_experts]，在 NVLink 域内每个 rank 上内容相同。条目 [r, c] 指定放进 rank r 第 c 个槽位的专家，编号为 owner × num_local_experts + local_idx，空槽为 −1。rank 自己的专家不能出现在自己的槽位里 README:337–339，测试中的映射生成器正是这样断言的 test_prefetch_weights.py:62–96。两个调用在整个域内都是集合操作：每个 rank 都要调用，即使它没有东西要发。

The owner does all the work所有工作都由持有者完成

Each rank scans the shared mapping and keeps the entries whose expert it owns. A cub::BlockScan compacts them, in mapping order, into a task list in shared memory: local expert, destination rank, destination slot eplb.cuh:29–64. Warps then claim chunks from one counter in the workspace. A claim index maps to a weight, then a chunk, then a task, with the task as chunk_idx % num_tasks, so consecutive claims go to different destinations:

每个 rank 扫描共享的映射，只保留自己持有的专家所在的条目。cub::BlockScan 按映射顺序把它们压缩成共享内存里的任务列表：本地专家、目标 rank、目标槽位 eplb.cuh:29–64。随后各 warp 从工作区中的同一个计数器领取分块。领取序号依次映射到权重、分块、任务，其中任务为 chunk_idx % num_tasks，因此相邻的领取落到不同的目标上：

For prefetch, one elected lane per warp TMA-loads a 12 KiB chunk of its own expert into shared memory and TMA-stores it through the peer's NVLink pointer: a push prefetch_weights.cuh:70–87. Up to 16 tensors can travel in one call, so weights and their FP8 scales move together without any dtype conversion eplb.cuh:69–87. Gradient reduction runs the same iterator the other way. The owner TMA-loads a 24 KiB chunk of the peer's FP32 gradient over NVLink, which is a pull, and adds it into its own expert_grads with a bulk reduce-add, so the SMs never do the arithmetic:

预取时，每个 warp 选出一个 lane，用 TMA 把自己专家的一个 12 KiB 分块读进共享内存，再经 peer 的 NVLink 指针用 TMA 写出去，这是“推” prefetch_weights.cuh:70–87。一次调用最多可传 16 个张量，权重和它们的 FP8 scale 可以一起搬运，不做任何类型转换 eplb.cuh:69–87。梯度规约反向使用同一个迭代器：持有者经 NVLink 用 TMA 读入 peer 的 FP32 梯度的一个 24 KiB 分块（这是“拉”），再用 bulk reduce-add 累加进自己的 expert_grads，SM 本身不做加法：

An NVLink barrier comes before the transfers and another after them, so the redundant tensors are visible to their users by the time the event completes prefetch_weights.cuh:65–92. Try the mapping below. Click cells to change it, then run prefetch and reduce and watch how the task counts spread across owners.

传输前后各有一次 NVLink barrier，保证事件完成时冗余张量对使用者可见 prefetch_weights.cuh:65–92。在下面的映射上试试：点击格子修改，再运行预取和规约，看任务数如何分布在各个持有者上。

Numbers and details worth knowing值得知道的数字与细节
  • Warps per block come from shared memory minus the 32 KiB task table, divided by chunk + mbarrier prefetch_weights.hpp:29–37. With H100/H200's 232,448 B that is 16 warps for prefetch and 8 for reduce, if the device-side mbarrier is 8 bytes. I computed this; I didn't observe it.
  • lb_get_theoretical_num_sms budgets NVLink bandwidth against per-SM HBM write bandwidth: ⌈430.3 / 45⌉ rounded to even gives 10 SMs with the chapter 01 defaults ep.py:845–852.
  • The README asks for per-expert byte counts that are multiples of 32. The host check for prefetch enforces 16 ep.hpp:1014–1018, while the gradient path enforces 32 reduce_grads.hpp:40–42. Stick to 32.
  • Reduction adds and never clears. Seed expert_grads with the local gradient and zero the redundant gradients before the next accumulation README:376.
  • 每个 block 的 warp 数等于共享内存减去 32 KiB 任务表，再除以（分块 + mbarrier）prefetch_weights.hpp:29–37。按 H100/H200 的 232,448 B、设备端 mbarrier 为 8 字节计，预取为 16 个 warp，规约为 8 个。这是推算，未经实测。
  • lb_get_theoretical_num_sms 用 NVLink 带宽对照每 SM 的 HBM 写带宽：按第 01 章的默认值，⌈430.3 / 45⌉ 取偶数得 10 个 SM ep.py:845–852。
  • README 要求每个专家的字节数是 32 的倍数。预取的 host 检查只要求 16 ep.hpp:1014–1018，梯度路径则要求 32 reduce_grads.hpp:40–42。统一按 32 来。
  • 规约只加不清。先用本地梯度初始化 expert_grads，下一次累加前把冗余梯度清零 README:376。

§2Engram: table rows fetched by RDMA readsEngram：用 RDMA 读取表行

Engram stores large per-layer tables whose rows are hidden elements wide, sharded across all ranks and kept in GPU memory or pinned host memory. fetch(indices) takes an int32 tensor of shape [num_layers, num_tokens, num_entries_per_token] and gathers those rows into this GPU with RDMA gets README:378–382. Rank r stores num_entries_per_layer[l] rows of layer l, so a global row index is the owner's rank times that count plus the local row. That follows from the ranges the fetch kernel assigns to each peer engram_fetch.cuh:105–107.

Engram 保存很大的逐层表，每行宽 hidden 个元素，分片存放在所有 rank 上，位于 GPU 显存或 pinned host 内存中。fetch(indices) 接收形状为 [num_layers, num_tokens, num_entries_per_token] 的 int32 张量，用 RDMA get 把这些行收集到本 GPU README:378–382。rank r 存放第 l 层的 num_entries_per_layer[l] 行，所以全局行号等于持有者 rank 乘以该行数再加本地行号，这一点可从 fetch kernel 分给每个 peer 的区间推出 engram_fetch.cuh:105–107。

Setting it up初始化

  • Sizes. get_storage_size_hint returns the GPU bytes (a receive area of layers × max_tokens × entries × row bytes, plus this rank's shard of the FP8 scale table) and the per-rank storage bytes engram.hpp:251–271.
  • Storage shared inside a node. In hybrid mode each process creates its storage segment, exports it as a file descriptor, and shares (pid, fd) with all_gather_object engram.py:73–77. The hybrid elastic allocator then maps every local rank's shard into each process's address space symmetric.hpp:192–300 (see chapter 02), and the context registers one GIN-only window per shard context.cpp:207–223. A remote reader can therefore reach every shard on a node through a single RDMA peer.
  • Its own communicator. The buffer always creates a fresh NCCL communicator with the GDAKI Gin type forced through the environment, and raises NCCL_WIN_STRIDE when the registered bytes would exceed GPU memory engram.py:61–94.
  • Filling it. write copies each layer's local table into the shard back to back, and splits the FP8 scale table across the NVLink ranks' GPU buffers engram.hpp:109–155.
  • 大小。get_storage_size_hint 返回 GPU 字节数（层数 × max_tokens × 条目数 × 行字节 的接收区，加上本 rank 的 FP8 scale 表分片）和每个 rank 的存储字节数 engram.hpp:251–271。
  • 节点内共享存储。hybrid 模式下，每个进程创建自己的存储段，导出为文件描述符，并用 all_gather_object 共享 (pid, fd) engram.py:73–77。hybrid elastic 分配器随后把本节点每个 rank 的分片都映射进每个进程的地址空间 symmetric.hpp:192–300（见第 02 章），context 再为每个分片注册一个仅供 GIN 使用的窗口 context.cpp:207–223。因此远端读者通过一个 RDMA peer 就能访问一个节点上的所有分片。
  • 独立的 communicator。该 buffer 总是新建一个 NCCL communicator，通过环境变量强制使用 GDAKI 类型的 Gin；当注册字节数会超过显存时，还会调大 NCCL_WIN_STRIDE engram.py:61–94。
  • 写入数据。write 把每层的本地表依次拷进分片，并把 FP8 scale 表切分到各 NVLink rank 的 GPU buffer 中 engram.hpp:109–155。

One launch, one hook per layer一次启动，每层一个 hook

fetch launches one kernel for all layers, on every SM, with 32 warps per block: 28 issue warps and 4 scale-factor warps when the table is FP8 engram.hpp:36–45. Each issue warp owns one (RDMA peer, GIN context) pair and a stride of 32-token tiles engram_fetch.cuh:13–39. Layer by layer, its lanes read indices, use a ballot to keep those behind their peer, and append them to a 64-entry circular queue in shared memory. Once more than 32 rows are queued, it posts 32 of them as gets, one per lane. The doorbell rings only once per flush_depth / active warps requests, and the other posts are marked to aggregate engram_fetch.cuh:109–171:

fetch 为所有层只启动一个 kernel，占满全部 SM，每个 block 32 个 warp：表为 FP8 时是 28 个 issue warp 加 4 个 scale warp engram.hpp:36–45。每个 issue warp 负责一个（RDMA peer, GIN context）组合，并按跨步分到若干 32-token 块 engram_fetch.cuh:13–39。它逐层处理：各 lane 读索引，用 ballot 留下属于自己 peer 的那些，追加到共享内存中一个 64 项的环形队列；队列中超过 32 行时，就把其中 32 行作为 get 发出，每个 lane 一个。doorbell 每 flush_depth / 活跃 warp 数 个请求才敲一次，其余请求标记为可合并 engram_fetch.cuh:109–171：

After each layer, the last warp of each peer context posts a flush and stores its request handle in last_gin_requests[layer][peer_context] engram_fetch.cuh:173–205. The Python call returns right away with one hook per layer. Calling hook l launches a tiny kernel that waits on layer l's handles, then returns that layer's view of the receive buffer engram.hpp:234–248 engram_fetch_wait.cuh:9–28. Layer 0's compute can start while layer 1's rows are still in flight, and the test waits on the layers in both orders test_engram.py:77–94. FP8 scale factors don't travel over RDMA: the scale warps read them from the NVLink-sharded table engram_fetch.cuh:208–254.

每层结束时，每个 peer context 的最后一个 warp 发出 flush，并把请求句柄存进 last_gin_requests[layer][peer_context] engram_fetch.cuh:173–205。Python 调用立即返回，每层一个 hook。调用第 l 个 hook 会启动一个很小的 kernel，等待第 l 层的句柄，再返回该层在接收 buffer 中的视图 engram.hpp:234–248 engram_fetch_wait.cuh:9–28。第 1 层的行还在路上时，第 0 层的计算就可以开始；测试也分别按正序和逆序等待各层 test_engram.py:77–94。FP8 scale 不走 RDMA，由 scale warp 从按 NVLink 分片的表中读取 engram_fetch.cuh:208–254。

Try calling hooks[1]() before hooks[0](): each hook waits only for its own layer. Latencies are random. The model uses one GIN context per peer, where the real kernel spreads many issue warps over num_qps contexts per peer.

试试先调用 hooks[1]() 再调用 hooks[0]()：每个 hook 只等待自己那一层。延迟是随机的。模型中每个 peer 只有一个 GIN context，真实 kernel 会把大量 issue warp 分摊到每个 peer 的 num_qps 个 context 上。

Sizing QPs with Little's law用 Little 定律确定 QP 数

An RDMA read occupies a slot until its response returns. get_theoretical_config assumes a 10 µs round trip and a NIC read rate of 45 Mpps, or 90 Mpps for MT4131 parts. It divides the reads in flight by 16 outstanding reads per QP and by the number of RDMA peers to get the QP count, then doubles the queue depth from 1024 until every request has a slot. When that would take more than 32,768 slots, it adds QPs instead and asks the constructor to restrict read atomics engram.hpp:273–299 engram.py:129–144.

一次 RDMA 读会占用一个槽位，直到响应返回。get_theoretical_config 假设往返 10 µs、网卡读速率为 45 Mpps（MT4131 为 90 Mpps），用在途读数量除以每 QP 16 个未完成读、再除以 RDMA peer 数，得到 QP 数；然后把队列深度从 1024 开始翻倍，直到每个请求都有槽位。如果需要超过 32,768 个槽位，就改为增加 QP，并让构造函数限制读原子操作 engram.hpp:273–299 engram.py:129–144。

Calculator计算器get_theoretical_config, portedget_theoretical_config 移植版

Defaults match tests/engram/test_engram.py. The number of RDMA peers is num_ranks / ginMinStride, a property NCCL reports for the communicator context.cpp:65–73, so pick the value your topology produces.

默认值与 tests/engram/test_engram.py 一致。RDMA peer 数等于 num_ranks / ginMinStride，这是 NCCL 为该 communicator 报告的属性 context.cpp:65–73，请按你的拓扑选择。

§3Pipeline send/recv: slots, arrivals and releases流水线 send/recv：槽位、到达与释放

PPBuffer moves one tensor at a time between neighbors in a ring of pipeline stages. send(x, dst) and recv(x, src) accept only the previous or next rank pp.hpp:79–111, and tensors must be contiguous with 32-byte-aligned pointers and sizes README:384–386. The group is RDMA-only: the context is built with hybrid mode off and at most two QPs are used pp.hpp:54–60 pp_send_recv.hpp:20–23.

PPBuffer 在由流水线 stage 组成的环上，一次在相邻 rank 之间搬运一个张量。send(x, dst) 和 recv(x, src) 只接受前一个或后一个 rank pp.hpp:79–111，张量必须连续，指针和大小都要 32 字节对齐 README:384–386。该组只走 RDMA：context 以关闭 hybrid 模式的方式创建，最多使用两个 QP pp.hpp:54–60 pp_send_recv.hpp:20–23。

The storage holds four regions of num_max_inflight_tensors slots each, every slot num_max_tensor_bytes rounded up to 64 bytes: a receive region and a send staging region for each ring direction pp.hpp:44–49. Four counters per direction sit in the workspace: send_count, recv_count, arrival (one per QP) and release pp/workspace.cuh:11–18. They live in GPU memory and only the kernels read them, so the host never synchronizes.

存储分四个区域，每个区域 num_max_inflight_tensors 个槽，每个槽 num_max_tensor_bytes（向上对齐到 64 字节）：每个环方向各一个接收区和一个发送暂存区 pp.hpp:44–49。每个方向在工作区里有四个计数器：send_count、recv_count、arrival（每 QP 一个）和 release pp/workspace.cuh:11–18。它们位于显存中，只由 kernel 读取，host 从不同步。

  1. send picks slot send_count % num_max_inflight_tensors and spins until release ≥ send_count − num_max_inflight_tensors + 1, meaning the receiver has emptied that slot. Every SM then TMA-copies its share of x into the staging slot with a two-stage pipeline pp_send_recv.cuh:27–102. After a grid sync, the data goes out as up to two Gin puts, each carrying a strong signal-add on the receiver's arrival counter pp_send_recv.cuh:132–170.
  2. recv waits until every QP's arrival reaches recv_count + 1, TMA-copies the slot into x, and after a grid sync signals release on the sender pp_send_recv.cuh:202–233.
  1. send 选择槽位 send_count % num_max_inflight_tensors，自旋等待 release ≥ send_count − num_max_inflight_tensors + 1，即接收方已经清空该槽位。随后每个 SM 用两级流水的 TMA 把自己那部分 x 拷进暂存槽 pp_send_recv.cuh:27–102。grid sync 之后，数据以最多两个 Gin put 发出，每个都在接收方的 arrival 计数器上附带一次 strong signal-add pp_send_recv.cuh:132–170。
  2. recv 等待每个 QP 的 arrival 达到 recv_count + 1，用 TMA 把槽位拷进 x，grid sync 之后在发送方上发出 release 信号 pp_send_recv.cuh:202–233。

The widget shows one direction of the ring. Shrink the slot count or slow the receiver, and the send kernel starts spinning on release. That backpressure is the only flow control, which is why the test keeps every send behind the receive issued num_max_inflight_tensors sends earlier test_pp.py:38–42. A program that issues more sends than that before the matching receives are queued spins until the GPU timeout.

下面的组件展示环的一个方向。减少槽位数或让接收方变慢，send kernel 就开始在 release 上自旋。这种反压是唯一的流量控制，所以测试总让每次 send 落在 num_max_inflight_tensors 次之前的那次 recv 之后 test_pp.py:38–42。如果程序在对应的 recv 入队之前发出更多 send，就会一直自旋到 GPU 超时。

Flow control流量控制stage s → stage s+1stage s → stage s+1

One tick is one send attempt and one receive check. A put's arrival signal and a receive's release signal each take one tick to land. The staging copy and the two-QP split are folded into a single move.

一个时钟包含一次 send 尝试和一次 recv 检查。put 附带的 arrival 信号与 recv 发出的 release 信号都需要一个时钟才能到达。暂存拷贝和两个 QP 的拆分合并成一次移动。
