Bucket CollectivesBucket 集合通信

How BucketBuffer runs batched all-gather, reduce-scatter and all-reduce for context and data parallelism: tensors planned into one registered storage, NVLink reductions done by multicast loads, all-gather moved by copy engines, and RDMA traffic paced by a credit ring.

BucketBuffer 如何为 context 并行与数据并行执行批量 all-gather、reduce-scatter 和 all-reduce：张量事先规划进同一块已注册的 storage，NVLink 上的规约由 multicast load 完成，all-gather 由 copy engine 搬运，RDMA 流量则由信用环控制节奏。

§1One storage, many groups一块 storage，多个组

A BucketBuffer owns one contiguous block of symmetric memory and registers it with one or more process groups, for example a CP group and a DP group over the same GPUs bucket.py:184–234. The C++ side builds one comm::Context per group. The first context allocates the memory, and every later one reuses it and only registers its own NCCL window, so all groups see the same bytes bucket.hpp:79–106. Each context asks NCCL for multicast (lsaMultimem) whenever its group has more than one NVLink rank, and gets one QP on a single node or 1024 / num_rdma_ranks QPs across nodes. An ncclAllGather of the context index checks that every rank registered its groups in the same order.

BucketBuffer 拥有一整块连续的对称内存，并把它注册到一个或多个进程组，例如同一批 GPU 上的一个 CP 组和一个 DP 组 bucket.py:184–234。C++ 侧为每个组建一个 comm::Context：第一个 context 分配内存，之后的 context 复用同一块内存，只注册自己的 NCCL window，所以所有组看到的是同一批字节 bucket.hpp:79–106。组内 NVLink rank 多于一个时，context 会向 NCCL 申请 multicast（lsaMultimem）；单节点时分配 1 个 QP，跨节点时分配 1024 / num_rdma_ranks 个。随后对 context 编号做一次 ncclAllGather，检查所有 rank 注册组的顺序一致。

In front of the storage sits a fixed workspace: signal arrays for up to 8 contexts, and a 256 MiB ChunkStorage that the RDMA paths use as a staging area workspace.cuh:14–26 chunk.cuh:12–17.

storage 前面是一块固定的工作区：最多 8 个 context 的信号数组，以及一块 256 MiB 的 ChunkStorage，RDMA 路径把它当作中转区 workspace.cuh:14–26 chunk.cuh:12–17。

Computed from the structs由结构体推算

One context's BucketSignals takes 794,688 bytes, most of it the all-gather tails (8 QPs × 8,192 chunks × 8 B). Eight of them plus the chunk storage come to 262.1 MiB, which rounds up to a 264 MiB workspace on every rank, whatever the storage size.

单个 context 的 BucketSignals 占 794,688 字节，大头是 all-gather 的 tail（8 个 QP × 8,192 个 chunk × 8 B）。8 份信号加上 chunk storage 共 262.1 MiB，向上对齐后每个 rank 都有 264 MiB 的工作区，与 storage 大小无关。

Planning tensors into the storage把张量规划进 storage

Collectives read and write the storage directly, so their tensors must live inside it. BufferAllocator lets you lay them out before the buffer exists. Each allocate() returns a meta tensor and reserves an offset rounded up to 2 MiB. When the buffer is built, materialize() swaps every placeholder for a CUDA view of the storage at its offset allocator.py:10–36. The same plan must be used on every rank.

集合通信直接读写 storage，所以相关张量必须位于其中。BufferAllocator 让你在 buffer 创建之前就排好布局：每次 allocate() 返回一个 meta 张量，并预留一个向上对齐到 2 MiB 的偏移。buffer 建好后，materialize() 把每个占位符替换成 storage 在该偏移处的 CUDA view allocator.py:10–36。所有 rank 必须使用同一份计划。

Plan规划BufferAllocator and sessionBufferAllocator 与 session

Starts with the two tensors from tests/buffer/test_allocation.py plus a 4 MiB one. At most four tensors, one color each. Hover a segment for its offset.

初始为 tests/buffer/test_allocation.py 里的两个张量，再加一个 4 MiB 张量。最多四个，每个一种颜色。鼠标悬停可看偏移。

Tiny tensors cost 2 MiB each in a plan, so plans suit a few large, long-lived gradient or activation buffers. For tensors you already have elsewhere, open with buffer.session():. Inside it, the three collective methods are temporarily replaced by wrappers that copy external inputs into storage (packed at 64-byte alignment from offset 0), run the original collective, and copy results back when you call wait() bucket.py:19–181. A session starts allocating from offset 0 again, so it overwrites whatever a plan put there. All calls in one session must use the same group, and sessions can't nest.

在计划中，小张量也要各占 2 MiB，所以计划适合少量大而长期存在的梯度或激活 buffer。对已经分配在别处的张量，可以用 with buffer.session():。在 session 内，三个集合通信方法被临时替换为包装函数：先把外部输入拷进 storage（从偏移 0 起按 64 字节对齐紧凑排布），再执行原来的集合通信，调用 wait() 时把结果拷回 bucket.py:19–181。session 从偏移 0 重新开始分配，会覆盖计划放在那里的数据。同一个 session 内所有调用必须使用同一个组，且 session 不能嵌套。

§2Three collectives, three topologies, nine paths三种集合通信、三种拓扑、九条路径

Every call is batched: up to 64 buckets, each described by an offset into the storage and a byte count, travel to the kernel as one __grid_constant__ list comm/bucket.cuh:10–39. Reduce-scatter and all-reduce take FP32 only. Reduce-scatter returns the rank's own shard as a view of the input; all-reduce overwrites its input; all-gather returns 1-D views bucket.hpp:113–324. Which kernel runs depends on the group's physical shape: one node (NVLink only), one GPU per node (RDMA only), or both.

每次调用都是批量的：最多 64 个 bucket，每个用 storage 内的偏移和字节数描述，作为一个 __grid_constant__ 列表传进 kernel comm/bucket.cuh:10–39。reduce-scatter 与 all-reduce 只支持 FP32。reduce-scatter 返回输入中本 rank 那一段分片的 view；all-reduce 原地覆盖输入；all-gather 返回一维 view bucket.hpp:113–324。具体运行哪个 kernel 取决于组的物理形态：单节点（只有 NVLink）、每节点一张 GPU（只有 RDMA），或两者兼有。

§3All-gatherAll-gather

All-gather is the one collective that reports num_sms = 0, and passing anything else is rejected bucket.hpp:245–257. On a single node that is literal. The host builds a list of copies, one per (peer, bucket), from the local shard to the same offset on the peer through its NVLink pointer, and brackets them with two rounds of stream memory operations:

all-gather 是唯一报告 num_sms = 0 的集合通信，传入其他值会被拒绝 bucket.hpp:245–257。在单节点上这完全属实：host 为每个（peer, bucket）构造一次拷贝，把本地分片经 peer 的 NVLink 指针拷到相同偏移处，前后各用一轮 stream 内存操作包起来：

copy_engine_sync is a batch of cuStreamBatchMemOp operations: write this call's sequence number into slot me of every peer's signal array, then wait until slot p of the local array holds at least that number for every peer driver.cpp:67–87. copy_engine_push is one cudaMemcpyBatchAsync with cudaMemcpyFlagPreferOverlapWithCompute driver.cpp:50–65. So the barrier, the data movement and the closing barrier all run on the copy engines and the stream front end. Because the sequence numbers are counted on the host, the call refuses to run under CUDA graph capture driver.cpp:14–19. This path also accepts a source outside the storage when you pass dsts, and adds a local copy for it all_gather.hpp:93–103.

copy_engine_sync 是一批 cuStreamBatchMemOp 操作：把本次调用的序号写进每个 peer 信号数组的第 me 格，再等待本地数组中每个 peer 对应的第 p 格都不小于该序号 driver.cpp:67–87。copy_engine_push 是一次带 cudaMemcpyFlagPreferOverlapWithCompute 的 cudaMemcpyBatchAsync driver.cpp:50–65。于是 barrier、数据搬运和收尾 barrier 全部由 copy engine 和 stream 前端完成。由于序号在 host 上计数，这个调用拒绝在 CUDA graph capture 下运行 driver.cpp:14–19。传入 dsts 时，这条路径也接受 storage 之外的输入，并为其多加一次本地拷贝 all_gather.hpp:93–103。

Across nodes SMs do take part. With one GPU per node, a cooperative kernel on every SM has its warps take destination ranks round-robin and put each bucket's shard straight to the same offset on the peer all_gather/rdma.cuh:38–48. It has no closing barrier. The barrier runs inside wait(), and for this path it flushes the QPs first bucket.hpp:313–323.

跨节点时 SM 就要参与了。每节点一张 GPU 时，一个在所有 SM 上运行的 cooperative kernel 让各 warp 轮流认领目标 rank，把每个 bucket 的分片直接 put 到对端相同偏移处 all_gather/rdma.cuh:38–48。它没有收尾 barrier：barrier 在 wait() 中执行，对这条路径会先 flush QP bucket.hpp:313–323。

Hybrid: RDMA chunks, copy-engine forwarding混合路径：RDMA 分块，copy engine 转发

The hybrid path splits the work between a small kernel and the copy engines. The kernel launches one CTA per RDMA rank. CTA d sends this rank's shard to its rail peer on node d, and its first 8 warps each drive one QP. Every chunk is split into 8 parts, one per QP, and each QP increments that chunk's tail on the receiver when its part lands. A QP with nothing to send still signals, so the counts stay uniform all_gather/hybrid.cuh:50–79:

混合路径把工作分给一个小 kernel 和 copy engine。kernel 为每个 RDMA rank 启动一个 CTA：CTA d 把本 rank 的分片发给节点 d 上的 rail peer，前 8 个 warp 各驱动一个 QP。每个 chunk 拆成 8 份，每个 QP 一份，各 QP 的数据落地时把接收方该 chunk 的 tail 加一。没有数据可发的 QP 也照样发信号，让计数保持一致 all_gather/hybrid.cuh:50–79：

Meanwhile the host has already queued the forwarding on the stream. First the local shard goes to the NVLink peers. Then, for each chunk, it queues a stream wait until all 8 tails reach num_rdma_ranks − 1, meaning every remote node's part has arrived, followed by a copy-engine push of those remote pieces to the NVLink peers all_gather.hpp:173–226. The chunk size is picked on the host by a small timeline model: pushing the local shard, the RDMA transfer, and forwarding every remote shard are estimated from the detected bandwidths, with 10 µs of copy-engine overhead per chunk wave. More chunks let forwarding start earlier but add waves. Chunks are at least 4 MiB (so each QP puts 512 KiB or more) and at most 64 per call all_gather.hpp:120–142.

与此同时，host 已在 stream 上排好转发：先把本地分片发给 NVLink peer；然后为每个 chunk 排一次 stream 等待，直到 8 个 tail 都达到 num_rdma_ranks − 1，即所有远端节点的那份都已到达，再接一次 copy engine 推送，把这些远端数据转发给 NVLink peer all_gather.hpp:173–226。chunk 大小由 host 上一个小的时间线模型决定：推送本地分片、RDMA 传输、转发所有远端分片的时间都按检测到的带宽估算，每一波 chunk 另计 10 µs 的 copy engine 开销。chunk 越多，转发开始得越早，但波数也越多。chunk 至少 4 MiB（每个 QP 至少 put 512 KiB），每次调用最多 64 个 all_gather.hpp:120–142。

After the kernel, wait() runs a barrier without a QP flush, because the tails already proved that every put landed bucket.hpp:315–321.

NVLink: one load per four floatsNVLink：每四个 float 一次 load

Inside one node the reduction is done by the NVLink switch. The storage is mapped at a multicast address, and multimem.ld_reduce.add.v4.f32 on that address returns the sum of those four floats over every GPU in the node ptx.cuh:162–174. Each rank walks only its own shard, so the kernel is one grid-stride loop between two barriers:

在单节点内，规约由 NVLink switch 完成。storage 被映射到一个 multicast 地址，对该地址执行 multimem.ld_reduce.add.v4.f32 就会返回节点内所有 GPU 上这四个 float 的和 ptx.cuh:162–174。每个 rank 只遍历自己的分片，所以 kernel 就是两个 barrier 之间的一个 grid-stride 循环：

Each thread keeps 8 loads in flight before storing, and scale is applied in the same pass. The closing barrier makes sure no rank starts overwriting inputs a peer is still reading nvlink.cuh:52–56.

每个线程在写出前保持 8 个 load 在途，scale 也在同一趟里乘上。收尾 barrier 保证没有 rank 在 peer 仍在读取时就改写输入 nvlink.cuh:52–56。

RDMA: a credit ring through the chunk storageRDMA：穿过 chunk storage 的信用环

Across nodes every rank must send R − 1 slices of its input and add R − 1 incoming slices into its own shard. The receiver can't add straight from the wire, so data lands first in the 256 MiB chunk storage. That space is split into one region per source rank, and each region into slots of 32 KiB, 2,048 of them with 4 ranks rdma.cuh:30–32. A ChunkIterator numbers the chunks of all buckets as one flat sequence, so chunk c uses slot c mod S in generation ⌊c / S⌋ chunk.cuh:54–102. Issue warps wait for a credit, then put the chunk with a signal-add on its tail:

跨节点时，每个 rank 要发出输入的 R − 1 段，并把收到的 R − 1 段累加进自己的分片。接收方无法直接对线上数据做加法，所以数据先落进 256 MiB 的 chunk storage。这块空间按来源 rank 分区，每区再切成 32 KiB 的槽，4 个 rank 时每区 2,048 个 rdma.cuh:30–32。ChunkIterator 把所有 bucket 的 chunk 编成一个平坦序列，于是 chunk c 使用第 c mod S 个槽、第 ⌊c / S⌋ 代 chunk.cuh:54–102。issue warp 先等信用，再 put 该 chunk，并对其 tail 做 signal-add：

Up to 8 lanes of one warp serve 8 destinations at once. On the receiving side, a reduce warp waits until the tail of each source's slot reaches generation + 1, adds that chunk into its shard in FP32 with the final scale, and writes the new generation back into the sender's head with put_value. It sends that credit only if a later chunk will reuse the slot rdma.cuh:130–226. Heads and tails are cleared at the start of every launch rdma.cuh:80–91. Shrink the ring below and slow the reducer to watch the sender stall:

一个 warp 最多用 8 个 lane 同时服务 8 个目标。在接收端，reduce warp 等每个来源对应槽的 tail 达到“代数 + 1”，把该 chunk 以 FP32 累加进自己的分片（最后一批再乘 scale），然后用 put_value 把新的代数写回发送方的 head。只有当之后还有 chunk 复用该槽时才发送这份信用 rdma.cuh:130–226。head 和 tail 在每次启动时清零 rdma.cuh:80–91。在下面把环调小、把规约调慢，就能看到发送方停下来等待：

BF16 on the wire, FP32 in memory线上 BF16，内存中 FP32

comm_precision="bf16" is accepted only for RDMA-only groups reduce_scatter.hpp:34–35. It adds cast warps that convert each FP32 chunk bound for a peer (128 KiB with up to 8 ranks, 64 KiB beyond) into BF16, written into the first half of the same chunk, so each put carries half the bytes. The rounding is stochastic but reproducible. Its random bits are a hash of the four FP32 bit patterns and the vector's position in the bucket, so the same input always rounds the same way rdma.cuh:348–441:

comm_precision="bf16" 只在纯 RDMA 组上被接受 reduce_scatter.hpp:34–35。它增加了 cast warp，把发往 peer 的每个 FP32 chunk（不超过 8 个 rank 时为 128 KiB，更多时为 64 KiB）转成 BF16，写进同一个 chunk 的前半段，于是每次 put 只携带一半字节。舍入是随机的但可复现：随机位来自对四个 FP32 位模式及该向量在 bucket 中位置的哈希，所以同样的输入总是以同样的方式舍入 rdma.cuh:348–441：

The receiver accumulates the incoming BF16 into FP32 partial sums in its own shard rdma.cuh:529–628, so only the transfer loses precision. The warp counts and batch sizes change with the rank count, and the kernel is compiled for the exact architecture instead of the family, since cvt.rs is architecture-specific reduce_scatter.hpp:83–117.

接收方把收到的 BF16 累加进自己分片中的 FP32 部分和 rdma.cuh:529–628，所以只有传输这一步损失精度。warp 数和批大小随 rank 数变化；由于 cvt.rs 与具体架构相关，kernel 按精确架构而非架构族编译 reduce_scatter.hpp:83–117。

Side effect on the input对输入的副作用

The cast warps write the packed BF16 back over the FP32 source of every peer-bound chunk (the store goes to the same chunk_ptr it read from, lines 377–434). After a BF16 reduce-scatter, only your own shard of the input holds meaningful data. The other shards hold packed bytes, so don't reuse them. This is my reading of the code; the README doesn't mention it.

cast warp 会把打包后的 BF16 写回每个发往 peer 的 chunk 的 FP32 源数据上（写入与读取的是同一个 chunk_ptr，见 377–434 行）。BF16 reduce-scatter 之后，输入中只有本 rank 的分片还是有意义的数据，其余分片存放的是打包字节，不要再使用。这是我读代码得出的结论，README 未提及。

Hybrid: reduce in the node, then one hop混合路径：先节点内规约，再走一跳

With several nodes of several GPUs, each block has 8 multimem warps, 2 issue warps and 2 reduce warps reduce_scatter.hpp:37–82. The multimem warps of local rank l sum, over the node, every shard that belongs to a rank with local index l. The node sum overwrites that part of the local input. Their paired issue warp waits on a named barrier, then puts each node-reduced chunk to the rail peer that owns it, with the same head/tail credit ring as above. The owner's own node contributes in place without a put hybrid.cuh:102–200. A single elected lane per reduce warp then waits for each node's chunk, TMA-loads it into 64 KiB of shared memory, and adds it into the output with a TMA reduce-add (cp.reduce.async.bulk.add.f32) hybrid.cuh:201–278. The network therefore carries one node-level sum per remote node, instead of every GPU's copy.

多节点、每节点多 GPU 时，每个 block 有 8 个 multimem warp、2 个 issue warp 和 2 个 reduce warp reduce_scatter.hpp:37–82。本地编号为 l 的 rank 上的 multimem warp，在节点内对所有归本地编号 l 的 rank 所有的分片求和，节点和覆盖本地输入中的那部分。配对的 issue warp 在 named barrier 上等待，然后通过与上面相同的 head/tail 信用环，把每个节点内规约后的 chunk put 给拥有它的 rail peer；所有者自己节点的那份原地参与，无需 put hybrid.cuh:102–200。随后每个 reduce warp 的一个被选出的 lane 等待各节点的 chunk，用 TMA 读进 64 KiB 共享内存，再用 TMA reduce-add（cp.reduce.async.bulk.add.f32）累加进输出 hybrid.cuh:201–278。因此网络上对每个远端节点只传一份节点级的和，而不是每张 GPU 各传一份。

all-reduce 原地进行，所以每条路径都是 reduce-scatter 与 all-gather 共用一趟。

  • NVLink. Each rank reduces its shard with multimem.ld_reduce and stores the result with multimem.st, which writes it to that shard on every GPU in the node at once. Both happen in one loop all_reduce/nvlink.cuh:35–51.
  • RDMA. Ownership goes chunk by chunk, not shard by shard: 64 KiB chunk c belongs to rank c mod R. Issue warps put every non-owned chunk into its owner's chunk storage through a credit ring. Reduce warps on the owner TMA reduce-add each peer's copy into the chunk in place, return the credit, and put the finished chunk to every peer all_reduce/rdma.cuh:89–251. With a non-unit scale, the last peer is added in registers so the multiply fuses into that final add.
  • Hybrid. Four warp roles. Multimem warps reduce chunk c inside the node on local rank c mod N. An issue warp sends the node sum to rail owner (c / N) mod R. The owner's reduce warp sums all nodes into a chunk-storage slot and puts the result back to every rail peer. Broadcast warps then TMA-load finished chunks through a double-buffered tile and multicast them to the NVLink peers with multimem.cp.async.bulk all_reduce/hybrid.cuh:11–332.
  • NVLink。每个 rank 用 multimem.ld_reduce 规约自己的分片，再用 multimem.st 写回，一次写到节点内所有 GPU 的该分片上。两者在同一个循环中完成 all_reduce/nvlink.cuh:35–51。
  • RDMA。归属按 chunk 而不是按分片划分：64 KiB 的 chunk c 归 rank c mod R。issue warp 经信用环把每个非自己所有的 chunk put 进所有者的 chunk storage；所有者的 reduce warp 用 TMA reduce-add 把各 peer 的副本原地累加进 chunk，归还信用，再把完成的 chunk put 给所有 peer all_reduce/rdma.cuh:89–251。scale 不为 1 时，最后一个 peer 在寄存器中累加，乘法与这最后一次加法融合。
  • 混合。四种 warp 角色：multimem warp 在本地编号为 c mod N 的 rank 上做 chunk c 的节点内规约；issue warp 把节点和发给 rail 所有者 (c / N) mod R；所有者的 reduce warp 把各节点的贡献累加进一个 chunk storage 槽，再把结果 put 回每个 rail peer；broadcast warp 通过双缓冲 tile 用 TMA 读入完成的 chunk，并用 multimem.cp.async.bulk multicast 给 NVLink peer all_reduce/hybrid.cuh:11–332。

The hybrid launcher trades warps for shared memory. It uses 8 multimem warps per issue warp up to 32 nodes and 4 beyond, and 256 KiB chunks up to 4 nodes and 64 KiB beyond. The broadcast tiles shrink when more broadcast warps are needed to cover every node all_reduce.hpp:27–47. In the explorer, pick all_reduce with hybrid 2 × 2 to watch the four stages in order.

混合路径的启动器在 warp 与共享内存之间做权衡：32 个节点以内每个 issue warp 配 8 个 multimem warp，超过则配 4 个；4 个节点以内 chunk 为 256 KiB，超过则为 64 KiB；需要更多 broadcast warp 来覆盖所有节点时，broadcast tile 随之缩小 all_reduce.hpp:27–47。在上面的浏览器中选择 all_reduce 与 hybrid 2 × 2，就能按顺序看到这四个阶段。

Building a BucketBuffer asserts that both NVLink and RDMA bandwidth can be detected, even for a group that uses only one of them bucket.py:215–217.
