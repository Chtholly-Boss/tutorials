§2A token slot, byte by byte一个 token 槽，逐字节拆解

Every buffer on the EP path stores tokens in one fixed-size format, TokenLayout token.cuh:10–41. The hidden vector comes first, then the FP8 scale factors if there are any, then the metadata the receiver needs: the top-k expert indices, the router weights, the token's global index (rank × num_max_tokens_per_rank + token), and one linked-list index per top-k lane that hybrid combine uses later. Each part starts on a 32-byte boundary for TMA, and the whole slot is rounded up to 64 bytes for RDMA.

EP 路径上的所有 buffer 都用同一种定长格式 TokenLayout 存放 token token.cuh:10–41。最前面是 hidden 向量，其后是 FP8 缩放因子（如果有），最后是接收方需要的元数据：top-k 专家索引、router 权重、token 的全局索引（rank × num_max_tokens_per_rank + token），以及每个 top-k lane 一个的链表索引，供 hybrid combine 之后使用。每一段都从 32 字节边界开始以满足 TMA，整个槽再向上对齐到 64 字节以满足 RDMA。

Because the metadata travels inside the slot, one TMA store or one RDMA put moves a complete token. The copy in shared memory carries one more field, the mbarrier the warp waits on for its TMA load. How many of those copies fit in 227 KiB decides how many dispatch warps each block gets.

由于元数据就放在槽里，一次 TMA store 或一次 RDMA put 就能搬运一个完整 token。共享内存里的副本多一个字段：warp 等待 TMA load 完成所用的 mbarrier。227 KiB 共享内存能放下多少个这样的副本，就决定了每个 block 有多少个 dispatch warp。

Warps per SM assume H100/H200's 232,448 B of opt-in shared memory and 256 experts for the notify counters. FP8 uses one 4-byte pack per 128 channels, which covers both FP32 scales per 128 channels and UE8M0 scales packed four to an int. Buffer sizing itself budgets for the worst case, ⌈hidden / 32⌉ packs ep.hpp:267–269.

每 SM 的 warp 数按 H100/H200 可申请的 232,448 B 共享内存、以及 notify 计数器按 256 个专家计算。FP8 按每 128 个通道一个 4 字节 pack 计算，这同时覆盖了每 128 通道一个 FP32 scale 和每 int 打包 4 个 UE8M0 scale 两种情况。buffer 大小本身按最坏情况 ⌈hidden / 32⌉ 个 pack 预留 ep.hpp:267–269。

§3Direct dispatch: notify warps and dispatch warpsDirect dispatch：notify warp 与 dispatch warp

With one scale-out rank, every block of dispatch_impl splits into 4 notify warps and as many dispatch warps as shared memory allows. Both groups start after the same barrier and run at the same time dispatch.cuh:73–78.

只有一个 scale-out rank 时，dispatch_impl 的每个 block 分成 4 个 notify warp 和共享内存所能容纳的若干 dispatch warp。两组 warp 在同一次 barrier 之后开始，同时运行 dispatch.cuh:73–78。

Counting before sending先计数，再发送

Each notify warp takes a strided share of the tokens and counts them into shared memory with atomicAdd_block: one counter per expert, and one per destination rank after deduplicating lanes with __match_any_sync. The per-SM counts are then merged in a single pass dispatch.cuh:91–146. Each SM adds (1 << 32) | count to a 64-bit word in the workspace, so the upper half counts arriving SMs while the lower half accumulates the sum. SM 0 waits until the upper half equals kNumSMs, and at that point it knows the lower half is final. No separate grid barrier is needed.

每个 notify warp 以跨步方式分到一部分 token，用 atomicAdd_block 在共享内存里计数：每个专家一个计数器；每个目标 rank 也有一个，计数前先用 __match_any_sync 对 lane 去重。随后一趟合并所有 SM 的计数 dispatch.cuh:91–146：每个 SM 向工作区中的一个 64 位字加上 (1 << 32) | count，高 32 位统计已到达的 SM 数，低 32 位累加总和。SM 0 等到高半部分等于 kNumSMs，此时就知道低半部分已是最终值，无需另做一次 grid barrier。

SM 0 then publishes the counts: one put_value per destination rank for its token count, and the per-expert counts either as individual NVLink stores or as one RDMA put per peer dispatch.cuh:150–177. Every count travels encoded as −v − 1, so a zeroed slot reads as "not arrived", while any real value, zero tokens included, decodes to something non-negative. Once all peers have written, SM 0 aligns each local expert's count, fills the host-visible copy the CPU is polling, and two warps compute the prefix sums: inclusive per source rank and exclusive per expert dispatch.cuh:183–256.

随后 SM 0 发布计数：每个目标 rank 一次 put_value 写 token 数；各专家的计数则要么逐个经 NVLink 写入，要么每个 peer 一次 RDMA put dispatch.cuh:150–177。所有计数都以 −v − 1 编码传递：清零后的槽读出来表示“尚未到达”，而任何真实值（包括 0 个 token）解码后都非负。所有 peer 写完之后，SM 0 把每个本地专家的计数按对齐值取整，填好 CPU 正在轮询的 host 可见副本，再由两个 warp 计算前缀和：按来源 rank 的包含式前缀和、按专家的排除式前缀和 dispatch.cuh:183–256。

Moving the data搬运数据

Dispatch warp w of SM s handles token s + w·kNumSMs, then every kNumDispatchWarps·kNumSMs tokens after that. For each token, one elected lane TMA-loads the hidden vector into the warp's shared-memory slot while the other lanes fill in the metadata, one lane per top-k selection. The slot on each destination comes from the sender's own counter:

SM s 上的第 w 个 dispatch warp 处理第 s + w·kNumSMs 个 token，之后每隔 kNumDispatchWarps·kNumSMs 个 token 处理一个。对每个 token，一个被选出的 lane 用 TMA 把 hidden 向量读进该 warp 的共享内存槽，其余 lane 同时填写元数据，每个 top-k 选择占一个 lane。每个目标上的槽位来自发送方自己的计数器：

The counter lives in the sender's own workspace, and the receive buffer on every rank is divided into one region per source rank. Each sender therefore writes only into its own region, and no remote atomics are needed. The slot indices are also saved in dst_buffer_slot_idx, which is how a cached dispatch later replays exactly the same placement. Over NVLink, the warp TMA-stores the slot straight into the peer's buffer through its LSA pointer. When a peer is only reachable over RDMA (direct mode across nodes), the slot is first stored to a local send buffer and then posted with gin.put dispatch.cuh:358–389. The kernel ends with a barrier and cudaTriggerProgrammaticLaunchCompletion(), which releases the copy epilogue that is already waiting.

计数器位于发送方自己的工作区，而每个 rank 上的接收 buffer 按来源 rank 划分成独立区域。因此每个发送方只写自己的区域，不需要远程原子操作。槽位索引同时保存在 dst_buffer_slot_idx 中，缓存模式的 dispatch 之后就是靠它重放完全相同的摆放。走 NVLink 时，warp 通过 LSA 指针用 TMA 把槽直接写进 peer 的 buffer；当 peer 只能经 RDMA 到达（跨节点的 direct 模式）时，先把槽写到本地发送 buffer，再用 gin.put 发出 dispatch.cuh:358–389。kernel 以一次 barrier 和 cudaTriggerProgrammaticLaunchCompletion() 结束，后者放行早已在等待的 copy epilogue。

§4The copy epilogue and the expanded layoutCopy epilogue 与 expanded 布局

The epilogue runs on every SM of the GPU, not only the communication SMs. It walks the received tokens in source-rank order, TMA-loads each slot into shared memory, and decides where each row goes dispatch_copy_epilogue.cuh:113–124:

epilogue 在整张 GPU 的所有 SM 上运行，而不只是通信所用的 SM。它按来源 rank 的顺序遍历收到的 token，用 TMA 把每个槽读进共享内存，然后决定每一行写到哪里 dispatch_copy_epilogue.cuh:113–124：

  • Without do_expand, received token i becomes row i of recv_x, and recv_topk_idx keeps a local expert index for each lane (−1 for experts elsewhere).
  • With do_expand, every lane whose expert is local claims a row with an atomicAdd on that expert's cursor. The cursors start at the exclusive, alignment-padded prefix sums, so each expert fills one contiguous block that a grouped GEMM can read directly.
  • In cached mode, the rows are read back from recv_src_metadata, so a replay puts every row exactly where it went before.
  • 不开 do_expand 时，收到的第 i 个 token 就是 recv_x 的第 i 行，recv_topk_idx 为每个 lane 保存本地专家索引（专家不在本地时为 −1）。
  • 开启 do_expand 时，每个专家在本地的 lane 通过该专家游标上的 atomicAdd 领取一行。游标从按对齐值补齐后的排除式前缀和开始，因此每个专家填满一个连续区块，grouped GEMM 可以直接读取。
  • 缓存模式下，行号从 recv_src_metadata 读回，重放时每一行都落在与上次完全相同的位置。

When the epilogue finishes, psum_num_recv_tokens_per_expert[i] holds the start of expert i's block plus its real token count. That explains the odd-looking definition in the EPHandle docstring: psum[i] − align(psum[i−1]) is expert i's real count, and align(psum[i]) is where expert i+1 begins ep.py:47–53. You can see those numbers under each recv_x in the simulator. With do_zero_padding, the gaps are filled by TMA stores from a zeroed shared-memory row, cleared with st.bulk on SM100 dispatch_copy_epilogue.cuh:232–325.

epilogue 结束时，psum_num_recv_tokens_per_expert[i] 等于专家 i 区块的起点加上它的真实 token 数。这就解释了 EPHandle 文档里那个看起来有些奇怪的定义：psum[i] − align(psum[i−1]) 是专家 i 的真实计数，align(psum[i]) 是专家 i+1 的起点 ep.py:47–53。模拟器中每个 recv_x 下方就显示了这些数。开启 do_zero_padding 时，空隙由共享内存中一行清零的数据经 TMA store 填满，SM100 上用 st.bulk 清零 dispatch_copy_epilogue.cuh:232–325。

Row order inside an expert depends on the atomics, so two runs can place the same rows in different orders. EPBuffer(deterministic=True) sorts afterwards by each source token's global index and patches the metadata to match ep.py:113–205. For backward passes and other replays, pass the forward handle. The notify warps are then dropped (kNumNotifyWarps = 0), the CPU sync is skipped, and slots and rows come from the saved indices dispatch.hpp:62–66.

专家内部的行序取决于原子操作，所以两次运行可能把同样的行排成不同顺序。EPBuffer(deterministic=True) 会在事后按来源 token 的全局索引排序，并相应修正元数据 ep.py:113–205。反向传播或其他重放场景应传入前向的 handle：此时去掉 notify warp（kNumNotifyWarps = 0），跳过 CPU 同步，槽位与行号都取自保存的索引 dispatch.hpp:62–66。

§5Hybrid dispatch: through the rail peerHybrid dispatch：经由 rail peer 转发

Across several nodes with hybrid mode on, a token takes two hops. It crosses the network once per destination node, always to the GPU with the same local index there (the rail peer). That GPU then forwards it over NVLink to the ranks that own its experts. hybrid_dispatch_impl gives each block three roles: notify warps, scale-out warps that feed the network, and forward warps that drain it hybrid_dispatch.cuh:106–656.

开启 hybrid 模式跨多个节点时，token 要走两跳：先对每个目标节点跨一次网络，到达该节点上本地编号相同的那张 GPU（rail peer）；再由这张 GPU 经 NVLink 转发给持有其专家的 rank。hybrid_dispatch_impl 给每个 block 分配三种角色：notify warp、向网络送数据的 scale-out warp，以及从网络取数据的 forward warp hybrid_dispatch.cuh:106–656。

A scale-out warp and its forward warp form a channel. The wrapper sizes channels from shared memory: it takes as many slots as fit for both the dispatch and the combine layouts, halves that for the two roles, and caps it at 8 per SM, or 4 when prefer_overlap_with_compute is false ep.hpp:435–456. For EP 8 × 2 with hidden 7168 that gives 7 channels per SM, so 16 SMs run 112 channels. Each channel then owns ⌈4096 / 112⌉ = 37 slots per source node on every receiver. Slots are never reused within one call, so a channel's region never wraps around.

一个 scale-out warp 与对应的 forward warp 组成一个 channel。wrapper 按共享内存决定 channel 数：取 dispatch 与 combine 两种布局都放得下的槽数，除以 2 分给两种角色，每 SM 最多 8 个；prefer_overlap_with_compute 为 false 时最多 4 个 ep.hpp:435–456。EP 8 × 2、hidden 7168 时每 SM 有 7 个 channel，16 个 SM 共 112 个 channel；每个 channel 在每个接收方上、针对每个来源节点拥有 ⌈4096 / 112⌉ = 37 个槽。一次调用内槽不会复用，所以 channel 的区域不会绕回。

Batching the tail signal批量发送 tail 信号

The receiver has to know how many slots of a channel are filled. The scale-out warp keeps that count in registers, one lane per destination node, and publishes it with a Gin signal-add only every 6 tokens (kScaleoutUpdateInterval). It signals once more at the end, with a finish flag packed into the same 64-bit word hybrid_dispatch.cuh:337–351:

接收方需要知道一个 channel 里已经填了多少个槽。scale-out warp 把这个计数放在寄存器里，每个目标节点占一个 lane，只在每 6 个 token（kScaleoutUpdateInterval）时用一次 Gin signal-add 发布出去；结束时再发一次，把 finish 标志打包进同一个 64 位字 hybrid_dispatch.cuh:337–351：

The widget below shows what the interval trades off. The forwarder may only read slots below the signaled tail, so the first tokens wait in the buffer until the first signal lands. A short interval cuts that wait but spends an RDMA atomic every few tokens; a long one saves atomics and delays the forwarder. Drag the interval and replay.

下面的组件展示这个间隔在权衡什么。forwarder 只能读取已发布 tail 以下的槽，所以最先到的 token 要在 buffer 里等第一个信号落地。间隔短，等待就短，但每隔几个 token 就要花一次 RDMA 原子操作；间隔长，省下原子操作，但 forwarder 开工更晚。拖动间隔再重放试试。

On the receiving side, each forward warp polls the signaled tails of every source node for its channel, picks the next node round-robin, and forwards at most 6 slots before moving on, so one busy node can't starve the others hybrid_dispatch.cuh:490–532. For each token it deduplicates the local destination ranks, takes a slot from its own per-destination counter, and TMA-stores the slot over NVLink. It also records what combine will need later: the token's source index, which scale-up ranks received it and at which slots (token_metadata_at_forward), and a per-channel linked list of positions hybrid_dispatch.cuh:559–627.

在接收端，每个 forward warp 轮询本 channel 上所有来源节点的已发布 tail，按轮转挑选下一个节点，每次最多转发 6 个槽就换下一个，避免某个繁忙节点饿死其他节点 hybrid_dispatch.cuh:490–532。对每个 token，它对本地目标 rank 去重，从自己的按目标计数器领取槽位，再经 NVLink 用 TMA 写入。它还记录 combine 之后要用的信息：token 的来源索引、哪些 scale-up rank 收到了它以及落在哪个槽（token_metadata_at_forward），以及每个 channel 的位置链表 hybrid_dispatch.cuh:559–627。

§6CombineCombine

Combine is dispatch played backwards, driven entirely by the handle. It needs no counting pass, because every rank already knows what it received and where each token came from.

combine 就是反向播放的 dispatch，完全由 handle 驱动。它不需要计数阶段，因为每个 rank 已经知道自己收到了什么、每个 token 来自哪里。

Direct combineDirect combine

Each warp takes a contiguous range of received tokens. For token i it reads recv_src_metadata, which gives the source token, the source rank, and the top-k lane that was the master for this rank. It then writes one row into the source rank's combine buffer combine.cuh:84–238. There are three cases:

每个 warp 负责一段连续的已接收 token。对第 i 个 token，它读取 recv_src_metadata，得到来源 token、来源 rank，以及本 rank 对应的 master top-k lane，然后往来源 rank 的 combine buffer 写一行 combine.cuh:84–238。分三种情况：

  • Non-expanded layout, or only one local expert row: TMA-load the row and store it.
  • Several local rows with allow_multiple_reduction: sum them in registers first, then store one row.
  • allow_multiple_reduction=False: send every expert row to its own top-k slot and leave all the summing to the source.
  • 非 expanded 布局，或本地只有一行专家输出：TMA 读入该行后直接写出。
  • 本地有多行且开启 allow_multiple_reduction：先在寄存器中求和，再写出一行。
  • allow_multiple_reduction=False：每个专家行发往各自的 top-k 槽位，求和全部留给来源 rank。

On the source, the combine buffer has one region per sender rank when the group is no larger than top-k, and one region per top-k slot otherwise (use_rank_layout) combine_utils.cuh:8–18. The simulator has 4 ranks and top-2, so it uses the top-k layout. combine_reduce_epilogue then sums, for each token, the regions its top-k selections point to (deduplicated per rank), adds up to two bias tensors, and writes BF16 combine_reduce_epilogue.cuh:62–142. The reduction keeps BF16 arithmetic when it can:

在来源 rank 上，当组的大小不超过 top-k 时，combine buffer 按发送 rank 分区；否则按 top-k 槽位分区（use_rank_layout）combine_utils.cuh:8–18。模拟器是 4 个 rank、top-2，所以用的是 top-k 布局。随后 combine_reduce_epilogue 对每个 token 把其 top-k 选择指向的区域（按 rank 去重）求和，加上至多两个 bias 张量，写出 BF16 combine_reduce_epilogue.cuh:62–142。规约能用 BF16 运算时就用 BF16：

With at most two sources and no bias, the sum stays in bfloat162 adds. Otherwise every source is accumulated in FP32 (a fused add.rn.f32.bf16 on SM100) and rounded once at the end combine_utils.cuh:67–169.

来源不超过两个且没有 bias 时，求和全程使用 bfloat162 加法；否则所有来源都在 FP32 中累加（SM100 上是融合的 add.rn.f32.bf16），最后只舍入一次 combine_utils.cuh:67–169。

Hybrid combineHybrid combine

Hybrid combine replays the dispatch route in reverse with two roles hybrid_combine.cuh:107–622. Scale-up warps walk the per-channel linked lists that dispatch left behind. For each token they send its row, locally reduced if needed, over NVLink to the forwarder it came through, and publish their progress with st.release.sys every 3 tokens. Forward warps replay token_metadata_at_forward in the original order. For each token they wait until every scale-up peer holding a piece of it has passed that point, reduce the pieces, and send one row back to the source node with an RDMA put. A final signal round per channel takes the place of a closing barrier.

hybrid combine 用两种角色反向重放 dispatch 的路径 hybrid_combine.cuh:107–622。scale-up warp 遍历 dispatch 留下的每 channel 链表，把每个 token 的行（必要时先本地规约）经 NVLink 送回当初转发它的 forwarder，并每 3 个 token 用 st.release.sys 发布一次进度。forward warp 按原来的顺序重放 token_metadata_at_forward：对每个 token，等所有持有其部分结果的 scale-up peer 都越过这个位置，把各部分规约，再用一次 RDMA put 把一行送回来源节点。每个 channel 最后一轮信号交换取代了收尾的 barrier。

Forward warps do the arithmetic while scale-up warps mostly copy. So when a block has exactly 4 or 8 channels and the layout isn't expanded, the kernel shifts registers between them with setmaxnreg: 40 for the scale-up warps and 216 for the forward warps hybrid_combine.cuh:100–112. The EP 8 × 2 example above has 7 channels per SM, so it keeps the default split.

forward warp 负责运算，scale-up warp 主要做拷贝。因此当 block 恰好有 4 或 8 个 channel 且不是 expanded 布局时，kernel 用 setmaxnreg 在两者之间重新分配寄存器：scale-up warp 40 个，forward warp 216 个 hybrid_combine.cuh:100–112。上面 EP 8 × 2 的例子每 SM 有 7 个 channel，所以保持默认分配。

§7Choosing SMs and QPsSM 与 QP 数量的选择

get_theoretical_num_sms models one dispatch–combine pair, measured per unit of data ep.py:430–541. Assuming uniform routing, it estimates how many ranks and nodes a token reaches: G·(1 − C(E − E/G, k) / C(E, k)) for G groups. From that it adds up the HBM bytes the SMs must read and write and the bytes each link must carry. The slower link sets the time, and the SM count is how many SMs it takes for their HBM traffic, at 180 GB/s read and 45 GB/s write per SM by default, to keep up. A 30% margin is added and the result rounded up to a multiple of 4. The estimator below ports it line by line, so you can see which term wins.

get_theoretical_num_sms 以单位数据量为尺度，对一对 dispatch–combine 建模 ep.py:430–541。它假设路由均匀，估算一个 token 平均触及多少个 rank 和节点：对 G 个组为 G·(1 − C(E − E/G, k) / C(E, k))。据此累加 SM 需要读写的 HBM 字节和每条链路需要承载的字节。较慢的链路决定耗时，SM 数就是让各 SM 的 HBM 流量（默认每 SM 读 180 GB/s、写 45 GB/s）跟得上所需的数量。再加 30% 余量，向上取到 4 的倍数。下面的估算器逐行移植了这段代码，可以看到是哪一项胜出。

Observation观察

With hybrid mode off across nodes, the RDMA traffic is computed but never chosen as the bound, because the check requires num_scaleout_ranks > 1 ep.py:511–515. The estimate then follows the NVLink term. That is my reading of the code; I haven't checked it against a run.

跨节点且关闭 hybrid 模式时，RDMA 流量虽然算了出来，却不会被选为瓶颈，因为判断条件要求 num_scaleout_ranks > 1 ep.py:511–515，于是估算沿用 NVLink 那一项。这是我读代码的结论，尚未用实际运行验证。

Defaults: 18 NVLink links × 26.562 GB/s × 0.9 as nvidia-smi reports on H100/H200 SXM, and a 400 Gb/s CX-7 port read from ibstat and divided by 8 envs.py:193–283. Hover a bar to see its formula.

默认值：H100/H200 SXM 上 nvidia-smi 报告的 18 条 NVLink × 26.562 GB/s × 0.9，以及从 ibstat 读出、再除以 8 的 400 Gb/s CX-7 端口 envs.py:193–283。鼠标悬停在条上可看公式。

With these bandwidths the model asks for 16 SMs on one node and 16 for EP 8 × 2, where RDMA is the bound, and 8 for EP 8 × 4. For comparison, the V2 README reported 12 SMs for EP 8 × 2 and 6 for EP 8 × 4 on SM90 with CX-7 README@main:45–48. The 30% margin and the rounding to 4 land the estimate one step above those hand-picked points.

按这些带宽，模型给出的结果是：单节点 16 个 SM；EP 8 × 2 为 16 个，瓶颈是 RDMA；EP 8 × 4 为 8 个。作为对照，V2 README 在 SM90 + CX-7 上报告的是 EP 8 × 2 用 12 个 SM、EP 8 × 4 用 6 个 README@main:45–48。30% 的余量加上取整到 4 的倍数，让估算值比这些手选的配置高出一档。

QPs follow from the SM count. In hybrid mode each channel slot gets its own (16 per SM) plus one for the notify warps; direct mode uses min(num_sms, 9). Both are capped at what the buffer allocated ep.py:543–560. How warps are mapped onto those QPs is covered in chapter 02.

QP 数由 SM 数决定。hybrid 模式下每个 channel 位各用一个（每 SM 16 个），再加一个给 notify warp；direct 模式用 min(num_sms, 9)。两者都不超过 buffer 分配的数量 ep.py:543–560。warp 如何映射到这些 QP 上，放在第 02 章讲。
