§1What DeepEP doesDeepEP 做什么

In a mixture-of-experts layer every token picks its top-k experts, and those experts live on different GPUs. DeepEP moves the tokens. Dispatch sends each token to every rank that hosts one of its chosen experts. Combine sends the expert outputs back and sums them into the token's original row. Both are all-to-all kernels that write over NVLink inside a node and over RDMA between nodes.

在 MoE 层中，每个 token 选出自己的 top-k 专家，而这些专家分布在不同的 GPU 上。DeepEP 负责搬运 token：dispatch 把每个 token 发往持有其所选专家的每个 rank；combine 把专家输出送回来，并累加到该 token 原来的那一行。两者都是 all-to-all kernel，节点内经 NVLink 写入，节点间经 RDMA 写入。

§2Four layers, two compile times四层结构，两个编译时机

  • Python (deep_ep/buffers/) fills in defaults, estimates SM and QP counts, and wraps results in EPHandle and EventOverlap objects.
  • Host C++ (csrc/) checks shapes and dtypes, allocates output tensors, orders the compute and communication streams, and calls a launch wrapper. All of it is registered as one pybind11 module python_api.cpp:19–51.
  • Launch wrappers (csrc/kernels/*/) size the warp counts to fit shared memory, then print a C++ template instantiation into a string and hand it to DeepJIT.
  • Device headers (deep_ep/include/deep_ep/) contain the kernels (impls/), byte layouts (layout/), NCCL Gin wrappers (comm/) and inline PTX (common/ptx.cuh).
  • Python 层（deep_ep/buffers/）补全默认参数，估算 SM 与 QP 数量，并把结果包装成 EPHandle 和 EventOverlap 对象。
  • Host C++ 层（csrc/）检查形状与 dtype，分配输出张量，安排计算 stream 与通信 stream 的先后，然后调用 launch wrapper。整层注册为一个 pybind11 模块 python_api.cpp:19–51。
  • Launch wrapper（csrc/kernels/*/）按共享内存容量决定 warp 数，再把 C++ 模板实例化写成字符串交给 DeepJIT。
  • 设备头文件（deep_ep/include/deep_ep/）包含 kernel（impls/）、字节布局（layout/）、NCCL Gin 封装（comm/）和内联 PTX（common/ptx.cuh）。

Importing the package does two things before any buffer exists __init__.py:19–56. It checks that the libnccl.so already mapped into the process is byte-for-byte the library DeepEP was built against, because PyTorch may have loaded its own copy. Then it hands DeepJIT the shipped include directory and the NCCL headers, plus the flags that pick the GDAKI Gin backend runtime/jit.hpp:17–47.

import 时，在任何 buffer 创建之前会做两件事 __init__.py:19–56：先检查进程里已映射的 libnccl.so 与 DeepEP 构建时链接的库是否逐字节相同，因为 PyTorch 可能加载了自己的那一份；再把随包分发的 include 目录、NCCL 头文件路径以及选择 GDAKI Gin 后端的编译宏交给 DeepJIT runtime/jit.hpp:17–47。

§3Rank domains: physical and logicalRank 的物理域与逻辑域

DeepEP doesn't read a hostfile. It asks NCCL. The size of the LSA team (load/store accessible: peers whose memory this GPU can address directly over NVLink) is the NVLink domain size, and the world size divided by it is the number of RDMA domains context.cpp:52–63.

DeepEP 不读 hostfile，而是直接问 NCCL。LSA team（load/store accessible，即本 GPU 能经 NVLink 直接寻址其显存的 peer）的大小就是 NVLink 域的大小，world size 除以它得到 RDMA 域的个数 context.cpp:52–63。

The kernels work with a second, logical pair of sizes: scale-out and scale-up. With allow_hybrid_mode=True (the default) they equal the physical pair. With it off, the whole group becomes one scale-up domain, and is_scaleup_nvlink turns false, so peers outside the node are reached with RDMA puts from the same kernel that stores to NVLink peers.

kernel 面对的是另一组逻辑尺寸：scale-out 与 scale-up。allow_hybrid_mode=True（默认）时，它们等于物理尺寸；关闭后，整个组被当作一个 scale-up 域，is_scaleup_nvlink 变为 false，于是向 NVLink peer 写数据的同一个 kernel 也直接用 RDMA put 访问节点外的 peer。

§4One symmetric window per buffer每个 buffer 一块对称窗口

Each buffer owns a comm::Context. Its constructor creates an NCCL device communicator with the GDAKI flavor of Gin (GPUDirect Async Kernel-Initiated: the GPU itself writes work requests to the NIC), one Gin context per allocated QP. It then allocates a single block of GPU memory and registers it as an NCCL window on every rank context.cpp:121–205.

每个 buffer 拥有一个 comm::Context。它的构造函数创建一个 NCCL device communicator，使用 GDAKI 形式的 Gin（GPUDirect Async Kernel-Initiated：由 GPU 自己向 NIC 写工作请求），每个分配的 QP 对应一个 Gin context；随后分配一整块显存，并在所有 rank 上把它注册为 NCCL window context.cpp:121–205。

Every rank registers the same layout, so a byte offset means the same thing everywhere. A kernel turns a local pointer into a peer's NVLink address with ncclGetLsaPointer(window, offset, peer) and stores to it directly, usually with a TMA bulk store. For a peer across the network it calls gin.put(team, peer, window, offset, …) with the same offset, and the NIC performs the write comm/handle.cuh:64–92 201–214.

所有 rank 注册的布局相同，所以同一个字节偏移在每个 rank 上含义一致。kernel 用 ncclGetLsaPointer(window, offset, peer) 把本地指针换算成 peer 的 NVLink 地址后直接写入，通常是一次 TMA bulk store；对网络另一端的 peer，则用同一个偏移调用 gin.put(team, peer, window, offset, …)，由 NIC 完成写入 comm/handle.cuh:64–92 201–214。

§5Kernels specialized per shape按形状特化的 kernel

Launch wrappers don't pass sizes as kernel arguments. They print them into a template instantiation and compile that string. Rank counts, hidden size, top-k, SM count, QP count and even the timeout become constexpr values inside the kernel, which lets the compiler unroll loops over top-k lanes and fold buffer offsets into constants.

launch wrapper 不把尺寸当作 kernel 参数传入，而是把它们写进一个模板实例化字符串再编译。rank 数、hidden 大小、top-k、SM 数、QP 数，甚至超时周期，都成为 kernel 内的 constexpr，编译器因此可以展开 top-k 相关的循环，并把 buffer 偏移折叠成常量。

DeepJIT keys its cache on the generated source, the contents of every header it includes, the compiler version and the effective compiler flags. A hit in the in-memory map returns an already loaded kernel. A hit on disk ($HOME/.dj by default, EP_JIT_CACHE_DIR to move it) skips nvcc. Only a miss on both runs the compiler deep_jit/runtime.hpp:56–97.

DeepJIT 的缓存键由生成的源码、所包含每个头文件的内容、编译器版本和实际生效的编译选项共同决定。内存缓存命中时直接返回已加载的 kernel；磁盘缓存（默认 $HOME/.dj，可用 EP_JIT_CACHE_DIR 修改）命中时跳过 nvcc；两者都未命中才会真正调用编译器 deep_jit/runtime.hpp:56–97。

§6Anatomy of one dispatch call一次 dispatch 调用的全过程

The CPU can't allocate recv_x until it knows how many tokens this rank will receive, and only the kernel can find that out. DeepEP resolves this inside one call: the kernel publishes the counts early, the CPU waits for them, and a second kernel does the final copy.

CPU 在知道本 rank 会收到多少 token 之前无法分配 recv_x，而这个数只有 kernel 才能算出来。DeepEP 在一次调用内解决这个矛盾：kernel 尽早公布计数，CPU 等待这些计数，再由第二个 kernel 完成最终拷贝。

  1. Stream prologue. The communication stream waits for the compute stream, or for previous_event if one is given. Passing previous_event requires allocate_on_comm_stream=True, so outputs aren't carved out of memory the overlapped compute kernels may still be using ep.hpp:122–150.
  2. Launch. The host zeroes its count slots, then launches dispatch_impl on the communication stream ep.hpp:549–582.
  3. Kernel. After a barrier, the notify warps count tokens per destination rank and per expert, exchange the counts with every peer, and write prefix sums plus the host-visible counts. Meanwhile each dispatch warp loads one token into shared memory with TMA and stores it into a receive slot on every destination rank. A final barrier makes the data visible, then cudaTriggerProgrammaticLaunchCompletion() releases the next kernel dispatch.cuh:393–399.
  4. CPU wait. With the GIL released, the CPU polls the mapped counts until every one is ready, or throws after num_cpu_timeout_secs ep.hpp:610–662. Counts travel encoded as −v − 1, so the zero left by the reset decodes to −1, meaning "not written yet" math.cuh:25–33.
  5. Copy epilogue. The host allocates recv_x at the exact size and launches dispatch_copy_epilogue with programmatic dependent launch. It waits in cudaGridDependencySynchronize(), then copies tokens from the receive buffer into recv_x, grouped by expert when do_expand=True dispatch_copy_epilogue.cuh:59–61.
  6. Stream epilogue. An event is recorded on the communication stream. The compute stream either waits for it right away or keeps running, with the tensors kept alive by record_stream or by the event itself ep.hpp:152–181.
  1. Stream prologue。通信 stream 等待计算 stream；若传入了 previous_event，则等待该事件。传入 previous_event 时必须同时设置 allocate_on_comm_stream=True，以免输出张量占用与之重叠的计算 kernel 仍在使用的显存 ep.hpp:122–150。
  2. 启动。host 先清零计数槽，再在通信 stream 上启动 dispatch_impl ep.hpp:549–582。
  3. Kernel。一次 barrier 之后，notify warp 统计发往每个 rank、每个专家的 token 数，与所有 peer 交换计数，并写出前缀和以及 host 可见的计数。与此同时，每个 dispatch warp 用 TMA 把一个 token 读进共享内存，再写到每个目标 rank 的接收槽。最后一次 barrier 保证数据可见，随后 cudaTriggerProgrammaticLaunchCompletion() 放行下一个 kernel dispatch.cuh:393–399。
  4. CPU 等待。在释放 GIL 的情况下，CPU 轮询映射的计数，直到全部就绪；超过 num_cpu_timeout_secs 则抛出异常 ep.hpp:610–662。计数以 −v − 1 编码传递，清零后的 0 解码为 −1，表示“尚未写入” math.cuh:25–33。
  5. Copy epilogue。host 按精确大小分配 recv_x，并以 programmatic dependent launch 启动 dispatch_copy_epilogue。它先在 cudaGridDependencySynchronize() 处等待，然后把 token 从接收 buffer 拷进 recv_x；do_expand=True 时按专家分组 dispatch_copy_epilogue.cuh:59–61。
  6. Stream epilogue。在通信 stream 上记录一个事件。计算 stream 要么立即等待它，要么继续执行，此时张量由 record_stream 或事件本身保持存活 ep.hpp:152–181。

Deferring the epilogue推迟 epilogue

With defer_epilogue=True, steps 4 and 5 don't happen inside dispatch(). The C++ side packages them as a closure and returns it next to the event:

设置 defer_epilogue=True 后，第 4、5 步不在 dispatch() 内执行。C++ 侧把它们封装成一个闭包，与事件一起返回：

Python registers the closure on the returned EventOverlap. Calling .wait() makes the current stream wait for the event and then runs the closure, so the CPU spin and the copy epilogue happen on whatever stream is current at that moment ep.py:749–757 event.py:38–58. Launch the communication early, queue independent work, and pay for the synchronization only where the expert GEMMs need recv_x.

Python 把这个闭包注册到返回的 EventOverlap 上。调用 .wait() 时，当前 stream 先等待事件，再执行闭包，因此 CPU 轮询和 copy epilogue 都发生在当时的当前 stream 上 ep.py:749–757 event.py:38–58。这样可以尽早发起通信、排入无关的计算，只在专家 GEMM 真正需要 recv_x 的地方才付出同步的代价。

With do_cpu_sync=False there is no CPU wait at all. The host allocates for the worst case, num_max_tokens_per_rank × num_ranks rows, and the epilogue kernel reads the real count from GPU memory ep.hpp:663–669. That is the decoding configuration, where the next kernel reads valid ranges from psum_num_recv_tokens_per_expert.

若 do_cpu_sync=False，则完全没有 CPU 等待。host 按最坏情况分配 num_max_tokens_per_rank × num_ranks 行，epilogue kernel 从显存中读取真实计数 ep.hpp:663–669。这是 decoding 场景的用法，后续 kernel 通过 psum_num_recv_tokens_per_expert 确定有效区间。
