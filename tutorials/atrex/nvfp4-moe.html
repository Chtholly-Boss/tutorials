ATREX 如何用 4 位浮点跑完一整层 MoE：kernel 实际采用的块格式与舍入、按专家分组 token 的排序、融合了 SwiGLU 的块缩放 mma.sync GEMM、把 top-k 行加回去的四种方式，以及按 batch 大小挑选 kernel 链的调度器。

§1One layer, end to end一层的完整流程

The public entry point is atrex.nvfp4_fused_moe. It looks at the first tensor's device, maps (nvidia, sm120) to the implementation module, and raises for anything else api/nvfp4_fused_moe.py:11–47. The operator starts after the router: the caller passes topk_ids and topk_weights, and the operator computes both expert projections, the activation and the weighted sum. It writes BF16 into a caller-owned output and returns nothing nvfp4_fused_moe_sm120.py:257–371.

公共入口是 atrex.nvfp4_fused_moe。它查看第一个张量所在的设备，把 (nvidia, sm120) 映射到实现模块，其他情况直接报错 api/nvfp4_fused_moe.py:11–47。这个算子从 router 之后开始：调用方传入 topk_ids 和 topk_weights，算子负责两次专家投影、激活和加权求和，把 BF16 结果写进调用方提供的 output，不返回任何值 nvfp4_fused_moe_sm120.py:257–371。

§2NVFP4 as the kernels round itkernel 眼中的 NVFP4

An NVFP4 tensor stores every value as a 4-bit E2M1 number (±0, 0.5, 1, 1.5, 2, 3, 4, 6), groups of 16 consecutive values along K share one FP8 E4M3 scale, and one FP32 global scale per expert stretches the whole tensor into the range E4M3 can express moe_common.cuh:110–124. Activations are quantized on the fly with the same four steps everywhere: take the block's largest magnitude, form global_scale · amax / 6, round it to E4M3, then divide the values by the rounded scale and round each to E2M1.

NVFP4 张量把每个值存成 4 位 E2M1 数（±0、0.5、1、1.5、2、3、4、6），沿 K 方向每 16 个连续值共享一个 FP8 E4M3 缩放，每个专家再有一个 FP32 global scale 把整个张量拉进 E4M3 能表示的范围 moe_common.cuh:110–124。激活在运行时量化，所有地方都用同样的四步：取块内最大绝对值，算出 global_scale · amax / 6，舍入成 E4M3，再用舍入后的缩放去除各个值，并把每个值舍入为 E2M1。

The last line wraps cvt.rn.satfinite.e2m1x2.f32: round to nearest even, clamp to ±6, two values per byte with the even-indexed value in the low nibble quantization_utils.cuh:51–73. Reading the value back is e2m1 · SF / global_scale, and the GEMMs fold the two global scales into a single alpha = 1 / (a_gs · w_gs) per expert nvfp4_fused_moe_sm120.py:408–417. Try it on one block:

最后一行封装的是 cvt.rn.satfinite.e2m1x2.f32：就近偶数舍入，钳到 ±6，每字节两个值，偶数下标的值放在低 4 位 quantization_utils.cuh:51–73。还原值为 e2m1 · SF / global_scale，GEMM 把两个 global scale 合并成每专家一个 alpha = 1 / (a_gs · w_gs) nvfp4_fused_moe_sm120.py:408–417。下面用一个块试试：

Quantizer量化器One NVFP4 block, 16 values一个 NVFP4 块，16 个值

The block scale rounded to 0 in E4M3. The scaled values saturate to ±6, but they all dequantize to 0, so this block is lost. A larger global scale fixes it.块缩放在 E4M3 中舍入成了 0。放大后的值饱和到 ±6，但反量化后全部为 0，这个块的信息丢失了。增大 global scale 即可解决。

Storage: 16 values take 8 bytes of codes plus 1 byte of scale, 4.5 bits per value before the per-expert FP32 global scale. The widget rounds exactly like the device code except that it uses exact division where the kernel uses rcp.approx.ftz, so a value sitting exactly on a rounding boundary can land one code away.

存储：16 个值占 8 字节编码加 1 字节缩放，不计每专家的 FP32 global scale 时为每值 4.5 位。组件的舍入与设备代码一致，只是 kernel 用 rcp.approx.ftz 的地方这里用精确除法，所以恰好落在舍入边界上的值可能相差一个编码。

Two things stand out when you play with it. With global_scale = 1, small activations produce block scales deep in E4M3's subnormal range, and the randn × 1e-4 preset rounds the scale to zero. The test uses 1 for activations and 448 · 6 / amax for weights, which puts the largest block scale of each expert at E4M3's maximum test:286–301. And a single outlier in a block pushes every other value toward 0, because 16 values share one scale.

动手试会发现两点。global_scale = 1 时，小激活值产生的块缩放落在 E4M3 很深的次正规区，randn × 1e-4 预设甚至把缩放舍入成 0。测试对激活用 1，对权重用 448 · 6 / amax，让每个专家最大的块缩放正好是 E4M3 的最大值 test:286–301。另外，块内只要有一个离群值，其余值都会被压向 0，因为 16 个值共享一个缩放。

Where the scales live缩放存放在哪里

Scale factors are not stored row by row. Every writer uses the 128×4 swizzle: 128 rows × 4 scale vectors form one 512-byte tile, and inside it byte (r mod 32)·16 + ⌊(r mod 128)/32⌋·4 + (kv mod 4) belongs to row r, vector kv quantization_utils.cuh:241–261. The payoff is on the reading side: a GEMM thread fetches the four scales of its row for one 64-wide K atom with a single 32-bit shared-memory load, which is exactly the operand the block-scaled MMA takes gemm_sm120_v20.cuh:335–341 436–437.

缩放因子不是逐行存放的。所有写入方都用 128×4 swizzle：128 行 × 4 个缩放向量组成一个 512 字节的 tile，tile 内第 (r mod 32)·16 + ⌊(r mod 128)/32⌋·4 + (kv mod 4) 个字节属于第 r 行、第 kv 个向量 quantization_utils.cuh:241–261。好处在读取端：GEMM 线程用一次 32 位共享内存读取，就能拿到本行在一个 64 宽 K atom 上的四个缩放，这正是块缩放 MMA 需要的操作数 gemm_sm120_v20.cuh:335–341 436–437。

§3From topk_ids to grouped rows从 topk_ids 到分组行

A grouped GEMM needs each expert's rows next to each other. routing_sort builds that order in three kernels. The first gives every (expert, token block) pair a CTA that marks which of its tokens chose the expert and prefix-sums the marks with cub::BlockScan. The second turns the per-block counts into global offsets, and the third scatters rows into place routing_sort.cu:181–204 527–622. Rows inside an expert therefore keep token order. Each row carries its unpermuted id u = k·M + t, the rank of the slot times M plus the token, and a −1 slot never matches any expert, so it simply disappears.

grouped GEMM 需要每个专家的行彼此相邻。routing_sort 用三个 kernel 建立这个顺序：第一个为每个（专家, token 块）分配一个 CTA，标出块内哪些 token 选了该专家，并用 cub::BlockScan 对标记做前缀和；第二个把各块计数变成全局偏移；第三个把行散射到位 routing_sort.cu:181–204 527–622。因此同一专家内的行保持 token 顺序。每行带着未置换编号 u = k·M + t，即槽位序号乘 M 再加 token；−1 槽位不会匹配任何专家，于是直接消失。

Two variants exist. For the 512-expert shape with at most 16 tokens, one CTA of 512 threads does everything: each thread owns an expert, builds a 16-bit token mask and scans once. The same launch also zeroes the output, resets completion counters and writes the per-expert alphas, which removes separate graph nodes from every decode layer routing_sort.cu:42–103 493–522. The gather path (§6) instead counts with atomics and scatters with atomicAdd cursors, so row order inside an expert is not fixed there routing_sort.cu:409–448.

另有两种变体。对于 512 专家的形状且 token 不超过 16 个时，一个 512 线程的 CTA 包办一切：每个线程负责一个专家，构造 16 位 token 掩码并做一次扫描。同一次启动还顺带清零输出、重置完成计数器、写入每专家的 alpha，从而让每个 decode 层少掉几个独立的 graph 节点 routing_sort.cu:42–103 493–522。gather 路径（§6）则用原子操作计数、用 atomicAdd 游标散射，因此那里专家内的行序不固定 routing_sort.cu:409–448。

expand_input_rows then walks the permuted rows. One 128-thread CTA per row gathers the token's hidden vector, and each thread quantizes one 16-value block, so no warp shuffle is needed for the block max. The scales go into a per-expert region that starts at align(offset[e] + 127·e, 128), which guarantees every expert its own 128-row-aligned scale tiles; padding rows are written as zeros expand_input_rows.cu:49–158. If hidden_states is already NVFP4, the same kernel only copies codes and re-lays the linear input scales into the swizzle 165–236.

随后 expand_input_rows 遍历置换后的行。每行一个 128 线程的 CTA 收集该 token 的 hidden 向量，每个线程量化一个 16 值块，因此求块最大值不需要 warp shuffle。缩放写入从 align(offset[e] + 127·e, 128) 开始的每专家区域，保证每个专家都有自己的、按 128 行对齐的缩放 tile；填充行写零 expand_input_rows.cu:49–158。如果 hidden_states 本来就是 NVFP4，同一个 kernel 只拷贝编码，并把线性排布的输入缩放重排进 swizzle 165–236。

§4GEMM1 and the fused SwiGLUGEMM1 与融合的 SwiGLU

The large-batch GEMM1 is written by hand, not generated by CUTLASS. A tiny prologue kernel lists the (expert, M-tile, N-tile) triples, so one CTA per triple needs no search gemm_sm120_v20.cuh:168–211. Each CTA owns a 128×128 output tile and walks K in steps of 128 with two shared-memory stages. Thread 0 arms an mbarrier with the expected byte count and issues two TMA loads, A as a 2D box and B as a 3D box with the expert as the third coordinate. Meanwhile 128 threads fetch the matching scale bytes with 16-byte cp.async gemm_sm120_v20.cuh:343–397.

大 batch 的 GEMM1 是手写的，不是 CUTLASS 生成的。一个很小的前置 kernel 列出所有（专家, M-tile, N-tile）三元组，每个三元组一个 CTA，无需查找 gemm_sm120_v20.cuh:168–211。每个 CTA 负责 128×128 的输出 tile，以 128 为步长沿 K 前进，共享内存分两级。线程 0 给 mbarrier 设好期望字节数并发出两个 TMA load：A 用 2D box，B 用以专家为第三维的 3D box；同时 128 个线程用 16 字节 cp.async 取对应的缩放字节 gemm_sm120_v20.cuh:343–397。

The math is one PTX instruction, SM120's block-scaled FP4 MMA. It multiplies a 16×64 E2M1 tile by a 64×8 E2M1 tile into FP32, and takes one 32-bit register of four UE4M3 scales per operand, one scale per 16 K values (scale_vec::4X):

计算只有一条 PTX 指令：SM120 的块缩放 FP4 MMA。它把 16×64 的 E2M1 tile 与 64×8 的 E2M1 tile 相乘并累加到 FP32，每个操作数带一个 32 位寄存器，装着四个 UE4M3 缩放，每 16 个 K 值一个（scale_vec::4X）：

SwiGLU on interleaved columns交错列上的 SwiGLU

GEMM1 produces 2I columns per row, and SwiGLU needs the matching up and gate values together. ATREX expects w1 already interleaved in groups of 8 rows: the test builds each 16-row group from 8 rows of w1's second half followed by 8 rows of its first half test:698–705. The activation then computes SiLU(second 8) × first 8 for every pair of 8-column groups, entirely in FP32 up_gate_activation.cu:82–103 up_gate_pybind.cu:364–379.

GEMM1 每行产出 2I 列，而 SwiGLU 需要对应的 up 与 gate 值放在一起。ATREX 要求 w1 事先按 8 行一组交错：测试把每个 16 行组构造成 w1 后半部分的 8 行接着前半部分的 8 行 test:698–705。激活随后对每对 8 列组计算 SiLU(后 8 列) × 前 8 列，全程在 FP32 中进行 up_gate_activation.cu:82–103 up_gate_pybind.cu:364–379。

The interleave is what makes fusion cheap. In a warp's 4 × 8-column atoms, accumulator groups 0 and 1 hold one gate/up pair and groups 2 and 3 the next, so the fused kernel applies SwiGLU to its own registers, requantizes the result to NVFP4 with two shuffles for the block max, and writes FP4 codes plus swizzled scales directly. The BF16 gemm1_out never exists gemm_sm120_v20_fused_act.cuh:424–487. For the 512-expert shape, a variant rounds through BF16 before the activation on purpose, to reproduce FlashInfer's materialized intermediate e512_topk10_gemm1.cuh:32–39.

交错正是让融合变得便宜的原因。在一个 warp 的 4 个 8 列 atom 中，累加器组 0 和 1 是一对 gate/up，组 2 和 3 是下一对，因此融合 kernel 直接在自己的寄存器里做 SwiGLU，用两次 shuffle 求块最大值后把结果重新量化成 NVFP4，直接写出 FP4 编码和 swizzle 后的缩放，BF16 的 gemm1_out 根本不会出现 gemm_sm120_v20_fused_act.cuh:424–487。对于 512 专家的形状，有一个变体故意在激活前经过一次 BF16 舍入，以复现 FlashInfer 物化出来的中间结果 e512_topk10_gemm1.cuh:32–39。

Small batches use other GEMM1 kernels built from the same MMA with different tiles: 16-row tiles with 4 warps (task29), a split-K version for a single token, and an 80×256 tile that reads rows straight from hidden_states through the permutation, so no expanded copy is written (task13) task29:42–57 e512_topk10_gemm1.cuh:286–320 task13:36–51.

小 batch 使用由同一条 MMA 搭成、tile 不同的其他 GEMM1 kernel：4 个 warp 的 16 行 tile（task29）、单 token 的 split-K 版本，以及 80×256 的 tile，它通过置换直接从 hidden_states 读行，不写展开副本（task13）task29:42–57 e512_topk10_gemm1.cuh:286–320 task13:36–51。

The fourth path turns a reduction that would otherwise need atomics into a deterministic one.     Computed, not measured推算而非实测

    The tile-fill numbers assume every token picks its k experts uniformly at random: active experts ≈ E·(1 − (1 − k/E)M), rows per active expert = M·k divided by that. Real routers are skewed, which leaves some experts fuller and many emptier. The repository reports no per-path timings, so this page doesn't claim which chain is fastest.

    填充率假设每个 token 均匀随机地选 k 个专家：活跃专家数 ≈ E·(1 − (1 − k/E)M)，每个活跃专家的行数为 M·k 除以它。真实 router 是有偏的，会让部分专家更满、更多专家更空。仓库没有给出各路径的耗时，所以本页不断言哪条链最快。

    A few eligibility rules sit around the branching. hidden_states must be BF16, or uint8 NVFP4 together with input_sf. output must be BF16.     分支之外还有几条资格规则。hidden_states 必须是 BF16，或者是附带 input_sf 的 uint8 NVFP4；output 必须是 BF16。传入 shared_event 时必须设置 output_preinitialized=True，因为这个事件用来等待另一个生产者（例如 shared expert），其结果会累加进同一个 buffer nvfp4_fused_moe_sm120.py:340–401。
