FlashAttention Decode on SM103SM103 上的 FlashAttention 解码

ATREX's SM103 attention path accepts exactly one production shape: 4 query tokens per request, 16 query heads sharing one KV head of width 256, and 128-token KV pages. This chapter follows that call from the eligibility check through the paged-KV loads, the per-request KV splits, the warp-specialized pipelines and the base-2 online softmax, to the kernel that merges the splits.

ATREX 在 SM103 上的 attention 路径只接受一种生产形状：每个请求 4 个 query token，16 个 query 头共享一个宽 256 的 KV 头，KV 按 128 token 分页。本章从资格检查出发，依次讲分页 KV 的加载、按请求划分的 KV split、warp 专用化的流水线、以 2 为底的在线 softmax，最后是合并各 split 的 kernel。

    §2Turning decode into tensor-core work把解码变成张量核的活

    Decode has few query rows: 4 tokens × 16 heads = 64 rows per request, all reading one KV head. For BF16 the MMA tile is M = 128, K = 64 473–478. The runtime sets prediction_tile=2, so one CTA covers 16 heads × 2 query positions = 32 columns (N = 32).     解码的 query 行很少：每个请求 4 个 token × 16 个头 = 64 行，全部读同一个 KV 头。kernel 把共享同一个 KV 头的各个头和 query 位置折叠进 MMA 的 N 维（gqa_pack），把 KV token 放在 M 维 aka_decode_cutedsl.py:97–116。BF16 下 MMA tile 为 M = 128、K = 64 473–478。runtime 设置 prediction_tile=2，所以一个 CTA 覆盖 16 个头 × 2 个 query 位置 = 32 列（N = 32）；两个 CTA 组成大小为 2 的 cluster，覆盖全部 4 个位置 aka_decode_runtime.py:113–129 cutedsl:570–578。

    §3Walking a paged KV cache遍历分页 KV cache

    vLLM stores K and V as [pages, 128, 1, 256], and each request's page_table row lists its physical pages in order. The kernel's TMA boxes take at most 64 tokens per page: it asserts page_size in (8, 16, 32, 64) cutedsl:450. So the runtime reshapes the cache into twice as many 64-token pages before launch aka_decode_runtime.py:344–350 and tells the kernel that table pages are 128 tokens, two sub-pages each cutedsl:436–437.

    vLLM 把 K、V 存为 [pages, 128, 1, 256]，每个请求在 page_table 中的一行按顺序列出它的物理页。kernel 的 TMA box 每页最多 64 个 token：它断言 page_size in (8, 16, 32, 64) cutedsl:450。于是 runtime 在启动前把 cache 重新看成两倍数量的 64 token 页 aka_decode_runtime.py:344–350，并告诉 kernel 表页是 128 token、每页两个子页 cutedsl:436–437。

    Before each 128-token tile, the Q/K TMA warp copies the tile's page-table entries into a 4-stage shared-memory ring with cp.async, writing −1 for pages past the request's end cutedsl:837–869. The physical sub-page is entry × 2 + (logical page mod 2). K arrives as boxes of 64 tokens × 64 dimensions, 8 per tile. V arrives as boxes of 128 dimensions × 64 tokens, 4 per tile 929–946. K and V share one ring of shared-memory stages: tAsV is built on the same storage as tAsK 754–755.

    每个 128 token 的 tile 开始之前，Q/K 的 TMA warp 用 cp.async 把该 tile 的 page table 项拷进一个 4 级的共享内存环，超出请求末尾的页写成 −1 cutedsl:837–869。物理子页号为 entry × 2 + (逻辑页 mod 2)。K 以 64 token × 64 维的 box 到达，每个 tile 8 个；V 以 128 维 × 64 token 的 box 到达，每个 tile 4 个 929–946。K 和 V 共用一个共享内存 stage 环：tAsV 建在与 tAsK 相同的存储上 754–755。

    Walk演示From page table to TMA boxes从 page table 到 TMA box

    Sixteen physical pages stand in for the cache. In the kernel, the TMA copy with a −1 page index is issued anyway; I read that as relying on TMA's out-of-bounds zero fill, with the causal mask hiding those rows. That is an inference, not a comment in the code.

    这里用 16 个物理页代表 cache。kernel 中页号为 −1 的 TMA 拷贝照样发出；我的理解是它依赖 TMA 越界时填零，再由因果掩码屏蔽这些行。这是推断，代码里没有注释说明。

    A batch has only 16 to 28 requests, but one request's KV can run to tens of thousands of tokens: the production inventory reaches 29,358 test:32–34. So each request's tiles are split across several CTAs. The host decides how many CTA slots to launch aka_decode_runtime.py:82–104:

    一个 batch 只有 16 到 28 个请求，但单个请求的 KV 可能长达数万 token：生产清单中最长的是 29,358 test:32–34。因此每个请求的 tile 会被分给多个 CTA。host 端决定启动多少个 CTA 槽位 aka_decode_runtime.py:82–104：

    The per-request assignment happens on the GPU, from seqused_k, at the start of the decode kernel cutedsl:646–669. One warp holds one request per lane. It sums the 128-token tiles across lanes, sets span = ⌈total / split_target⌉, gives request b min(max_splits, ⌈tiles_b / span⌉) splits, and uses a lane prefix sum to map its CTA index to a (request, split) pair 368–388. Split j takes tiles j, j + splits, j + 2·splits, and so on 808–811. The grid always has split_target + batch CTAs along x, and CTAs that find no work exit at once 824–826.

    每个请求具体分几份，是在 decode kernel 开头由 GPU 根据 seqused_k 算出来的 cutedsl:646–669。一个 warp 的每个 lane 负责一个请求：先在 lane 间对 128 token 的 tile 数求和，令 span = ⌈总数 / split_target⌉，给请求 b 分配 min(max_splits, ⌈tiles_b / span⌉) 份，再用 lane 前缀和把本 CTA 的编号映射到（请求, split）368–388。第 j 份处理第 j、j + splits、j + 2·splits…个 tile 808–811。grid 在 x 方向总有 split_target + batch 个 CTA，分不到工作的 CTA 立即退出 824–826。

    §5Warp roles and pipelineswarp 分工与流水线

    Each CTA runs 384 threads in three warpgroups cutedsl:446 610–623. Warpgroup 0 holds four single-purpose warps: one issues the K·Qᵀ MMAs, one the Vᵀ·Pᵀ MMAs, one the TMA loads for Q, K and the page table, and one the V loads plus the final output store. Warpgroup 1 computes the softmax. Warpgroup 2 rescales the output and writes it. The roles hand work to each other through four pipelines 732–744.

    每个 CTA 有 384 个线程，分成三个 warpgroup cutedsl:446 610–623。warpgroup 0 由四个各司其职的 warp 组成：一个发 K·Qᵀ 的 MMA，一个发 Vᵀ·Pᵀ 的 MMA，一个负责 Q、K 和 page table 的 TMA 加载，一个负责 V 的加载与最终输出的写回。warpgroup 1 计算 softmax，warpgroup 2 对输出做重缩放并写出。各角色之间通过四条流水线交接 732–744。

    按第 501–526 行计算，取 get_smem_capacity_in_bytes('sm_100') = 232,448 字节：固定分配（Q、P 的 stage、barrier、page table 环、max 与 sum 缓冲）约占 50 KB，剩下的空间放得下 11 个 128 × 64 BF16 的 stage，再让出一个给 barrier，共 10 个 16 KiB 的 stage。一个 tile 要用 8 个（K、V 各 4 个），所以同时在途的略多于一个 tile 的 K 和 V。

    The kernel rebalances registers with setmaxnreg: 64 per thread for the MMA and TMA warps, 120 for softmax, 208 for correction cutedsl:624–630. Named barriers keep the two TMA warps and the two MMA warps in lock-step, so K for a coming tile and V for the current one interleave in the shared ring instead of competing for it 688–691 871–878 929–938.

    §6Online softmax, as the kernel does itkernel 里的在线 softmax

    The softmax works in base 2. The score scale is folded into scale_s_log2_e = softmax_scale · log₂e cutedsl:567, so exp2(x − m) equals exp(scale·s − m′) and the hardware can use its fast base-2 exponential (fastmath=True, line 91). Each softmax thread owns one KV row of the 128 × 32 tile. It takes each column's maximum across the warp, then publishes it with a shared-memory atomic max. sM is never reset, so it holds the running maximum over every tile seen so far:

    softmax 以 2 为底计算。score 的缩放被并入 scale_s_log2_e = softmax_scale · log₂e cutedsl:567，因此 exp2(x − m) 等于 exp(scale·s − m′)，硬件可以使用快速的 2 为底指数（fastmath=True，第 91 行）。每个 softmax 线程负责 128 × 32 tile 中的一行 KV：先在 warp 内求每列的最大值，再用共享内存上的原子 max 发布出去。sM 从不清零，所以它保存的是到目前为止所有 tile 的运行最大值：

    Probabilities go to shared memory as BF16 for the Vᵀ·Pᵀ MMA, and the rows' partial sums go to TMEM cutedsl:1161–1173. The correction warpgroup keeps the output consistent as the maximum grows. O is double-buffered in TMEM, so consecutive tiles accumulate into alternating buffers. Before a buffer takes another tile, it is multiplied by 2^(m_old − m_new), where m_old is the maximum it was last scaled to 1245–1266:

    概率以 BF16 写入共享内存供 Vᵀ·Pᵀ 的 MMA 使用，各行的部分和写入 TMEM cutedsl:1161–1173。correction warpgroup 负责在最大值增长时保持输出一致。O 在 TMEM 中双缓冲，相邻 tile 交替累加到两个缓冲。某个缓冲在接收下一个 tile 之前，先乘以 2^(m_old − m_new)，其中 m_old 是它上一次对齐到的最大值 1245–1266：

    The correction uses the maximum from two tiles ago (sM_lane_prev_prev), because each buffer only sees every other tile. At the end the two buffers are merged with one last correction cutedsl:1270–1303. Step through the same math below; one scores column stands for one (head, query position) column of the tile.

    修正用的是两个 tile 之前的最大值（sM_lane_prev_prev），因为每个缓冲只接收隔一个的 tile。最后再做一次修正，把两个缓冲合并 cutedsl:1270–1303。下面可以逐步执行同样的计算；一列 score 代表 tile 中的一个（头, query 位置）列。

    Playground演练Running max and two O buffers运行最大值与两个 O 缓冲

    Tiles hold 8 scores here instead of 128, and values are scalars instead of 256-wide rows. The widget models the math, not the lag between warpgroups: in the kernel the correction for a tile runs a stage behind the softmax that produced it.

    这里每个 tile 只有 8 个 score（kernel 中是 128 个），value 也是标量而不是 256 宽的行。组件模拟的是数学，而不是 warpgroup 之间的时间差：kernel 中某个 tile 的修正比产生它的 softmax 晚一个 stage。

    The causal mask costs almost nothing. Query position p may see KV indices up to seqlen − 4 + p cutedsl:49–51, so only the request's last tile runs the masked path, or its last two when that last tile holds only 1 to 3 tokens 54–80 1108–1123. The kernel also has a tile-skipping option (threshold_scale_factor, "BLASST"), but the runtime passes None, so it is off in this path aka_decode_runtime.py:365–369.

    因果掩码几乎没有开销。query 位置 p 能看到的 KV 下标最大为 seqlen − 4 + p cutedsl:49–51，所以只有请求的最后一个 tile 走带掩码的路径；若最后一个 tile 只有 1 到 3 个 token，则是最后两个 54–80 1108–1123。kernel 还支持跳过 tile 的选项（threshold_scale_factor，即 “BLASST”），但 runtime 传入 None，因此这条路径中它是关闭的 aka_decode_runtime.py:365–369。

    §7Merging the splits合并各个 split

    With reduction_mode="kernel", every CTA writes an unnormalized FP32 partial output plus its running max M and row sum L to a workspace cutedsl:154–179. The first CTA of each request also writes the request's split count into the extra plane 174–175. A second kernel merges the splits for each (request, head, query position) row 259–362:

    在 reduction_mode="kernel" 下，每个 CTA 把未归一化的 FP32 部分输出、运行最大值 M 和行和 L 写进工作区 cutedsl:154–179。每个请求的第一个 CTA 还会把该请求的 split 数写进额外的那个平面 174–175。第二个 kernel 对每个（请求, 头, query 位置）行合并各 split 259–362：

    This is the standard log-sum-exp merge: m* = max mj, L = Σ 2mj − m* Lj, and O = Σ 2mj − m* Oj / L. It reads only splits_b planes per request, taken from the metadata plane cutedsl:325. The merge kernel is launched with programmatic dependent launch. It can start while the decode kernel drains, and waits in griddepcontrol_wait before reading partials 324 1337.

    这就是标准的 log-sum-exp 合并：m* = max mj，L = Σ 2mj − m* Lj，O = Σ 2mj − m* Oj / L。每个请求只读取 splits_b 个平面，这个数取自元数据平面 cutedsl:325。合并 kernel 以 programmatic dependent launch 启动：它可以在 decode kernel 收尾时就开始，并在读取部分结果之前于 griddepcontrol_wait 处等待 324 1337。

    The workspace is allocated on every call through PyTorch's allocator aka_decode_runtime.py:324–335. That keeps concurrent streams from sharing scratch space, and it stays graph-safe. The tests fill an injected workspace with NaN to prove no stale value is read, and run two streams at once to check that workspaces never alias test:265–303.

    工作区在每次调用时经 PyTorch 的分配器申请 aka_decode_runtime.py:324–335，这样并发的 stream 不会共用临时空间，也能兼容 CUDA graph。测试把注入的工作区填满 NaN，以证明不会读到残留值；还同时跑两个 stream，检查工作区从不重叠 test:265–303。
