§1One step, end to end一步的全过程

Each TP rank runs one scheduler process with one Engine. The scheduler picks a batch, then prepares everything the GPU needs on the CPU: it pads the batch to a CUDA graph size, allocates KV slots for the new tokens, computes positions and write locations, asks the attention backend for metadata, and builds the sampling arguments scheduler.py:204–217. Only then does it call Engine.forward_batch.

每个 TP rank 运行一个调度进程，其中有一个 Engine。调度器选出一个 batch，然后在 CPU 上备齐 GPU 需要的一切：把 batch 补齐到某个 CUDA graph 尺寸，为新 token 分配 KV 槽，计算位置与写入地址，向 attention backend 要元数据，并构造采样参数 scheduler.py:204–217。之后才调用 Engine.forward_batch。

The model never receives the batch as an argument. ctx.forward_batch parks it in a global Context for the duration of the forward, and every layer reads ctx.batch from there: the attention layer takes positions and metadata from it and hands the whole batch to the backend core.py:100–122 layers/attention.py:47–57. The same object carries the batch through graph capture, which is how a captured graph ends up reading the static buffers. The scheduler writes next_tokens_gpu straight into its GPU token pool, so the next decode step can start without waiting for the CPU copy scheduler.py:227–233. Chapter 01 covers the overlap loop built on that.

模型从不以参数形式接收 batch。ctx.forward_batch 在前向期间把它放进全局 Context，各层都从那里读取 ctx.batch：attention 层从中取位置与元数据，再把整个 batch 交给 backend core.py:100–122 layers/attention.py:47–57。捕获 graph 时也用同一个对象传递 batch，这就是被捕获的 graph 最终读取静态 buffer 的原因。调度器把 next_tokens_gpu 直接写进 GPU 上的 token pool，下一个 decode 步因此不必等 CPU 拷贝完成 scheduler.py:227–233。基于这一点的重叠循环见第 01 章。

§2Building an engine构建 engine

The constructor runs in a fixed order, and the order matters because later steps size themselves from memory that earlier steps consumed engine.py:29–110:

构造函数按固定顺序执行。顺序很重要，因为后面的步骤要根据前面步骤已经占用的显存来决定自己的大小 engine.py:29–110：

  1. Resolve the configuration. _adjust_config turns --attn auto into a concrete backend and forces page size 64 for TRT-LLM (§5).
  2. Pick the device and a private stream. All engine work is queued on self.stream, and forward_batch asserts it is current.
  3. Set up communication. By default a gloo group plus Mini-SGLang's own PyNCCL communicator, sized for one full forward of hidden states engine.py:112–137.
  4. Measure free memory. Every TP rank reports its free memory, the engine fails if they differ by more than 2 GiB, and sizing uses the largest value engine.py:170–189.
  5. Build the model on the meta device, then load weights, so no memory is spent on random initialization.
  6. Size and allocate the KV pool from what is left (§3), plus one dummy page.
  7. Allocate the page table: max_running_req + 1 rows by max_seq_len rounded up to 32, one int32 per token. The extra row belongs to the dummy request.
  8. Create the attention backend, the MoE backend if needed, and the sampler, then capture CUDA graphs (§4).
  1. 解析配置。_adjust_config 把 --attn auto 变成具体 backend，并为 TRT-LLM 强制页大小 64（§5）。
  2. 选定设备与一条专用 stream。engine 的所有工作都排在 self.stream 上，forward_batch 会断言它是当前 stream。
  3. 建立通信。默认是一个 gloo 组，加上 Mini-SGLang 自带的 PyNCCL communicator，其缓冲区按一次完整前向的 hidden states 大小分配 engine.py:112–137。
  4. 测量空闲显存。每个 TP rank 报告自己的空闲显存；若相差超过 2 GiB 则直接报错，容量计算取其中的最大值 engine.py:170–189。
  5. 先在 meta 设备上构建模型，再加载权重，不在随机初始化上浪费显存。
  6. 用剩余显存确定并分配 KV 池（§3），另加一个 dummy 页。
  7. 分配 page table：max_running_req + 1 行，每行 max_seq_len 向上取整到 32，每个 token 一个 int32。多出的那一行属于 dummy 请求。
  8. 创建 attention backend、必要时的 MoE backend 以及 sampler，然后捕获 CUDA graph（§4）。

§3Sizing the KV poolKV 池的大小

The KV pool gets everything the model didn't take, up to --memory-ratio of the free memory measured before loading. The model's footprint is measured, not computed: it is the drop in free memory across weight loading engine.py:148–168.

KV 池拿走模型没占用的全部显存，上限是加载前测得空闲显存的 --memory-ratio 倍。模型占用是测出来的，而非算出来的：就是加载权重前后空闲显存的差值 engine.py:148–168。

With tensor parallelism each rank stores only its share of KV heads. When there are more ranks than KV heads, div_even(..., allow_replicate=True) returns 1 and the heads are replicated misc.py:20–26. The pool itself is one tensor shaped [2, layers, pages, page_size, local_kv_heads, head_dim] mha_pool.py:28–32. The engine also caps max_seq_len at the number of KV tokens, so a request longer than the whole pool is never admitted engine.py:65–73.

在张量并行下，每个 rank 只存自己那份 KV head。当 rank 数多于 KV head 数时，div_even(..., allow_replicate=True) 返回 1，KV head 被复制 misc.py:20–26。池本身是一个形状为 [2, layers, pages, page_size, local_kv_heads, head_dim] 的张量 mha_pool.py:28–32。engine 还把 max_seq_len 限制在 KV token 总数以内，因此比整个池还长的请求不会被接纳 engine.py:65–73。

Calculator计算器_determine_num_pages, ported_determine_num_pages 移植版

The formula is the engine's. The inputs are examples: model shapes come from the public Hugging Face configs, weights are BF16 parameter counts divided evenly across TP ranks, and the free-memory presets are typical values for those GPUs. On a real run the engine measures the weights instead.

公式与 engine 一致。输入只是示例：模型形状取自公开的 Hugging Face 配置，权重按 BF16 参数量在 TP rank 之间均分，空闲显存预设是这些 GPU 的典型值。真实运行时 engine 会实测权重占用。

What the headroom pays for剩余显存用在哪里

The attention workspaces (128 MiB each for FlashInfer and TRT-LLM), the CUDA graph pool and every activation are allocated after the KV pool, so they all have to fit in the part of free memory that --memory-ratio leaves out. That is my reading of the allocation order in the constructor. If graph capture runs out of memory, lowering the ratio or --cuda-graph-max-bs is the lever.

attention workspace（FlashInfer 与 TRT-LLM 各 128 MiB）、CUDA graph 内存池以及所有激活都在 KV 池之后分配，因此都必须挤进 --memory-ratio 留下的那部分空闲显存。这是我根据构造函数中的分配顺序得出的结论。如果捕获 graph 时显存不足，可调的就是这个比例或 --cuda-graph-max-bs。

§4CUDA graphsCUDA graph

A decode step for a small batch launches hundreds of short kernels, and launching them one by one from Python can take longer than running them. The engine records the whole decode forward once per batch size into a CUDA graph and replays it later with one launch. The batch sizes come from a simple rule graph.py:49–67:

小 batch 的一次 decode 会启动数百个短 kernel，从 Python 逐个启动它们，可能比执行它们还慢。engine 为每个 batch 大小把整个 decode 前向录制成一张 CUDA graph，之后一次启动即可重放。batch 大小列表来自一条简单规则 graph.py:49–67：

Capture runs largest size first, and every graph after the first reuses the first graph's memory pool graph.py:105–147. Each capture builds a decode batch of bs copies of the dummy request, points the batch's input_ids, out_loc and positions at slices of one static buffer, runs one warm-up forward, and records a second forward inside torch.cuda.graph. The logits land in a static [max_bs, vocab] FP32 buffer graph.py:20–46.

捕获从最大的尺寸开始，第一张之后的每张 graph 都复用第一张的内存池 graph.py:105–147。每次捕获都构造一个由 bs 份 dummy 请求组成的 decode batch，让 batch 的 input_ids、out_loc、positions 指向同一个静态 buffer 的切片，先跑一次预热前向，再在 torch.cuda.graph 内录制第二次前向。logits 写进一个静态的 [max_bs, vocab] FP32 buffer graph.py:20–46。

Replay pads first. pad_batch appends dummy requests up to the first captured size that fits. Then replay copies the real inputs into the static buffer, lets the attention backend refresh its captured metadata, replays the graph, and returns only the first batch.size rows of logits graph.py:149–166:

重放之前先补齐。pad_batch 追加 dummy 请求，补到第一个放得下的已捕获尺寸。随后 replay 把真实输入拷进静态 buffer，让 attention backend 刷新捕获时的元数据，重放 graph，只返回 logits 的前 batch.size 行 graph.py:149–166：

The dummy request is what makes padding safe. It uses the page table's extra row, and the engine points every slot of that row at the extra dummy page, so padded rows read and write KV only there engine.py:88–98. Graphs are skipped for every prefill, for decode batches larger than the largest graph, and entirely when --cuda-graph-max-bs 0. The interactive shell sets the maximum to 1 args.py:231–234.

让补齐变得安全的是 dummy 请求。它使用 page table 多出的那一行，engine 把这一行的每个位置都指向额外的 dummy 页，于是补齐的行只在那里读写 KV engine.py:88–98。所有 prefill、超过最大 graph 的 decode batch 都不走 graph；--cuda-graph-max-bs 0 时则完全关闭。交互式 shell 把最大值设为 1 args.py:231–234。

§5Choosing attention backends选择 attention backend

An attention backend implements five methods: forward, prepare_metadata, and three for CUDA graphs (init_capture_graph, prepare_for_capture, prepare_for_replay) base.py:12–34. Three are registered: fa (FlashAttention through sgl_kernel), fi (FlashInfer) and trtllm (TRT-LLM kernels shipped in FlashInfer) attention/__init__.py:22–40.

一个 attention backend 实现五个方法：forward、prepare_metadata，以及三个 CUDA graph 相关方法（init_capture_graph、prepare_for_capture、prepare_for_replay）base.py:12–34。已注册的有三个：fa（经 sgl_kernel 的 FlashAttention）、fi（FlashInfer）和 trtllm（FlashInfer 自带的 TRT-LLM kernel）attention/__init__.py:22–40。

--attn takes one name or two separated by a comma. With two different names, create_attention_backend wraps them in a HybridBackend that sends prefill batches to the first and decode batches to the second, and forwards all three graph methods to the decode backend, since only decode is ever captured attention/__init__.py:52–68 base.py:37–63. With auto, capability 10.0 and above gets trtllm, capability 9.x gets fa,fi, and anything older gets fi. Any choice that contains trtllm forces page size 64 unless it is already 16, 32 or 64 engine.py:218–233.

--attn 接受一个名字，或用逗号隔开的两个名字。两个名字不同时，create_attention_backend 把它们包成 HybridBackend：prefill batch 交给前者，decode batch 交给后者，三个 graph 方法全部转给 decode backend，因为只有 decode 会被捕获 attention/__init__.py:52–68 base.py:37–63。选 auto 时，capability 10.0 及以上用 trtllm，9.x 用 fa,fi，更老的用 fi。只要选择中包含 trtllm，页大小不是 16、32、64 时就被强制改为 64 engine.py:218–233。

Resolver解析器From --attn to two backends从 --attn 到两个 backend

    Follows validate_attn_backend, _adjust_config and create_attention_backend in order. FlashInfer decode uses tensor cores when q heads per KV head is at least 4, unless MINISGL_FLASHINFER_USE_TENSOR_CORES overrides it fi.py:236–242.

    依次按 validate_attn_backend、_adjust_config、create_attention_backend 实现。每个 KV head 对应的 q head 数不少于 4 时，FlashInfer decode 使用 tensor core，除非被 MINISGL_FLASHINFER_USE_TENSOR_CORES 覆盖 fi.py:236–242。

    Why two backends, and one caveat为什么要两个 backend，以及一处值得注意的地方

    The docs only say the split is "to maximize efficiency". The usual reason is that prefill is a long, compute-bound attention over many query tokens, while decode has one query token per request, is bound by KV reads, and has to be cheap to capture in a graph. The two favor different kernels. Separately, is_sm100_supported compares capability ≥ (10, 0), so capability 12.x GPUs also resolve auto to trtllm arch.py:17–29. I haven't checked whether those kernels run there.

    文档只说拆分是为了“最大化效率”。通常的原因是：prefill 是针对大量 query token 的长 attention，受计算限制；decode 每个请求只有一个 query token，受 KV 读取限制，而且必须便于捕获进 graph。两者适合不同的 kernel。另外，is_sm100_supported 比较的是 capability ≥ (10, 0)，所以 capability 12.x 的 GPU 也会把 auto 解析为 trtllm arch.py:17–29。这些 kernel 能否在那里运行，我没有验证。

    §6Attention metadataAttention 元数据

    Every backend starts from the same three numbers per request: cached_len (tokens whose KV is already stored), device_len (tokens after this step) and their difference, extend_len core.py:44–57. Query lengths come from extend_len, key lengths from device_len, and cu_seqlens_q is built one of three ways fa.py:67–105:

    每个 backend 都从每个请求的同样三个数出发：cached_len（KV 已存好的 token 数）、device_len（本步之后的 token 数）以及两者之差 extend_len core.py:44–57。query 长度来自 extend_len，key 长度来自 device_len，cu_seqlens_q 有三种构造方式 fa.py:67–105：

    The global page table always stores one raw token location per position, whatever the page size. FlashAttention and TRT-LLM want page indices, so they take every page_size-th location and divide it by the page size. FlashInfer skips that step entirely: it concatenates the raw locations, declares page size 1, and views the cache as one token per page fi.py:176–225. Its plan() call runs on the CPU the first time a layer uses the metadata, after waiting on an event so the previous plan's pinned staging buffer isn't overwritten mid-copy fi.py:123–166.

    无论页大小是多少，全局 page table 总是为每个位置存一个原始 token 位置。FlashAttention 与 TRT-LLM 需要页号，所以每隔 page_size 取一个位置再除以页大小。FlashInfer 完全省掉这一步：它把原始位置拼接起来，声明页大小为 1，把 cache 看成每页一个 token fi.py:176–225。它的 plan() 在某一层第一次用到元数据时于 CPU 上执行，执行前先等待一个事件，避免上一次 plan 的 pinned 中转 buffer 在拷贝途中被覆盖 fi.py:123–166。

    For CUDA graphs, FA and TRT-LLM capture against fixed-size buffers (sequence lengths, cu_seqlens_k and a [max_bs, max_seq_len / page_size] page table), and prepare_for_replay copies the live values into them fa.py:107–136.     对于 CUDA graph，FA 与 TRT-LLM 基于固定大小的 buffer 捕获（序列长度、cu_seqlens_k，以及 [max_bs, max_seq_len / page_size] 的 page table），prepare_for_replay 把实时值拷进这些 buffer fa.py:107–136。FlashInfer 为每个捕获尺寸创建一个 CUDAGraphBatchDecodeWithPagedKVCacheWrapper，它们都指向同一组索引 buffer，重放时只需重新 plan 进去 fi.py:244–271。所有 backend 都先用 store_kv 把新的 K、V 写到 batch.out_loc，再在 cache 上计算 attention mha_pool.py:45–56；该 kernel 见第 04 章。

    §7Sampling采样

    Logits reach the sampler one row per request. In prefill the LM head first gathers each request's last token with the backend's get_last_indices, which is cu_seqlens_q[1:] − 1; in decode every row is already a last token. Under TP the vocabulary shards are all-gathered before the logits are returned embedding.py:87–108.

    logits 以每个请求一行的形式到达 sampler。prefill 时，LM head 先用 backend 的 get_last_indices（即 cu_seqlens_q[1:] − 1）取出每个请求的最后一个 token；decode 时每一行本来就是最后一个 token。在 TP 下，词表分片先做 all-gather 再返回 logits embedding.py:87–108。

    A request is greedy when its temperature is 0 or its top-k is 1, and its top-p is 1 core.py:15–25. An all-greedy batch skips every tensor and takes an argmax. In a mixed batch, greedy requests get temperature 10−6, which makes the softmax put essentially all mass on the top token. The top-k and top-p tensors are only built when some request actually uses them, which picks one of four FlashInfer calls: plain sampling, top-k, top-p, or both, after a temperature-scaled softmax sample.py:24–45. prepare runs in the scheduler's CPU phase, so its host-to-device copies are queued before the forward starts.

    当请求的温度为 0 或 top-k 为 1，且 top-p 为 1 时，它是贪心的 core.py:15–25。全是贪心请求的 batch 跳过所有张量，直接取 argmax。在混合 batch 中，贪心请求的温度被设为 10−6，softmax 几乎把全部概率放在最大的那个 token 上。只有当确实有请求用到 top-k 或 top-p 时才构造对应张量，由此在四种 FlashInfer 调用中选一种：普通采样、top-k、top-p 或两者兼用，前面都有一次按温度缩放的 softmax sample.py:24–45。prepare 在调度器的 CPU 阶段执行，所以它的 host 到 device 拷贝在前向开始之前就已排队。
