§1Prefix sharing, live前缀共享实验

Start with the whole mechanism on a pool of 24 token slots. Each letter is one token, and every request generates two lowercase output tokens. Admit requests, finish them, and watch the tree grow, split and give memory back. The lab runs the same steps as RadixPrefixCache and the scheduler's CacheManager: the walk in the tree, locking, page allocation with eviction, and the two cache_req calls.

先在一个只有 24 个 token 槽的池上看完整机制。每个字母代表一个 token，每个请求生成两个小写的输出 token。提交请求、结束请求，观察树如何生长、分裂并归还内存。实验与 RadixPrefixCache 以及调度器的 CacheManager 执行相同的步骤：树中查找、加锁、带驱逐的 page 分配，以及两次 cache_req 调用。

Radix labRadix 实验24 slots · max 4 running24 个槽 · 最多 4 个运行中请求

in tree, locked在树中，已锁定 in tree, evictable在树中，可驱逐 private to a request请求私有 free空闲 free, but still in a row已空闲但仍在某行中 tree: gold = walked, green = new, dotted gold = split树：金色 = 走过，绿色 = 新建，金色点线 = 分裂

    Simplified: one request's steps run as one sequence, frees happen immediately instead of at the end of the result loop, and timestamps are a logical clock instead of time.monotonic_ns(). Hover a tree node for its slots.

    简化之处：一个请求的各步骤按顺序执行；释放立即发生，而不是在结果处理循环结束时；时间戳用逻辑时钟代替 time.monotonic_ns()。鼠标悬停在树节点上可以看到它的槽位。

    Three things to try. Admit follow-up of ABCDE after ABCDE finishes: the new prompt contains the previous turn's output, so most of it is already in the tree. Admit batch: ABCJK × 2: both requests match before either inserts, so the second finds its prompt already cached at insert time and gives its own slots back (§7). Switch to page_size 2: matches and inserts round down to whole pages, so an odd-length prefix leaves one token uncached.

    可以试三件事。在 ABCDE 结束后提交 ABCDE 的后续轮次：新 prompt 包含上一轮的输出，大部分已在树中。提交 同批：ABCJK × 2：两个请求都在对方插入前完成匹配，于是第二个在插入时发现 prompt 已被缓存，把自己的槽位还回去（§7）。切换到 page_size 2：匹配与插入都按整页向下取整，奇数长度的前缀会留下一个 token 不被缓存。

    §2The KV pool: one tensor for every layerKV 池：所有层共用一个张量

    MHAKVCache allocates a single tensor of shape (2, num_layers, num_pages, page_size, local_kv_heads, head_dim). Index 0 holds keys and index 1 values, and the KV heads are split across TP ranks mha_pool.py:16–37. For writes, each layer's slice is viewed as a flat list of num_pages × page_size token rows, so a "slot" is simply a row number in that view.

    MHAKVCache 只分配一个形状为 (2, num_layers, num_pages, page_size, local_kv_heads, head_dim) 的张量：下标 0 存 key，下标 1 存 value，KV head 在 TP rank 之间切分 mha_pool.py:16–37。写入时，每一层的切片被看作 num_pages × page_size 行的扁平 token 表，所谓“槽位”就是这张表里的行号。

    The engine sizes the pool after loading the model. It measures how much memory the weights took, keeps memory_ratio (0.9 by default) of the free memory it saw before loading, and divides the rest by the bytes one page costs across all layers engine.py:148–168 config.py:20–31:

    engine 在加载模型之后确定池的大小：先测出权重占用了多少显存，取加载前空闲显存的 memory_ratio（默认 0.9），扣掉权重后，再除以一个 page 在所有层上占用的字节数 engine.py:148–168 config.py:20–31：

    cache_per_page = 2 × head_dim × (num_kv_heads / tp) × page_size × dtype_bytes × num_layers

    Worked numbers算例

    Using the public model configs (not part of this repo): Qwen3-32B has 64 layers, 8 KV heads and head_dim 128, so in BF16 one token costs 2 × 128 × 8 × 2 × 64 = 256 KiB on one GPU, or 64 KiB per GPU at TP 4. Qwen3-0.6B (28 layers, same heads) costs 112 KiB per token. That is more than the 32B model at TP 4, because the small model's KV heads aren't split.

    按公开的模型配置（不在本仓库中）计算：Qwen3-32B 有 64 层、8 个 KV head、head_dim 128，BF16 下单卡每个 token 占 2 × 128 × 8 × 2 × 64 = 256 KiB，TP 4 时每卡 64 KiB。Qwen3-0.6B（28 层，head 相同）每个 token 占 112 KiB，比 TP 4 下的 32B 模型还多，因为小模型的 KV head 没有被切分。

    The pool gets one extra page beyond the computed count. The page-table row reserved for the dummy request (row max_running_req) is filled with the first slot of that page, so padded entries in a CUDA-graph batch read and write a page no real request owns engine.py:54–63 88–98. Chapter 03 covers the graph padding itself.

    池比计算出的数量多一个 page。为 dummy 请求保留的 page-table 行（第 max_running_req 行）被填成这个 page 的首个槽位，因此 CUDA graph batch 中的填充项读写的是一个不属于任何真实请求的 page engine.py:54–63 88–98。graph 填充本身在第 03 章介绍。

    §3The page table: one row per request, one entry per tokenPage table：每个请求一行，每个 token 一项

    The page table is an int32 tensor of shape (max_running_req + 1, align32(max_seq_len)). Despite its name it stores raw token slots, one per position, even when page_size is larger than 1 engine.py:65–72 core.py:101–104. Each running request owns one row, handed out by TableManager from a plain Python free list table.py:4–21.

    page table 是一个形状为 (max_running_req + 1, align32(max_seq_len)) 的 int32 张量。名字虽叫 page table，存的却是原始 token 槽位，每个位置一项，即使 page_size 大于 1 也是如此 engine.py:65–72 core.py:101–104。每个运行中的请求占一行，由 TableManager 从一个普通的 Python 空闲列表分配 table.py:4–21。

    Free KV memory is tracked as a tensor of page start slots, [0, p, 2p, …] for page size p. allocate_paged counts the pages each request needs to cover positions [cached_len, device_len), takes them from the front of the free list, expands each page into its p slots, and scatters them into the rows with one indexed assignment cache.py:42–53 106–146. Freed pages are appended at the back, so recently freed memory is reused last.

    空闲 KV 内存用一个 page 起始槽位的张量记录，page 大小为 p 时是 [0, p, 2p, …]。allocate_paged 统计每个请求覆盖位置 [cached_len, device_len) 所需的 page 数，从空闲列表头部取出，把每个 page 展开成 p 个槽位，再用一次索引赋值写进各行 cache.py:42–53 106–146。释放的 page 追加到末尾，所以最近释放的内存最后才被复用。

    Consumers read the row in different shapes. The scheduler gathers out_loc, the slots the forward pass writes, straight from the row scheduler.py:204–210. FlashAttention and TRT-LLM take every p-th entry and divide by p to get page numbers fa.py:92–97. FlashInfer is handed the raw slots with page_size=1, so for it every token is its own page fi.py:210–220.

    不同的使用者以不同形状读取这一行。调度器直接从行中取出 out_loc，即前向要写入的槽位 scheduler.py:204–210。FlashAttention 和 TRT-LLM 每隔 p 项取一项再除以 p，得到 page 编号 fa.py:92–97。FlashInfer 拿到的是原始槽位，并设 page_size=1，对它来说每个 token 都是单独一页 fi.py:210–220。

    Views视图One request's row, three readers一个请求的行，三种读法

    Cobalt = prefix matched from the tree, green = pages allocated for this request, dashed = allocated past device_len to finish the last page. The free list is pre-shuffled to show a pool after some churn, and small numbers under the row are positions.

    钴蓝 = 从树中匹配到的前缀，绿色 = 为本请求分配的 page，虚线 = 为补满最后一页而分配在 device_len 之后的槽位。空闲列表预先打乱，模拟运行一段时间后的池；行下方的小数字是位置。

    §4Writing K and V: one warp per token写入 K 与 V：每个 token 一个 warp

    Every attention backend calls kvcache.store_kv(k, v, batch.out_loc, layer_id) before running attention, and the pool forwards it to store_cache mha_pool.py:45–56. The kernel is JIT-compiled per row size and gives each token one warp. The warp reads the slot index, then copies the token's K row and V row into that slot store.py:15–42:

    每个 attention 后端在计算 attention 之前都会调用 kvcache.store_kv(k, v, batch.out_loc, layer_id)，池再把它转给 store_cache mha_pool.py:45–56。kernel 按行大小 JIT 编译，每个 token 分配一个 warp：warp 读出槽位下标，再把该 token 的 K 行和 V 行拷进这个槽位 store.py:15–42：

    The kernel's test writes to random unique slots and compares against a torch.compile'd indexed assignment, for batch sizes from 1 to 32,768 test_store.py:9–53. Its sibling in index.cu uses the same warp-per-row pattern in the other direction: it gathers embedding rows, and for a vocabulary sharded across TP ranks it zero-fills rows outside the local shard before the all-reduce index.cu:61–96 embedding.py:33–42. It isn't part of the KV path.

    kernel 的测试写入随机且互不重复的槽位，并与经 torch.compile 的索引赋值对比，batch 大小从 1 到 32,768 test_store.py:9–53。index.cu 中的兄弟 kernel 用同样的“每行一个 warp”模式反向工作：它 gather embedding 行；词表在 TP rank 间切分时，把不在本地分片内的行填零，再做 all-reduce index.cu:61–96 embedding.py:33–42。它不属于 KV 路径。

    §6The radix treeRadix 树

    Each node holds a run of token ids as its key and the matching KV slots as its value, plus a ref count and a timestamp radix_cache.py:17–84. Children are indexed by their first page: the first token when page_size is 1, or a tuple of the first page_size tokens otherwise 234–237. Keys and values stay on the CPU, and the comparison that finds where two token runs diverge is a native std::mismatch called through tvm-ffi radix.cpp:19–40.

    每个节点以一段 token id 为 key，以对应的 KV 槽位为 value，另有 ref count 和时间戳 radix_cache.py:17–84。子节点按其第一页索引：page_size 为 1 时是第一个 token，否则是前 page_size 个 token 组成的 tuple 234–237。key 与 value 都留在 CPU 上，找出两段 token 从哪里开始不同的比较，是经 tvm-ffi 调用的原生 std::mismatch radix.cpp:19–40。

    Walk and split查找与分裂

    Both matching and inserting start with _tree_walk. It follows children page by page, rounds each match down to a whole page, and splits a node when the match ends inside it. After a split, the upper half keeps the original ref count and every node on the path gets the current timestamp radix_cache.py:205–231 69–81.

    匹配和插入都从 _tree_walk 开始。它逐页沿子节点向下走，把每次的匹配长度向下取整到整页，匹配在某个节点中间结束时就分裂该节点。分裂后，上半部分保留原来的 ref count，路径上的每个节点都被打上当前时间戳 radix_cache.py:205–231 69–81。

    Observation观察

    The interface says match_prefix "will not modify the cache" base.py:82–93. In the radix manager it does change the tree's shape, because the walk splits nodes and refreshes timestamps. The set of cached tokens and slots stays the same, so the statement holds for contents but not for structure.

    接口注释说 match_prefix “不会修改缓存” base.py:82–93。在 radix 管理器中它确实会改变树的形状，因为查找会分裂节点并刷新时间戳。已缓存的 token 与槽位集合不变，所以这句话对内容成立，对结构不成立。

    Insert, lock and evict插入、加锁与驱逐

    • Insert rounds the sequence down to whole pages, walks it, and hangs whatever didn't match below the node where the walk stopped. The new leaf starts unlocked, so its length is added to evictable_size. The return value reports how much was already cached, which is what the caller must free radix_cache.py:136–146.
    • Lock walks from the handle's node to the root and increments each ref count. A node that goes from 0 to 1 moves its length from evictable to protected, and unlocking reverses it. The root starts with ref count 1, so it's never evicted 101–130.
    • Evict collects every unlocked leaf, heapifies them by timestamp and pops the oldest until enough tokens are freed. When a parent loses its last child and is unlocked, it joins the heap, so a whole idle branch can go in one call 148–203.
    • 插入先把序列向下取整到整页，查找一遍，再把未匹配的部分挂在查找停下的节点之下。新叶子初始未锁定，其长度计入 evictable_size。返回值报告已缓存了多少，调用者需要释放这一部分 radix_cache.py:136–146。
    • 加锁从 handle 的节点走到根，逐个增加 ref count。ref count 从 0 变为 1 的节点，其长度从 evictable 转为 protected；解锁时反向操作。根节点初始 ref count 为 1，因此永不被驱逐 101–130。
    • 驱逐收集所有未锁定的叶子，按时间戳建堆，不断弹出最旧的直到释放足够的 token。父节点失去最后一个子节点且未锁定时会加入堆，因此一次调用可以清掉整条空闲分支 148–203。

    Eviction works on whole nodes, so it can free more than was asked for. The caller appends every evicted slot's page start to the free list cache.py:106–113. Six tests pin down that pages stay aligned and never overlap after eviction when page_size is larger than 1 test_cache_allocate.py:58–203.

    驱逐以整个节点为单位，因此可能释放比要求更多的内存。调用者把每个被驱逐槽位的 page 起点追加到空闲列表 cache.py:106–113。六个测试确保 page_size 大于 1 时，驱逐后的 page 依然对齐且互不重叠 test_cache_allocate.py:58–203。

    §7A request's life in the cache请求在缓存中的一生

    1. Match. The scheduler matches input_ids[:len − 1], never the whole prompt. At least one token is always prefilled, which the model needs to produce logits for the next token cache.py:27–30 core.py:38–42.
    2. Admit. PrefillAdder estimates the request's footprint as new prompt tokens plus max_tokens. It adds a reservation for what running decodes still need (their remaining tokens plus one partly filled page each) and compares the total with available_size = evictable + free. It then locks the match and checks again, because the locked tokens stop counting as evictable prefill.py:39–63 decode.py:27–30.
    3. Copy the hit. The matched slots are copied into the request's page-table row, and the matched token ids into the token pool, so the prefix costs no computation prefill.py:56–61.
    4. Allocate and run. allocate_paged covers the rest, evicting if needed, and the forward pass writes K and V for positions [cached_len, device_len) (§3, §4).
    5. Cache after prefill. Inside lazy_free_region, each non-chunked prefill calls cache_req(finished=False). That inserts the prompt, frees duplicates and moves the lock to the new, longer handle scheduler.py:146–165.
    6. Cache at the end. A finished or aborted request calls cache_req(finished=True) and returns its table row scheduler.py:200–202.
    1. 匹配。调度器匹配的是 input_ids[:len − 1]，而不是整个 prompt。这样至少有一个 token 需要 prefill，模型要靠它产生下一个 token 的 logits cache.py:27–30 core.py:38–42。
    2. 准入。PrefillAdder 把请求的占用估计为新 prompt token 数加 max_tokens，再加上为运行中 decode 预留的量（它们剩余的 token 数，以及每个请求一个未填满的 page），与 available_size = evictable + 空闲 比较。随后锁定匹配结果并再检查一次，因为被锁定的 token 不再计入 evictable prefill.py:39–63 decode.py:27–30。
    3. 复制命中部分。匹配到的槽位被拷进请求的 page-table 行，匹配到的 token id 拷进 token pool，因此前缀不需要任何计算 prefill.py:56–61。
    4. 分配并运行。allocate_paged 补齐其余部分，必要时驱逐；前向为位置 [cached_len, device_len) 写入 K、V（§3、§4）。
    5. prefill 后缓存。在 lazy_free_region 内，每个非分块的 prefill 调用 cache_req(finished=False)：插入 prompt、释放重复部分，并把锁转移到新的、更长的 handle 上 scheduler.py:146–165。
    6. 结束时缓存。结束或被中止的请求调用 cache_req(finished=True)，并归还 table 行 scheduler.py:200–202。

    Range区间What happens发生什么

    Frees made while processing a batch's results are collected and appended to the free list in one concatenation when the loop ends cache.py:93–104. With overlap scheduling, the next batch has already been prepared from the old free list by then. Chapter 01 covers that loop.

    处理一个 batch 结果期间的释放会被收集起来，在循环结束时用一次拼接追加到空闲列表 cache.py:93–104。开启 overlap scheduling 时，此时下一个 batch 已经基于旧的空闲列表准备好了。这个循环在第 01 章介绍。

    Observation: the duplicate range keeps pointing at freed slots观察：重复区间仍指向已释放的槽位

    When [old_handle.cached_len, cached_len) is non-empty, cache_req(finished=False) frees this request's slots for that range. I found no code that then rewrites the request's page-table row to point at the tree's copy; the only writes to the table are at admission and in allocate_paged. Upstream SGLang does rewrite the row right after the equivalent free sglang radix_cache.py:594–613. If my reading is right, a request that shared a batch with an identical prefix keeps decoding against slots that are back on the free list. The data stays correct only until those slots are reallocated. Since freed pages go to the back of the list, that needs memory pressure. The "batch: ABCJK × 2" preset in the lab outlines those slots. I have not reproduced a wrong output on a GPU.

    当 [old_handle.cached_len, cached_len) 非空时，cache_req(finished=False) 会释放本请求在该区间的槽位。我没有找到随后把请求的 page-table 行改为指向树中副本的代码，对该表的写入只发生在准入和 allocate_paged 中。上游 SGLang 在对应的释放之后确实会重写这一行 sglang radix_cache.py:594–613。如果我的理解正确，与相同前缀的请求同批进入的请求，会继续基于已回到空闲列表的槽位做 decode；数据只在这些槽位被重新分配之前保持正确。由于释放的 page 排在列表末尾，这需要内存压力才会发生。实验中的 “同批：ABCJK × 2” 预设会描边标出这些槽位。我没有在 GPU 上复现出错误输出。
