How a compact reimplementation of SGLang serves a model: an API server, tokenizer processes and one scheduler per GPU, tied together by ZeroMQ sockets on one side and NCCL on the other.

SGLang 的精简重实现是怎样提供模型服务的：一个 API server、若干 tokenizer 进程、每张 GPU 一个 scheduler，一侧用 ZeroMQ socket 连接，另一侧用 NCCL 连接。

§1What Mini-SGLang isMini-SGLang 是什么

Mini-SGLang is a compact implementation of SGLang, written to be both a working inference server and a readable reference README.md:11. It keeps the optimizations that matter for serving: a radix-tree prefix cache, chunked prefill, overlap scheduling, tensor parallelism, CUDA graphs for decode, and FlashAttention, FlashInfer and TensorRT-LLM attention kernels README.md:13–23 features.md:31–59. The model registry covers Llama, Qwen2, Qwen3, Qwen3-MoE and Mistral architectures register.py:5–12.

Mini-SGLang 是 SGLang 的精简实现，目标是既能真正提供推理服务，又能作为可读的参考实现 README.md:11。它保留了对服务性能真正重要的优化：radix 树前缀缓存、chunked prefill、overlap scheduling、张量并行、decode 阶段的 CUDA graph，以及 FlashAttention、FlashInfer 和 TensorRT-LLM 的 attention kernel README.md:13–23 features.md:31–59。模型注册表覆盖 Llama、Qwen2、Qwen3、Qwen3-MoE 和 Mistral 架构 register.py:5–12。

You start it with python -m minisgl --model <path> [--tp N], which serves an OpenAI-compatible /v1/chat/completions endpoint. Adding --shell-mode (the docs write --shell, which argparse accepts as a prefix) gives an interactive chat in the terminal, and the LLM class runs the same scheduler in-process for offline batches (§6).

用 python -m minisgl --model <path> [--tp N] 启动，即可提供兼容 OpenAI 的 /v1/chat/completions 接口。加上 --shell-mode（文档写作 --shell，argparse 会把它当作前缀接受）会在终端里打开交互式对话；LLM 类则在同一进程内运行同一个 scheduler，用于离线批处理（§6）。

How big is "compact"?“精简”有多小？

The README says about 5,000 lines of Python. wc -l over python/minisgl/**/*.py at this commit gives 8,090, which also counts blank lines, comments, docstrings and the 575-line benchmark client. The CUDA/C++ sources under kernel/csrc add another 1,971 lines.

README 说大约 5,000 行 Python。在该提交上对 python/minisgl/**/*.py 执行 wc -l 得到 8,090 行，其中包括空行、注释、docstring 以及 575 行的 benchmark 客户端。kernel/csrc 下的 CUDA/C++ 源码另有 1,971 行。

§2Processes and sockets进程与 socket

launch_server runs in the main process. It parses the arguments, creates the API server's two ZMQ sockets, then spawns the backend with the spawn start method: one scheduler process per TP rank, one detokenizer, and --num-tokenizer extra tokenizer processes launch.py:40–113. The default is 0 extra tokenizers, in which case the detokenizer process also does the tokenizing. The main process waits on a multiprocessing queue for num_tokenizer + 2 ready messages: one from scheduler rank 0, one per tokenizer, one from the detokenizer. Only then does it start uvicorn launch.py:105–111.

launch_server 在主进程中运行。它先解析参数、创建 API server 的两个 ZMQ socket，再用 spawn 方式启动后端：每个 TP rank 一个 scheduler 进程、一个 detokenizer，以及 --num-tokenizer 个额外的 tokenizer 进程 launch.py:40–113。默认没有额外 tokenizer，此时 detokenizer 进程兼做分词。主进程在一个 multiprocessing 队列上等待 num_tokenizer + 2 条就绪消息：scheduler rank 0 一条、每个 tokenizer 一条、detokenizer 一条，之后才启动 uvicorn launch.py:105–111。

Control messages travel over ZMQ ipc:// sockets whose paths end in .pid=<pid>, so two servers on one machine don't collide scheduler/config.py:8–33. Tensors between GPUs go through NCCL, and the scheduler ranks also share a gloo CPU group for barriers and small broadcasts engine.py:112–137.

控制消息走 ZMQ ipc:// socket，路径以 .pid=<pid> 结尾，因此同一台机器上的两个服务不会冲突 scheduler/config.py:8–33。GPU 之间的张量走 NCCL；各 scheduler rank 之间还共享一个 gloo CPU group，用于 barrier 和小规模广播 engine.py:112–137。

    Simplified: the steps are drawn one after another. With overlap scheduling (the default) rank 0 sends a token's DetokenizeMsg after it has already launched the next GPU step, so replies trail the GPU by one step (§5, chapter 01).

    简化之处：各步骤依次绘制。开启 overlap scheduling（默认）时，rank 0 在已经启动下一次 GPU 计算之后才发送某个 token 的 DetokenizeMsg，因此回复比 GPU 慢一步（见 §5 与第 01 章）。

    Two details from the hop list matter later. Rank 0 is the only scheduler that talks to the tokenizer side. It forwards whatever it received to the other ranks, and all ranks then run identical schedulers, so they build identical batches without further coordination io.py:27–65. The message count travels over gloo because a SUB socket can't tell a receiver when a batch of messages is complete io.py:100–122.

    跳转列表里有两个细节后面会用到。rank 0 是唯一与 tokenizer 一侧通信的 scheduler，它把收到的内容原样转发给其他 rank；所有 rank 运行完全相同的调度器，因此无需额外协调就能构造出相同的 batch io.py:27–65。消息计数之所以走 gloo，是因为 SUB socket 无法告诉接收方一批消息何时收齐 io.py:100–122。

    Aborts follow the same path in the other direction of intent. When an HTTP client disconnects mid-stream, the API server sends AbortMsg(uid); the tokenizer turns it into AbortBackendMsg, and every scheduler removes the request from its prefill or decode set and frees its resources api_server.py:190–209 scheduler.py:190–195.

    取消请求沿同一条路径传递。HTTP 客户端在流式输出中途断开时，API server 发送 AbortMsg(uid)；tokenizer 把它转换为 AbortBackendMsg，每个 scheduler 把该请求从 prefill 或 decode 集合中移除并释放资源 api_server.py:190–209 scheduler.py:190–195。

    §4On the wire线上格式

    All messages are plain dataclasses. serialize_type turns one into a dict whose first key is __type__, the class name, followed by its fields in declaration order; nested dataclasses become nested dicts. A tensor becomes {__type__: "Tensor", buffer, dtype}, and only 1D tensors are allowed message/utils.py:9–35. The ZMQ wrappers pack that dict with msgpack.packb(..., use_bin_type=True) mp.py:12–31. On the way in, deserialize_type looks the name up in the receiving module's globals() and calls the class with the fields as keyword arguments message/utils.py:52–69.

    所有消息都是普通的 dataclass。serialize_type 把它转换成一个 dict：第一个键是 __type__（类名），后面按声明顺序排列各字段；嵌套的 dataclass 变成嵌套的 dict。张量变成 {__type__: "Tensor", buffer, dtype}，且只允许一维张量 message/utils.py:9–35。ZMQ 封装再用 msgpack.packb(..., use_bin_type=True) 打包这个 dict mp.py:12–31。接收时，deserialize_type 在接收模块的 globals() 中按名字查找类，再把各字段作为关键字参数传入构造 message/utils.py:52–69。

    Messages come in three families, one per receiver, each with a Batch…Msg wrapper for sending several at once: tokenizer messages (TokenizeMsg, DetokenizeMsg, AbortMsg), backend messages (UserMsg, AbortBackendMsg, ExitMsg) and frontend messages (UserReply) tokenizer.py:11–43 backend.py:12–41 frontend.py:9–29. The inspector below runs the same two steps in your browser and shows every byte.

    消息分三族，按接收方划分，每族都有一个 Batch…Msg 包装用于一次发送多条：tokenizer 消息（TokenizeMsg、DetokenizeMsg、AbortMsg）、backend 消息（UserMsg、AbortBackendMsg、ExitMsg）和 frontend 消息（UserReply）tokenizer.py:11–43 backend.py:12–41 frontend.py:9–29。下面的检查器在浏览器中执行同样的两步，并展示每一个字节。

    What the byte count says字节数说明了什么
    
        
    For short messages, field names and type tags make up most of the bytes, because every message repeats its class name and field names. That cost is small next to a GPU step, and it buys a format any process can decode without a schema file. This is my reading of the trade-off; the repo doesn't discuss it.
    
        
    对于短消息，字段名和类型标签占了大部分字节，因为每条消息都重复携带类名和字段名。与一次 GPU 计算相比这点开销很小，换来的是任何进程无需 schema 文件即可解码的格式。这是我对这一取舍的理解，仓库中并未讨论。

    §6Offline: the LLM class离线：LLM 类
    
      
    LLM is a subclass of Scheduler built with offline_mode=True and a TP size of 1. Offline mode skips all the ZMQ setup and routes receive_msg and send_result to two methods LLM overrides io.py:30–33. offline_receive_msg tokenizes pending prompts in the scheduler's own process and hands out only as many as fit in the prefill budget per call. offline_send_result appends tokens to a per-request list. generate() loads the prompts and runs the normal scheduler loop until offline_receive_msg raises RequestAllFinished on an empty queue llm.py:28–98.
    
      
    LLM 是 Scheduler 的子类，用 offline_mode=True 和 TP 大小 1 构造。离线模式跳过全部 ZMQ 初始化，把 receive_msg 和 send_result 指向 LLM 覆写的两个方法 io.py:30–33。offline_receive_msg 在 scheduler 自己的进程里对待处理 prompt 分词，每次调用只放出 prefill 预算容得下的数量；offline_send_result 把 token 追加到各请求的列表中。generate() 装入 prompt 后运行普通的调度循环，直到 offline_receive_msg 在队列为空时抛出 RequestAllFinished llm.py:28–98。
    
      
      
    The scheduler only asks for a blocking receive when it has nothing else to run, so the exception fires exactly when every prompt has been handed out and every running request has finished scheduler.py:83–96.
    
      
    scheduler 只有在无事可做时才发起阻塞接收，因此这个异常恰好在所有 prompt 都已放出、所有运行中的请求都已结束时抛出 scheduler.py:83–96。
