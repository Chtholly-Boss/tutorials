Scheduler调度器

How one scheduler process per GPU turns a stream of requests into prefill and decode batches: an admission check that reserves every request's full output, chunked prefill under a token budget, overlap scheduling that sees each step's tokens one step late, and the ordering rule that keeps TP ranks in lockstep.

每张 GPU 上的一个调度进程如何把请求流变成 prefill 与 decode 批：为每个请求预留全部输出的准入检查、受 token 预算约束的分块 prefill、晚一步才看到结果的重叠调度，以及让各 TP rank 保持同步的排序规则。

§1The loop主循环

Every tensor-parallel rank runs its own Scheduler in its own process. It owns the Engine and four managers. TableManager hands out rows of the per-request token and page tables. CacheManager hands out KV pages and prefix matches. PrefillManager holds requests waiting to be prefilled, and DecodeManager holds requests that are generating scheduler.py:45–76.

每个张量并行 rank 都在自己的进程里运行一个 Scheduler。它持有 Engine 和四个管理器：TableManager 分配每个请求在 token 表与 page 表中的行，CacheManager 分配 KV page 并做前缀匹配，PrefillManager 保存等待 prefill 的请求，DecodeManager 保存正在生成的请求 scheduler.py:45–76。

run_forever picks one of two loops. The default is overlap_loop, shown below. Setting MINISGL_DISABLE_OVERLAP_SCHEDULING=1 switches to normal_loop, which does the same work but processes each batch's results right after launching it scheduler.py:108–131 env.py:69.

run_forever 在两个循环中选一个。默认是下面的 overlap_loop；设置 MINISGL_DISABLE_OVERLAP_SCHEDULING=1 则改用 normal_loop，它做同样的工作，但每启动一个 batch 就立刻处理它的结果 scheduler.py:108–131 env.py:69。

  1. Receive. The call blocks only when there is nothing else to do: no batch in flight and nothing runnable.
  2. Apply messages. New requests join the prefill queue; aborts free resources.
  3. Schedule. Pick the next batch and build its metadata on the scheduler's own CUDA stream.
  4. Launch. The engine stream waits for the scheduler stream, then runs the forward pass.
  5. Process the previous batch. Wait for its sampled tokens, append them, and finish or cache requests.
  1. 接收。只有在无事可做时（没有在途 batch，也没有可运行的请求）才阻塞。
  2. 处理消息。新请求加入 prefill 队列；abort 释放资源。
  3. 调度。挑选下一个 batch，并在调度器自己的 CUDA stream 上构建其元数据。
  4. 启动。engine stream 先等待调度器 stream，再执行前向计算。
  5. 处理上一个 batch。等待其采样得到的 token，追加到请求上，然后结束或缓存请求。

§2A request's life请求的一生

A UserMsg carries token ids and sampling parameters. The scheduler drops it if the prompt already fills max_seq_len, and clamps max_tokens so that prompt plus output fits scheduler.py:175–189. The request then becomes a PendingReq at the tail of pending_list prefill.py:123–124.

UserMsg 携带 token id 与采样参数。如果 prompt 已经占满 max_seq_len，调度器直接丢弃它；否则把 max_tokens 截断到 prompt 加输出能放下的长度 scheduler.py:175–189。随后请求变成 PendingReq，排到 pending_list 末尾 prefill.py:123–124。

Finishing is decided on the CPU once the tokens come back. A request ends when it has produced max_tokens tokens (can_decode turns false) or sampled EOS, unless ignore_eos is set scheduler.py:150–156 core.py:44–61. Freeing returns the table row and hands the request's pages to the cache manager with finished=True scheduler.py:200–202. An abort removes the request from whichever queue holds it scheduler.py:190–195.

是否结束在 token 回到 CPU 之后才判断：请求生成满 max_tokens 个 token（can_decode 变为 false），或采样到 EOS（除非设置了 ignore_eos）时结束 scheduler.py:150–156 core.py:44–61。释放时归还 table 行，并以 finished=True 把请求的 page 交给 cache manager scheduler.py:200–202。abort 会把请求从它所在的队列中移除 scheduler.py:190–195。

§3Choosing the next batch选择下一个 batch

Each step runs exactly one batch, and prefill always gets the first chance. A decode batch runs only when PrefillManager returns nothing; the code marks other policies as a TODO scheduler.py:219–225.

每一步只执行一个 batch，而且 prefill 总是优先。只有 PrefillManager 什么也没返回时才执行 decode 批；其他策略在代码中标为 TODO scheduler.py:219–225。

Admission准入

PrefillManager walks pending_list in order and stops at the first request it cannot add, so a large request at the head blocks everything behind it prefill.py:126–151. A new request needs a free table row and enough KV space for its whole future: the uncached prompt tokens plus max_tokens, on top of everything already reserved prefill.py:39–63. The reservation starts from the running requests' remaining outputs, plus page_size − 1 tokens each for a partly filled last page decode.py:27–30. Pages are allocated later, in _prepare_batch, and only for the tokens the batch will write cache.py:42–53.

PrefillManager 按顺序遍历 pending_list，遇到第一个加不进去的请求就停止，因此排在队首的大请求会挡住它后面的所有请求 prefill.py:126–151。新请求需要一个空闲的 table 行，以及足以容纳其全部未来的 KV 空间：未命中缓存的 prompt token 加上 max_tokens，再叠加所有已预留的量 prefill.py:39–63。预留量的起点是运行中请求的剩余输出，每个再加 page_size − 1 个 token 用于未填满的最后一页 decode.py:27–30。page 本身要等到 _prepare_batch 才分配，而且只为本 batch 要写入的 token 分配 cache.py:42–53。

The lock-then-recheck in _try_allocate_one matters with the radix cache. Locking a matched prefix makes it unevictable, which shrinks available_size, so the check runs again after the lock prefill.py:50–54 cache.py:32–34. Chapter 02 covers the cache side.

_try_allocate_one 中“先加锁再复查”的做法对 radix cache 很重要：锁住匹配到的前缀会让它不可驱逐，从而减小 available_size，所以加锁后要再检查一次 prefill.py:50–54 cache.py:32–34。缓存这一侧放在第 02 章讲。

Reading of the code读代码得出的结论

I found no preemption or retraction path in the scheduler. Admission reserves the full max_tokens up front, so once a request is running it should never run out of pages. This follows from the reservation arithmetic and a search of the package for retraction code; the source doesn't state it as a design rule.

我在调度器中没有找到抢占或撤回（retraction）路径。准入时就预留了完整的 max_tokens，因此请求一旦运行，就不应再缺 page。这是根据预留量的算术以及在整个包中搜索撤回代码得出的，源码并没有把它写成设计规则。

Decode

A decode batch is every running request, one token each, sorted by uid decode.py:32–35. A request enters running_reqs right after the batch holding its last prefill chunk is launched: filter_reqs adds the batch's requests and keeps only those that can still decode decode.py:14–15 scheduler.py:232.

decode 批包含所有运行中的请求，每个一个 token，按 uid 排序 decode.py:32–35。包含请求最后一个 prefill chunk 的 batch 一启动，请求就进入 running_reqs：filter_reqs 把 batch 中的请求并入，只保留仍能 decode 的 decode.py:14–15 scheduler.py:232。

    The model follows PrefillAdder and DecodeManager with page_size = 1 and no prefix-cache hits. Results are applied in the same step (the normal_loop order), prompt and output lengths are in tokens, and KV "used" counts every token already written to the cache.

    模型遵循 PrefillAdder 与 DecodeManager 的逻辑，page_size = 1，没有前缀缓存命中。结果在同一步内生效（即 normal_loop 的顺序），prompt 与输出长度以 token 计，KV“已用”统计所有已写入缓存的 token。

    Try the three scenarios. Long prompt splits R0 across three steps, during which nobody decodes. KV reservation admits R0 and R1, then holds R2 until R1 finishes because the reservation for their remaining output leaves too little room, and R3 waits behind R2 even though it would fit.     试试三个场景。Long prompt 把 R0 拆成三步执行，这期间没有任何请求 decode。KV reservation 先接纳 R0 和 R1，然后一直扣住 R2，直到 R1 结束，因为为它们剩余输出预留的空间让余量不足；R3 虽然放得下，也只能排在 R2 后面等待。Table slots 用 max_running_req 限制运行中的请求数。

    §4Chunked prefill分块 prefill

    The token budget is max_extend_tokens: 8,192 by default, set with --max-prefill-length config.py:16 args.py:164–171. Each admitted request takes min(budget, remaining prompt) tokens. If that is less than what remains, the request is built as a ChunkedReq prefill.py:65–90:

    token 预算就是 max_extend_tokens：默认 8,192，可用 --max-prefill-length 设置 config.py:16 args.py:164–171。每个被接纳的请求取 min(预算, 剩余 prompt) 个 token；如果少于剩余量，就构造成 ChunkedReq prefill.py:65–90：

    • A chunk spends the whole remaining budget, so the loop stops there. At most one request per batch is chunked, and it is always the last one.
    • The chunked request moves to the front of pending_list, ahead of everything the loop didn't reach prefill.py:150. Its next chunk runs in the next prefill step and reuses its table row and cache handle, without a second admission check prefill.py:96–102.
    • A ChunkedReq reports can_decode = False. It never enters running_reqs, its sampled token is ignored, and its token write goes to column −1 prefill.py:23–29 scheduler.py:147–149 scheduler.py:262–267.
    • 一个 chunk 会用掉剩余的全部预算，所以循环就此停止。每个 batch 至多有一个请求被分块，而且它总是最后一个。
    • 被分块的请求移到 pending_list 最前面，排在循环没来得及处理的所有请求之前 prefill.py:150。它的下一个 chunk 在下一个 prefill 步执行，沿用原来的 table 行与 cache handle，不再做准入检查 prefill.py:96–102。
    • ChunkedReq 的 can_decode 为 false：它不会进入 running_reqs，采样出的 token 被忽略，token 写入的位置是第 −1 列 prefill.py:23–29 scheduler.py:147–149 scheduler.py:262–267。

    With the default budget, a 20,000-token prompt runs as chunks of 8,192, 8,192 and 3,616 tokens. The third step still has 4,576 tokens of budget, which go to the requests behind it. Because prefill has priority, running requests produce no tokens during those three steps. The simulator's Long prompt scenario shows the same pause at a smaller scale.

    按默认预算，一个 20,000 token 的 prompt 会分成 8,192、8,192 和 3,616 三个 chunk 执行。第三步还剩 4,576 个 token 的预算，留给排在后面的请求。由于 prefill 优先，这三步中运行中的请求不会产生任何 token。模拟器的 Long prompt 场景在小规模上展示了同样的停顿。

    §5Overlap scheduling重叠调度

    The scheduler uses two CUDA streams. Its own stream carries metadata work: page allocation, positions, index tensors and attention metadata, all copied with non_blocking=True. The engine's stream runs the forward pass and first waits on the scheduler stream scheduler.py:51–55 scheduler.py:204–217.

    调度器使用两个 CUDA stream。它自己的 stream 承担元数据工作：分配 page、生成 position、索引张量和 attention 元数据，全部用 non_blocking=True 拷贝。engine 的 stream 运行前向计算，开始前先等待调度器 stream scheduler.py:51–55 scheduler.py:204–217。

    Step N+1 can start before step N's tokens reach the CPU because the next input never comes from the CPU. _forward writes each sampled token into token_pool on the GPU at the request's next position, and the next batch gathers its input_ids from token_pool:

    第 N+1 步之所以能在第 N 步的 token 回到 CPU 之前开始，是因为下一步的输入从不经过 CPU。_forward 把每个采样出的 token 写进 GPU 上 token_pool 中该请求的下一个位置，下一个 batch 再从 token_pool 取出它的 input_ids：

    The engine advances every request's lengths with complete_one() when it launches the batch, so the CPU's bookkeeping runs one step ahead of what it has actually seen engine.py:199–200. The sampled tokens come back through a non-blocking copy and an event engine.py:202–206. _process_last_data waits on that event only when it processes the batch, one iteration later scheduler.py:138–143.

    engine 在启动 batch 时就用 complete_one() 推进每个请求的长度，所以 CPU 的记账比它实际看到的结果超前一步 engine.py:199–200。采样出的 token 通过一次非阻塞拷贝和一个 event 传回 engine.py:202–206，_process_last_data 要到下一轮迭代处理该 batch 时才等待这个 event scheduler.py:138–143。

    Timeline时间线Six steps, two lanes六步，两条泳道

    S: receive + schedule + prepareS：接收、调度、准备 P: process resultsP：处理结果 CPU waiting / GPU idleCPU 等待 / GPU 空闲 F: forward passF：前向计算

    The costs are illustrative, not measured. The ordering is the code's: in overlap_loop, S(k) and the launch of F(k) come before P(k−1). In normal_loop, P(k) waits for F(k) before S(k+1) starts.

    各项耗时仅作示意，并非实测。顺序与代码一致：overlap_loop 中，S(k) 和 F(k) 的启动发生在 P(k−1) 之前；normal_loop 中，P(k) 要等 F(k) 完成后，S(k+1) 才开始。

    One step late晚一步

    Seeing results one step late has a cost. A request that samples EOS in step N was already scheduled into step N+1, so it computes one extra row. When step N's results are processed, the request is freed and recorded in finished_reqs. When step N+1's results arrive, a guard skips the second free scheduler.py:158–166. The extra token is still sent back, and the API server drops it because it has stopped waiting on that uid api_server.py:116–123.

    晚一步看到结果是有代价的。在第 N 步采样到 EOS 的请求，此前已经被排进了第 N+1 步，因此会多算一行。处理第 N 步结果时，该请求被释放并记入 finished_reqs；第 N+1 步的结果到达时，一个判断会跳过第二次释放 scheduler.py:158–166。多出的 token 仍会被发回，API server 已不再等待该 uid，于是将其丢弃 api_server.py:116–123。

    ForwardInput keeps each batch's index tensors alive until its results are processed; the comment above it says this avoids illegal memory accesses under overlap scheduler.py:34–39. Pages freed while processing results are collected in lazy_free_region and returned to the free list with one concatenation at the end cache.py:93–104.

    ForwardInput 会让每个 batch 的索引张量一直存活到其结果被处理为止；它上方的注释说明，这样做是为了在重叠调度下避免非法内存访问 scheduler.py:34–39。处理结果期间释放的 page 先收集在 lazy_free_region 中，最后一次性拼接回空闲列表 cache.py:93–104。

    §6Keeping TP ranks in lockstep让 TP rank 保持同步

    Only rank 0 talks to the tokenizer. Each iteration it drains its ZMQ pull queue, broadcasts the message count over the CPU process group, and republishes the raw bytes on a ZMQ PUB socket. The other ranks read the count, then exactly that many messages from their SUB socket io.py:88–122. Every rank applies the same messages in the same order and runs the same scheduling code on the same state. Only rank 0 sends results back io.py:124–133.

    只有 rank 0 与 tokenizer 通信。每轮迭代它先取空自己的 ZMQ pull 队列，通过 CPU 进程组广播消息条数，再把原始字节重新发布到 ZMQ PUB socket 上。其他 rank 读取条数，然后从各自的 SUB socket 上恰好读取这么多条消息 io.py:88–122。于是每个 rank 按相同顺序处理相同的消息，在相同的状态上运行相同的调度代码。只有 rank 0 把结果发回 io.py:124–133。

    Identical state wasn't quite enough. Req is a dataclass with eq=False, so it hashes by object identity core.py:28, and running_reqs is a set of them. Before the pinned commit, the decode batch was list(self.running_reqs), whose order depends on where each process happened to allocate the objects. Commit 9a91cfa sorts by uid:

    但仅有相同的状态还不够。Req 是 eq=False 的 dataclass，因此按对象身份计算哈希 core.py:28，而 running_reqs 是由它们组成的 set。在固定提交之前，decode 批是 list(self.running_reqs)，其顺序取决于各进程恰好把对象分配在哪里。提交 9a91cfa 改为按 uid 排序：

    TPSame requests, different rows相同的请求，不同的行
    Why the order matters为什么顺序重要

    This is my reading; the commit states only the fix. In tensor parallelism, the all-reduce after a row-parallel layer adds each rank's partial result row by row, so row i has to be the same request on every rank. With mismatched order, row i sums pieces of two different requests.

    以下是我的理解，提交本身只说明了修复内容。张量并行中，行并行层之后的 all-reduce 按行把各 rank 的部分结果相加，因此第 i 行在每个 rank 上都必须是同一个请求。顺序不一致时，第 i 行会把两个不同请求的部分结果加在一起。
